# Этап 293. Однодневный диапазон возвращает пусто, а любой — теряет последний день

## Обращение

Отчёт #61 от 03.09.2026, аккаунт 35:

> При запросе списка счетов за конкретный день через `date_from` и `date_to`
> с одной и той же датой API возвращает `totalCount=0`, хотя агрегат
> `get_average_invoice` по `create_date` на этот же день показывает
> существующие счета.

Агент сделал ровно то, что написано в описании инструмента: «Filter invoices
created on or after this date» / «on or before this date». Отчёт не про
непонимание контракта.

## Что происходит на самом деле

`invoice.create_date` — `timestamp` (схема Ветменеджера, `client`/`invoice`
в дампе `vetmanager-extjs`). Фильтр строится как

```python
combined_filters.append(_filter_gte("create_date", resolved_date_from))
combined_filters.append(_filter_lte("create_date", resolved_date_to))
```

то есть `create_date <= '2026-09-02'`. Сравнение идёт с полуночью, и совпадёт
только счёт, созданный ровно в `00:00:00`.

Следствий два, и второе хуже первого:

1. однодневный диапазон возвращает пусто — видно сразу;
2. **любой** диапазон молча теряет свой последний день — не видно ничем, кроме
   сверки с другим источником.

Проверено на живом стенде 04.09.2026:

| запрос | `totalCount` |
|---|---|
| `date_from=2026-09-02, date_to=2026-09-02` | 0 |
| `date_from=2026-09-02, date_to=2026-09-03` | 27 |

Первая строка второго ответа — счёт с `create_date = 2026-09-02 11:17:42`,
которого «не существовало» в предыдущем запросе.

## Почему это дожило до сентября

Ровно этот дефект уже чинили: известная проблема #21 — «get_payments date
filters now use whole-day timestamp range», статус `fixed`. Починили **один
инструмент из двух**.

И оба раза рядом стоит зелёный тест, прибивающий неверное поведение:

- `tests/test_ergonomic_filters.py` — тест на `get_invoices` требует
  `by_op["<="] == today.isoformat()` (голая дата) и стоит **непосредственно
  над** тестом на `get_payments`, который требует
  `by_op["<"] == f"{tomorrow} 00:00:00"` (граница суток);
- `tests/test_stage172_debtors_filters.py:123` — то же для `get_debtors`:
  `("last_visit_date", "<=", "2026-06-17")`.

Зелёный тест сделал дефект похожим на решение. Поэтому оба теста в этом этапе
**переписываются**, а не дополняются, и показываются красными до правки кода.

## Где ещё тот же класс

Обход всех сравнений даты с timestamp-колонкой:

| место | поле | тип поля | состояние |
|---|---|---|---|
| `tools/invoice.py` `get_invoices` | `create_date` | timestamp | **дефект** |
| `tools/client.py` `get_debtors` | `last_visit_date` | timestamp | **дефект** |
| `tools/_inactive_helpers.py` | `last_visit_date` | timestamp | **дефект**, граница `cutoff_newest` теряет день |
| `tools/invoice.py` `invoice_date_*`, агрегаты | `invoice_date` | timestamp | верно (`_day_start` / `_next_day_start`) |
| `tools/finance.py` `get_payments` | `create_date` | timestamp | верно (этап 21) |
| `tools/medical_card.py` | `date_create` | timestamp | верно |
| `tools/admission.py`, `tools/schedule.py` | `admission_date` | timestamp | верно (явные `00:00:00`) |

## Цель

Диапазон дат в списковых инструментах означает сутки целиком: нижняя граница —
начало первого дня, верхняя — начало следующего дня после последнего,
строгим сравнением. Однодневный диапазон возвращает данные этого дня.

## Scope

1. `get_invoices`: `date_from`/`date_to` переводятся на `>= _day_start(from)` и
   `< _next_day_start(to)`. Помощники уже есть в том же файле и используются
   для `invoice_date`.
2. `get_debtors`: то же для `last_visit_date_from`/`last_visit_date_to`.
3. `_inactive_helpers`: верхняя граница окна становится `< начало следующего
   дня после cutoff_newest`.
4. Переписать два теста, прибивающих неверное поведение.
5. Описания параметров привести в соответствие: «on or before this date»
   остаётся верным по смыслу для пользователя, но перестаёт быть неверным
   по факту.

### Вне scope

- Общий реестр «какие поля Ветменеджера — timestamp» и сторож на будущее
  (пункт 293.3): отдельная работа, её цена выше, чем у самой починки, и
  делать её внутри исправления живого дефекта — смешивать два риска.
- `get_payments`, `medical_card`, `admission`, `schedule` — уже верны,
  трогать нечего.
- Семантика `invoice_date` против `create_date` не меняется: это разные поля
  с разным смыслом, и запрет их смешивать остаётся.

## Декомпозиция

- **293.1** `get_invoices` + переписанный тест. ≤ 40 LOC.
- **293.2** `get_debtors` и `_inactive_helpers` + переписанный тест. ≤ 60 LOC.
- **293.3** Сторож на будущее. Отдельно, в этом этапе не делается.

## Acceptance

1. `get_invoices(date_from=X, date_to=X)` отдаёт счета, созданные в течение дня
   X, а не пусто.
2. Многодневный диапазон включает последний день целиком.
3. Фильтр уходит на Ветменеджер как `>= 'X 00:00:00'` и `< 'X+1 00:00:00'` —
   проверяется по фактическому запросу, а не по внутреннему состоянию.
4. То же для `get_debtors` и окна неактивных клиентов.
5. Тесты, прибивавшие голую дату, переписаны и показаны красными до правки.
6. Полный набор зелёный.
7. Проверка на живом стенде: однодневный запрос за 02.09.2026 возвращает
   ненулевой `totalCount`.
