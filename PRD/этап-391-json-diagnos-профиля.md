# Этап 391. Разбор JSON диагнозов в профиле питомца

## Цель и проверенные факты

Фидбек #136 → KI 81: `get_pet_profile` превращает строку JSON из `medical_cards.diagnos` в один неразрешённый ID, оставляя агрегат `diagnoses` пустым. Наблюдаемый контракт поля — JSON-массив объектов `{ "id": число, "type": число }`; `diagnos_text` содержит названия через `;\n`, `diagnos_type_text` — названия с типом в скобках. OpenAPI описывает `diagnos`, `diagnos_text`, `diagnos_type_text` как строки, а справочник диагнозов `/rest/api/MedicalCards/AllDiagnoses` — как объекты `id/title`. Текущий профиль хранит названия в `diagnosis_titles` карты и `diagnoses` верхнего уровня, неизвестные ID — в `unresolved_diagnosis_ids`.

## Архитектурное решение

Проблема — ошибочная трактовка сериализованного массива как скалярного ID. Разбор выполняется в `resources/pet_profile.py` у владельца агрегации, без изменения upstream запросов и прав. Рассмотрены: (1) регулярное выражение для извлечения цифр — не различает `id` и `type` и ломается на повреждённых значениях; (2) JSON-декодирование с проверкой структуры — выбрано; (3) полагаться только на текстовые поля — теряет ID и тип, не решает исходный дефект. Для прежних скалярных значений сохраняется прежний путь.

Карта с разобранными ссылками получает `diagnosis_references`: список `{id: строка, type: число}` для элементов с положительным целым `id` и целым `type` (включая 0, исключая bool) в исходном порядке, с устранением повторов пары `(id, type)`. Невалидный элемент пропускается. Если непустой массив целиком состоит из невалидных для нового формата элементов (включая наблюдавшиеся в этапе 225 `[32]` и `[{"id":32}]`), исходное значение остаётся unresolved, как до изменения; у карты без разобранных ссылок новое поле не появляется. Тип остаётся кодом upstream без выдуманного словаря. Только для корректной JSON-ветки: если есть хотя бы одна валидная ссылка, `diagnos_text` и `diagnos_type_text` разбиваются по `;\n`. Текст считается отображаемым списком диагнозов только когда оба непусты, имеют одинаковое число частей и каждая часть второго поля имеет вид `<соответствующее название> (<тип>)`. Если справочник разрешил часть JSON-ссылок, все эти известные названия дополнительно должны присутствовать в тексте; при противоречии текст отвергается как потенциально устаревший. Тогда `diagnosis_titles` берётся из текстового списка с дедупликацией, без предположений о соответствии отдельного названия ID. В противном случае названия разрешаются только через справочник: `diagnos_text` может независимо обновляться как свободная заметка (наблюдаемый контракт этапа 225). Независимый legacy-массив `diagnoses[]` добавляет свои справочные названия после текстового списка. Если подтверждённого текстового списка нет, названия разрешаются через справочник. Так частичный справочник не создаёт смесь разных версий названий и свободная заметка не превращается в диагноз. `diagnos_type_text` остаётся на карте в исходном виде: в нём уже есть человекочитаемая форма типов. `unresolved_diagnosis_ids` содержит отдельные строковые ID, отсутствующие в справочнике, даже когда текст карты доступен: поле означает пробел справочника, а не отсутствие читаемого названия. Агрегат `diagnoses` собирается из названий карт без повторов. Некорректный JSON сохраняет прежнюю непрозрачную строку как unresolved, чтобы не потерять сигнал о проблеме данных; пустой массив не создаёт unresolved.

Инварианты: прежний scalar `diagnos` и поле `diagnoses`-массив карт работают как раньше; значения `0`/пусто не создают диагноз; порядок и дедупликация стабильны; производные поля `diagnosis_titles`, `diagnoses` и `unresolved_diagnosis_ids` проходят действующую очистку свободного текста для деперсонализованных токенов; личные данные не попадают в новые логи. Откат — согласованный возврат resource, описания инструмента, правила деперсонализации и тестов одним изменением; нельзя оставлять описание нового поля после удаления поля. Опубликованные поля карты остаются добавочными. `Architecture Critique` требуется: меняется публичный MCP-ответ и поведение в production.

## Декомпозиция и приёмка

- 391.1 (≤2 ч, ≤150 строк): PRD и архитектурное/PRD ревью; красный интеграционный сторож на JSON-массив с известным и неизвестным ID, типами и текстовыми полями. Показать падение до изменения resource.
- 391.2 (≤2 ч, ≤150 строк): разбор и агрегация, фокусные тесты, живой вызов `get_pet_profile` на выбранном до проверки контуре; итоговый код и тело без ПД.
- 391.3 (≤2 ч): Spark и пара Astra/Sol для committed diff, аудит, один полный mock и real suite при наличии ключей, выпуск и зелёные Tests/Deploy Prod.

Приёмка: Корректная JSON-строка не появляется целиком в unresolved; повреждённая строка сохраняется в unresolved карты и профиля при успешном ответе; отдельные ID и type видны в ответе; названия доступны из справочника и из `diagnos_text` при согласованном `diagnos_type_text` и пробеле справочника; независимый текст не подменяет справочный диагноз; старые тесты проходят; тесты покрывают пустой и повреждённый JSON, старые массивы `[32]`/`[{"id":32}]`, невалидные элементы и повторы, отсутствие нового поля у карт без ссылок, scalar-совместимость и деперсонализацию производных полей. Данные из чужого кода не переносятся — только внешний контракт.
