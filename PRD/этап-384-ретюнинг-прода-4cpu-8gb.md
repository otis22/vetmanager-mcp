# Этап 384. Ретюнинг production под 4 CPU / 8 ГБ

## Цель и границы

После апгрейда 13.10.2026 использовать доступную память без OOM и оставить
запас для трёх MCP-воркеров этапа 385. 384.1 — только этот PRD; 384.2 —
конфигурация, сторожа и devtr6; 384.3 — аудит, выпуск и наблюдение production.
Три воркера, перенос process-local метрик и изменение схемы деплоя принадлежат
этапу 385 и здесь не реализуются.

## Проверенные факты и открытые измерения

По проверке владельца после ребута ~08:18 UTC: 4 CPU / 7,8 ГБ, все контейнеры
healthy, `/healthz` 200, 227 вызовов за 3 часа без ошибок; суммарно занято
~2 CPU и ~1,7 ГБ. Это снимок, а не гарантия пикового потребления. БД ~120 МБ.
`docker-compose.yml:13-26` задаёт PostgreSQL 1 CPU/512M,
`shared_buffers=128MB`, `effective_cache_size=256MB`, `max_connections=50`,
`work_mem=4MB`, `maintenance_work_mem=64MB`, `wal_buffers=4MB`,
`checkpoint_completion_target=0.9`. MCP (`:154-158`) — 1 CPU/512M;
Prometheus (`:168-194`) — 0.5 CPU/384M, лимит продублирован в `cpus`/`mem_limit`;
Grafana (`:196-222`) — 0.5 CPU/256M, также два способа задания лимита,
по снимку занято ~74% лимита. Redis (`:39`) не имеет ограничения.

`Dockerfile:25-36` ставит FastMCP через pip, Uvicorn прямо не фиксирует;
поэтому `uv.lock` с 0.52.3 не определяет production image. Доступный локально
Uvicorn — 0.42.0 без `uvloop` и `httptools`; точную версию и extras **в новом
production image** 384.2 проверяет после сборки. `server.py:205-225` создаёт
`uvicorn.Config` с `ws="websockets-sansio"` и вызывает `asyncio.run(server.serve())`.
У `Server.run()` в 0.42.0 используется `config.get_loop_factory()`, а нынешний
ручной `asyncio.run(...serve())` её обходит: одной установки extras недостаточно.
`_DrainingUvicornServer` переопределяет `handle_exit` и `shutdown`, поэтому
проверка SIGTERM обязательна. 385 решает сам запуск нескольких процессов.

Нет приложенного production RSS одного MCP-процесса, `docker stats` по пикам,
`prometheus_tsdb_head_series` или RSS Prometheus. «60+ метрик» — число имён,
не число временных рядов; по нему heap вычислить нельзя. До выпуска 384.3
снять безопасный read-only снимок `docker stats --no-stream` и **только поля**
`docker inspect`: `HostConfig.Memory`, `HostConfig.NanoCpus`, `State.OOMKilled`,
`State.StartedAt`, `Image` по пяти контейнерам. Полный `docker inspect`
с `Config.Env` не сохранять: он содержит секреты. Также снять
`process_resident_memory_bytes`,
`prometheus_tsdb_head_series` и `prometheus_tsdb_head_chunks` на production,
затем повторить через 1 и 24 часа. Не записывать URL с токеном или тело метрик
целиком. Если данные не доступны, это открытый параметр; безопасный дефолт
ниже сохраняется, а отсутствие измерения явно сообщается владельцу.

Опорные требования: главный PRD, разделы 4.3.8–4.3.10 и 5;
`artifacts/technical-requirements-vetmanager-mcp-ru.md`, разделы 2–3 и
pre-deploy backup. Настройки PostgreSQL сверены с
[документацией PostgreSQL 16](https://www.postgresql.org/docs/16/runtime-config-resource.html):
`work_mem` расходуется на каждую операцию и сессию, `effective_cache_size`
лишь оценка для планировщика. Режимы `loop/http/ws` сверены с
[документацией Uvicorn](https://www.uvicorn.org/settings/).

## Архитектурное решение

**Проблема и ограничения.** 256M для Grafana почти заполнены; будущие три
MCP-процесса не поместятся в 512M. При этом сервис сейчас однопроцессный,
DB мала, production heap и пиковый RSS неизвестны. Лимиты не являются
резервацией памяти; сумма новых потолков должна оставлять место ОС, Docker,
page cache, reverse proxy и всплескам.

**Варианты.** (1) Не менять лимиты до этапа 385: сохраняет ближайший риск OOM
Grafana и вынуждает повторный рестарт. (2) Выдать всю свободную память
контейнерам и `work_mem=16MB`: нет данных о пиках, при `max_connections=50`
несколько сортировок/хешей способны превысить бюджет. (3) Умеренно поднять
потолки с запасом на три MCP-воркера, измерить реальный RSS и оставить
многопроцессность этапу 385 — выбранный вариант.

**Точные значения для 384.2.** В `docker-compose.yml`:

| Сервис | CPU | Память | Правка |
|---|---:|---:|---|
| `mcp` | `3` | `2G` | `deploy.resources.limits` (сейчас строки 154–158) |
| `postgres` | `1` | `1G` | `deploy.resources.limits` (строки 13–17) |
| `prometheus` | `0.5` | `768M` | и `mem_limit`, и `deploy.resources.limits` (строки 168, 190–194) |
| `grafana` | `0.5` | `512M` | и `mem_limit`, и `deploy.resources.limits` (строки 196–197, 218–222) |
| `redis` | `0.5` | `512M` | добавить `deploy.resources.limits` после `command` (строка 39) |

Сумма потолков памяти — 4,75 ГБ из 7,8 ГБ, остаётся ~3,05 ГБ вне контейнерных
лимитов; сумма CPU-потолков 5,5 ядра, это независимые максимумы, не обещанная
одновременная производительность. MCP получит до 3 CPU для трёх воркеров 385;
до их запуска один процесс всё равно использует не более одного ядра.
Для MCP 2G — безопасный начальный бюджет
этапа 385: три процесса по условным 512 MiB дают 1536 MiB и ~512 MiB
на общий overhead/пики. Это **допущение**, не измеренный RSS. Перед включением
трёх воркеров 385.2 обязан сверить peak container memory и RSS каждого
процесса под нагрузкой: при >70% лимита на 3 воркерах или OOM план пересмотреть
до production, а не просто поднять CPU. Redis получает cap, поскольку его
текущее безлимитное потребление разрушает бюджет хоста; отключённые persistence
и малый текущий контур не заменяют проверки пика. Redis хранит transient
rate-limit state без persistence: OOM/restart обнулит его. До введения 512M
снять 24-часовой peak Redis/cgroup и `INFO memory`; если peak >358MiB
(70% от 512MiB), cap не применять и вернуть PRD на пересмотр. На devtr6
проверить, что при недоступном Redis production `RATE_LIMIT_REQUIRE_REDIS`
действительно даёт ожидаемый fail-closed отказ, а не незаметно сбрасывает
лимиты; на production отслеживать `OOMKilled` и degraded backend metric.

Для PostgreSQL в `command` (`docker-compose.yml:18-26`) установить
`shared_buffers=256MB`, `effective_cache_size=512MB`; `work_mem=4MB`
оставить до измерения конкурентных запросов. `max_connections=50`,
`maintenance_work_mem=64MB`, `wal_buffers=4MB`,
`checkpoint_completion_target=0.9` оставить без изменения. 256MB достаточно
для текущей БД ~120MB и оставляет память 1G cgroup для процессов/запросов;
предложенные 512MB буферов здесь чрезмерны без измеренного cache miss.
Поднимать `work_mem` до 8/16MB при лимите 1G нельзя без данных о количестве
одновременных sort/hash операций и пиковом RSS: даже одна hash-операция на
каждое из 50 соединений при стандартном multiplier 2 и 8MB требует до
800MB сверх общих буферов.
`effective_cache_size=512MB` — оценка 256MB shared buffers и примерно 256MB
file cache в пределах 1G cgroup, не выделение памяти; прежнее предложение
2GB завысило бы доступный контейнеру cache. При трёх воркерах
текущий `storage.py:93-94` допускает до 30 DB connections на воркер
(pool 10 + overflow 20), теоретически 90 > `max_connections=50`.
В 385.1/385.2 обязательно уменьшить pool/overflow до суммарно ≤40
со служебным резервом 10 (начальный ориентир по 10+3 на воркер); сам pool
этим этапом не меняется, потому что воркеры ещё не включаются.

**Uvicorn.** В `Dockerfile:25-36` добавить отдельное требование
`"uvicorn[standard]==0.42.0"` в production-зависимости; в `pyproject.toml`
добавить такое же требование для согласованности metadata, обновить `uv.lock`
если проектная проверка требует lock. Проверить разрешение зависимостей с
FastMCP при сборке; при конфликте не форсировать downgrade, зафиксировать
совместимую конкретную версию после проверки API `Server.run()`.
В `server.py:217-225` заменить внешний `asyncio.run(server.serve())` на
`server.run()` для применения loop factory; `ws="websockets-sansio"` оставить
явным: выбор WebSocket implementation независим от event loop и HTTP parser.
Проверить в образе фактические `uvicorn.__version__`, импорты `uvloop` и
`httptools`, а также тип работающего loop и HTTP protocol. Если extras или
`Server.run()` ломают drain, WebSocket или установленный FastMCP, восстановить
прежний `asyncio.run(server.serve())`, убрать extras, оставить
`loop="asyncio"`/`http="h11"` и повторить SIGTERM/GET SSE проверку;
аргументированно закрыть uvloop-подпункт отказом. Тихий fallback на asyncio
недопустим.

**Инварианты.** HTTP/MCP контракт, auth, данные и число воркеров не меняются.
`/healthz`, `/readyz`, `/metrics`, `ws="websockets-sansio"` и drain при SIGTERM
работают как раньше. Конфиг Compose должен применять реальные cgroup-потолки:
`docker compose config` недостаточно, проверить выбранные поля `docker inspect`
после up; `Config.Env` и полный вывод не сохранять.
Новые лимиты не логируют секреты и данные клиник. Architecture Critique
требуется из-за production performance/storage; объединён с сильным PRD-review:
prompt проверяет архитектуру, альтернативы, полноту, нагрузку и откат.

## Риски рестарта, выпуск и откат

Изменение `command` PostgreSQL, лимитов и образа вызывает recreate/restart
контейнеров при `docker compose --profile production up -d` на production.
Голое `docker compose up -d` не выбирает сервисы профиля `production`, а
`up -d` без `--build` не пересобирает MCP image. Существующий
`scripts/deploy_server.sh:195-266,360` делает сборку, backup и `up`, но Redis
в явный список выпуска не включает. Поэтому после штатного deploy применить
полный состав пяти сервисов, как в 384.3; сверить фактические image ID и
cgroup. Возможны временные
отказы MCP, обрыв текущих HTTP-сессий, восстановление WAL и деградация
латентности; доступность без паузы этим этапом не обещается. До санкционированного
владельцем выпуска: зелёный CI, pre-deploy backup БД по действующему скрипту,
проверенный restore path, свободное место, свежие RSS/series и окно с допустимой
паузой. **До того как deploy script перезапишет тег** сохранить старый image ID
`vetmanager-mcp` под отдельным локальным rollback tag и записать SHA старого
исходника/Compose. Подготовить проверенный rollback bundle **из отслеживаемых
git файлов прежнего SHA** (код и Compose без `.env`/секретов) для передачи на
production тем же механизмом rsync, что в `.github/workflows/deploy-prod.yml`;
проверить, что rollback image запускается и bundle соответствует прежнему SHA.
Без этих условий production deploy не начинать.

Для сравнения latency 384.2/384.3 запускает на devtr6 до/после одинаковую
нагрузку 10 конкурентных клиентов ×20 безопасных `tools/list` с тестовым
bearer, а на production с одного клиента по 100 последовательных безопасных
запросов каждого типа (`/readyz`, MCP initialize, `tools/list`) до/после в
сопоставимом 30-минутном окне. Для каждого типа и контура считать p95 по
времени клиента, фиксировать число успешных ответов и ошибки. Регрессия —
p95 после >1,5× p95 до **и** разница >100ms при всех успешных ответах
(200 на devtr6, 100 на production для каждого типа). Если ответов меньше,
латентность неопределённа: дополнить выборку, не объявлять улучшение;
production health/errors и OOM остаются отдельными немедленными критериями.
Текущие Prometheus summary дают sum/count/max, но не p95, поэтому не выводить
p95 из них. При OOM, неготовности `/readyz`, падении PG, потере drain или
подтверждённой регрессии latency — `git revert` кодового коммита в исходном
репозитории, восстановить на production прежние код **и Compose** из
подготовленного bundle через rsync без удаления серверной `.env`/данных,
вернуть сохранённый rollback image ID под тег `vetmanager-mcp` и повторить
`docker compose --profile production up -d --force-recreate --no-build postgres redis mcp prometheus grafana`
под тем же санкционированным окном. Серверный `git revert` сам по себе не
работает: CI деплоит через rsync с `SKIP_GIT_PULL=1`, а MCP монтирует `.:/app`.
Проверить фактический старый image ID, старый исходник из bind mount,
Compose и Uvicorn, затем health, PG `SHOW`, cgroup и
OOMKilled. Данные PostgreSQL/volumes не удалять.
При неудачном старте PG из-за конфигурации вернуть прежние параметры и 512M
лимит тем же откатом; резервная копия нужна на случай независимого повреждения
данных, не как обычный способ отката конфигурации.
