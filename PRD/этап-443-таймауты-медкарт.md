# Этап 443. Таймауты чтения медкарт — расследование 443.1

## Цель и границы

Установить, какой участок чтения `get_medical_cards_by_date` не укладывается
в бюджет, и выбрать проверяемую работу для 443.2. Этот документ фиксирует
read-only факты на 29.10.2026; реализация, тесты и изменение стенда сюда не входят.
Продуктовый ориентир — стабильное чтение клинической документации через MCP
при сохранении полного охвата запроса и защиты данных. Технический контекст:
`artifacts/prd-vetmanager-mcp-ru.md`,
`artifacts/technical-requirements-vetmanager-mcp-ru.md` и PRD 398/403.

## Наблюдения Sentry и логов

Read-only Sentry: организация `home-xv3`, проект `python`, окно `14d`.
События сгруппированы по тексту ошибки, поэтому issue не равен отдельной
причине. В issue 7795965516 (PYTHON-24) — 11 событий с 16 по 26.10,
2 аккаунта; последний stack показывает локальное истечение общего бюджета
GET (`CancelledError` → `TimeoutError` → `VetmanagerTimeoutError`), затем
обёртку ошибки медкарт. В issue 7804173781 (PYTHON-2A) — 3 события 21.10,
1 аккаунт; последний stack содержит `ReadTimeout` при разрешении хоста и
`Timeout resolving Vetmanager host`, затем ту же обёртку медкарт. По данным
Sentry это минимум 14 событий ошибки медкарт в двух механизмах, а не 14
уникальных вызовов/пользователей. Номера аккаунтов намеренно не публикуются.

Issue 7813162755 (PYTHON-2E) — 7 событий с 26 по 29.10, 2 аккаунта,
общий бюджет GET; последний stack/подсказка `related_tool` относится к
`get_store_documents`. Это **соседний сигнал**, не доказательство таймаута
медкарт. Sentry не даёт для этих issue надёжного распределения медкарт по
`limit`, `offset`, датам и размеру HTML. Частоты не нормированы на число
вызовов за то же окно.

Проверены `docker logs --since 336h` трёх production-воркеров
`vetmanager-mcp-mcp-1`, `vetmanager-mcp-mcp2-1`, `vetmanager-mcp-mcp3-1`.
На момент проверки доступно 2294/232/232 строк соответственно. Поиск по
`get_medical_cards_by_date`, `time budget was exhausted`, `ReadTimeout`,
`resolution timeout` дал 0 совпадений в каждом контейнере. Это ограничение
логирования/ретенции или словаря поиска, не свидетельство отсутствия ошибок:
Sentry содержит события за то же время.

## Путь вызова и предыдущие решения

`tools/medical_card.py:get_medical_cards_by_date` проверяет дату и сортировку,
при относительной дате может отдельно получить clinic-local today, строит
фильтры `date_create` и при необходимости `clinic_id`/`doctor_id`/`creator_id`,
затем делает **один** `VetmanagerClient.get("/rest/api/MedicalCards")` на страницу.
Автоматического разбиения диапазона на дни и внутреннего обхода страниц нет.
`limit` ограничивает возвращаемые записи; без измерения upstream нельзя
утверждать, что он ограничивает время/объём обработки на стороне ВМ.
Результат разбирается и измеряется `record_tool_call` с исходами
`success`/`timeout`/`error`; `VetmanagerTimeoutError` оборачивается советом
уменьшить страницу, сбросить `offset` для каждого дня и сохранить полный охват.

`vetmanager_client.py:96` задаёт `READ_REQUEST_BUDGET_SECONDS = 30.0`.
После этапа 403 `asyncio.timeout_at` начинается перед `_request_core` для
одного retry-enabled GET и охватывает разрешение хоста, повтор и передачу
ответа. Это общий бюджет **одного** VM GET, не всего пользовательского
сценария. Этап 398 добавил измерение исходов и безопасную подсказку, оставил
20/30 секунд и не ввёл автоматическое дробление. Этап 403 подтвердил
10 конечных timeout на 258 вызовов медкарт за предшествующие 7 дней
(3,88%; снимок 23.10), исправил end-to-end deadline, но не поднял число 30:
метрика summary без бакетов не даёт p50/p95/p99. Эти числа нельзя переносить
на новое 14-дневное окно как текущую долю.

`identifier_aliases.canonical_tool` добавляет проекции только для имён в
`list_projection.LIST_FIELDS`: `get_admissions`, `get_invoices`,
`get_clients`. Медкарт там нет. Нормализация ключей/аргументов не делает
дополнительный REST-запрос и не объясняет сетевые 30 секунд. Свежий alias
`card_id` из 441 относится к другому инструменту; `fields` из 442 не
подключён к медкартам. Следовательно, причинная связь 441/442 с этим путём
по текущему коду не подтверждается.

## Ранжированные гипотезы

1. **Задержка разрешения хоста или сетевого пути MCP → ВМ.** Для части
   инцидентов прямо подтверждена stack trace PYTHON-2A и сообщением #142
   по admissions. Нужен раздельный счётчик/тайминг фаз по корреляции без URL,
   ключей и клинических данных; проверить, повторяется ли сигнал после 21.10.
2. **Медленный ответ `/MedicalCards` или передача полного HTML.** Один день
   с примерно 10 картами и три значения `limit` всё равно дают таймаут;
   гипотеза про HTML в #140 правдоподобна, но не измерена. Нужны сравнимые
   запросы на одном заранее выбранном контуре, размер ответа и фазы
   запроса; проверить REST-контракт до идеи «лёгкого режима».
3. **Фиксированный 30-секундный бюджет как ограничитель удачного хвоста.**
   PYTHON-24 подтверждает истечение бюджета, но не показывает, завершился
   бы запрос через 31–60 с; повышение без распределения задержек может
   ухудшить занятость воркеров.
4. **Дробление по дням/пагинация.** Помогает только многодневному диапазону
   либо если сервер реально сокращает работу при малом `limit`. Для #140/#142
   уже один день и `limit=10`, поэтому как основной фикс не доказано.
5. **Alias/fields 441/442.** По коду не лежат на пути медкарт; низкая
   вероятность. Перепроверить только если production SHA отличается от
   изученного дерева.

## Архитектурное решение для 443.2

**Проблема:** текущая ошибка объединяет разные причины под одной подсказкой.
**Контекст:** нужен полный клинический охват, безопасные логи, совместимый
публичный MCP-контракт и ограниченная нагрузка на ВМ. `MedicalCards` —
чувствительные данные; в evidence допускаются только длительности, коды,
счётчики, размеры и обезличенные параметры запроса.

**Варианты:** поднять per-tool бюджет (простое изменение, но вероятно
удлинит неуспешные вызовы); автоматически дробить диапазон (сложность,
возможные дубли/частичный результат, не решает один день); локально убирать
HTML после ответа (сократит MCP-ответ, но не время upstream-загрузки);
использовать подтверждённую REST-проекцию, если она существует (потенциально
снижает сетевой объём, но контракт пока не проверен); сначала разделить
фазы/воспроизвести запрос (минимальный риск и проверяемый выбор).

**Выбор:** 443.2 начать с ограниченной диагностики и сопоставимого
read-only воспроизведения, затем выбрать **один** минимальный фикс по
измеренному узкому месту. При подтверждённом host resolution чинить его;
при медленном REST проверить оптимизацию/поддерживаемую проекцию с ВМ;
при стабильно успешном хвосте сверх 30 с обсуждать per-tool бюджет по
новым метрикам. Не вводить неподтверждённый параметр REST.

**Инварианты:** никакой потери дней, врачей, филиалов или страниц;
`offset=0` для каждого самостоятельного дня, дедупликация по ID при
объединении; таймауты и частичные данные не выдаются за полный успех;
секреты/ПД/URL экспорта не попадают в логи и evidence; не менять write-пути.
**Откат:** диагностические метки можно отключить без изменения контракта;
любой выбранный фикс должен иметь отдельный откат в PRD реализации.

Декомпозиция 443.2: (1) ≤2 ч — сопоставимая read-only проба и анализ фаз;
(2) ≤2 ч — PRD конкретного исправления и красный сторож;
(3) ≤150 строк за шаг — реализация, живой вызов выбранного стенда с кодом и
обезличенным телом, проверки и выпуск. Изменение performance/production
поведения требует Architecture Critique и PRD-review перед реализацией.
Риск: новые диагностические измерения могут показать проблему на стороне ВМ;
тогда корректный итог — передать подтверждённый контрактный сигнал ВМ и
не маскировать проблему повышением бюджета.
