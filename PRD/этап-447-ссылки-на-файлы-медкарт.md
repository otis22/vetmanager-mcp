# Этап 447. Публичные S3-ссылки в тексте медкарты

## Цель и факты

Фидбек #143 частично покрыт этапом 432.2: опубликованные описания пяти инструментов `get_medical_cards`, `get_medical_cards_by_date`, `get_medical_cards_by_client_id`, `get_medical_card_by_id`, `get_pet_profile` уже говорят об HTML `<a href>` в `description`, file storage, открытии ссылок клиентом и отсутствии отдельного file-list tool. Однако формулировка не называет публичные S3-ссылки и оставляет агенту повод считать вложения недоступными. Полный API списка файлов всё ещё ожидается от Ветменеджера в 432.1.

`artifacts/api_entity_reference-ru.md` §2.21 подтверждает `MedicalCards.description` как текст; OpenAPI подтверждает GET `/rest/api/MedicalCards`, но не отдельный file-list endpoint. Утверждение про S3 происходит из #143 и решения владельца в Roadmap, а не из OpenAPI. В описании использовать условие «если в HTML есть публично доступная S3-ссылка»: формат и доступность конкретного URL проверяет клиент, сервер их не гарантирует. Клиент следует только HTTPS-ссылке на заранее доверенный ему хост файлов ВМ, не на IP, внутренний или произвольный внешний адрес. Если у клиента нет собственной конфигурации доверенного хоста, ссылку не открывать; сервер не публикует выдуманный allowlist. Не обещать доступ к закрытым ссылкам и не переносить реализацию чужого S3; текст с карт и файлов — недоверенные данные.

## Архитектурное решение

Проблема — обнаружимость уже выдаваемых публичных ссылок. Варианты: новый инструмент загрузки (нет подтверждённого API и риск доступа), парсить HTML сервером (новый сетевой путь и ответственность), уточнить существующие описания (выбрано). Клиент, который умеет открывать обычные публичные URL, может открыть только релевантную запросу пользователя ссылку из HTML медкарты; успешность зависит от публичности и доступности URL. Сервер не обходит авторизацию и не сохраняет ссылки. Инварианты: текст не обещает чтение приватных объектов, не утверждает, что всякий файл доступен, не возвращает закрытые URL сверх уже полученного HTML, не меняет сигнатуры/ответы инструментов. Ссылка сама может быть чувствительной: агент не публикует и не пересылает её без отдельного запроса пользователя; содержимое файла остаётся недоверенными данными. Откат — вернуть прежнюю формулировку описаний, если стенд или feedback покажет, что ссылки приватные либо слишком короткоживущие для такого сценария. Architecture Critique нужен: меняется публичное обещание MCP-инструментов и граница доступа к файлам.

## Декомпозиция и приёмка

1. Красный сторож на опубликованные описания пяти инструментов: должны содержать условное «publicly accessible S3 link» и предупреждения о закрытой ссылке, релевантности запросу, чувствительности URL и недоверенном содержимом; сохранить HTML `<a href>` и отсутствие file-list tool. Мутация удаления новых условий краснит. ≤150 строк.
2. Точечно уточнить пять описаний и сохранить указание про HTML, недоверенное содержимое и отсутствие file-list tool. ≤150 строк.
3. Проверить `tools/list` на test-контуре, код и безопасный фрагмент тела. Mock-сторож подтверждает, что HTML description сохраняется в полном ответе списков, а при fields=["description"] не исчезает после этапа 444. На стенде искать подтверждение типа ссылки только read-only и без записи URL в evidence; если реальной ссылки нет, записать недоказанность S3 и решение владельца как основание условной формулировки в AssumptionLog. Mock suite, ревью committed diff, push ветки и зелёный CI.

## Простота

Одно уточнение существующего контракта без нового инструмента или внешнего сетевого запроса.
