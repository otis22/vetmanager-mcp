# Этап 435. Гистограммы латентности инструментов

## Цель и инвентаризация

Этап 403 не смог получить p50/p95/p99 и доли вызовов за порогом: Prometheus видит только count/sum/max. `service_metrics.py` экспортирует summary `vetmanager_tool_call_latency_seconds` с метками `endpoint`, `tool`, `method`; `vetmanager_upstream_request_latency_seconds` с `target`, `status`; `vetmanager_http_request_latency_seconds` с `route`, `method`. Все собираются локально и в Redis через `shared_metric_counters.py`, где агрегат тоже хранит лишь count/sum/max. Имена и формат старых серий сохраняются.

`host_resolver.py` уже записывает каждую попытку HTTP к billing API как upstream request (`target=billing_api`, `status` ограничен исходом). Логическое разрешение хоста включает кеш, coalescing, до двух попыток и паузу; отдельной latency-серии пока нет. GET read timeout 20 с на фазу и 30 с общий для retry-enabled read (этап 403). Billing API имеет 10 с read timeout на попытку.

## Архитектурное решение

**Проблема:** среднее и накопительный максимум не дают распределения и доли медленных вызовов.

**Варианты:** менять старые summary на histogram сломало бы существующие запросы; хранить только process-local buckets потеряло бы вызовы других MCP слотов; записывать имя каждого инструмента и endpoint умножило бы число рядов на редкие и динамические значения. Выбраны новые серии с фиксированными метками, сохраняющие старые метрики.

**Серии:** `vetmanager_tool_call_duration_seconds` (`tool`, `method`): `get_medical_cards_by_date`, `invoice.list`, `invoiceDocument.list`, `MedicalCards.get_by_id`, остальные `other`; метод нормализован в GET/POST/PUT/PATCH/DELETE/other. Для каждого вызова `_tool_family_label(labeled_endpoint)` сначала даёт кандидат; точное совпадение с фиксированным allowlist сохраняется, любой другой результат без исключений становится `other` **до** записи в локальный или Redis histogram. Имена здесь — значения существующего **metric label**, не всегда имя MCP tool: `_tool_family_label` берёт `endpoint#operation` (`invoice#list` → `invoice.list`, `invoiceDocument#list` → `invoiceDocument.list`, `MedicalCards#get_by_id` → `MedicalCards.get_by_id`) либо явный `tool_name` (`get_medical_cards_by_date`). Сторож сверяет путь `record_tool_call`. `vetmanager_billing_api_duration_seconds` (`status`): HTTP попытки `billing_api`, `http_200`, `http_4xx`, `http_5xx`, `malformed_response`, `invalid_origin`, `connect_timeout`, `read_timeout`, `timeout`, `tls_verification_failed`, `connect_error`, `network_error`, остальные `other`. Значения выведены из `host_resolver.py` и `upstream_transport.py`. `vetmanager_host_resolution_duration_seconds` (`outcome`): только uncached логическое разрешение с исходами `success`, `error`, `cancelled` и без домена. Количество рядов ограничено, URL, ID, токены и данные клиники не попадают в labels.

**Бакеты:** общие границы `0.1, 0.25, 0.5, 1, 2.5, 5, 10, 20, 30, 60` секунд и `+Inf`. Дробные границы нужны для медианы коротких вызовов (этап 403: среднее успешных billing 0.311 с, invoice 0.248 с); 10/20/30 покрывают timeout. `_bucket` кумулятивны, `_count` совпадает с `+Inf`, `_sum` хранит секунды. В Redis hash `vetmanager:metrics:v1:histogram:<sha256(family\0label)>` хранить `family`, `label_key`, `count`, `sum_seconds`, `bucket_0.1` … `bucket_60` как **кумулятивные** целые: при наблюдении увеличить каждый `bucket_X` с `duration ≤ X`; `+Inf` выводится из count. В `le` и именах полей ровно строки `0.1,0.25,0.5,1,2.5,5,10,20,30,60` без `.0`. Вариант бакетов фиксирован в версии prefix; смена границ требует v2. TTL нет, как у старых latency keys: это накопительные ряды с момента запуска. `snapshot` читает новую схему; mixed-version deployment не удаляет старые серии. Старый reader сканирует строго `LATENCY_KEY_PREFIX + "*"`, где `LATENCY_KEY_PREFIX = "vetmanager:metrics:v1:latency:"`; новые ключи с `histogram:` не совпадают. Старый `COUNTERS_KEY` — отдельный hash, не scan. Очередь переполнения хранит в агрегате вектор кумулятивных счётчиков вместе с count/sum; при ошибке доставки векторы складываются поэлементно; запись отложена, но сама Redis-транзакция атомарна. Текущий best-effort delivery может потерять события при длительном сбое и повторить после неоднозначной ошибки EXEC: точность распределения не сильнее текущего механизма Redis summary. При недоступном Redis `/metrics` возвращает ошибку, локальные и Redis данные не складываются. Старые summary продолжают использовать прежний агрегат из трёх значений.

**Граница host resolution:** измеряем только единственную uncached общую задачу `_resolve_vetmanager_host_uncached`, включая повторы и паузы, один раз при её завершении. Кеш-хиты и отмена отдельного ожидающего вызова не создают отдельного наблюдения: `asyncio.shield` сохраняет общую задачу. `outcome=cancelled` относится только к отмене самой общей задачи (например shutdown), а не ожидающего клиента.

**Инварианты:** существующие серии неизменны; одна попытка billing API даёт одно наблюдение, одно логическое host resolution даёт одно; подсчёт не меняет исход операции; ошибки метрик не маскируют сетевой исход; Prometheus может вычислить `histogram_quantile` и долю выше каждого порога; нет произвольных меток. Новая запись добавляет одну Redis-транзакцию на каждое наблюдение сверх существующего summary: в худшем случае 10 bucket-инкрементов, count и sum, один `HSET` метаданных. Не объединяем с summary: отдельный prefix сохраняет mixed-version чтение. Проверить нагрузку на стенде и после релиза в Prometheus, если заметна — отдельный этап оптимизации без изменения контрактов.

**Откат:** убрать запись новых серий и их экспорт, не трогая старые summary; после остановки новых слотов оператор выполняет SCAN MATCH `vetmanager:metrics:v1:histogram:*` + UNLINK и фиксирует факт в релизном журнале. Очередь новых слотов при остановке теряется. Без удаления повторное включение продолжит прежние накопительные ряды — это допустимо только если те же границы и смысл labels. Для анализа неполной истории сохранить время выката всех слотов в релизном журнале и брать окно PromQL после него.

Architecture Critique обязателен: Redis-схема, нагрузка на запись и публичный Prometheus contract затронуты. Сильная пара одновременно проверяет архитектуру и полноту PRD.

## Декомпозиция и приёмка

1. **435.1a, ≤ 150 строк теста:** сторож на `# TYPE ... histogram` и `/metrics` после наблюдений, все `le`, кумулятивность, `+Inf == count`, сумма, четыре выбранных tool-label и `other`, нормализация метода и billing status. До реализации запустить и сохранить красный вывод; доказать чувствительность теста.
2. **435.1b, ≤ 150 строк теста:** Redis cross-slot и overflow, явное чтение старым reader (`git show` базовой версии или изолированный legacy reader) после записи новых ключей и проверка его успеха, логическое разрешение один раз при retry, cache hit, отмене ожидающего вызова и самой общей задачи, error и запись метрики при сбое Redis.
3. **435.2a, ≤ 150 строк:** bucket storage и shared Redis delivery с коалесцированием, чтение snapshot и экспорт text 0.0.4.
4. **435.2b, ≤ 150 строк:** запись tool, billing API и логического host resolution. Фокусные тесты и живой вызов devtr6 с bearer из `.env`; сохранить только код, обезличенную форму ответа и фрагмент `/metrics`.
5. Аудит, committed diff Spark → Astra+Opus, один полный mock+real suite на финальном SHA, push, зелёный CI.

## Простота

Переиспользуем существующие точки `record_tool_call` и `record_upstream_request`, добавляя отдельную обёртку только для логического host resolution. Без сторонней библиотеки и без конфигурации бакетов во время исполнения.
