# Этап 445. Обнаружимость фильтров врача и автора в аудите медкарт

## Цель

Обезличенный read-only снимок production feedback #144, переданный владельцем 30.10 ~19:45 МСК (копия вне репозитория: `stage445-prd-final/owner-snapshot.txt`): агент выгружал карты всех филиалов за период и фильтровал локально; в вызове были только `date_from`, `date_to`, `limit`, `offset`. Нужны одновременно отбор по лечащему врачу и автору записи, с пагинацией и полным текстом. В `get_medical_cards_by_date` уже есть `doctor_id` и `creator_id`, оба передаются независимыми REST-фильтрами `medicalCards`; опубликованное описание уже прямо называет оба ID и допускает их сочетание с периодом, но не говорит, что для аудита нужно предпочесть серверную выборку локальной фильтрации всей клиники. Факт production-вызова без обоих ID показывает, что перечисления параметров не хватило в этом сценарии. Это узкий пробел обнаружимости, не функции; второй общий перечень аргументов не добавляем.

## Контракт и границы

- `doctor_id` означает лечащего ветеринара; `creator_id` — автора записи (контракт этапа 380; его query-aware mock проверил исходящие фильтры, а живой devtr6 показал поля и совпадение ролей в ответе, но не селективность фильтров). Они не взаимозаменяемы. Передавать только названную пользователем роль; если он просит обе, передать оба ID в одном вызове вместе с `date_from`/`date_to`, `limit`/`offset`; не фильтровать выгрузку локально.
- Границы ревью, не новый текст описания: по умолчанию поиск по всем филиалам. `clinic_id` только при явном ограничении филиалом. Использовать явные даты периода; если филиалы имеют разные локальные границы дня, инструмент не доказывает одинаковый календарный охват каждого филиала — сообщить эту границу или сверять филиалы отдельно по запросу пользователя. Перебирать страницы, пока ответ явно доказывает конец (`total_known`, `truncated` и размер страницы); при неизвестном `total`, непрошедшей странице или достижении `offset=10000` не объявлять аудит полным. Дедуплицировать по ID.
- Формат подтверждён `tools/medical_card.py:get_medical_cards_by_date` (возврат после REST GET и `LimitParam`): ответ содержит `total`, `total_known`, `truncated`, `limit`, `offset`, `medical_cards`; `LimitParam` и проверка offset в этом же инструменте ограничивают страницы. Полный `description` остаётся в стандартном ответе; `fields` использовать только если пользователь сознательно ограничил набор полей. Нельзя обещать, что фильтры ускорят любой запрос или что один ID охватывает вторую роль.
- OpenAPI v6 подтверждает GET `/rest/api/MedicalCards`; разрешённые поля фильтра берутся из `FILTER_FIELDS_BY_ENTITY["medicalCards"]`, не из догадки о `user_id`.

## Решение и декомпозиция

1. Красный сторож опубликованного описания: явный выбор серверных фильтров вместо выгрузки всех карт и локальной фильтрации; если пользователь просит обе роли, оба ID в одном вызове с периодом и пагинацией; мутация удаления этой подсказки краснит. Полный текст проверяется отдельным тестом неизменности ответа, но не копируется в описание. ≤150 строк.
2. Точечно добавить в `SPECIAL_TOOL_DESCRIPTIONS["get_medical_cards_by_date"]` только две мысли: предпочесть серверные `doctor_id`/`creator_id` выгрузке всех карт с локальной фильтрацией; если нужны обе роли, передать оба ID в одном вызове с периодом и пагинацией. Остальные пункты раздела «Контракт и границы» служат ревью-критериями, не копируются в описание. Не менять сигнатуру, фильтры и ответы. ≤150 строк.
3. Живой read-only вызов на `.env` test-контуре с обоими ID, датой, лимитом и offset; приложить HTTP-код и обезличенные счётчики для выборок без role-фильтра, только doctor_id, только creator_id и с обоими, а также проверить ID обеих ролей в возвращённых строках без публикации их значений или содержимого карт. Для сильного доказательства найти непустое пересечение, причём хотя бы одна одиночная выборка должна иметь строку вне пересечения. Если test-контур не содержит такой комбинации, записать живую проверку как ограниченную: GET/200 и совпадение ролей в ответе не доказывают применение REST-фильтра, когда все строки имеют одну пару ID. Сценарий 3/2/2/1 этапа 380 работает через query-aware mock upstream и доказывает построение двух outgoing clauses, но не реальную селективность Vetmanager. Независимость реального upstream остаётся непроверенной до различающей выборки; не выдавать пустой или совпадающий ответ за её доказательство. Проверить `tools/list`, mock и real suite, committed diff review, CI ветки.

## Архитектурная критика и откат

Новый агрегирующий инструмент и расширение REST не нужны: путь уже существует. Риск — текст может подсказать фильтровать по автору, когда пользователь просил лечащего врача; поэтому роли разделены и совместное применение условно на запрос обоих. Откат — вернуть прежнюю формулировку, если опубликованная подсказка ухудшит выбор аргументов. Сущности и права не меняются.
