# Этап 361. Маска телефонов с пробелами и точками

## Цель и решение владельца

Исправить пропуск десятизначных телефонов формы `XXX XXX XX XX` и
`XXX.XXX.XX.XX` в обезличенных ответах, CSV, диагностике и feedback.
Решение Владимира от 03.10.2026: при неразличимости телефона и ряда
клинических чисел той же формы клинические данные важнее. Такие телефоны
остаются немаскированным исключением. Существующие ожидания корпуса этапа 330
не менять; добавить в него новые клинические случаи.

## Граница распознавания

Номер без `+7`/`8` в форме 3/3/2/2 маскируется только при явном телефонном
маркере перед ним в той же строке и в пределах 32 символов: `тел.`, `тел:`,
`телефон`, `телефона`, `моб.`, `мобильный`, `звонить`, `звоните`,
`перезвонить`, `сот.`, `сотовый`, `whatsapp`, `вотсап`, `phone`, `tel`,
`контактный телефон` (без учёта регистра и только по границе слова).
Между маркером и номером допустимы только пробелы и `:`, `№`, `#`, `-`;
другие слова и цифры разрывают связь. Маркер после номера не учитывается:
он может относиться к следующему фрагменту. В перечне после помеченного
номера контекст переходит к следующему номеру только через запятую или
отдельное «и», без других слов и чисел. Более длинный числовой ряд не
маскируется частично. `номер` может означать номер анализа или документа,
а `т.` — температуру, поэтому они не являются надёжными маркерами.
Без маркера форма остаётся
клиническим рядом, даже если первая группа похожа на мобильный код `9xx`:
по одной форме нельзя доказать, что это телефон. Числа с клиническими единицами
и рядом с идентификатором сохраняют защиту этапа 330. Уже распознаваемые
слитные, префиксные и дефисные телефоны сохраняют прежнее поведение.
Общие предлоги `с`, `до`, `после`, `в`, `на` не служат доказательством телефона
для новой формы, хотя участвуют в прежней логике сохранения уже распознаваемых
номеров. Новому кандидату нужен отдельный узкий фильтр контактных маркеров.
Проверка публичных текстов входит в аудит: обещание абсолютной маски всех
телефонов при принятом исключении было бы неверным.
Структурированное поле `phone` и CSV-колонка «Телефон» скрывают значение
отдельным слоем по имени поля, даже без маркера внутри строки; это проверяет
отдельный сторож. В свободном тексте такой подсказки нет.

Контракт REST не меняется: меняется только локальная очистка строк. По
`artifacts/api_entity_reference-ru.md` поле MedicalCards.description содержит
клинические данные и примечания. Живой тест на разрешённом тестовом контуре
временно дописывает синтетические данные к существующей карте, читает её через
инструмент и восстанавливает исходное поле в `finally` с проверкой равенства.
Используется заведомо несуществующий номер `000 000 00 00`; остаток
предыдущего прерванного прогона с маркером этапа очищается при старте.
Перед восстановлением тест сравнивает описание с записанной пробой и при
обнаруженном конфликте отказывается перезаписывать его. У REST-контракта нет
подтверждённой атомарной условной записи; гонка между проверкой и PUT остаётся
риском тестового контура. На production тест не запускается.

## Архитектурное решение

Проблема: общий `phone_redaction.py` после этапа 330 узнаёт только короткий
вариант после `тел.` и пропускает форму 3/3/2/2 с пробелами/точками.
Ограничения: сохранение клинических таблиц, один матчер для всех потребителей,
без новых зависимостей и без обхода уже работающих правил.

Варианты: (1) всегда маскировать 3/3/2/2 — портит клинические ряды и нарушает
решение владельца; (2) распознавать по `9xx` — ненадёжно, клиническое значение
может быть таким же; (3) требовать явный телефонный контекст — выбран.
Общая регулярка находит форму, а общий фильтр допускает её только по близкому
контексту. `iter_phone_matches` и `redact_phone_numbers` используют один фильтр;
`depersonalization.py`, экспорт, `error_tracking.py` и feedback используют
этот модуль без второго паттерна.

Инварианты: весь корпус этапа 330 зелёный без изменения ожиданий; клинические
ряды 3/3/2/2 не маскируются; контакты с явной пометкой маскируются на всех
путях; нет частичной маскировки ряда. Rollback — возврат только нового
варианта и фильтра, при этом старые формы остаются закрыты. Ошибка в новом
правиле видна по красным сторожам и фокусным тестам.

Architecture Critique требуется: изменение production privacy behavior.

## Подзадачи и приёмка

1. PRD и Architecture Critique + PRD-review: граница исключения подтверждена.
2. Красные сторожа для обезличенного ответа, CSV, error tracking и feedback;
   клинические ряды 3/3/2/2, перечень контактов, границы длинного ряда и
   структурированные поля добавлены в корпус. Не более 150 строк.
3. Изменить один матчер, получить зелёный фокусный набор и провести аудит.
   Не более 150 строк.
4. На разрешённом тестовом контуре проверить чтение медкарты с числовой
   таблицей без плейсхолдеров и маску телефона в заметке; выполнить полный
   mock + real suite один раз перед push. Получить committed diff reviews,
   push в main и зелёные Tests/Deploy Prod.
5. Сверить FAQ лендинга и README с принятым исключением. Если видимый текст
   требует правки, пройти визуальный гейт перед выпуском.

Стенды не смешиваются: real-suite использует `TEST_DOMAIN`/`TEST_API_KEY` из
`.env`; bearer-контур отдельно и здесь не нужен. Живой ответ изменённого
инструмента фиксируется кодом и безопасным телом без персональных данных.
