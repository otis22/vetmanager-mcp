# Этап 461. PREVIEW_FAILED / OTHER при выручке филиалов

## Цель и проверенные факты

Четыре обращения #163–166 от одного аккаунта 12.11.2026 имеют общий fingerprint и относятся к одному кластеру. Роль пользователя из доступной обезличенной фактуры неизвестна; задача человека — узнать выручку филиалов за заданный период. Куратор передал read-only structured snapshot одного уже существующего job (`scratchpad/run-461-20261116/safe-snapshot.json`): job 12, `failed/PREVIEW_FAILED`, upstream `job.error_subtype=OTHER`, GET job 200, GET data 409 `INVALID_TRANSITION`, `mcp_workaround` отсутствует. Класс `upstream_preview_other` подтверждён структурированным полем. Конкретная внутренняя причина `OTHER` не раскрыта и не установлена; это не доказательство ошибки MCP или синтаксиса запроса. Новый job не создавался.

`get_report_ai_job` уже распознаёт узкие случаи `PREVIEW_FAILED` по маркерам комбинаций, провайдера и `good.id`; произвольный `error_message_safe` после распознавания заменяется безопасным текстом. Общий `PREVIEW_FAILED` не доказывает ни один из этих случаев. Сырые SQL и значения отчёта в ответ/документы не переносить. Локальная OpenAPI v6 не описывает Report AI job endpoints; для счётов документированы `/rest/api/invoice`, `invoice_date`, `status`, `amount`, `clinic_id`, `id`. `api_entity_reference-ru.md` называет `exec` статусом проведённого счёта; `tools/invoice.py` использует тот же статус для `get_revenue_summary`. OpenAPI задаёт list filter с оператором `>`, а `filters.py` разрешает `invoice.id`; `tools/crud_helpers.py::paginate_all` уже использует `id > last_id` при `offset=0`. Публичный `get_invoices` передаёт raw `filter` и `sort` через `crud_list`, где оба валидируются по реестру `invoice` с полем `id`; `crud_list` возвращает upstream-ответ с `data.totalCount` без обрезания. В MCP есть `get_invoices` с `limit≤100`, `offset≤10000`, фильтрами по этим полям и сортировкой; `get_revenue_summary` ограничен 20 страницами по 100 и помечает неполный результат `truncated`.

## 461.1. Безопасная диагностика и резервный путь

Безопасный срез получен. Дальнейшая диагностика не должна запрашивать intent, SQL, тексты ошибок, строки отчёта, названия клиник, account details, host/URL, токены и production logs.

Цепочка: GET job успешно показывает терминальный отказ, GET data закономерно отвергается `INVALID_TRANSITION`. Ошибка preview произошла в upstream Report AI; MCP недостаёт безопасной подсказки для подтверждённого subtype. Повторять только чтение состояния уже существующего job. Эскалация upstream должна назвать `PREVIEW_FAILED/OTHER` и отсутствие детального структурированного класса, не обвинять конкретный внутренний компонент.

Проверяемый ручной fallback для выручки **по проведённым счетам**, при наличии разрешённого `finance.read` и конкретного периода: один раз сканировать все доступные проведённые счета через `get_invoices` с `status=exec`, `invoice_date_from/to`, сортировкой `id ASC`, `limit=100`, `offset=0`. Следующую страницу читать с дополнительным фильтром `id > last_id`, снова `offset=0`; продолжать до пустой страницы или страницы короче 100. Запомнить `totalCount` первой страницы; на каждой следующей странице требовать `totalCount = initial_totalCount - scanned_count_before_page`, а в конце `scanned_count = initial_totalCount`. Отсутствующий, некорректный или изменившийся счётчик, неработающий `id > last_id` или повтор ID запрещают объявлять итог полным. Проверять строгое возрастание ID, корректный статус/период, положительный числовой `clinic_id` и конечность `amount`; суммировать Decimal отдельно по каждому встреченному `clinic_id`, включая нулевые и отрицательные суммы проведённых счетов, как делает режим `invoiced` в `get_revenue_summary`. Отдельные возвраты платежей сюда не включаются: это другая финансовая семантика. При аномалии остановиться и не объявлять сумму полной. При несовпадении счётчиков из-за конкурентных изменений остановиться и сообщить «неполно»; не повторять скан автоматически. Даже при совпадении REST не даёт snapshot: результат обозначить как проверенный на момент чтения, не как транзакционный срез. `get_revenue_summary` с `truncated=true` и обычная offset-пагинация до 10000 не подтверждают полную сумму.

## 461.2. Условная реализация и приёмка

Выбран адресный MCP fix для **структурированного** `failed/PREVIEW_FAILED/error_subtype=OTHER`: добавить `mcp_workaround` с закрытым кодом `report_ai_upstream_preview_other`, безопасным классом `upstream_preview_other`, `safe_to_retry=false`, запретом повторного StartReport и шагами по чтению счетов с полной keyset-пагинацией. Шаги по счетам применимы только если исходный запрос был о выручке филиалов по проведённым счетам; для иной темы или финансовой метрики агент не подменяет результат суммой счетов. Шаги прямо требуют `finance.read`; если права нет, агент сообщает о невозможности прямого чтения и не предлагает обход или повышение до «Полного доступа». Отсутствие `error_subtype`, другое значение, другой status/error_code не классифицировать как этот случай. Существующий `mcp_workaround` не перезаписывать. Узкий уже известный SQL-дефект комбинаций с `safe_to_retry=false` сохраняет приоритет; структурированный `OTHER` ставится перед эвристиками провайдера и good.id, которые разрешают retry. HTTP 409 `INVALID_TRANSITION` не менять. Не менять права, не обходить очистку и не возвращать сырой диагностический текст.

Test-first focused red каждого нового сторожа на исходном коде, отдельно green, owning, fast; аудит и pre-review рабочего diff; полный default, применимые real/live проверки, затем commit, committed-diff review и push ветки. Изменённый инструмент вызывается вживую на заранее выбранном test/devtr6 контуре с сохранением только безопасных кода и тела. Guard должен краснеть при удалении точного условия классификации, `safe_to_retry=false`, пагинационного шага или очистки опасного текста. Тестовая матрица: exact OTHER, отсутствие/другой subtype, другие status/error_code, existing workaround, пересечение с комбинацией и retry-эвристиками, права `finance.read` в тексте; публичный `get_invoices` принимает `filter.id >`, `sort.id ASC`, `limit=100`, `offset=0` и возвращает `data.totalCount`; на второй странице сохраняет одновременно `status=exec` и обе границы `invoice_date`. Сторож текста проверяет указание на группировку `clinic_id`, сверку счётчика и прекращение расчёта при ошибке. Фактический полный проход более 100 счетов и арифметика принадлежат агентскому ручному workflow, а не новому runtime-коду; при отсутствии такого набора на стенде синтетический контрактный тест проверяет две страницы, без утверждения о живой полноте. Для live-вызова нужен реальный `get_report_ai_job`; если стенд не имеет failed/OTHER, показать безопасный ответ существующего job без создания новых jobs и отдельно сохранить mock-доказательство target case. До implementation пройти PRD/Architecture Critique gates.

## Архитектурное решение

Проблема — один внешний код покрывает разные причины; эвристика по самому `PREVIEW_FAILED` может отправить пользователя в неверный retry и умножить jobs. Структурированный upstream subtype `OTHER` даёт достаточную границу для безопасного класса, но не для конкретной внутренней причины. Действующий MCP уже имеет точку узкой классификации до очистки сообщения. Вариант «автоматически повторять отчёт» отвергнут из-за неизвестной внутренней причины и риска дублей; вариант «назначить дефект конкретному upstream-компоненту» отвергнут из-за отсутствия подробного сигнала. Выбранный путь добавляет одно условие в существующий классификатор и использует существующий read tool с keyset-пагинацией; новая публичная операция не вводится. Инварианты: fail-closed доступ, отсутствие SQL/PII, неизменность уже запущенного job, запрет повторного StartReport на retry и приоритет более безопасной уже известной классификации. Откат: удалить одну ветку и её текст, сохранив прежнюю очистку и upstream escalation; до отката агенту предлагать ручной fallback по PRD. Architecture Critique требуется, поскольку меняется MCP-ответ и production behavior.

## Upstream escalation

Передать куратору обезличенное описание: существующий job вернул `failed/PREVIEW_FAILED` с `error_subtype=OTHER`, чтение data отвергнуто 409 `INVALID_TRANSITION`; subtype слишком широк для исправления конкретной upstream-причины. Запросить у владельца Report AI дальнейший структурированный, безопасный подкласс отказа или исправление установленного им дефекта. Не передавать SQL, intent, строки, адреса и внутренние детали.
