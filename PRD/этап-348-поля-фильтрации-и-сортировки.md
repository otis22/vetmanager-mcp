# Этап 348. Поля фильтрации и сортировки в `tools/list`

## Цель и факты

В `tools/list` у большинства параметров `sort`/`filter` отсутствует описание. Локальные allowlist уже применяются к обычным REST list endpoints, но FastMCP не переносит текст `filter/sort` из docstring в JSON Schema параметров. Срез супервизора 25.09.2026 подтверждает повторяющиеся отказы угаданных полей. Прямой доступ к production запрещён.

Наблюдаемый контракт Ветменеджера разделяет заголовок партии и строки: `good_id` относится к строке, а не заголовку. Поля обычных endpoint сверяются с внешним контрактом и результатами ранее выполненной read-only пробы devtr6, закреплёнными в `filters.py`; расхождения записываются в AssumptionLog только как внешнее поведение. OpenAPI v6 и `artifacts/api_entity_reference-ru.md` являются дополнительными источниками формата запросов. На devtr6 25.09.2026 запросы к `AllDiagnoses`, `anonymousList` и `messages/reports` с невозможным `id` и обратной сортировкой вернули HTTP 200 и побайтно тот же JSON, что без клауз (для отчёта задана тестовая кампания); значит, поддерживаемых полей этих клауз нет. `PartyAccountDoc` вернул одну строку без клаузы и ноль строк при `good_id=-987654321` (оба HTTP 200); `document_id` строки привёл к заголовку с тем же `id` (HTTP 200), а `good_id` на заголовке дал HTTP 406 `Invalid filter item name: <good_id>.`. Это подтверждает весь путь поиска. В публичные файлы не переносятся внутренние исходники, пути, имена методов и порядок проверок другого репозитория.

## Декомпозиция

1. Сверить все 39 инструментов с `sort` и 36 с `filter` с внешним контрактом; составить явное соответствие инструмент → контракт полей. На devtr6 проверить, влияют ли `sort`/`filter` на результаты `AllDiagnoses`, `anonymousList` и `messages/reports`; если не влияют, убрать их из публичной сигнатуры вместо рекламы неработающих полей. `MedicalCards` использует обычный REST list; его поля сверить отдельно. ≤2 часа.
2. Написать сторож, который читает реальный экспорт `tools/list` и требует формат клаузы и все допустимые поля у каждого параметра. Показать Red искусственным удалением описания и для связи `good_id`/`get_party_account_docs`. ≤150 строк.
3. Добавить описания к JSON Schema параметров при регистрации инструментов без изменения формы поддерживаемых вызовов; в подсказке о партиях указать путь через строки партии, `good_id` и `document_id`. Для ранее незащищённых обычных `MedicalCards` и `invoiceDocument` применить те же подтверждённые поля в локальной валидации, чтобы отклонение сортировки было наблюдаемым. Логировать имя отклонённого sort property только если это короткий безопасный идентификатор ASCII; иначе писать маркер. ≤150 строк.
4. Проверить изменённые инструменты на devtr6 живыми вызовами и кодами/телами ответа, провести аудит, full mock + opt-in real suite, committed diff review, push и зелёный CI. ≤2 часа.

## Архитектурное решение

**Проблема.** Описание общего инструмента не гарантирует видимости допустимых полей в схеме отдельного аргумента. Агент угадывает их и получает отказ.

**Контекст.** FastMCP экспортирует `FunctionTool.parameters` как `inputSchema`. Существующий `enhance_tool_descriptions` меняет описания инструмента после регистрации; аналогичная финальная стадия может менять JSON Schema параметра. Allowlist `FILTER_FIELDS_BY_ENTITY` проверен read-only пробами, но для специальных путей общий список неприменим. Форма `list[dict] | None` сохраняется для поддерживаемых путей. Удаление игнорируемых параметров меняет контракт: старый клиент, передающий их по памяти, после выката получит ошибку валидации вместо прежнего успешного ответа без применения клауз. Проверка на закреплённой версии FastMCP: вызов тестового инструмента с лишним `sort` дал `ValidationError: unexpected_keyword_argument`. Это намеренная коррекция; альтернативой было бы оставить ввод с пометкой `ignored`, но он продолжил бы создавать ложное впечатление возможности фильтрации. Обычные вызовы без этих параметров не меняются. Логи не должны содержать значения фильтра/сортировки, включая персональные данные.

**Варианты.** `Annotated` во всех функциях дублирует десятки перечней и трудно синхронизируется. Динамически извлекать поля из docstring нельзя надёжно. Явная карта tool → entity и централизованное дополнение схемы использует существующий каталог и обнаруживает новые инструменты без карты. Для специальных путей поля публикуются только после проверки на тестовом API; если клаузу endpoint игнорирует, параметр снимается.

**Инварианты.** В каждом оставшемся `sort` и `filter` есть формат и допустимые поля; `good_id` указан для `get_party_account_docs`, но не заголовков `get_party_accounts`; локальная валидация и список видимых полей согласованы; лог содержит только имя отвергнутого поля; OAuth/доступ не меняется. Снятие игнорируемых параметров является намеренной коррекцией MCP-контракта.

**Rollback.** Если обновление клиентского каталога вызывает проблемы, восстановить снятые параметры временно с описанием `ignored; no supported fields`, сообщая устаревшему клиенту о необходимости обновления; затем исправить вызывающую сторону. При несовместимости версии FastMCP вернуть прежний способ дополнения схемы, сохранить сторож и исправить механизм экспорта. Если стенд опровергнет поле, убрать его из подсказки и allowlist с отдельным красным тестом до выпуска.

Architecture Critique required: публичный MCP-контракт и граница между описаниями и вызовом. Гейт охватывает полноту PRD.

## Приёмка

- Все оставшиеся параметры `sort`/`filter` в реальном `tools/list` имеют имена допустимых полей и формат объекта; три специальных пути после стендового подтверждения не рекламируют игнорируемые параметры. Сторож обходит весь каталог и падает при новом инструменте с клаузой без карты.
- Старый вызов одного из трёх путей с удалённой клаузой получает явную ошибку валидации; вызов без неё сохраняет прежний ответ.
- Путь поиска поступлений товара указан как `get_party_account_docs(filter good_id)` → `document_id` → `get_party_account_by_id`, а поле `good_id` отсутствует в подсказке заголовков.
- Отказ сортировки оставляет в runtime log имя поля без значения только для короткого безопасного идентификатора; произвольный текст и управляющие символы заменяются маркером.
- Красные сторожа, живые ответы devtr6, полный mock и real suite, аудит, AssumptionLog, сильные review, push и зелёный CI.

## Простота

Одна карта соответствия и один проход по зарегистрированным инструментам. Новых wrappers вызова и сетевых запросов нет.
