# Этап 464. Наблюдение workers и измеримый простой

## Цель

Наблюдать доступность каждого из трёх production workers и пользовательского маршрута, определять подтверждённые границы отказа и восстановления и проверять правило владельца: простой строго более 30 минут — ненормальный инцидент. При пропусках наблюдений показывать диапазон неопределённости. Исторический вывод допустим только по обезличенному снимку, который готовит куратор.

## Проверенные факты

- `docker-compose.yml`: production слоты `mcp`, `mcp2`, `mcp3`; каждый обслуживает `/healthz`, `/readyz`, `/metrics`.
- `ops/prometheus/prometheus.yml`: scrape только `mcp:8000` раз в 15 с, bearer token file. Текущий `up` доказывает только доступность одного target для Prometheus.
- Grafana `MCP up` использует этот `up` как единый status. `/readyz` проверяет storage; `/healthz` — liveness. Ответ `/metrics` может быть успешен при проблеме пользовательского сценария.
- Исторического снимка всех слотов и пользовательского маршрута в разрешённых артефактах нет. Куратор собирает 30-дневный обезличенный снимок по `scratchpad/run-464-20261116/blocker.md`; старые ряды новых scrape targets не появятся задним числом. Приём снимка требует указать источник, UTC-период, частоту проб, полноту и поля `timestamp, signal, slot, state`: `slot` равен `slot1`/`slot2`/`slot3` для worker и `service` для маршрута; `state` равен `ok`/`fail`/`missing`. Отдельный `monitor` signal отмечает недоступность самого Prometheus/probe. Допустимы только состояния и коды, без логов, host/IP, URL, токенов, PII и payload клиники. Неподтверждённое происхождение или лишние поля блокируют исторический вывод.
- Новое решение владельца 16.11.2026: strong pair — Astra + Kimi K3 вместо Claude; прежние бюджеты и release gates сохраняются.

## Ретроспективная проверка 30 суток

Куратор передал обезличенные `history-handoff.md`, `production-history-30d.json`, `production-docker-events-30d.json` и `production-nginx-health-history.json` вне Git. Период Prometheus: 2026-10-17T18:54:39Z — 2026-11-16T18:54:39Z. Для единственного старого target `slot1` ряд `up` содержит 172 801 точку с шагом 15 секунд без пропусков и ошибок запроса. Проверка границ `observed_runs` и штатный offline-анализатор дали 26 серий `up=0`: максимальный промежуток от первой до последней нулевой точки — 30 секунд, максимальная внешняя граница между соседними успешными точками — 60 секунд; все 26 классифицированы `within_30m`. На этом полном *ряду scrape `slot1`* правило «более 30 минут» не нарушено. `up` описывает успешность scrape, а не готовность worker или доступность MCP для пользователя; краткое изменение между точками не исключено.

Для `slot2`/`slot3` исторических рядов нет. Docker events покрывает только короткое окно 16.11.2026 и не является 30-дневной историей health. Nginx сохранил 22 точечных HTTP 200 за период менее 30 суток, без непрерывного мониторинга и без истории MCP-сценария. Поэтому простой этих workers и пользовательского сервиса ретроспективно **неизвестен**; ни соблюдение, ни нарушение 30-минутного правила для них не установлено. Новые ряды не восстанавливают прошлое.

## Архитектурное решение

1. Существующий полный scrape `/metrics` у `mcp` остаётся источником общих счётчиков: `service_metrics.py` отдаёт часть Redis-wide series одинаково на всех слотах, поэтому сумма трёх копий исказила бы dashboard. Второй Prometheus job собирает только служебный `up` всех `mcp`/`mcp2`/`mcp3` (app metrics этого job отбрасываются), с закрытым `slot` label. Guard фиксирует отсутствие тройного счёта.
2. Отдельный Compose probe exporter на Python stdlib обслуживает `/probe-metrics`: по запросу Prometheus параллельно делает GET `/readyz` каждого из трёх внутренних слотов и HTTPS GET `${SITE_BASE_URL}/healthz` через существующий Nginx (`scripts/stage385_deploy.py` содержит `location /` для healthz). URL берётся только из production env, должен быть HTTPS без credentials/query/fragment; TLS identity проверяется; timeout каждого запроса 4 с, cadence 15 с (внутренний readiness может занять 3 с). В метриках только фиксированные `slot`, `ok` (200 и ожидаемое JSON поле), `fail` (получен ответ с ошибкой) или `unknown` (DNS/connect/TLS/timeout: причина может быть в сети probe); endpoint без published port и защищён тем же metrics bearer, а цель запроса фиксирована, не задаётся клиентом. Probe не пишет URL/ответы/секреты в лог. `up` самого exporter показывает, состоялось ли измерение; `up=0` или `unknown` не превращается в отказ target. Сервисная readiness выводится только при наличии всех трёх worker series. Это подтверждает health route через proxy, но не успешное выполнение MCP-инструмента; влияние на пользователя дополнительно устанавливается по обезличенному факту отказа или smoke.
3. Успешный `/metrics` означает только работоспособность метрик; успешный `/readyz` — готовность слота. Сервисная недоступность подтверждается отказом health route через Nginx либо одновременным отказом `/readyz` всех трёх слотов при работающем probe. Успешный `/healthz` при нуле ready slots означает вероятный общий storage outage, поскольку liveness не проверяет storage; это подтверждённая недоступность по health check, не «противоречие». Если exporter не работает или серия отсутствует, состояние неизвестно. Деградация одного worker показывается отдельно.
4. Начало инцидента: первый подтверждённый отказ после последнего успеха. Восстановление: первый успешный повтор сценария и подтверждённая готовность workers. Анализатор выдаёт `observed_failure_span_seconds` между первой и последней failed-пробой и `outer_window_seconds` между соседними успешными пробами; ни одно поле не называется доказанной длительностью непрерывного простоя. Пробел делает непрерывность неизвестной. Даже ряд неуспешных точечных проб или Docker health samples не доказывает отсутствие краткого восстановления между ними: результат `observed_over_30m` — наблюдаемая цепочка, требующая расследования, не доказанная непрерывная длительность. Анализатор не выдаёт confirmed `over_30m` из CSV точечных проб ни при каком названии источника. При уже красной первой пробе начало left-censored, при красной последней пробе конец right-censored. Нет данных = неизвестно, а не 0; ровно 30 минут не считается `>30m`.
5. Для истории использовать только снимок куратора; до него публиковать метод и границы, без числового ретроспективного вердикта. Не делать production SSH/SQL/HTTP.
6. По отдельному новому решению владельца без смены Roadmap scope review runner Kimi заменяет обязательного второго сильного ревьюера, чтобы гейты этого этапа могли выполняться. Он запускает профиль без инструментов, получает весь объект inline, сохраняет stream JSON и metadata, отклоняет tool calls/пустой ответ и валидирует `findings`. Бюджеты Astra/Kimi независимы: по 2 валидных verdict и максимум 3 infrastructure attempts на gate. Визуальный gate остаётся blocked без передачи и подтверждения PNG-пикселей Kimi.

## Architecture Critique

Проверить: не выдаёт ли успешный `/metrics` ложную готовность; различимы ли 3 слота и публичный маршрут; не трактует ли PromQL пустой ряд как нулевой простой; не превращается ли scrape failure в «сервис упал»; не теряются ли интервалы Prometheus outage; сохраняется ли приватность labels и auth token. Для Kimi проверить fail-closed поток, отсутствие инструментов, сохранение evidence и запрет валидного `[]` при отсутствии прочитанного контекста.

## Декомпозиция

- 464.1a (≤2 ч): bootstrap нового решения владельца — заменить активный review contract, сделать runner `tools: []` и guards. Первые regression risks: неверная интерпретация Kimi stream как прежнего envelope, незамеченный tool call, ложное `[]` из пустого потока, запись CLI вне разрешённого каталога.
- 464.1b (≤2 ч): test-first конфигурация всех workers и независимой readiness-проверки, обновить dashboards/операционные определения; включить exporter в штатный `stage385_deploy.py` запуск и rollback, проверить Compose/deploy path.
- 464.1c (≤2 ч): синтетические timeline tests для начала/восстановления и границ 30 минут, затем реализация offline анализатора снимка.
- 464.1d (≤2 ч): получить снимок куратора, проверить покрытие/историю, зафиксировать выводы или честный предел, затем release gates.

## Приёмка и rollback

Все три workers имеют раздельные series по Compose/Prometheus config и проверяются guard; ложная готовность не выводится из `/metrics`. Тесты различают наблюдаемую цепочку failed-проб строго дольше 30 минут, верхнюю границу ≤30 минут, пограничный и неизвестный из-за пропуска случаи; подтверждённой непрерывной длительности из точечных проб нет. Снимок сохраняется обезличенным вне Git; вывод сообщает период, источники, покрытие и границы. Без снимка историческая приёмка остаётся открытой и push запрещён. Откат конфигурации — возврат прежнего scrape/dashboard после проверки сохранности monitoring; исторические ряды нового мониторинга при откате теряются.

## Простота

Фиксированный набор трёх targets и один offline анализатор достаточны при текущем масштабе. Новая БД, сбор PII и перехват пользовательских запросов для измерения простоя не нужны.
