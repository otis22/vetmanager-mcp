# Этап 359. Ограничить скан журнала аутентификации

## Цель и факты

На 02.10.2026 супервизор наблюдал 154 463 строки `token_usage_logs`, из них 154 086 успешных аутентификаций; `activation_telemetry_scan_failed` с `TimeoutError` возникал 22/43/85/346 раз за 28.09–01.10. Скан метрик запускается раз в минуту с бюджетом 2 с на хосте 1 vCPU. На исходном SHA до этапа `_accounts_with_requests` переносит все успешные строки в Python ради множества ID, затем для `first_mcp_request` пересекает его с аккаунтами последних 30 дней. `last_request_by_account` агрегирует весь журнал. Соседние `_count_live_accounts` и `collect_activation_funnel` в `scripts/product_metrics_report.py` повторяют перенос всех строк окна ради множества ID.

Главный PRD (`artifacts/prd-vetmanager-mcp-ru.md`) требует рабочий `/metrics`; технические требования описывают активационные gauges. Это локальный журнал, Vetmanager REST API не вызывается и OpenAPI здесь неприменим. Модель журнала подтверждает `account_id NOT NULL`, тип события `token_auth_succeeded`, текущий индекс `(event_type,event_at)`; последний не помогает выборке по аккаунтам без ограничения времени.

## Декомпозиция

- 359.1 (≤2 ч): проектирование, PRD и архитектурное ревью, план PostgreSQL и миграции.
- 359.2 (≤150 строк кода): красный сторож на объёме около 154 тыс. строк и инварианты метрик/предупреждений; запросы скана и индекс.
- 359.3 (≤150 строк кода): аудит соседних запросов, ограничение множеств, проверка миграции на копии схемы, ревью и выпуск.

## Архитектурное решение

**Проблема.** Передача журнала целиком растёт с числом запросов клиентов и съедает бюджет телеметрии.

**Контекст и ограничения.** Журнал растёт постоянно; число активных аккаунтов много меньше числа записей. Скану нужны только аккаунты, уже участвующие в расчёте: для недавних вызовов — `connected_with_active_token_ids`; для первого вызова — `new_account_ids`, для последнего времени — аккаунты с действующим bearer/OAuth-доступом. Последний словарь потребляет только цикл `anchored_accounts` в `scan_activation_telemetry`: bearer-строки и OAuth-only-строки с действующим доступом. Кабинет и отчёт этим словарём не пользуются. Отозванный доступ не создаёт anchor и предупреждение. Значения и условия предупреждений должны сохраняться. PostgreSQL 16; в проде таблица сравнительно небольшая. Обычное построение индекса удерживало бы блокировку записи в течение построения (на 154 тыс. строк ориентировочно секунды, точный срок зависит от нагрузки). Поэтому индекс строится `CREATE INDEX CONCURRENTLY` в отдельном autocommit-блоке PostgreSQL, так что чтение и запись журнала продолжаются. На SQLite миграция создаёт обычный индекс. Alembic выполняет его через `autocommit_block`; на входе проверяет `pg_index` для своего имени: недействительный индекс удаляет `DROP INDEX CONCURRENTLY`, валидный с точным определением принимает как результат прерванного запуска до записи Alembic-ревизии, несовпадающий валидный отклоняет. `lock_timeout` на PostgreSQL ограничен 5 с на получение коротких блокировок, `statement_timeout` ограничивает весь build 120 с, включая ожидание старых транзакций. Прод напрямую не измеряем.

**Варианты.** `DISTINCT` без ограничения сокращает только сеть, но БД всё равно проходит весь журнал. Ограниченный `DISTINCT` проходит все события выбранных аккаунтов. Материализованная сводка требует синхронизации записи и backfill. Выбран общий индекс по `(account_id,event_type,event_at)` (параметризованный `event_type` работает и с generic plan PostgreSQL) и `EXISTS` по нужным аккаунтам; последний запрос использует коррелированный скалярный подзапрос по аккаунту с `ORDER BY event_at DESC LIMIT 1`, чтобы брать верхний `event_at` обратным проходом по индексу, а не через `GROUP BY max` всего журнала. Выборка в Python ограничена числом аккаунтов, а поиск для каждого — индексом, не числом строк журнала. Для отчётного окна кандидатами служат все неархивированные аккаунты; применить `EXISTS` без переноса повторов. Старый индекс `(event_type,event_at)` оставить: он обслуживает оконные подсчёты и может быть выбран планировщиком для разреженной свежей активности; цена — ещё одно обновление индекса на запись, оправданное устранением минутных глобальных сканов.

**Инварианты.** OAuth и bearer события считаются одинаково; порог `>= since` сохраняется; отсутствие успешных событий не создаёт usage. Метрики воронки и тишины, дедуп предупреждений, статус архива и действующего доступа сохраняются. Индекс не содержит PII, публичный API не меняется. Результаты без кандидатов — пустые, без SQL `IN ()` или глобального скана.

**Rollback.** Код можно вернуть; downgrade той же ревизии снимает индекс `DROP INDEX CONCURRENTLY IF EXISTS` в autocommit-блоке без потери данных. При откате кода старый скан вновь медленный, поэтому предпочтителен новый индекс с откатом только запроса. Проверка миграции: upgrade/downgrade/upgrade на временной схеме PostgreSQL test DB с `EXPLAIN (ANALYZE, BUFFERS)` для recent и latest запросов, 154 086 строками журнала (один аккаунт с плотной историей и 201 без событий) и отсутствием свежей активности, без prod-доступа. Два аккаунта подключены и имеют действующие токены: занятый и молчащий; скан обязан выдать их gauges и предупреждения по занятому после 8 дней тишины. Это проверяет дорогой нулевой поиск и ограничение результата; другие распределения нагрузки оцениваются после выката по телеметрии. При отмене concurrent build возможен INVALID индекс: удалить его CONCURRENTLY перед повтором; при сбое после успешного build и до смены ревизии принять только валидный индекс с точным определением. Если DROP завершился до фиксации downgrade-ревизии, повторное удаление отсутствующего индекса проходит безопасно.

Architecture Critique требуется: performance, storage и production behavior. Он покрывает PRD целиком.

## Приёмка

1. Красный сторож в default unit suite на SQLite фиксирует SQL-форму глобальной выборки и число извлечённых строк на синтетическом журнале порядка 154 тыс.; посев выполняется пакетно один раз в тесте, без ORM на каждую строку. После изменения объём результата ограничен числом аккаунтов; на локальном test PostgreSQL с ≥154 тыс. событий `EXPLAIN (ANALYZE, BUFFERS)` для representative recent и latest запросов скана показывает index scan, а latest — `Index Only Scan Backward` под `LIMIT 1`, и отсутствие сканирования большинства журнальных строк, на проверенном синтетическом распределении с одной плотной историей и 201 аккаунтом без событий; границы `since` и смешанную активность покрывают отдельные функциональные тесты. Проверка PostgreSQL запускается в CI на изолированной временной схеме: upgrade/downgrade/upgrade и планы обязательны, повторный прогон не зависит от общей test DB. Жёсткий локальный бюджет скана ≤2 с включается `STAGE359_PERFORMANCE_GATE=1`; на общем CI-раннере время только логируется и не является жёстким критерием.
2. На одинаковых данных до/после совпадают активационные gauges и предупреждения тишины, включая OAuth-only, события на границе времени и отозванный доступ, который не даёт предупреждения.
3. Аудит всех чтений `TokenUsageLog` ради множества аккаунтов: аналогичные места в отчёте ограничены.
4. Миграция проверена на копии схемы и обратима; блокировка индекса оценена.
5. Все фокусные и полные проверки, ревью сторонней моделью, Tests и Deploy Prod зелёные. После выката супервизор проверяет число `activation_telemetry_scan_failed`/`TimeoutError` за 60 минут и длительность `/metrics`: целевое число ошибок — 0 за полный час после выката; каждый вызов `/metrics` должен завершаться быстрее 2 с при сборе без иных задержек, фактическую длительность и p95 за час супервизор сверяет по доступной ему телеметрии.

## Простота

Один индекс и существующие SQLAlchemy-запросы; новой таблицы, кэша и слоя синхронизации нет. При разумном изменении типа события меняется индекс и два места запроса.
