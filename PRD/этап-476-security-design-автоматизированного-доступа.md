# Этап 476 — Security design автоматизированного доступа (#175/#176)

Статус: design для решения владельца, 20.11.2026. База исследования:
`13396486bc0bbd25787dc3f8acf8c2c8f5fe61ef`; правила `AGENT_ONBOARDING.md`
1.2 от 14.11.2026 и `AGENTS.md` на этой базе.

## Цель

Определить безопасные границы для регулярного доступа клинической интеграции без
интерактивного сотрудника и для выборок большого объёма, чтобы владелец мог
отдельно решить, какой сценарий разрабатывать. Этап не выдаёт новых полномочий
и не разрешает запуск интеграции. #175/#176 связаны в операционном разборе с
machine-to-machine, bulk и local CLI (KI #98, `acknowledged`); исходные логи
не устанавливают ни допустимый объём данных, ни согласие клиники на экспорт.

## Пользовательская задача и границы

- Интегратор клиники хочет запускать повторяемую задачу по расписанию и видеть,
  какой именно доступ ей дан и когда он перестанет работать.
- Владелец данных должен заранее знать виды данных, получателя, частоту,
  максимальный объём и способ немедленно прекратить доступ.
- Локальный CLI рассматривается как клиент MCP для оператора, а не как прямой
  доступ к БД сервиса или REST Vetmanager. Серверный процесс не превращается
  в «сотрудника» с неограниченным доступом.
- В этом этапе нет кода, новых MCP tools, выдачи ключей, миграций, изменения
  production/known_issues, тестовых или production вызовов. Реализация,
  разрешение bulk и изменение модели полномочий требуют отдельного решения
  владельца и следующего PRD.

## Проверенные исходные факты

- `token_scopes.py` задаёт именованные права и карту REST методов; неизвестный
  пишущий путь закрыт. Обычно `DELETE /rest/api/` требует `records.delete`,
  но удаление `timesheet` требует `schedule.write` и доступно через
  `delete_timesheet` (также в `frontdesk`). Код здесь расходится с кратким
  правилом 2 в `AGENTS.md` о любом `DELETE`. Вывод этого design: при выборе
  credentials исключать `schedule.write`, если задаче не нужно изменение и
  удаление смен; расхождение правил требует отдельного решения, не правки кода
  в этапе 476.
  Неизвестное REST-чтение сейчас допускается с метрикой; это незакрытый край,
  поэтому новый автоматизированный путь не может полагаться на него.
- `tool_access_registry.py` задаёт права каждого инструмента и пресеты.
  `tools/list` фильтруется теми же правами. `report_ai.write` нужен для запуска
  отчёта со свободным текстом; `analytics.read` его не заменяет. Пресет
  `report_ai` содержит десять прав, включая доступ к клиническим данным.
  `get_report_ai_job`, `get_report_ai_job_data` и
  `get_report_export_download` требуют `analytics.read`: запрет запуска нового
  отчёта не запрещает чтение уже созданного результата. Это право есть и в
  `read_only`/`frontdesk`; read-сторона проверяется отдельно. Для каждого job
  разрешение явно включает либо исключает чтение существующих отчётов; если
  job нужны другие `analytics.read` tools, одного общего scope недостаточно
  для запрета чтения отчётов — нужен серверный allowlist инструментов/job.
- При `is_depersonalized` общая обёртка `tools/__init__.py` очищает результаты
  инструментов; отчётный канал дополнительно очищает ключи и значения колонок.
  Обычный credential без этого флага может возвращать персональные поля через
  list tools. Исходный locator отчётной выгрузки не выдаётся клиенту и не
  пишется на диск. Новый bulk канал должен сохранять эти границы и проверять
  очистку на всех типах результата, а не выдавать upstream URL или сырые данные
  обходным путём.
- Основной PRD §4.2 описывает account-scoped bearer credentials с независимыми
  сроками и статусами; технические требования §3 описывают bearer-only MCP.
  Наличие пресета не доказывает, что он подходит для автоматической выгрузки.
- Операционный разбор #175/#176 от 17.11 связывает их с KI #98 и запрещает
  неподдержанное хранение ключей и обходные endpoints. Подробные поля исходных
  репортов в доступных логах не приведены; до реализации нужно сверить их с
  владельцем продукта без новой production диагностики в этом этапе.
- В первом пилоте 19.11 истёкший normal credential
  привёл к пропущенным отчётам при здоровых workers. После разрешённой ротации
  новый credential сохранил `report_ai`, деперсонализацию, срок 60 дней и
  точную IP привязку. Проверка фактического tool call с разрешённого и другого
  сервера была важнее успешного MCP initialize. Это урок, а не предложение
  копировать операционный способ хранения ключа в продукт.

## Модель угроз

| Актив / граница | Угроза | Требование к будущему решению |
|---|---|---|
| Bearer и конфигурация клиента | утечка из файла, аргумента CLI, лога, CI или LLM контекста | выдача с коротким сроком и отдельной идентичностью задачи; секрет не выводится и не попадает в репозиторий; секретное хранилище или защищённый локальный файл только по явной поддерживаемой инструкции |
| Права и tenant | чужой account, расширение пресетом, обход `tools/list`, подмена операции | проверка account и scope на каждом вызове и на втором REST слое; отсутствие права означает отказ до обращения к ВМ |
| Массовая выборка | автоматизированный сбор персональных/медицинских данных и накопление за пределами задачи | отдельное разрешение на конкретный набор данных и получателя, лимит объёма/частоты/срока, минимизация и деперсонализация по классу данных |
| Свободный текст/отчёты | чтение закрытых медкарт через вычисляемый отчёт | `report_ai.write` и условия очистки сохраняются; произвольный query не становится read-only обходом |
| Сеть и артефакты | URL выгрузки, redirect или адрес хранилища уходит клиенту/в логи | только контролируемая выдача результата через MCP; запрет прямого upstream locator; аудит без содержимого ответа |
| Длительная работа | истечение ключа, ротация, повтор после timeout, бесконечная пагинация | наблюдение `expires_at`, проверка авторизованного data call, ограничение job и безопасный retry без нового побочного задания |
| Компрометация машины | злоумышленник запускает CLI или копирует credential | узкий scope, привязка к разрешённой среде, быстрый отзыв, независимые ключи для разных задач и сред |

IP ограничение снижает риск переноса токена, но не доказывает личность процесса
за NAT и не заменяет scopes, срок или отзыв. TLS обязателен для передачи bearer.
Разрешение из одной сети не даёт согласия на bulk.

## Варианты и решение для следующего этапа

| Вариант | Польза | Риск/цена | Вывод |
|---|---|---|---|
| Существующий scoped bearer для server-to-server через MCP | минимальное изменение архитектуры; действуют реестр и REST слой | статический секрет, ручная ротация; scopes не ограничивают поля, получателя, фильтр, суммарный объём или частоту | кандидат лишь для задачи, чьи границы уже принудительно обеспечены существующими инструментами; для bulk одного bearer недостаточно |
| Отдельная service identity с выдачей короткоживущих credentials | разделяет сотрудника и job, упрощает отзыв и атрибуцию | новый issuance/auth lifecycle и эксплуатация; риск автоматического расширения прав | исследовать отдельным этапом только при доказанной потребности нескольких постоянных jobs |
| Локальный CLI поверх того же MCP | удобен оператору для разовой подтверждённой задачи | shell history, локальные файлы, соблазн прямого REST/БД доступа | допустимый интерфейс-кандидат; не отдельная модель доверия и не способ обхода bulk разрешений |
| Прямой Vetmanager REST, общий full-access ключ или upstream export URL | быстрый доступ | обходит registry, очистку, аудит и отзыв по задаче | отклонить |

Предлагаемый порядок: сначала проверить, может ли один конкретный сценарий
работать в границах уже существующих инструментов и их принудительных лимитов.
Если его задача является bulk, до запуска нужен отдельный механизм, который
на стороне сервиса связывает credential/job с разрешёнными полями, фильтром,
идентичностью зарегистрированного MCP клиента, общим объёмом, частотой и сроком,
включая последовательность
обычных list-вызовов. Клиентская настройка, инструкция оператору и разбиение
на страницы не обеспечивают эту границу. При отсутствии такого механизма bulk
не разрешается даже с узким scoped bearer. CLI, если нужен, применяет те же
серверные ограничения. Окончательный выбор и выпуск credential — решение
владельца после уточнения #175/#176, владельца данных и допустимого набора полей.
Сервис может ограничить получателя своего MCP ответа до зарегистрированного
клиента, но не может запретить этому клиенту дальнейшую пересылку уже
полученных данных. Если конечная доставка нужна, её получатель, политика
хранения и технический контур утверждаются отдельно; это остаточный риск,
который владелец данных принимает явно до bulk запуска.

## Границы bulk access

1. Bulk означает систематическую выборку многих записей или полный диапазон
   данных, даже если каждый запрос использует обычный list tool. Разбиение на
   страницы не отменяет bulk-классификацию. Порог в записях/байтах здесь не
   выдумывается: отдельный PRD задаёт его для конкретного сценария. Регулярная
   выборка списков по расписанию по умолчанию считается bulk, включая
   накопление маленьких ежедневных порций. Единичное чтение заранее известной
   записи по ID без обхода списка может быть non-bulk; право на него не даёт
   права расширить задачу до обхода всех ID.
2. Разрешение описывает purpose, account, сущности и поля, фильтр/период,
   зарегистрированного MCP клиента и конечного получателя (если он отличается),
   срок хранения, частоту, максимум записей/байтов и владельца.
   Отсутствие любого из этих параметров означает отсутствие bulk разрешения.
   Само описание разрешения не даёт технической защиты: future implementation
   должна применять эти границы на сервере к совокупности вызовов job.
3. Клинические тексты, медкарты, контакты и финансовые детали не включаются в
   «типовой» bulk доступ. Для них требуется отдельное обоснование и проверка
   деперсонализации/минимизации на полном пути, включая названия колонок.
4. Нужны явные верхние границы на один job и период, pagination и deadline;
   достижение границы останавливает job с видимой ошибкой. Неограниченный
   auto-pagination и скрытое возобновление после отказа недопустимы.
5. Новый export/streaming endpoint или tool не наследует права от обычного GET:
   до разработки определяются отдельные scope и registry mapping, второй
   REST слой и правила выдачи артефакта. Неизвестное чтение нельзя использовать
   как канал автоматизированного доступа. До пилота набор вызовов job
   ограничивается зарегистрированными tools и mapped REST путями; каждый
   `vetmanager_rest_unmapped_read_total` от job вызывает остановку и разбор,
   а не молчаливое продолжение.
6. Любой bulk результат остаётся в контролируемом контуре MCP, с очисткой по
   классу данных и без upstream locator. Внешняя доставка и срок хранения
   результата требуют отдельного решения и договора с клиникой.

## Credential lifecycle, отзыв и аудит

- Для каждого job/среды нужен отдельный credential с указанием account,
  владельца, purpose, scopes, срока, network binding, `is_depersonalized` и
  идентификатора клиента. По умолчанию автоматизированный credential
  деперсонализирован. Идентифицирующие поля допустимы только после отдельного
  решения владельца данных с перечнем полей, получателем, обоснованием и
  технической проверкой пути выдачи; обычный scoped bearer сам по себе такого
  разрешения не даёт.
  Пресет — начальная подсказка; конечные права проверяются по задачам и
  `tool_access_registry`, без автоматического `full_access` и `records.delete`.
  Автоматизированные credentials не выпускаются из `frontdesk`/другого
  широкого preset без явного effective scope manifest. `schedule.write`
  считается правом на удаление смен и исключается, если оно не утверждено
  отдельно; до разрешения расхождения правила и кода это блокирующее условие.
  Пустой/отсутствующий scope manifest для job credential запрещён: текущий
  `deserialize_token_scopes` трактует его как legacy full access. Также нельзя
  без проверки использовать legacy preset snapshots: они расширяются при
  чтении до актуального набора. Будущий issuance обязан сохранять и
  показывать точный *effective* список прав, отклонять неожиданное расширение
  и не применять legacy upgrade к автоматизированным credentials.
- Владелец устанавливает максимальный TTL и максимальную длительность
  перекрытия старого и нового credential до запуска пилота; 60 дней из
  прошлого восстановления не являются значением по умолчанию. После
  перекрытия старый credential отзывается независимо от успеха следующих jobs.
  Значения выбираются по измеренным частоте jobs и времени безопасной
  ротации, а не из срока исторического ключа; отсутствие утверждённых
  максимумов блокирует пилот. То же относится к окну предупреждения и
  распространения отзыва.
- До первого запуска оператор видит `expires_at`; предупреждение до истечения
  приходит заблаговременно по согласованному окну, а не после 401. Проверка
  доступности вызывает безопасную авторизованную операцию с данными в рамках
  уже выданного scope и не раскрывает данные в мониторинге. Health worker и
  `initialize` не заменяют эту проверку.
- Ротация: выпуск нового credential с теми же или более узкими правами,
  установка через поддерживаемый секретный канал, positive data call и
  negative проверка ограничений, затем отзыв старого. Истёкший credential не
  «продлевается» изменением БД; возврат старого файла не является rollback.
  При компрометации отзыв немедленный, затем расследование по audit ID.
  Проверка статуса и срока credential должна происходить на каждом data call
  либо через кэш с заранее утверждённым максимальным сроком; отзыв считается
  завершённым только после подтверждённого отказа старого credential в
  пределах этого окна. Окно утверждает владелец до реализации.
- Аудит фиксирует issuance/rotation/revoke, actor или service identity,
  account, credential ID (без raw), purpose, scope snapshot, время,
  network binding, tool/job ID, тип данных, заявленный и фактический объём,
  outcome и причину отказа. Корреляция с upstream job нужна без сохранения
  запросов, ответов, PII, секретов или export locator в обычном логе.
- Записи аудита создаются на стороне сервиса вне доступа клиентского credential,
  с защитой от изменения/удаления актором job и проверяемой целостностью.
  Изменение или пропуск записи даёт отдельный сигнал. Ответственный за account
  видит историю и может сопоставить отзыв с фактическим последним доступом.
- Для bulk нужен след запуска и завершения, отказа по лимиту, отмены и
  повторов. Минимальная retention покрывает срок credential и период
  расследования, утверждённый владельцем; доступ к аудиту и alert thresholds
  утверждаются до реализации. Отсутствие этих значений блокирует пилот.

## Решения владельца до реализации

1. Какая конкретная рабочая задача в #175 и #176, кто получатель и владелец
   данных, чем подтверждена его санкция на регулярный доступ?
2. Какие сущности/поля и максимальные объём, период, частота и срок хранения
   действительно нужны? Требуется ли вообще bulk или достаточно агрегата?
3. Достаточны ли отдельные scoped bearer и поддерживаемый secret storage для
   пилота, либо обоснован новый lifecycle service identity?
4. Какое окно предупреждения о `expires_at`, кто реагирует на отказ и кто
   вправе отзывать credential и останавливать job?

Ответы становятся входом отдельного PRD. До них KI #98 остаётся
`acknowledged`, а безопасность текущих инструментов и пресетов не меняется.

## Критерии приёмки design

- Есть сравнение server-to-server, scoped bearer/service identity и local CLI;
  указаны выбранный кандидат и причины отказа от прямого REST/full access.
- Модель угроз покрывает утечку credential, горизонтальный доступ, массовую
  выгрузку, обход отчётных прав и отказ при истечении срока.
- Bulk определён по поведению, а не по одному размеру ответа; перечислены
  обязательные параметры разрешения и fail-closed поведение при их отсутствии.
- Указаны требования к audit, expiry наблюдению, безопасной ротации и отзыву.
- Источники и непроверенные предположения разделены; документ не содержит
  ключей, клинических данных, внутренних адресов или чужой реализации.
- Только Markdown diff, пройден PRD review, итог оставлен для решения владельца.

## Декомпозиция и простота

476.1: собрать проверенные факты и design (этот документ); 476.2: PRD review,
внести поправки, передать решения владельцу. Это документные подзадачи,
каждая менее двух часов без реализации. Самый простой вариант для единичного
чтения известной записи без обхода списка и с уже обеспеченными лимитами —
отдельный узкий scoped bearer на MCP. Регулярная выборка списков требует bulk
enforcement независимо от размера одной страницы.
Для bulk этот вариант сам по себе недостаточен. Новая service identity и
отдельный bulk endpoint не предполагаются заранее: их необходимость решается
по конкретному сценарию и способу серверного enforcement.
