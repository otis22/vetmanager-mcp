# Этап 434 — надёжный путь определения долга по счёту

## Цель и проверенные факты

`unpaid_invoices` сейчас запрашивает два набора по сохранённому `payment_status` (`none`, `partial`). По подтверждённому code-path Ветменеджера колонка может расходиться с фактической оплатой; UI определяет её из сумм. Нулевой счёт после возврата аванса может перейти `full → none`, хотя долга 0. Данные тестового домена не используются как обоснование. `get_invoices` уже возвращает `amount` и `paid_amount` и имеет фильтры суммы; менять реализацию фильтров не требуется.

Главный PRD `artifacts/prd-vetmanager-mcp-ru.md` требует обнаружимых MCP prompts и ясных описаний параметров (4.1.3, 4.1.7). Технические требования сохраняют существующий FastMCP и список API. `artifacts/api_entity_reference-ru.md` (Invoice) и OpenAPI v6 (`invoice`, `/rest/api/invoice`) подтверждают поля `amount`, `paid_amount`, `payment_status`, `create_date`, а также строковое представление денежных значений. Утверждение о расхождении статуса основано на данном супервизором подтверждённом code-path, а не на OpenAPI.

## Архитектурное решение

- Проблема: выборка сначала по неточной колонке может исключить реального должника, а также включить нулевой счёт без долга.
- Выбор: один `get_invoices(limit=limit, sort=create_date DESC)` без фильтра `payment_status`; для каждой полученной строки численно сравнить `paid_amount < amount`, долг = `amount - paid_amount`, включая нулевую и частичную оплату. Строки с долгом ≤ 0 исключить. Отсутствующие, `null`, нечисловые и бесконечные суммы не приравнивать к нулю: пропустить строку и сообщить число непроверенных. `limit` означает число **проверенных** счетов, а не гарантированное число должников. Полнота доказана лишь если `totalCount` — корректное число и проверено столько строк; при `totalCount > fetched`, отсутствующем/сомнительном счётчике или упоре в лимит без доказательства конца явно сообщить о частичной выборке и предложить пагинацию `offset` с той же сортировкой. При непроверенных строках также не объявлять список полным.
- Варианты: два фильтра `payment_status` сохраняют дефект; фильтры `paid_amount_max`/`amount_min` по отдельности не выражают сравнение двух колонок каждой строки и могут пропустить частично оплаченные счета. Серверный агрегат или новая логика в tool выходит за рамку этапа.
- Совместимость: сигнатура и поведение `get_invoices` остаются прежними; меняются только инструкция в MCP prompt и docstring параметра. Загрузка одного prompt вызова снижается с двух запросов до одного. Для полного списка нужна пагинация, ограниченная существующими `limit`/`offset` API.
- Ответ `crud_list` передаёт upstream `data` без удаления `totalCount`; OpenAPI описывает `data.invoice` и `data.totalCount`. Автоматический полный обход истории в prompt не предписывается: пользователь получает явную частичность и может задать меньший период или запросить следующую страницу. При постраничном просмотре одинаковые `create_date` и новые счета могут дать дубли/пропуски; не обещать снимок без пропусков.
- `status` счета прежний prompt не фильтровал: `payment_status` не является фильтром жизненного цикла. Этап сохраняет отсутствие `status` фильтра. Изменение бизнес-правила по черновикам/удалённым счетам требует отдельного решения владельца.
- Инварианты: полностью неоплаченные и частично оплаченные счета с `amount > paid_amount` остаются в ответе; долг вычисляется из чисел, не лексикографически; `0/0` не попадает в должники; при неполной странице ответ не выдаётся за полный; исходные суммы и личные поля не пишутся в evidence.
- Rollback: откатить prompt/docstring коммит, если живой API не возвращает нужные поля или после выпуска обнаружится, что ответ вводит пользователя в заблуждение о полноте/сумме долга; при недоступном API выпуск заблокирован.

Architecture Critique: required — меняется публичная инструкция MCP и смысл ответа; совместить с полным PRD-review.
