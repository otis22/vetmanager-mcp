# Этап 455. Периодные позиции счетов: 1000 обращений и длинное ожидание Report AI

## Цель
Полная выборка позиций счетов для аналитики должна проходить более 20 GET,
с сохранившимся конечным пределом 1000 и честным отказом от неполных результатов.

## Контекст и проверенные факты
- `tools/finance.py` считает общий `calls` для invoice и invoiceDocument.
  Константа равна 20; результат limited не содержит продолжаемого offset.
- Глобальная страница выдаётся после чтения периода: limit=1 не уменьшает
  необходимую глубину сканирования. Именно это делает большой период дорогим.
- Сейчас нет общего asyncio timeout для инструмента; GET имеет отдельный бюджет
  READ_REQUEST_BUDGET_SECONDS и HTTP phase timeouts в VetmanagerClient.
- `scripts/init_server.sh` задаёт proxy_read_timeout 3600s для `/mcp`.
  Runtime агента и его transport меняются отдельно: execution без общего
  короткого deadline, MCP tool_timeout1900с (100с запаса к1800с сервера).
- API-контракт: invoice.invoice_date задаёт период, invoiceDocument.document_id
  связывает позиции со счётом; IN пакет <=500 и URL <=7000 bytes остаются.

## Дополнение владельца: Report AI
Текущее ожидание ограничено30с и16GET, а стадия считается зависшей через15мин.
Новый контракт: wait_seconds0..1800, default0 остаётся; рекомендация next_action
для activejob —1800с; лимит возраста очереди/неподвижной стадии1800с.
Обычный короткий wait_timeout позволяет продолжить bounded wait того жеjob.
Сетевой poll_failed, нетanalytics.read, реальный stale>=1800 — pause.
Число GET внутри ожидания ограничено1000 и дополнительно рассчитано по
запрошенному времени/интервалу2с (до900GET за1800с). Новых create/saves нет;
дубликаты запрещены, save/confirmation consent сохраняется. Документация
helper и описания tools синхронизируются с этим контрактом.

## Архитектурное решение
Изменить существующую константу периодной выборки на 1000, обновить публичное описание инструмента
и документированный контракт. Сохранить существующие два счётчика-гейта до GET,
общую сортировку, фильтры, проверку повторных страниц и результат limited.
Новых классов, persistent state, сессий или флагов не вводить.
Для полной периодной выборки добавить общий deadline1800с; каждый из двух
upstream-циклов использует единый локальный boundedGET helper с оставшимся
временем черезasyncio.wait_for. При истечении — limited_reason=time_budget,
пустые строки/count=null/next_offset=null, число реально начатых обращений.
При известном totalCount достигнутый total завершает цикл и на полной странице.
В Report AI после последнего разрешённого poll терминальный ответ проверяется
до добавления wait_timeout; статус для человека возвращается сразу. Сервер stateless;
общий budget MCP-вызовов в одном пользовательском запросе (run) реализуется в runtime агента,
не в этом внутреннем цикле. Параллелизацию upstream не добавлять.

## Подзадачи
1. Контракт и ревью PRD, <=2ч.
2. Красные сценарии сканирования >20 и исчерпания 1000 по обоим циклам, <=150 LOC.
3. Константа/описание, <=150 LOC.
4. Report AI: longwait/validation/next_action/guards, <=150 LOC.
5. Фокусные и полные проверки, живой read-only вызов, <=2ч.
6. Committed review, push, зелёные CI и deploy, проверка tool description/live read.

## Приёмка
1. Выборка, требующая >20 и <=1000 GET, возвращает полную страницу и totalCount.
2. Оба цикла останавливаются **до** 1001-го GET; limited сообщает ровно 1000,
   без ложных строк, count или продолжаемого offset.
3. Если последнее необходимое чтение — 1000-е, результат может быть полным.
4. Пагинация, IN-пакет/URL cap, фильтры и защита от повторных страниц сохранены.
5. Описание в tools/list больше не обещает максимум20, явно говорит1000.
6. Живая проверка на `.env` test-контуре: только GET, код/безопасное summary тела.
7. Прокси допускает3600с; полная периодная выборка ограничена1800с,
   timeout означает честный limited/time_budget. HTTP phase timeouts остаются.

8. Report AI принимает1800, отвергает1801/bool/negative до записи; нет
   create/reject/save retry. В ожидании на1200с job не считается stale.
9. Искусственные часы доказывают ожидание>30с и>16poll, остановку при1800с
   и возврат ready/needs_confirmation сразу без ожидания оставшегося срока.
10. earlytimeout => poll того жеid; poll_failed/stale => pause без duplicate;
    ready_to_save по-прежнему требует явного согласия.

## Уточнение бюджета одного запроса пользователя
В bot-panel общий внешний бюджет составляет30000 MCPtools/call на один запрос
пользователя. Наш предел1000 внутренних RESTGET относится только к одному
вызову периодного инструмента, не является общим бюджетом пользователя и
не умножается до30000: такое изменение прочитало бы до3млнстрок в640МБworker.

## Уточнение внутренней пагинации
При тесте1000pages найден ещё существующий внутренний max_offset10000:
он остановил бы цикл до1000GET. `crud_list` получает internal-only параметр
max_offset(default10000), периодный метод передаёт1000×page_size=100000.
Публичные tool-схемы и offset caps остальных инструментов не меняются.
Это уточнение позволяет выполнить уже принятую границу1000, а не вводит
новый контракт или абстракцию.

## Вне scope
Бизнес-сравнение комбинаций, DB schema и приватная документация других проектов;
смена токенов/IP/прав, изменение данных клиник, число tools/call в bot-panel,
сохранение/создание Report AI отчётов, глобальное отключение сетевых timeout.

## Простота
Используются существующие константы/цикл ожидания/next_action,0 новых классов. Локальный helper объединяет ровно два одинаковых
upstreamcall-site и общийdeadline; общей framework-абстракции нет. Два конечных предохранителя (deadline и capGET) необходимы
для долгого ожидания и защиты при неисправных часах/слишком частом polling.
Параллельных upstream-запросов не добавляется.

## Риски и проверка
Полное сканирование может прочитать до100000 строк и потребить больше памяти;
сохраняется1000GET и существующая последовательная обработка. Неполный результат
не выдавать за достоверный. Большие возвраты ограничиваются limit<=100;
метаданные полноты и global offset доступны только после полного сканирования.
