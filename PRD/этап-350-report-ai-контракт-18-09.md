# Этап 350. Report AI после релиза 18.09

## Цель и проверенные факты

Поддержать новый внешний контракт Report AI, переданный Д. Сиротой 18.09 и
проверенный супервизором на devtr6 25.09. Прямые обращения к production и
production DB запрещены; известные проблемы фиксируем письменно для владельца.
Локальный OpenAPI v6 содержит `StartReport` и `reportFile`, но не описывает
`report-ai-job`; для новых состояний источником служит постановка и live devtr6.
`api_entity_reference-ru.md` не содержит новой схемы этих методов.

Новые ответы: `QUEUE_TIMEOUT` после часа в очереди; `LLM_UNAVAILABLE` при
таймауте провайдера; `reject` кандидата только из `needs_confirmation`, затем
асинхронный переход к `ready_to_save`/`failed`; `StartReport` отдаёт
`REPORT_NOT_ALLOWED_FOR_REST`, `CONSTRUCTOR_BUSY`, `RUN_RATE_LIMITED` с
`retry_after_seconds` у последних двух; `reportFile` отдаёт
`FILE_BUILD_NOT_STARTED`, `FILE_NOT_READY` (оба 409, retry 5 с),
`FILE_BUILD_FAILED` (422). Ошибки в `data.error_code`, в `failed` есть
`error_message_safe`, иногда с SQL. `/data` отдаёт до 10 000 строк; `limited`
указывает на обрезку.
Успешный `get_report_ai_job` сначала классифицирует старый `PREVIEW_FAILED`
по тексту внутри процесса, затем заменяет `error_message_safe` постоянным
объяснением причины. Исходный текст ни агенту, ни logger не передаётся.
HTTP 403 `StartReport` в клиенте должен пройти общий разбор `data.error_code`
и задержки до специальной обработки; иначе машина теряет новый контракт.

`retry_after_seconds` читаем из `data.retry_after_seconds` (при старой
обёртке допускаем `data.details.retry_after_seconds`), только целое значение
1–3600; bool, float и строку отвергаем. Иначе применяем 30 секунд для
`StartReport` и 5 секунд для `reportFile`. Никакой серверной
задержки не исполняем автоматически: её видит агент как совет.
`FILE_BUILD_NOT_STARTED` после успешного `StartReport` — ждать тот же
`report_file_id` 5 секунд: тестовое file 324 прошло через этот код к 200.
`FILE_NOT_READY` — тот же шаг. Если StartReport не наблюдали в этой сессии,
проверить переданный file ID и всё равно не начинать новый экспорт молча.
После 12 опросов или минуты вернуть «ещё строится» с тем же ID; позднее
возобновить проверку по решению пользователя. `FILE_BUILD_FAILED` — остановиться, показать
человеку и предложить новый экспорт только после решения пользователя.

## Scope и декомпозиция

- 350.1 (≤2 ч): контракт, PRD, Architecture Critique и PRD-review.
- 350.2a (≤150 строк логики): сохранить коды и retry delay на клиенте,
  классифицировать export и status, убрать SQL из агентского ответа.
- 350.2b (≤150 строк логики): reject tool с правами `report_ai.write`,
  подсказки агента и метрики по ограниченному набору кодов.
- 350.2c (≤2 ч): красные сторожа, обратная совместимость со старыми текстами.
- 350.3 (≤2 ч): живой test-contour smoke, аудит, полный suite, ревью,
  выпуск и зелёный CI.

## Архитектурное решение

**Проблема.** Коннектор теряет машинные причины ошибок 403/404 и опирается на
старые тексты. Агент не может отказаться от кандидата, а сырой SQL может
оказаться в `error_message_safe`.

**Контекст.** Внешний API и право `report_ai.write` уже есть; POST запускает
работу. Status polling обходит GET cache. Данные и выгрузки проходят слой
деперсонализации. Метрики и логи не должны содержать job text, SQL, tenant ID
или произвольный `error_code` как Prometheus label. Сохраняем старый формат.

**Варианты.** Только обновить prompt: мало, потому что клиент теряет код.
Парсить только сообщения: ломается при смене текста. Центрально сохранить
машинный код и задержку в `VetmanagerError`, затем в Report AI классифицировать
из закрытого набора: совместимо и ограничивает cardinality. Выбран третий.

**Инварианты.** Reject вызывается один раз по воле агента и затем только
polling каждые 5–10 секунд не более 6 раз за один диалоговый ход. Очередь
может жить до серверного `QUEUE_TIMEOUT` после 60 минут; после локального
лимита агент сообщает «задание ещё выполняется, вот job_id» и позднее
проверяет тот же job по запросу человека. Для активной стадии ориентир
15 минут на состояние, но это не обязывает держать диалог открытым.
Повторного
reject после краткого `needs_confirmation` нет. POST без автоматического
сетевого retry. При timeout или 409 `INVALID_TRANSITION` после reject агент
смотрит статус того же job, не считает reject успешным и не повторяет POST.
Если статус остался `needs_confirmation`, агент сообщает человеку о
неопределённом исходе; новую попытку делает только после его решения.
Проверка прав на `/reject` та же tenant-scoped, что на `/confirm`. 409 вне
`needs_confirmation` не повторяется. Сырые `message`, `details` и
`error_message_safe` Report AI не передаются агенту/в логи без проверки:
для известных кодов выдаётся постоянный текст, для неизвестных безопасный
общий текст. Логи и метрики получают только нормализованный код из закрытого
набора, неизвестный — `unknown`. Новая метрика
`vetmanager_report_ai_outcomes_by_code_total{operation,code}` допускает только
закрытые константы для обеих меток; в логе те же метки без тела ошибки.
`limited=true` означает обрезку. Экспорт не дублируется
при ожидании файла. Новые метрики имеют только константные метки.

**Rollback.** При проблеме с новыми ветками выпустить точечный revert
веток классификации и регистрации reject tool, сохранив отдельный sanitizer
успешного job payload и HTTP исключений. Тест на SQL leakage — обязательный
гейт такого исправления. Для уже начатого reject
агент продолжает `get_report_ai_job` до исхода, даже если tool больше нет;
при несовпадении кода остаётся старое распознавание по тексту.

Architecture Critique required: меняются публичный MCP контракт, безопасность
ответа и поведение на ошибках production.

## Приёмка

1. Reject кандидата приводит к polling того же job до результата; второй
   reject не предлагается при кратком `needs_confirmation` после первого.
2. Каждый новый код ведёт к ограниченному следующему действию; старые ответы
   продолжают работать. Код и задержка видны в метриках/логах без SQL.
3. SQL из `error_message_safe` не попадает в MCP-ответ или журнал.
   То же проверяется для HTTP `message` и `details`; безопасные старые тексты
   сохраняют классификацию, но не копируются в ответ целиком.
4. `limited` и 10 000 строк описаны корректно.
5. Все изменённые инструменты вызваны на devtr6; в AssumptionLog записаны
   HTTP код и очищенная форма тела (код, имена полей и неперсональные константы,
   без SQL, IDs клиники и содержимого отчёта); полные тесты, ревью и CI зелёные.
6. По KI-45, KI-55 и другим Report AI KI составлено письменное решение на
   основании доступного снимка; изменение production DB выполняет владелец.
7. Артефакт исследовательских заметок содержит статус/форму каждого
   наблюдённого live ответа; ненаблюдённые коды помечены как контракт из
   постановки, а не как проверенное тело. Сторожа delay: bool, float, строка,
   0, отрицательное, >3600, отсутствие и оба расположения поля.
8. Красные сторожа проверяют scope `report_ai.write` и видимость reject в
   `tools/list`, отказ token другого tenant, отсутствие автоматического
   повтора после timeout/409 и bounded polling guidance. Центральный клиент
   не меняет текст/тип ошибки для остальных инструментов; тесты проверяют
   обратную совместимость и отсутствие SQL даже в `str/repr` Report AI
   исключения и записях logger.

## Простота

Переиспользуем `VetmanagerError`, `mcp_workaround`, реестр инструментов и
существующие метрики. Новые слои хранения или автоматический retry не нужны.
