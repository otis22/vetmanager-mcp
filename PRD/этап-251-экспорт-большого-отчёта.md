# Этап 251. Экспорт большого отчёта не завершается

## Цель

Исключить бесконечный polling `get_report_export_file`: после ограниченного
локально наблюдаемого ожидания MCP должен вернуть явный итог с предложением
прекратить автоматический polling, не создавая новый export автоматически и не выдавая срок за
контракт Vetmanager.

## Воспроизведение и факты

- 24.08.2026 на devtr6 создан all-time агрегированный Report AI job: он дошёл
  до `ready_to_save`; после сохранения `StartReport` вернул build id, первый
  `reportFile` был HTTP 401 `build in progress`, второй через 5 секунд отдал
  все file locators. Старый symptom #38 не воспроизвёлся.
- Current retryable contract — только HTTP 409 либо HTTP 401 с `build in
  progress`/`not started`; HTTP 401 здесь не authentication failure.
- В репозитории нет `INVALID_ARGUMENT`; current `reportFile` path передаёт
  `file_id` query parameter. Поэтому код #38 не подтверждает upstream
  not-ready state: вероятнее всего это protocol-level classification внешнего
  клиента для невалидного tool call. Причину нельзя выдать за доказанную без
  raw call evidence.
- OpenAPI описывает оба endpoint как generic `GET` без status/retry/TTL
  contract. Upstream не публикует durable export status.

## Архитектурное решение

### Проблема и ограничения

Сейчас process-local observation хранит время успешного `StartReport`, но
`get_report_export_file` на retryable ответ всегда предлагает повторить.
Нельзя добавить server-side TTL, durable status, automatic retry или новый
`StartReport`: это ownership Vetmanager и создаст дубли экспорта.

### Варианты

1. Оставить бесконечную рекомендацию — не решает incident.
2. Объявить upstream export failed по неподтверждённому TTL — ложный contract.
3. Ввести явно *MCP-observed* bounded wait для одного process observation;
   после него вернуть actionable ToolError, но на каждом следующем вызове
   сначала всё ещё проверять upstream file: готовый build остаётся доступен.
4. Stateless deadline только в prose. Он проще, но не делает cap observable и
   не даёт машине отличить normal first poll от длительного wait.

Выбран вариант 3 с лимитом 30 минут: это conservative MCP guardrail, не SLA и
не утверждение о состоянии build; он прекращает hours-long automatic polling,
но не запрещает поздний direct poll того же `report_file_id`. Значение выбрано
как максимальное подтверждённое tenant-wide окно StartReport guard, а не из
успешного five-second probe; его нужно пересмотреть по observed cap/success
metrics. Если process был перезапущен, timer неизвестен: tool выполняет один
safe upstream poll и сообщает, что не может подтвердить elapsed time; он не
объявляет export failed и не советует бесконечные retries.

### Инварианты и rollback

- `StartReport` один раз на attempt; нет automatic/parallel retry.
- Никаких signed URLs, clinic data и credential values в логах/метриках/errors;
  opaque runtime correlation id разрешён только в structured log event.
- Неретраебельные HTTP ошибки остаются ошибками, а не `not ready`.
- После cap не начинать новый export: предыдущий build может завершиться позже.
  Пользователь может уменьшить выборку только как optional alternative после
  проверки, что прежний build не нужен/завершён. Если upstream добавит durable
  status, local cap заменяется им.

Architecture Critique: required — меняется public MCP error contract и
reliability boundary.

## Декомпозиция

1. Добавить constant и единый classifier observed export wait. ≤150 LOC.
2. Передавать bounded-wait ToolError с безопасной next action; subsequent poll
   remains able to return ready file. Record cap and eventual-success timing. ≤150 LOC.
3. Добавить mock regressions для before/at cap, unknown observation and
   non-retryable errors. ≤150 LOC.

## Acceptance criteria

1. Retryable `reportFile` на known observation в 30 минут возвращает clear
   stop-automatic-polling message, но later ready response succeeds.
2. Сообщение запрещает automatic/new export и не приписывает задержку размеру
   данных; unknown observation receives explicit one-safe-poll/no-age guidance.
3. `INVALID_ARGUMENT` не классифицируется как ready/not-ready без evidence.
4. Existing successful, 401 marker, 409 and 403 behavior remains covered;
   metrics distinguish cap, unknown observation and eventual success.
