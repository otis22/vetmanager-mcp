# Этап 433. Экономика: StoreDocument и оплата накладных

## Цель

Проверить, какие данные агент реально получает через складской REST ВМ и существующие MCP-инструменты, затем выбрать минимальное улучшение для сценариев наценки, оплаты расходных накладных и кэш-флоу.

## Подзадачи

1. 433.1 (до 2 ч): сопоставить модель, контроллеры и OpenAPI с инструментами; выполнить read-only вызовы на devtr6 для списка, документа, фильтров и строк; заполнить матрицу покрытия.
2. 433.2 (до 2 ч): выбрать навигацию/описания, точечное изменение существующих инструментов или ожидание API ВМ; если меняется код, принять красные сторожа, проверить живым вызовом и пройти Core Loop.

## Проверенные факты до живого исследования

- `get_store_documents` и `get_store_document_by_id` передают ответ `/rest/api/StoreDocument` без собственной проекции; список ограничен `FILTER_FIELDS_BY_ENTITY["storeDocument"]`.
- Контроллеры `StoreDocument` и `StoreDocumentOperation` в extjs допускают REST list/view. Модель StoreDocument имеет `document_type`, `status`, `supplier_id`, даты и связь `storeDocumentOperations`; модель операций содержит `document_id`, `good_id`, `quantity`, `price`, `invoice_document_id`.
- OpenAPI v6 называет типы `prihod`, `rashod`, `inventar`, `transfer`, `invoice`, `return_good`, `transfer_receiver`; `status` относится к жизненному циклу документа. `prihod` — поступление от поставщика, `rashod` — выбытие товара. В схеме StoreDocument нет поля статуса оплаты.
- OpenAPI содержит `GET /rest/api/cassarashod` и `/{ID}`. Модель extjs описывает поля `date`, `summa`, `status`, `recipient_of_funds` и `prihod_id`; возможное значение `prihod_id` как связи с накладной пока гипотеза для проверки живой записью. На devtr6 endpoint отвечает 200, но `totalCount=0`; формат безналичной суммы и классификации в REST не подтверждён.
- `artifacts/api_entity_reference-ru.md` описывает другой набор полей (`type`, `summa` и др.), расходящийся с OpenAPI v6 и моделью extjs. До живой проверки использовать его для значения конкретных полей нельзя.

## Архитектурное решение

Проблема: пользовательские финансовые вопросы требуют различать складское движение и фактическую оплату. Контекст: публичный контракт MCP, ограничения прав и деперсонализации, обратная совместимость инструментов. Варианты: (а) уточнить описания действующих складских инструментов и навигацию — помогает найти приходные накладные поставщика и предотвращает ложный вывод об оплате; (б) открыть `cassarashod` как новый read-only финансовый инструмент — REST существует, но devtr6 возвращает пустую таблицу, селективность фильтров, формат оплаченной/безналичной суммы и классификация не проверены на реальной записи; (в) ждать нового API ВМ — не требуется, поскольку REST-путь уже есть. Выбрано **(а)** сейчас; (б) остаётся кандидатом для отдельного выпуска после появления на тестовом контуре оплаченной приходной накладной и проверки её кассовых ордеров. Инварианты: не выдавать `StoreDocument.status=exec` за оплату; не суммировать исторические `storeDocumentOperations` как текущие строки; не выводить cash flow из суммы складского документа. Rollback: вернуть прежние описания, если навигация окажется ошибочной. `finance.read` и деперсонализация для будущего финансового инструмента должны рассматриваться при его отдельном PRD, до публикации данных получателя.

Architecture Critique: включён в PRD-review, поскольку меняются публичные описания MCP-инструментов; сильные ревью выявили существующий REST-путь и потребовали сузить реализацию до проверенного контракта.

## Живые факты devtr6, 23.10.2026

Контур: `TEST_DOMAIN=devtr6`, `TEST_API_KEY` из `.env`; адрес получен после HTTP 301 с прежнего домена. Ключ и персональные поля не сохранялись. Все запросы read-only. Прямые REST-ответы и два вызова MCP дали:

| Вызов | HTTP / тело ответа без персональных данных |

## Матрица покрытия

| Сценарий | Что агент видит сейчас | Чего не хватает / предел доказательства |
| --- | --- | --- |
| Документы приход/расход/перемещение/инвентаризация | `document_type`, `status`, `supplier_id`, `total`, даты, вложенные операции; фильтры по типу, поставщику и датам. OpenAPI перечисляет 7 типов. | На devtr6 15 `prihod`, 1 `inventar`, 1 `invoice`; `rashod` и `transfer` отсутствуют. Эти подсчёты получены живыми запросами по каждому типу. `prihod` — накладная поставщика, `rashod` — выбытие товара. |
| Проверка наценки | Заголовок приходной накладной и история операций (`price`, `cost`, `quantity`, `good_id`); другие инструменты читают цены продажи. | Операции включают версии одной строки (у документа 2 — 5 исторических записей), их нельзя суммировать. Не проверено общее правило выбора актуальной версии, связь партии с ценой реализации и правило единиц/НДС на дату. Точный процент наценки пока недоказуем. |
| Оплаченные/неоплаченные накладные поставщика | Агент видит приходные StoreDocument, сумму и поставщика. Кандидат `cassarashod` имеет поле `prihod_id`, но инструмента MCP пока нет. | `StoreDocument.status=exec` означает проведение, а не оплату. На devtr6 нет ни одного `cassarashod`; связь `prihod_id` с накладной, алгоритм полной/частичной оплаты и безналичная сумма на реальных данных не проверены. |
| Кэш-флоу: поставщики / прочие расходы | Агент видит складские суммы, но это не денежный поток. REST `cassarashod` существует, но MCP его не отдаёт. | На devtr6 нет строк, поэтому классификацию и полноту денежного потока на живом примере проверить нельзя; безналичная сумма может требовать отдельного поля `summa_cashless`. `Payment.invoice_id` относится к клиентскому счёту, не к накладной поставщика. |

## Условия следующего шага

Для завершения сценария нужен стенд с хотя бы одним приходом поставщика и связанными кассовыми расходами (включая частичную/безналичную оплату). После этого можно подтвердить статусы, сумму к оплате и классификацию прочих расходов. Для точной наценки нужно проверить правило актуальной версии складской операции, связь закупочной партии с ценой реализации, единицу измерения и НДС на нужную дату. Пока эти правила не установлены, агент не должен считать точный процент или полноту оплаты.

## Критерии приёмки

- Матрица показывает для каждого сценария доступные поля, отсутствующие данные и границу уверенности.
- Есть код и тело живого ответа с HTTP-кодом на devtr6 для складского списка, документа, фильтров и операций без публикации персональных данных или секрета.
- Если изменён инструмент, сторож показан красным, затем зелёным, а новый контракт вызван на стенде.
- Gate, suite, Roadmap, AssumptionLog и self-attestation выполнены по workflow.
