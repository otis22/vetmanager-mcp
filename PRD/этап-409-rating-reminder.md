# Этап 409. Контекстное напоминание об оценке Report AI

## Цель и границы

После чтения готового Report AI job агент видит шаг оценки. В `get_report_ai_job` и `get_report_ai_job_data` появляется `mcp_rating_reminder` только для терминального job с существующей локальной неоценённой строкой. После оценки поле исчезает. Используется существующая таблица; напоминания в прочих инструментах не входят в этап.

## Проверенные факты

- Этап 408 уже сделал схему `rate_report_ai_job(job_id, score, intent_text, comment=None)`; `job_id`, `score` 1–10 и `intent_text` обязательны, `comment` необязателен. **Текст напоминания и гайд обязаны назвать именно эти аргументы.** `rate_job` делает upsert и записывает `score` после успешного commit.
- Локальный ключ строки: `account_id`, `connection_id`, `domain`, `job_id`. `score NULL` означает отсутствие оценки. Нельзя ориентироваться только на job ID другого подключения. Данные `/data` не содержат статуса job; успешный ответ `/data` доступен для saved/existing_report_matched. Поэтому на `get_report_ai_job_data` успешный ответ служит доказательством одного из этих двух терминальных состояний. `built` включён в статусный predicate по явной постановке владельца, но в текущей локальной спецификации и обработчике статусов не встречается; тест проверяет его только как совместимость с возможным upstream значением. `ready_to_save`, `failed`, `rejected` не входят в напоминание по решению этапа 409; общий гайд продолжает объяснять оценку failed job с ID.
- `artifacts/technical-requirements-vetmanager-mcp-ru.md`: чтение job и данных остаётся на read-правах; запуск отчёта требует `report_ai.write`. Локальная оценка и напоминание не меняют upstream API. `artifacts/prd-vetmanager-mcp-ru.md` задаёт Report AI как инструмент построения отчёта; его фактический контракт статусов берётся из существующих инструментов и тестов.
- Контур живой проверки до запуска: `TEST_DOMAIN`/`TEST_API_KEY` из `.env` с изолированной локальной БД, как в stage 400. Bearer-стенд является иным контуром.

## Архитектурное решение

**Проблема:** общий гайд выдаётся до чтения строк, когда агент ещё не знает полезность отчёта. Нужно показать последующий шаг в момент готовности и убрать его после оценки.

**Варианты:** (1) напоминать в каждом последующем инструменте: расширение границы, лишние запросы к БД и навязчивость; (2) только усилить текст гайда: нет контекстного момента; (3) читать существующую локальную строку при готовом `get_report_ai_job` и успешном `/data`: выбранный вариант. Один узкий helper делает lookup по составному ключу и `score IS NULL` с коротким общим timeout на получение соединения и запрос. Для bounded `get_report_ai_job` lookup получает лишь оставшееся от общего 30-секундного deadline время (максимум 0.5 с), при исчерпании пропускается; без ожидания и для `/data` — максимум 0.5 с. В статусе job проверяется `built/saved/existing_report_matched`; для `/data` требуется `payload.success is True`, что удостоверяет доступность строк. Нет дополнительного upstream GET, новой таблицы или раскрытия сохранённого intent. Ошибка/таймаут lookup не ломает чтение отчёта: поле опускается, счётчик не растёт, в лог пишется безопасный класс ошибки.

**Инварианты:** не показывать поле для незарегистрированной, оценённой, чужой или нетерминальной строки; повторное чтение не кэширует решение об оценке; считать метрику только при фактической выдаче поля; текст не содержит ПД и соответствует схеме 408. `mcp_rating_guidance` остаётся общим руководством. `mcp_rating_reminder` является точным контекстным действием после готового отчёта: в статусе он сначала направляет прочитать `get_report_ai_job_data`, затем оценить полезность по реальным строкам. Читающий токен без `report_ai.write` всё равно видит поле по требованиям этапа, но текст поясняет, что для оценки требуется этот scope и что доступ можно запросить через обычный механизм. Тексты `REPORT_AI_RATING_GUIDANCE`, docstring трёх инструментов (`get_report_ai_job`, `get_report_ai_job_data`, `rate_report_ai_job`) и `tool_descriptions.py` для create/get/data/rate/helper ведут по create → poll → data → rate, с ветками confirm/save и failed по существующему workflow, в каждом упоминании оценки сохраняя обязательные `job_id`, `score`, `intent_text` и необязательный `comment`.

**Rollback:** убрать поле и счётчик, вернуть прежние тексты; схема БД не меняется. Для счётчика использовать отдельный Redis key, который прежние слоты игнорируют: новая семья в общем hash сломала бы `/metrics` прежних слотов при смешанном rollout. Проверить mixed-version чтение и возврат версии. При изменении upstream статусов пересмотреть terminal predicate по наблюдаемому контракту прежде чем расширять его.

## Декомпозиция

1. **409.1 PRD и гейт** (≤2 ч): архитектурная критика вместе с PRD-review, Spark → Astra + Sol xhigh; проверить соответствие схеме 408, права, отсутствие дополнительного upstream вызова.
2. **409.2a красные сторожа** (≤150 строк): до/после оценки на обоих инструментах, незарегистрированная/чужая/нетерминальная строка, счётчик выдачи, канонический шаг и аргументы в текстах. Показать падения.
3. **409.2b реализация** (≤150 строк на подзадачу): DB lookup, выдача поля, счётчик, тексты; фокусный green.
4. **409.2c выпуск** (≤2 ч): живой create → poll → save либо confirm → status с напоминанием → data с напоминанием → rate → отсутствие поля в обоих инструментах; аудит, commit, committed diff gate, финальный mock + real suite по SHA, push и зелёный Tests ветки.

## Оценка простоты

Один lookup в существующей таблице и один helper для двух ответов достаточны. Новая таблица, фоновый job, повторный запрос upstream и напоминания вне Report AI добавили бы сложность без пользы для выбранного момента оценки.

## Приёмка

- На терминальном job с локальной `score NULL` оба ответа содержат `mcp_rating_reminder`; после `rate_report_ai_job` его нет в обоих ответах. Не показывать на нетерминальном статусе, без строки и при чужой связке.
- Напоминание явно говорит `rate_report_ai_job(job_id, score, intent_text)` и необязательный `comment`; гайд и описания называют оценку финальным шагом канонического пути и не содержат `voluntary`.
- `vetmanager_report_ai_rating_reminders_total` растёт на каждую фактическую выдачу; доступен в `/metrics` без чувствительных labels.
- `success: false` у `/data` не выдаёт напоминание. Таймаут/ошибка локальной БД сохраняет исходный ответ обоих инструментов и не увеличивает метрику. Старый процесс читает shared snapshot после записи новой метрики без ошибки.
- Живой ответ каждого изменённого инструмента фиксируется кодом и безопасным фрагментом тела в AssumptionLog. После push Tests на `dev/roadmap-408-413` зелёный; анализ прод-воронки отложен до merge/deploy супервизором.
