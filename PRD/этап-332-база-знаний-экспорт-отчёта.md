# Этап 332. База знаний узнаёт отказы экспорта отчёта

## Цель

Версионировать правила и плейбуки для отказов `start_report_export` и
`get_report_export_download`, доказать тем же production-матчером, что каждый
пользовательский текст из веток экспорта получает ровно одну уместную известную
проблему, и подготовить воспроизводимое применение для супервизора.

## Проверенные факты и ограничения

- `_safe_export_error` различает: ещё не готовый 401/409; два tenant-wide 403;
  `not accessible for rest`; прочий 403; прочий HTTP-отказ.
- Неретраибельный 401 `reportFile` становится текстом
  `Getting report export file failed HTTP 401.`: `StartReport` уже мог создать
  `report_file_id`, но текущая авторизация не может получить готовый файл.
- Этап 317 сохраняет очищенный `no_match`-след после ошибки; production-следы и
  production DB в этот этап агент не читает.
- Канонический матчер — `agent_feedback_service.match_rules`; отдельный тестовый
  или deploy-матчер заводить нельзя.
- Production применяет только супервизор. Репозиторий содержит JSON-фикстуры и
  скрипт передачи JSON через stdin в `docker compose exec`, без секретов.
- Главный PRD требует понятного ответа на upstream 4xx; technical requirements
  закрепляют секреты вне логов и версионируемых артефактов.

## Scope

### 332.1 — фикстуры и применение (≤150 LOC данных/скрипта)

1. Расширить KI-45 правилами для финальных текстов отказа экспорта, кроме
   неретраибельного 401 скачивания, сохранив запрет повторного
   `start_report_export` после отказа. Сторож отдельно доказывает, что KI-45
   не совпадает с этим 401.
2. Завести отдельную фикстуру для неретраибельного 401 скачивания: файл создан,
   но скачивание с текущей авторизацией не разрешено; повторный StartReport не
   исправляет авторизацию. Создание выполняется из отчёта #80 через обычный
   `promote` сразу с 401 rules/playbook. Затем новый атомарный CLI
   `move-fingerprint 45 NEW_ID` проверяет, что обе записи несут один fingerprint,
   и очищает его у KI-45. Обратный вызов восстанавливает rollback. Так exact
   fingerprint ведёт к 401-записи, а KI-45 остаётся доступна по текстовым
   правилам. Default `promote` не меняется.
3. Перед заменой скрипт печатает текущие `match_rules_json` и
   `agent_playbook_json` KI-45 в локальный mode-600 before-state файл
   супервизора и останавливается, если снимок не получен. Это rollback и
   видимый контроль drift, а не перенос production-данных в git.
4. Подготовить `!`-скрипт для супервизора: загрузка JSON через stdin во
   временные файлы контейнера, `set-match-rules`/`set-playbook`, затем
   `promote` для отдельной записи, захват её ID, `move-fingerprint`, затем
   `match-effectiveness`. Агент скрипт против production не запускает.

### 332.2 — красный сторож и живая проверка (≤150 LOC теста)

1. Локальная фикстура `known_issues` загружает те же JSON-файлы, что применяет
   супервизор.
2. Инциденты строятся через `build_incident_from_exception`, как в runtime, и
   сопоставляются через `match_rules`.
3. Все пользовательские тексты веток `_safe_export_error` и ошибок payload
   находят ровно одну ожидаемую запись; матрица включает оба специальных 403,
   `not accessible`, иной 403, retryable 401 с обоими маркерами, retryable 409,
   неретраибельный 401, 404/500 и оба missing/payload failure. Неретраибельный
   401 не смешивается с временным 401 `build in progress`.
4. Сторож сначала показать красным удалением обязательного маркера/фикстуры,
   затем вернуть и показать зелёным.
5. На `devtr6` получить наблюдаемый ответ экспорта без печати локаторов и
   секретов, после чего прогнать канонический матчер на этом тексте.
6. Отдельный DB-тест вызывает `find_known_issue_match` с fingerprint #80 после
   миграции: выбран NEW401, а не KI-45; обратный `move-fingerprint` возвращает
   исходного владельца.

## Архитектурное решение

Проблема: production-данные являются source of truth, но ручная правка без
версии и теста снова оставит базу знаний немой при следующей переформулировке.

Варианты:

1. Добавить тексты только в `SEED_ISSUES`: seed владеет своими marker-записями,
   а KI-45 создана отдельно; это не гарантирует обновление нужной строки.
2. Изменить общий матчер: лишний риск ложных совпадений и смена runtime-контракта.
3. Хранить точные JSON-фикстуры и применяющий скрипт, тестируя их существующим
   матчером. Выбран этот вариант: минимальная новая поверхность и один источник
   данных для теста и применения. Единственное CLI-добавление — атомарный
   перенос fingerprint между двумя существующими проблемами с проверкой их
   текущего состояния; без него две записи с одинаковым fingerprint обходят
   смысловые правила до проверки текста.

Инварианты: правила валидны со строгими именами инструментов; один отказ даёт
ровно один playbook; KI-45 не матчится на неретраибельный 401; его fingerprint
принадлежит отдельной записи; retryable 401/409 предлагает ждать тот же export,
а неретраибельный 401 не предлагает новый StartReport; никакие секреты,
локаторы или production-выгрузки не попадают в git.

Rollback: супервизор вызывает обратный `move-fingerprint NEW401 45`, возвращает
JSON KI-45 из обязательного before-state файла и переводит отдельную 401-запись
из активного статуса. Код инструментов и схема storage не меняются.

Architecture Critique: not required — auth, storage, transport и публичный MCP
контракт не меняются; добавляются данные существующего matcher-контракта и
операционный скрипт. Семантика 401 проверяется по коду и стенду.

## Acceptance criteria

- Версионируемые JSON валидируются production-валидаторами.
- Красный сторож падает при удалении каждого обязательного класса отказа и
  зелёный на финальных фикстурах.
- Все ветки экспорта из `report_ai.py` покрыты; временный и постоянный 401
  получают разные рекомендации.
- Скрипт не содержит секретов, не использует `docker cp`, сохраняет before-state,
  создаёт отдельную 401-запись, переносит ей fingerprint и завершает
  `match-effectiveness`.
- Mock suite, real suite, ShellCheck/Bash syntax и roadmap structure зелёные.
- До подтверждённого применения и Deploy Prod этап остаётся не `done`.

## Out of scope

- Обращение агента к production, изменение production DB или чтение её следов.
- Изменение сообщений инструментов, matcher/storage schema или lifecycle
  известных проблем.
- Запись triage-результатов в `AssumptionLog` до подтверждения deployment.

## Оценка простоты

Новых классов, matcher-слоёв и форматов нет. Тест читает deploy-файлы напрямую;
скрипт лишь переносит их в контейнер и вызывает существующий CLI. Изменение
требования затронет фикстуру, один тест и скрипт (не более трёх мест).
