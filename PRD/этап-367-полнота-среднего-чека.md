# Этап 367. Проверяемая полнота среднего чека

## Цель

Средний чек сообщает число просмотренных счетов и проверенную по REST-счётчикам
полноту прохода, а при неоднозначном ответе не возвращает достоверный итог.

## Факты

Feedback #121 сообщает средний чек за шесть месяцев по одному счёту. Это
наблюдение само по себе не устанавливает дефект MCP. На devtr6 06.10.2026
прямой GET за 2026-04-05–2026-10-05 вернул HTTP 200, `totalCount=1`, один
положительный счёт; MCP вернул count=1 и тот же итог. Контрольная многосчётная
выборка 2020-01-01–2021-12-31: прямой GET вернул `totalCount=14`, 14 строк,
13 положительных сумм; keyset с `limit=2` прошёл 14 строк (8 страниц), MCP
посчитал те же 13 положительных счетов и совпал с независимым агрегатом. Evidence:
`~/.local/share/vetmanager-mcp-review-evidence/stage367_probe.json` и
`stage367_recent_probe.json`; в файлах только агрегаты. Сигнал #121 пока не
доказывает потери данных MCP; объяснение конкретной production-выборки не
установлено.

Главный PRD требует корректной фильтрации и пагинации, технические требования
— безопасных лимитов. OpenAPI v6 и справочник сущностей задают REST list
`/rest/api/invoice`, `amount`, `id`, `status`, `invoice_date`, `totalCount`.
Удалённый HEAD vetmanager-extjs `d6da5573b49c94be96788ddb25c126eccfbb8a8b`
считан в отдельный bare-cache внутри evidence, чужой репозиторий не менялся.
Наблюдаемый REST-контракт выдаёт `data.totalCount` для текущего фильтра,
включая `id >` на следующих страницах. На devtr6 это подтверждено остатками 14, 12, ...,
2, 0. Формула среднего — MCP-продуктовая семантика из этапов 172.5/351,
отдельного REST average endpoint нет.
Текущий `get_average_invoice` использует интервал `[date_from 00:00,
next_day(date_to) 00:00)`, `status=exec`, `id ASC`, `offset=0`, `id > cursor`;
среднее = округлённая HALF_UP до копейки сумма строго положительных `amount`,
делённая на число таких счетов, затем округлённая HALF_UP до копейки.
Порядок округления сохраняет прежнее поведение на дробных копейках.
Нулевые и отрицательные суммы не входят в
знаменатель. Исходный код принимал отсутствующий/нечисловой `totalCount` и
пропускает невалидный `amount`, сохраняя `success=true`. Это подтверждённый
локальным разбором дефект **сообщения о полноте**: нельзя проверить, сколько
строк отброшено и сколько обещал upstream. Реальная частота такого ответа на
devtr6 не установлена. Поле `amount` обязательное по текущему контракту;
подмена его `total`/`sum` не подтверждена контрактом.

## Scope и декомпозиция

- 367.1 (≤2 ч): проверить удалённый HEAD vetmanager-extjs без записи в чужой
  репозиторий; уточнить контракт list/count/amount; PRD и ревью.
- 367.2a (≤150 строк): красный сторож многосчётного периода с настоящим
  построителем фильтра/keyset, Decimal и проверяемыми счётчиками; опциональный
  строгий режим в общем `paginate_all`, по умолчанию выключенный.
- 367.2b (≤150 строк): красные сторожа на отсутствие/ошибку `totalCount`,
  преждевременный конец и невалидный обязательный `amount`; убрать
  неподтверждённую подмену `amount` полями `total`/`sum`; fail-closed
  только для среднего чека.
- 367.3 (≤2 ч): живой read-only вызов на devtr6, полный suite, аудит,
  Spark/Astra/Kimi strong reviews, push и зелёный CI.

## Архитектурное решение

**Проблема.** `success=true` и одно число не доказывают полноту периода.
Общий keyset helper имеет проверки прогресса, но для этого агрегата ему
разрешено считать страницу без `totalCount`. Консьюмер суммы пропускает
невалидное обязательное поле.

**Контекст.** Нельзя повышать нагрузку на production, менять REST/Vetmanager,
публиковать финансовые строки, менять публичный `get_invoices` и общий
лимит offset. Подтверждения потери строк на devtr6 нет. Совместимые поля
ответа и существующий бюджет 1000 GET/300 секунд остаются.

**Варианты.** (1) Увеличить число запросов и пересчитывать через другой API:
нет подтверждённого дефекта пагинации, растёт нагрузка. (2) Доверять числу
строк без `totalCount`: не доказывает полноту короткой страницы. (3) Для
среднего чека требовать count каждой страницы и обязательный `amount`,
сверять число просмотренных строк с начальным count, возвращать счётчики и
явный признак полноты. Выбран (3) как локальное усиление проверяемости.

Строгий режим общего helper включается отдельным аргументом только этим
инструментом; остальные вызывающие сохраняют прежнее поведение. Callback
передаёт начальный `totalCount` без повторного GET. Ошибка суммы сообщает
только поле и класс ошибки, без id или значения строки. Совместимые числовые
поля `average_invoice`/`total_revenue` остаются float; округлённая сумма
для отображения доступна в `total_amount` как строка. Для сложения
непересекающихся частей добавить `unrounded_total_amount`: Decimal-строку
суммы положительных исходных `amount` до округления. Общая сумма частей
округляется один раз HALF_UP, затем делится на общий `invoices_with_amount`
и округляется HALF_UP. `total_amount` частей само по себе неаддитивно при
дробных копейках. Тест покрывает две части по 1.004 и общий итог 1.01.

**Инварианты и контракт ответа.** Ответ `success=true` возможен только после
полного прохода. `complete=true` означает только совпадение просмотренных
строк с опубликованными REST-счётчиками во время прохода, а не snapshot
состояния клиники. В ответе есть `snapshot_consistency="not_guaranteed"`:
счёт с уже пройденным малым `id` может войти в фильтр после прохода курсора,
и REST не позволяет это обнаружить без snapshot. Поле `complete` нельзя
трактовать как гарантию неизменности данных за период. Ответ содержит
`upstream_total_count` (целое
число из первой страницы), `scanned_count` и `excluded_amount_count`.
`scanned_count == upstream_total_count` и
`invoices_with_amount + excluded_amount_count == scanned_count`;
`unrounded_total_amount` равно точной сумме положительных `amount`;
`excluded_amount_count` считает только строки с присутствующим конечным
числовым `amount <= 0`; отсутствующая, нечисловая или бесконечная сумма
вызывает отказ, без fallback к другим полям. `invoices_with_amount` остаётся
совместимым полем ответа для положительных сумм.
На пустой выборке все счётчики равны 0, `complete=true`, среднее 0;
если все суммы неположительные, `invoices_with_amount=0`, среднее 0.
`average_invoice` использует только положительные `amount` и Decimal.
Каждая страница обязана иметь целочисленный неотрицательный `totalCount`,
равный `upstream_total_count - scanned_count` перед этой страницей для её
текущего фильтра; отсутствие или расхождение вызывает отказ
без частичного итога. При изменении счетов во время прохода строгая проверка
может отказать даже при корректной работе REST; автоматического повтора и
дополнительных GET нет, повтор периода позже решает пользователь;
snapshot REST не обещает. Ошибка или бюджет не возвращают частичную сумму.

**Rollback.** Если upstream перестанет выдавать `totalCount` или изменит
семантику count, инструмент явно откажет; контракт сначала перепроверяется
на devtr6, после чего делается новая версия с явным отказом или иным
подтверждённым признаком полноты. Откат к прежнему `success=true` без
подтверждённой полноты запрещён. Feature flag не нужен: он позволил бы
включить заведомо недостоверный путь.

Architecture Critique требуется: меняются MCP contract и поведение при
неполном upstream-ответе. Гейт охватывает одновременно полноту PRD.

## Приёмка

Красные сторожа показаны с конкретным сломом; затем зелёные. Изменённый
инструмент вызван на devtr6, HTTP код и агрегатное тело без строк счетов,
id и персональных данных приложены к evidence,
строка о вызове внесена в AssumptionLog. Полный mock + real suite, аудит,
Spark scout и валидные Astra/Kimi strong verdict на PRD и committed diff,
зелёный CI.
Production подтверждается статусами штатных Tests/Deploy Prod. Прямой
агрегатный запрос к production запрещён действующей постановкой окружения;
поэтому фактические production-счётчики этим этапом не сверяются.
