# Этап 491.2. Подготовка host security maintenance и входные gates

## Цель и границы хода

Подготовить адресные ночные обновления production host по принятому
[runbook 491.1](этап-491.1-production-host-security-preflight.md), не создавая
риска неконтролируемого простоя или потери новых записей. Пока независимый
console-вход не проверен фактически, этот ход ограничен read-only диагностикой,
off-host recovery materials и подготовкой мониторинга. Пакетные операции,
production restart/reload и изменение таймеров не разрешены.

## Декомпозиция

1. ≤2 ч: снять UTC baseline SSH/nginx/Docker, трёх MCP workers, БД/Redis,
   release-state, APT cache/timers/locks и независимой console. Не выводить
   адреса, ключи, данные клиник и сырой конфиг в публичные артефакты.
2. ≤2 ч: по текущим APT lists симулировать отдельные группы, сохранить точные
   прежние и candidate `.deb` вне production, проверить package/version/arch и
   SHA, смоделировать обратные транзакции на копии post-forward dpkg status.
3. ≤2 ч: прочитать maintainer scripts/triggers, выяснить автоматические
   service actions и текущие загруженные host libraries. Проверить внешний
   монитор public routes, SSH и трёх workers без изменения сервисов.
4. ≤2 ч: свести gates A–E, остановиться при любом открытом входном gate,
   обновить Roadmap/AssumptionLog и передать конкретный следующий шаг.

через официальный архив Ubuntu; метаданные и SHA каждого проверены. Candidate
SHA совпали с локальным APT index. Для прежних версий отдельно проверены
подписи четырёх исторических Ubuntu Snapshot `InRelease`, их SHA-256 для
`Packages.xz` и SHA-256 всех 12 `.deb` в исторических `Packages` по
[официальной схеме проверки Ubuntu](https://documentation.ubuntu.com/security/software-integrity/archive-verification/).
SHA-256 bundle с подписанными metadata `c35ad1387ed335eba24265627e4709df235ebec49f9e3bbcaf09ff1c43199b4b`;
`tar --compare` прошёл. Обратная симуляция использовала копию production dpkg
status с полями candidate пакетов и локальные прежние `.deb`. Она проверяет
APT dependency solver; фактический runtime rollback возможен только после
реальной установки и не заявляется заранее.

Candidate scripts SSH могут останавливать и запускать `ssh.socket`/`ssh.service`;
nginx может выполнить `upgrade`/`restart`, `nginx-common` — restart/stop.
На production нет `policy-rc.d`, временное подавление service actions и его
снятие через trap ещё не проверены. Host libssl загружен nginx; host libcrypto
также загружен SSH, systemd/journald и другими процессами. Для OpenSSL нельзя
объявлять полную активацию, пока старые host mappings не устранены безопасно.
Container PostgreSQL/Redis используют отдельный mount namespace и не входят
в этот host-library вывод. Автоматический возврат БД или host snapshot запрещён.

Будущий gate D требует конкретного контроля: до пакетов сохранить исходные
enabled/active states обоих APT timers и SSH socket/service; временно исключить
запуск обоих timers и подтвердить отсутствие jobs/locks; временная
`policy-rc.d` должна отказывать в service actions с кодом 101 через оба
используемых maintainer scripts helper — `invoke-rc.d` и
`deb-systemd-invoke`. Её эффект проверяется в безопасном изолированном
сценарии до production установки; если какой-либо action обходит policy,
группа отменяется. Прямые `systemctl daemon-reload` не подавляются этой
политикой и требуют отдельного учёта. Ветка OpenSSH с прямым
`systemctl unmask/enable ssh.socket` возможна, если исходный socket станет
disabled: тогда план контроля пересматривается и шаг останавливается.
Forward и rollback используют один проверенный контроль. После безопасной
границы и post-check timers и политика возвращаются в точное исходное
состояние и это сверяется; отдельно сверяются сохранённые enabled/active
states `ssh.socket` и `ssh.service` после forward и после rollback.
Если rollback понадобился уже после успешного forward и снятия временного
контроля, до обратной транзакции повторно установить и проверить тот же
контроль timers/service actions; если это невозможно, пакетный rollback
не начинать и вести адресное восстановление через console.
Расхождение требует адресного восстановления через console и повторного
post-check; один успешный SSH login не закрывает этот gate. При невозможности
вернуть состояния — открытый инцидент.
Это критерий будущего gate, а не факт выполненного production контроля.

| Gate | Состояние | Что ещё требуется |

| C — RPO | **unconfirmed** | При возможном recovery switch доказать возраст точки ≤1 часа; живую БД сохранять при откате пакетов |
| D — packages/rollback | подписанное происхождение старых `.deb`, симуляция и bundle готовы; финальный gate **unconfirmed** | Свежие APT lists и версии, повтор прямой/обратной симуляции, проверенное подавление service actions, контроль timers; после каждой группы — реальные post-checks и готовность к адресному rollback без БД |
| E — окно/мониторинг | путь мониторинга проверен, окно **unconfirmed** | Согласованный ночной интервал, console observer и непрерывные public/SSH/worker checks |

Внешний read-only монитор на отдельном host (отличие machine-id от production
проверено без сохранения идентификаторов) трижды получил HTTP 200 от
`/healthz` и `/readyz`, успешный SSH и 3/3 healthy workers. Он не запускался
как постоянная ночная задача; при потере SSH worker status станет unknown, а
public routes продолжат измеряться. Приватные логи содержат только UTC,
коды и задержки. Точный путь закрытого evidence передан через внешний work log;
в публичный репозиторий он не помещается.

**Стоп:** gate A остаётся открытым, поэтому никакого `apt update`, установки,
upgrade, service restart/reload или production write в этом ходе. Текущий
backup/restore из 491.1 не подставляется вместо нового pre-change backup.
Следующая конкретная операция — фактический независимый вход в provider
console с проверкой возможности управлять host при отказе SSH. После этого
перед пакетами повторить свежий APT/rollback preflight, доказать control
maintainer actions, получить новый backup+restore и согласовать окно.

вход и подтвердить независимое от SSH управление этой машиной, передав

nginx, Python host и OpenSSL host в этом двухчасовом окне не планируются: для
каждой следующей группы нужны свои свежие backup+restore/APT gates и резерв
на восстановление; перед nginx также отдельный `nginx -t`, контроль
автоматических actions, управляемый restart нового master и public smoke,
перед библиотеками — инвентаризация и безопасная активация живых процессов.
SSH также отменяется, если входные gates не завершены до 03:00. При отказе
post-check обратная APT транзакция также идёт под тем же проверенным контролем
service actions и timers; исходную политику нельзя снять между forward и
rollback. После адресного восстановления сервиса либо безопасного прерывания
пакетного шага оператор в том же recovery проверяет отсутствие активной APT
транзакции, возвращает исходные состояния timers и удаляет временную политику
service actions с проверкой; ждать интервала 03:25–04:00 для этого нельзя. Если
возврат не подтверждён, инцидент остаётся открытым и console observer
сохраняет дежурство. Внешний монитор должен собирать UTC/status
каждые 10–15 секунд без пропущенных выборок; потеря SSH делает worker status
unknown, а не healthy. Первый сбой начинает recovery сразу; >30 минут простоя
фиксируется как инцидент. Возврат пакета сохраняет живую БД. Любой переход на
backup требует отдельного доказательства RPO ≤1 часа по UTC и совместимости
схемы; автоматический откат БД или host snapshot запрещён.
