# Этап 324. Внешние вызовы без бюджета

## Цель

Ограничить fan-out поиска клиентов по ФИО и время одного логического GET к
Vetmanager, не меняя семантику успешного поиска: merge, дедупликацию и
`totalCount`.

## Проверенные факты

### 324.1 Поиск клиента

- `_name_tokens` разделяет строку по whitespace, casefold'ит и не имеет
  количественного предела. После `dict.fromkeys` каждый уникальный токен
  порождает три `crud_list`: `last_name`, `first_name`, `middle_name` с
  `LIKE`; все корутины запускаются одним `asyncio.gather`.
- Стандартный REST filter соединяет элементы через AND. Вложенная OR-группа
  не является контрактом REST: probe 16.09.2026 вернул HTTP 406. Один list
  запрос не выражает OR по трём полям.
- В read-only исходниках Vetmanager найден custom GET
  `/rest/api/client/clientsSearchData?search_query=…`, однако он не является
  заменой контракта `get_clients`: не описан OpenAPI, возвращает другой
  projection с `client_id` вместо `id`, не возвращает `totalCount`, ищет также
  email/pet/breed/phone/card, жёстко берёт ACTIVE и TEMPORARY и применяет свой
  порядок. Поэтому переход на него изменил бы результат и исключён.
- Единственный существующий `asyncio.Semaphore` — приватный helper
  `tools/_inactive_helpers.py::_gather_bounded` для отключённых tools. Он
  закрывает переданные coroutine при отмене и привязан к другому домену;
  переиспользование создало бы обратную зависимость от inactive-модуля.

### 324.2 Retry GET

- `MAX_RETRIES_READ=3`, то есть один логический GET имеет до четырёх попыток.
  `Retry-After` ограничивается `RETRY_AFTER_MAX_SECONDS=300.0`; shared httpx
  timeout: connect=5 s, read=20 s, write=10 s, pool=2 s.
- Комментарий «cooldown has not elapsed, fail fast instead of waiting the full
  timeout» относится только к circuit breaker (OPEN/HALF_OPEN), не к дедлайну
  HTTP/MCP request. `request_context` хранит лишь correlation/request ids;
  `server.py` задаёт graceful-shutdown timeout, но не inbound request deadline.
  Следовательно F21 не закрыт существующим дедлайном.

## Решение

### 324.1

- Ввести константы рядом с name-search: максимум **4 уникальных токена** и
  максимум **4 одновременных** upstream-вызова. Четырёх слов достаточно для
  ФИО (фамилия, имя, отчество) и составного/двойного имени, но верхняя граница
  остаётся фиксированной и наблюдаемой: максимум 12 запросов на tool call.
- Более четырёх уникальных токенов отклонять `ToolInputError` до любого
  upstream-вызова. Это честнее усечения: усечение тихо меняло бы критерий
  `all(token in name_text ...)` и могло вернуть ложное совпадение. Docstring
  прямо назовёт предел и предложит убрать лишний квалификатор; это осознанное
  сужение input contract, а не изменение семантики успешного допустимого поиска.
- Локальный bounded gather должен быть небольшим helper в `tools/client.py`:
  `Semaphore`, `create_task`, отмена и ожидание оставшихся tasks при ошибке.
  Он не меняет порядок responses, поэтому merge/dedup/`totalCount` остаются
  прежними.

### 324.2

- Ввести константу общего времени logical GET **30 s**. Это больше одной
  read-attempt (20 s) и обычного короткого retry/backoff, но меньше двух
  последовательных read timeouts; без inbound deadline это необходимая
  собственная граница. Write-пути и `retry=False` не получают новый retry
  бюджет.
- Перед каждой попыткой и перед sleep вычислять остаток monotonic-дедлайна.
  Не начинать попытку при остатке < **0.25 s** (слишком мало даже для
  осмысленной отменяемой попытки) или ожидание, если остатка нет; если выбранный
  `Retry-After` или backoff больше остатка, не спать. Если upstream уже
  ответил retryable HTTP-статусом, немедленно поднять этот исходный HTTP error
  (в частности 429/503), не подменяя его timeout; только exhaustion без
  последнего HTTP-ответа даёт понятный `VetmanagerTimeoutError`. Каждая
  попытка HTTP получает timeout, ограниченный остатком бюджета
  (соответствующие httpx phase timeouts не расширяются).
- Сохраняются retry status codes, число попыток, breaker/accounting/cache и
  существующие ошибки network/HTTP. Budget exhaustion — локальный deadline, а
  не новый upstream failure; он не добавляет breaker failure. Полученный
  429/503 сохраняет свой HTTP status и не маскируется как timeout/состояние
  breaker. Сообщение не содержит URL, ключей или upstream response body.

## Декомпозиция

1. **324.1 (≤150 LOC):** красные тесты на максимум четырёх unique tokens,
   ноль запросов при превышении, максимум четыре одновременных `crud_list` и
   неизменный merge/`totalCount`; затем реализация.
2. **324.2 (≤150 LOC):** красные тесты на отсутствие sleep при `Retry-After`
   больше остатка, отсутствие новой попытки после исчерпания и timeout attempt
   в пределах остатка; затем реализация.
3. **324.3:** focused/full/opt-in live tests, аудит и review gates.

## Acceptance criteria

1. `get_clients(name=...)` делает не более 12 upstream list calls и не более
   4 одновременно; строка с >4 unique tokens даёт typed input error до I/O.
2. При допустимом имени сохраняются прежние merge, dedup, local filter,
   sort, `totalCount` и `truncated` semantics.
3. GET не превышает 30 s logical budget в retry path; чрезмерный
   `Retry-After` не вызывает sleep и сохраняет полученный retryable HTTP
   status; timeout error используется лишь без последнего HTTP-ответа. Под
   0.25 s остатка новая попытка не открывается; такой local deadline не
   добавляет circuit-breaker failure.
4. Новые regression guards показаны красными намеренной поломкой и затем
   зелёными.
5. Изменённый `get_clients` вызван read-only на test contour до и после;
   AssumptionLog содержит только безопасные к публикации status/body shape.

## Out of scope

- добавление или документирование custom Vetmanager endpoint;
- изменение REST filter syntax или server-side OR/full-text search;
- общий inbound deadline для всех MCP tools;
- изменение retry policy write methods и обычных GET без retry.

## Оценка простоты

Обе правки локальны в уже существующих границах: один small bounded gather у
единственного fan-out и один monotonic deadline в существующем retry loop.
Отдельный transport wrapper, configurable policy class или распространение
deadline через FastMCP добавили бы новые API/состояния без второго call-site.
Четыре токена и четыре одновременно — фиксированные константы, а не новая
конфигурация: требование продуктово ограничено ФИО, а не произвольным поиском.
