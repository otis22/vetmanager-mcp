# Этап 326. Безопасное завершение и архив Roadmap

## Цель

Вернуть механическим гейтам совместимость с архивом Roadmap и сделать перенос
закрытых этапов отказоустойчивым: один номер существует ровно в одном файле,
очередь держит ровно окно `max - 19 .. max`, а сбой или дубль не превращаются
в потерю истории.

## Scope и проверенные факты

- `check_stage_completion.sh` сейчас ищет заголовок только в `Roadmap.md`;
  закрытый и уже заархивированный этап 237 воспроизводит ложный
  `missing_roadmap_header`.
- Исторические заголовки читают `check_stage_completion.sh` и bulk-проверка
  `review_workflow_check.sh`; выбор активной задачи остаётся только по очереди.
- `archive_roadmap.py` вычисляет максимум только по очереди, использует порог
  `< max - 20`, удаляет кандидатов по `stage.name` и сначала пишет очередь.
- `check_roadmap_structure.py` уже знает `supervisor_pending`, но Core Loop и
  workflow-checker используют неполный словарь статусов.
- Этап 317 реализован коммитами `4a8fe83` и `c8902fe`; для финального SHA
  сохранены зелёные GitHub runs Tests `34684346294` и Deploy Prod
  `34684563908`. Остальное evidence восстанавливается только из фактических
  следов и не домысливается.

## Архитектурное решение

Парсер `check_roadmap_structure.py` остаётся единственным разборщиком этапов.
Identity этапа — полное `Stage.name`: номер вместе с буквенным суффиксом, поэтому
`103`, `103a` и `103c` различны. Арифметика окна использует только первый
числовой компонент, как и существующий parser. Архиватор сначала валидирует
форму и глобальную уникальность identity очереди и архива, затем строит оба
результата по identity. Существующий текст архива сохраняется байт-в-байт, новые
кандидаты только добавляются в хвост в порядке очереди. Оба результата сначала
пишутся в соседние временные файлы с `fsync`; commit выполняется атомарными
`os.replace`: сначала архив, затем очередь. Это не является транзакцией двух
файлов. Если вторая замена возвращает ошибку, архив откатывается из заранее
подготовленной временной копии и оба target остаются исходными. Внезапное
завершение процесса между заменами может оставить две одинаковые копии блока:
данные не теряются, строгая проверка дубля блокирует дальнейшую запись, а
восстановление состоит в сверке тел и удалении очередной копии через git-backed
ручную правку. Автоматически принимать такой дубль нельзя: он неотличим от
исходной порчи, которую finding F7 требует отклонять до записи.

Закрытые статусы для переноса — ровно `done` и `stop`; `todo`, `in_progress` и
`supervisor_pending` остаются в очереди независимо от возраста. Максимум
считается по обоим файлам. На корректном состоянии он совпадает с максимумом
очереди; если свежая закрытая запись уже оказалась в архиве и тем самым подняла
union-max, preflight structural-check отклоняет исходное распределение до любой
записи. Текущее окно — включительно
`max - 19 .. max`; закрытые номера `<= max - 20` должны быть в архиве, а
закрытая запись из текущего окна в архиве является ошибкой структуры.

Потребителям, которым нужна история конкретного этапа, передаются оба файла и
требуется ровно одно совпадение. Поиск активной задачи остаётся только в
`Roadmap.md`.

Rollback — git-revert кода и документов. Изменений API, production storage,
auth, MCP-контракта и внешних данных нет. Architecture Critique: not required:
изменяется локальный repository workflow без production/cross-module boundary.

## Acceptance

- Завершение заархивированного этапа 237 проходит проверку заголовка; отсутствие
  и дубль заголовка в двух файлах отклоняются.
- Архиватор до любой записи отклоняет повтор identity внутри одного файла и
  между файлами; `103`/`103a` не считаются дублем. Оба файла при таком отказе
  байт-в-байт неизменны; существующий архив никогда не перестраивается и не
  сортируется.
- При ошибке подготовки ни один target не меняется, а уже созданные tempfile
  удаляются; при обычной ошибке второй замены архив откатывается и оба target
  байт-в-байт исходные. Failure injection отдельно подтверждает порядок «архив
  раньше очереди»; если ломается и сам rollback, его recovery-copy не удаляется.
  Внезапный crash в этом промежутке оставляет две копии без потери данных и
  документированный ручной recovery, а не молчаливое продолжение.
- При максимуме `N` архивируются закрытые номера `<= N-20`; номера
  `N-19 .. N` остаются в очереди. Максимум берётся по объединению файлов.
- Structural gate отклоняет закрытый архивный этап из текущего окна.
- Текст этапа 319 соответствует фактическому closure-order, реальному числу
  исправленных заголовков и реально реализованной матрице гейтов.
- Core Loop запускает архиватор перед structural gate и commit; обычный
  review-check read-only, а его явный `--prepare-roadmap` выполняет эту
  подготовку. Оба Roadmap-файла обязательны; `supervisor_pending` допустим как
  открытый статус, автоопределяется только при отсутствии `in_progress` и не
  проходит completion gate.
- Все новые guard-тесты показаны красными намеренной поломкой и затем зелёными;
  ShellCheck, `bash -n`, полный Docker-набор, reviews, push, Tests и Deploy Prod
  зелёные.

## Простота

Новых сервисов и форматов нет: переиспользуются существующие parser/dataclass,
stdlib tempfile/`os.replace` и subprocess-тесты. Единственная небольшая helper-
функция для поиска заголовка оправдана двумя shell-потребителями либо остаётся
прямым объединённым grep, если тесты показывают, что helper не нужен.
