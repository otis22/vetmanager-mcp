контейнере, не теряя проверок на выпуске. Исходный fast на базовом коммите

## Архитектурное решение

Проблема: fast и default сейчас отличаются в основном browser и coverage;
fast наследует дорогие offline integration сценарии. Нужна явная граница
стоимости при сохранении полного release gate.

Ввести маркер `offline_integration` для 87 измеренных дорогих owning файлов.
Это класс стоимости, в который входят локальные процессы, loopback,
многокомпонентный lifecycle и долгие чисто вычислительные oracles; название
маркера описывает слой, а не тип каждого теста. Fast исключит маркер,
default продолжит выполнять каждый узел без изменения assertions.
Browser, real и PostgreSQL останутся в своих обязательных слоях. Само наличие
маркера не является доказательством ускорения: замер повторяется в контейнере.

Для каждого owning файла `offline-candidates.csv` фиксирует node count,
измеренное время, причину переноса по стоимости и обязательный default как
oracle. Его собственные assertions и фикстуры остаются тем же release
oracle; перенос меняет частоту запуска, а не содержание проверки. Сторож
сверяет точный состав default до и после маркировки.

Альтернатива — дробить весь suite на новые пакеты или удалять медленные
проверки. Это больше меняет ownership и может убрать oracle. Альтернатива —
параллелить suite; она повышает риск гонок общих ресурсов и не уменьшает
стоимость одиночного узла. Выбран явный маркер как минимальное изменение.

Diagnostic CLI принимает один node ID либо узкий owning suite, включает
tracemalloc, детальные logs и безопасные resource hooks только для него.
Обычные runners остаются без диагностических hooks. Exit code и warning policy
пробрасываются без смягчения. Прямой запуск `tests/` этим CLI запрещён.

Default и PostgreSQL получают отдельные manifests с набором собранных nodes,
fingerprints runtime, tests и dependencies, результатом, пропусками и SHA
входов. Проверяющий отклоняет отсутствие файла, несовпадение fingerprint,
неполное покрытие, потерянные и дублированные nodes, смешение разных runtime.
Сложность real runner не переносится автоматически: общий только формат
проверяемых инвариантов, где он действительно совпадает.

Источник ожидаемого состава — versioned inventory из collect-only до
исполнения, поддерживаемый вместе с тестами; runner сравнивает текущий
collect и JUnit с этим inventory, а не создаёт ожидание из своего результата.
CI не принимает забытый/новый node без обновления inventory. Fingerprints
охватывают runtime Python, миграции, test helpers и scripts, Dockerfile,
Compose, pyproject, pytest config и образ/версии зависимостей. Средовые
значения фиксируются только как безопасный идентификатор контура;
секреты/адреса не пишутся. Missing input и неполный JUnit — fail-closed.
Автор изменения tests/markers обновляет inventory в том же diff; reviewer
сверяет причины добавления/удаления nodes и границу контура. При CI mismatch
обновление inventory без проверки смыслового изменения покрытия запрещено.
Автор изменения runtime, зависимостей или CI также отвечает за повторный
расчёт fingerprints и нужных gates; reviewer сверяет список изменённых
inputs с manifest. Действующий real group runner сохраняет своё правило:
runtime/dependency меняет все группы, test/shared-helper — затронутые группы,
полный aggregate проверяет их согласованность на финальном runtime.
Default/PG result gate отклоняет любой JUnit skipped/failure/error/xpass,
даже когда node ID присутствует в inventory; ожидаемый skip-list пуст.

Инварианты: `-W error` и действующая политика warning; полный default и PG
не теряют тесты; real aggregate обязателен на актуальных fingerprints; никакие
новые skip/xfail, suppressions, скрытые retry/timeout не появляются; данные
клиники и адреса выгрузок не попадают в диагностические артефакты.

Rollback: снять новый маркер с изменённых тестов и вернуть прежнее выражение
fast, не меняя default/real/PG. Если 180 секунд недостижимы при сохранении
oracle, остановить оптимизацию и передать владельцу измерения.

Для rollback diagnostic и manifest/CI изменений требуется восстановить
прежние runners и CI целиком из предшествующего коммита; перед выпуском
повторить действующие полный default, PG и real aggregate. Откат только
fast-маркера при повреждённом release gate не допускается.

Три исходных skip закрываются отдельными обязательными oracle до приёмки:
`stage408` маркируется `postgres`, получает изолированный URL в PG job и
входит в его обязательный result gate; placeholder F4/F5 заменяется
детерминированной двухсессионной гонкой с PostgreSQL и проверкой итогового
счётчика; Docker Compose config test переносится в исполняемый host CI шаг
с безопасным синтетическим значением обязательной переменной. Для каждого
случая красная мутация удаляет/ломает oracle, затем точная команда gate
подтверждает green. Если гонка не имеет безопасной изоляции в текущем PG
контуре, PRD останавливается до решения владельца; skip не сохраняется.

Протокол 180 секунд: штатный test image/Compose profile, неизменный SHA и
дерево, одинаковый host и image ID, каждый запуск — от старта команды
`docker compose --profile test run --rm test python scripts/run_fast_test_suite.py`
до её exit. Записывать wall time, pass/skip/deselect и image ID каждого из
трёх последовательных запусков; все ≤180 с, counts и skips идентичны,
неожиданных/скрытых пропусков ноль. Cold/warm состояние image фиксировать,
не использовать cache результата pytest.
Перед каждым из трёх прогонов фиксировать доступность CPU и отсутствие
параллельных тяжёлых job на host. При доказанной внешней конкурирующей
нагрузке серия считается непригодной для вывода о 180 с и не выдаётся за
зелёную; скрытый retry ради достижения порога запрещён.

## Уточнения после Architecture Critique

Файловая граница `offline_integration` намеренна: она переносит и дешёвые
nodes внутри дорогого файла, зато не разрывает общие fixtures и сохраняет
точный owning suite в default. Node-level список параметризаций сложнее
поддерживать; в fast остаются 3361 nodes. Если конкретный контракт теряет
нужную быструю обратную связь, его лёгкий oracle выносится в отдельный файл
с красным guard.

Inventory генерируется детерминированным collect-only и хранится в версии
репозитория; автор любого runtime/test/dependency/CI изменения обновляет
его при изменении состава, reviewer проверяет diff nodes. Digest строится
из сортированных относительных путей и содержимого; missing input — ошибка.
Image ID сравнивается только внутри одного окружения/gate: локальный и CI
manifests не смешиваются. Runtime/dependency инвалидирует default, PG и все
real группы; tests/helpers — owning default/PG и затронутые real группы по
их existing import карте. CI и pre-push проверяют свежесть, а не импортируют
исторические passes. Fast drift виден в каждом CI fast job и в повторных
измерениях после расширения состава; при превышении 180 с требуется новый
cost-profile, а не повышение лимита без решения владельца.

Diagnostic CLI принимает только offline node или owning file; real markers
и наличие test credentials отклоняются до запуска. Логи пишутся вне repo;
фильтр удаляет известные значения секретных env-переменных, URL и
credential assignments. Неизвестные значения запросов фильтр не распознаёт;
поэтому CLI ограничен offline-тестами без test credentials, а evidence
хранится в приватном внешнем каталоге. Красная мутация с синтетическим
canary доказывает, что известное значение не попало в evidence. Exit code и
warnings-as-errors сохраняются.

После ремонта skip PG обязан собрать восемь обязательных nodes: исходные
шесть плюс stage408 и F4/F5. Шесть вместо восьми — красный result gate.
Для F4/F5 нужны две независимые сессии, явный барьер перед спорным UPDATE,
изолированные синтетические строки и cleanup; bounded ожидание только
обнаруживает зависание, retry нет. Если такой барьер нельзя реализовать
безопасно в существующем PG контуре, это узкий blocker для владельца.

Docker-dependent stage190 pytest node переносится в исполняемый host CI
validator с тем же `docker compose --profile production config` и
синтетической обязательной переменной. Старый pytest node удаляется только
после красной мутации host gate, прямого зелёного запуска validator и CI
guard на обязательный шаг без `continue-on-error`. Default inventory явно
теряет ровно этот node; остальные nodes файла остаются. Это устраняет
default skip при сохранении исполняемого oracle.

Один causal class на изменение: (1) skip oracles и CI, (2) fast-layer
маркировка, (3) diagnostic CLI, (4) default manifest, (5) PG manifest.
Каждый класс проходит focused red/green и собственный аудит; финальные
release gates выполняются после последней правки на совокупном дереве.

Сведение второго сильного ревью: Astra `[]`; Opus 0 high/6 medium.
Принято: ожидаемые PG nodes считать из versioned collect-only inventory,
не из числа в прозе; host validator stage190 выполнять локально перед
commit и обязательным CI шагом; центральный список 87 файлов применять
в `tests/conftest.py` через зарегистрированный marker; после маркировки
ранний адресный прогон оставшегося fast состава проверит оценку 126 с.
Versioned inventory около 4800 nodes принят сознательно: требование
fail-closed на потерю узла сильнее стоимости review diff; генератор
детерминирован, reviewer видит точные добавления и удаления. Манifests
каждого gate живут во внешнем evidence и сверяются в том же окружении,
локальный результат не засчитывается CI. Для нового медленного теста
fast CI проверяет wall budget; превышение блокирует принятие, не прячется
увеличением timeout. Простота оценена: один центральный список вместо 87
правок файлов; отдельные default/PG manifests без общего framework.

## Подзадачи и проверки

Каждая подзадача ограничена двумя часами или 150 строками кода.

1. Инвентаризация: собрать timings по файлам и узлам, 3 skip, зависимости
   сценариев и список доказанных дублей. Зафиксировать карту и критерий
   сохранения oracle до изменения тестов.
2. Маркеры: добавить `offline_integration` и перенести только измеренные
   сценарии. Красный guard на состав default и fast; затем одиночные green
   nodes, owning suites, fast.
3. Diagnostics: scoped CLI и красная мутация для propagation failure и отказа
   от broad scope; адресные ресурсные hooks без секретов/ПДн.
4. Default manifest: тесты на потерю, дубль, stale runtime/test/dependency и
   неполный набор; красный каждый guard, затем реализация и green.
5. PostgreSQL manifest: те же релевантные инварианты, красные guards и
   проверка реального временного PG контура.
6. CI/doc: обоснованные явные job timeout, команды в AGENTS/CLAUDE/workflow/
   README после их точного исполнения; Roadmap/AssumptionLog.
7. Финальные gates: аудит, три fast на неизменном дереве, полный default,
   PostgreSQL, последовательный real aggregate, затем commit, Spark и сильная
   пара committed-diff review, push рабочей ветки.

## Приёмка и открытые факты

Fast ≤180 секунд три раза подряд на одном SHA, одинаковый зелёный состав без
неожиданных/скрытых skip. Полный default, PostgreSQL и актуальный real
aggregate зелёные. Каждый guard имеет зафиксированную красную мутацию.
Architecture Critique и PRD review должны завершиться до реализации.
Карта стоимости полная на базовом WIP; смысловые oracles трёх skip и
выбранная граница fast требуют сильного Architecture/PRD review. До его
валидных verdict реализация запрещена.
