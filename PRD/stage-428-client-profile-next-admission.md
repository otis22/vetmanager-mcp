# Этап 428 — следующая запись в профиле клиента

## Цель и факты

`get_client_profile.next_admission` должен показывать ближайшую актуальную запись. Сейчас запрос берёт первый активный приём по возрастанию `admission_date` без временной границы, поэтому просроченная активная запись скрывает будущую.

OpenAPI `artifacts/vetmanager_openapi_v6.json`, schema `admission.admission_date`: `string`, `date-time`, `x-db-type: timestamp`, описание формата `YYYY-MM-DD HH:MM:SS`, пример без offset. `artifacts/api_entity_reference-ru.md:29` подтверждает формат. Сама спецификация не задаёт часовой пояс; существующий `get_client_upcoming_visits` использует дату клиники, нижнюю границу `YYYY-MM-DD 00:00:00` и общий `clinic_local_today(None, relative=True)`. Профиль не получает `clinic_id`; этот helper для вызова без клиники документированно использует дату процесса. Это ограничение нынешнего контракта, а не доказательство часового пояса всех филиалов.

## Архитектурное решение

- Проблема: `limit=1` применяется до проверки даты, поэтому фильтрация уже полученного элемента не раскрывает будущую запись.
- Выбор: добавить серверный `admission_date >= {clinic_local_today(None, relative=True)} 00:00:00` в запрос `next_admission`, сохранив `status IN`, сортировку и `limit=1`. Это совпадает с семантикой существующего upcoming visits.
- Граница: начало текущего дня, а не текущий момент. `get_client_upcoming_visits` считает сегодняшние записи предстоящими и принимает дату без offset. Поэтому запись, прошедшая ранее сегодня, остаётся допустимой в этом дневном контракте; отдельный тест закрепляет этот край. Текущий момент изменил бы смысл `next_admission` внутри дня и потребовал отдельного способа достоверно определить timezone при отсутствии `clinic_id`. У записи есть `clinic_id`, но он становится известен лишь после выборки; у клиента с записями в разных филиалах нет единого бесспорного филиала до неё. Искать филиал клиента дополнительными вызовами здесь нельзя без изменения контракта и нагрузки.
- Варианты: post-filter при `limit=1` неверен; отдельное вычисление времени клиники добавляет новую семантику и запросы без идентификатора филиала.
- Инварианты: недавние приёмы и остальные секции не меняются; будущая активная запись не скрывается просроченной; отсутствие записи в окне даёт `None`; частичные ошибки остаются прежними. Нагрузка: число и лимит запросов прежние.
- Ограничение timezone: текущий `clinic_local_today(None, relative=True)` использует системную дату процесса, поскольку `clinic_id` неизвестен. Локальный процесс на машине исполнителя сейчас MSK; timezone production-контейнера этим не доказан. Если контейнер в UTC, а филиал в MSK, с 00:00 до 03:00 по МСК граница ещё соответствует вчерашнему дню и может включить вчерашний визит. Этап сохраняет семантику общего upcoming visits; отдельная смена контракта требует идентификатора филиала и согласования для multi-clinic клиента. Production timezone не проверяется в этом этапе по прямому запрету production-проверок.
- Совместимость: существующий upcoming visits уже отправляет тот же фильтр на `/rest/api/admission`; живой стендовый вызов профиля должен подтвердить ответ этого запроса. При отказе upstream не выпускать этап; rollback после выпуска — откат коммита с фильтром и повторный выпуск, поскольку клиентская post-filter при `limit=1` неверна.

Architecture Critique: required, поскольку меняется поведение публичного MCP ресурса; провести вместе с полным PRD-review в одном strong gate.

## Декомпозиция и приёмка

1. 428.1 (≤2 ч): сверить API факты, выбрать границу, выполнить Spark → Astra + Opus PRD/Architecture gate.
2. 428.2 (≤150 строк): красный сторож с матрицей overdue+future, только overdue, только future, без записей, плюс ранее сегодня + позднее сегодня; заморозить `clinic_local_today` на фиксированном дне. Мок запроса должен применять полученные `filter`, `sort`, `limit` к строкам; сторож отдельно сверяет точную границу `admission_date >= YYYY-MM-DD 00:00:00`, `status IN`, сортировку ASC и `limit=1`. Показать падение до фикса, добавить фильтр, запустить фокусные проверки. Реальный read-only вызов `get_client_profile` на выбранном стенде с кодом и кратким обезличенным телом подтверждает совместимость upstream с фильтром и ответ 200; он не доказывает сценарий overdue+future, если таких записей нет у найденного клиента. Аудит, committed diff gate, полный mock+real suite, push, зелёный CI ветки.

Стенд для live: `.env` `TEST_DOMAIN`/`TEST_API_KEY` (API-key контур), не bearer-токен; проверить наличие переменных без печати секретов до вызова. Профиль читается через существующий MCP инструмент.
