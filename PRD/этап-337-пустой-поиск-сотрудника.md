# Этап 337. Подсказка при пустом поиске сотрудника по имени

## Цель

При успешном, но пустом `get_users(name=...)` дать агенту явную безопасную
тактику поиска по основе фамилии, не менять фактическую семантику поиска и не
делать автоматический fallback.

## Проверенные факты

- Репорт #84: полная фамилия из запроса пользователя не совпала с написанием в
  карточке клиники; поиск по основе нашёл активного врача.
- Супервизор проверил на devtr6: REST `like` и `get_users` одинаково находят
  фамилию по полной форме и по основе, если написание совпадает с карточкой.
- `get_users` выполняет две параллельные `like`-ветки по `last_name` и
  `first_name`, объединяет записи по id, сортирует и применяет страницу.
- OpenAPI для `GET /rest/api/user` задаёт envelope
  `data.user` + `data.totalCount`; справочник сущностей подтверждает поля
  `last_name`, `first_name`, `position_id`, `is_active`.
- Локальная проекция пользователя очищает только записи внутри `data`, но
  сохраняет верхнеуровневые ключи ответа. Глобальная деперсонализация рекурсивна
  и сохраняет служебный текст, не находящийся в whitelist PII-полей.

## Scope и декомпозиция

### 337.1. `mcp_hint` для пустого именного поиска

- Только при непустом `name` и итоговом `totalCount == 0` добавить на верхний
  уровень ответа `mcp_hint` с полями `code`, `summary`, `steps`, `do_not_do`.
- `code`: `user_name_search_empty`.
- Шаги: повторить `get_users` с основой фамилии из 3–4 букв (тот же параметр
  ищет также по `first_name`); при нескольких совпадениях выбрать по
  `position_id`/расписанию и подтвердить `get_user_by_id`; процитировать
  фамилию ровно как она записана в найденной карточке. В деперсонализованном
  режиме адресный placeholder — финальное значение: его цитировать дословно и
  не пытаться разрешить повторным `get_user_by_id`.
- `do_not_do`: не заключать после одного пустого точного поиска, что врача нет
  или он неактивен; не менять `is_active` на `None` вместо поиска по основе.
- Непустой результат и вызов без `name` не аннотировать. Исключения транспорта
  или доступа продолжают прерывать выполнение до построения ответа.
- Не выполнять автоматический повторный запрос и не менять `name`/`is_active`.

### 337.2. Описание инструмента

- В `tool_descriptions.py` добавить к `get_users` одну фразу: при пустом
  именном результате следовать `mcp_hint` и повторить поиск по основе фамилии.
  Шаги из runtime-контракта в description не дублировать.

Обе подзадачи меньше 150 строк и двух часов каждая.

## Архитектурное решение

**Проблема.** Пустой успешный ответ не отличает отсутствующего сотрудника от
несовпадения написания фамилии и не подсказывает следующий безопасный шаг.

**Контекст и ограничения.** Нужно сохранить upstream envelope, текущие две
параллельные ветки, pagination, privacy-проекцию, access checks и исключения.
Подсказка — метаданные MCP, а не запись Vetmanager и не PII.

**Варианты.** (1) Верхнеуровневый `mcp_hint`: отделён от `data`, переживает
проекцию и не классифицируется как поле user. (2) `data.mcp_hint`: ближе к
результату, но смешивает локальные метаданные с upstream entity/pagination
контрактом и текущая закрытая проекция `data` может его удалить. (3)
Автоматический fallback: скрывает изменение запроса и может вернуть похожего,
но другого сотрудника; владелец продукта его явно отклонил.

**Выбор.** Вариант 1. Маленький helper возвращает статический контракт, а
условный branch добавляется только после merge и вычисления итогового нуля.
Описание добавляется отдельным узким suffix в существующей точке композиции
`tools/list`, без дублирования generic-описания или privacy-текста.

**Инварианты.** Число и порядок REST-запросов не меняются; непустые ответы и
поиск без `name` сохраняют прежнюю форму; ошибки не превращаются в успешный
ответ; `mcp_hint` не содержит введённую фамилию или данные клиники; режим
деперсонализации сохраняет текст и свои placeholder-правила.

**Rollback/fallback.** Откат удаляет helper, условное добавление и suffix
описания. Если envelope/projection изменится, положение подсказки повторно
проверяется контрактными и privacy-тестами до переноса.

Architecture Critique: not required — изменение не затрагивает auth, storage,
transport, performance/load или ownership boundary; оно добавляет статическую
аннотацию к существующему успешному MCP-ответу.

## Acceptance criteria и тесты

- Пустой merged-результат при непустом `name` имеет полный `mcp_hint` и точный
  `code=user_name_search_empty`; форма и смысл шагов/запретов закреплены.
- Непустой поиск с `name` и вызов без `name` не имеют `mcp_hint`.
- Исключение одной из веток распространяется наружу и не аннотируется.
- Description содержит одну краткую ссылку на `mcp_hint` и основу фамилии.
- В деперсонализованном режиме hint сохраняется без placeholder/redaction, а
  user identity по-прежнему маскируется готовым sanitizer-тестом; найденный
  placeholder не предлагается разрешать повторным lookup.
- Сторожа принимаются красными: до реализации пустой результат не имеет hint;
  после реализации намеренное отключение branch роняет тот же тест.
- Live devtr6: полная существующая фамилия → одна запись без hint; `Ионова` →
  ноль записей с нужным code; вызов без `name` → без hint. Код и безопасно
  сохранённое тело каждого ответа записываются только во внешний evidence:
  имена и другие поля сотрудника маскируются, а в публичные PRD/AssumptionLog
  попадают лишь `totalCount`, наличие/отсутствие hint и его code.

## Out of scope

- `known_issues`, `report_problem`, другие инструменты, изменения upstream и
  любые production-вызовы.
- Автоматический поиск по основе, fuzzy matching и расширение `is_active=None`.

## Простота

Ожидается <50 LOC production-логики без новых общих абстракций и без сетевых
веток. Проверены triggers: factory/protocol, multi-hop indirection, dual API,
state machine и configurable fallback не нужны. Отдельный suffix оправдан
существующей композиционной точкой описаний и не смешивает search guidance с
privacy contract.
