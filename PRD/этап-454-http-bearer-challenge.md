# Этап 454. HTTP отказ при недействительном bearer

## Цель

Для `/mcp` вернуть HTTP 401 с `WWW-Authenticate` при невалидном или истёкшем bearer до обработки `initialize` и `tools/list`, чтобы клиент мог обнаружить OAuth и обновить access token. Проверить повтор чтения после refresh.

## Контракт и факты

- [MCP Authorization 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization), разделы Protected Resource Metadata Discovery Requirements, Token Handling, Error Handling: недействительный/истёкший access token требует HTTP 401; `WWW-Authenticate` с `resource_metadata` указывает клиенту discovery URL, если сервер выбирает этот механизм; 403 относится к недостаточным правам, 400 — к некорректному запросу. Авторизация передаётся в заголовке каждого HTTP-запроса.
- `oauth_challenge.build_oauth_bearer_challenge` уже строит challenge с публичным metadata URL, а `runtime_auth` возвращает его только как детали ошибки инструмента. `server._run_http_server` собирает ASGI middleware вокруг FastMCP. `runtime_auth.peek_runtime_scopes` проверяет срок и состояние обоих типов токенов, но `None` также означает сбой чтения прав или состояние аккаунта; использовать его как единственный признак 401 нельзя.
- Технические требования (`artifacts/technical-requirements-vetmanager-mcp-ru.md`) закрепляют stateless `streamable-http`, `/mcp`, два вида bearer. Vetmanager REST/OpenAPI не участвуют в этом изменении.

## Scope и приёмка

- Синтетический отсутствующий в хранилище, истёкший и отозванный bearer получают 401 на `initialize` и `tools/list`; challenge содержит `error="invalid_token"` и `resource_metadata`, разделённые по HTTP-синтаксису. Тело не содержит токен и персональные данные. Для OAuth проверить чужой resource, отсутствующий/неактивный grant и client; для постоянного ключа — disabled и revoked. Условия отказа совпадают с runtime на матрице токенов.
- Для GET/DELETE `/mcp` предъявленный недействительный bearer также даёт 401; публичные маршруты не затронуты. Два заголовка Authorization — некорректный запрос 400, чтобы preflight и FastMCP не выбрали разные токены. Отсутствующий заголовок и неправильная схема сохраняют прежнее поведение в этом этапе: цель — именно предъявленный недействительный bearer. Пустой bearer трактуется как неправильный заголовок. Отдельное изменение политики обязательности авторизации требует решения владельца.
- Сбой БД при preflight возвращает 5xx без `invalid_token` challenge и без деталей исключения.
- Публичные OAuth metadata/discovery endpoints сохраняют текущую доступность. Валидный постоянный ключ и OAuth access продолжают работать; ошибки прав сохраняют свою семантику.
- Истёкший OAuth access получает 401; штатный `/oauth/token` с действующим refresh выдаёт новый access; повторный read с новым access успешен. Обновление делает клиент через существующий OAuth flow, сервер не обновляет предъявленный access прозрачно.
- Локальный uvicorn/ASGI HTTP smoke сохраняет обезличенные status, заголовок и форму тела. Opt-in test REST запускается только при тестовых переменных `.env`.

## Архитектурное решение

Проблема: проверка bearer сегодня выполняется при вызове инструмента, после транспортного handshake. Транспортный middleware должен валидировать предъявленный bearer до FastMCP, ограничив проверку `/mcp` и не меняя публичные routes. Вынести общий предикат действительности токена из runtime auth: по хешу, статусу и сроку, для OAuth также resource, grant и client. Транспорт вызывает этот предикат; runtime сохраняет остальные проверки аккаунта, соединения, прав и Vetmanager credentials. Исключения БД/расшифровки не превращаются в `invalid_token`. `peek_runtime_scopes()` не использовать: `None` у него означает также отключённое соединение или сбой расшифровки. Ответ формировать существующим `build_oauth_bearer_challenge`, предварительно исправив разделители параметров на запятые согласно [RFC 6750 §3](https://www.rfc-editor.org/rfc/rfc6750#section-3); сохранить совместимость `_meta` через тот же builder. Рассмотреть два варианта: проверка при ASGI входе (выбрана — даёт 401 на initialize) и перехват ответов инструмента (отклонён — initialize/tools/list не вызывают инструмент). Не создавать usage audit событие для handshake. Индексный lookup на каждом запросе удваивает lookup для `tools/call`; до реализации измерить количество запросов на типовых путях и оценить передачу проверенного контекста через `scope`, не пропуская runtime проверку прав. При неверной интерпретации откат — убрать транспортный middleware и вернуться к прежнему контракту до исправления; rollback выполняется новым deploy кода, без дополнительных флагов конфигурации.

## Риски и простота

Риск совместимости: клиент, рассчитывающий на `tools/list` HTTP 200 с неверным bearer, увидит предусмотренный протоколом 401; валидные клиенты должны остаться без изменений. Ранее выданный OAuth access с неподходящим resource уже не проходит runtime `tools/call`, хотя мог проходить handshake; новый ранний 401 делает этот отказ видимым. Проверка записей на production напрямую запрещена рамками этапа; выкат и мониторинг выполняет куратор отдельно. Риск безопасности: не раскрывать токен в теле, заголовках и журнале; metadata URL строить штатной функцией. Риск нагрузки: дополнительный indexed lookup на `/mcp`. Простейшее решение — один middleware и штатный builder challenge, без новых OAuth endpoints или фоновых задач. После сильного review проверить, что дополнительные абстракции не нужны.

## Решения по замечаниям второго PRD-review

- Повторный индексный lookup для `tools/call` принят: preflight делает один запрос по хешу, runtime оставляет полную проверку прав и аудит. Передача результата через `scope` усложнила бы границу доверия и позволила бы забыть повторную проверку при изменениях runtime. В тесте проверять не больше одного дополнительного запроса на успешный handshake; если замер на живом локальном контуре покажет заметную задержку, пересмотреть до commit.
- `_meta` остаётся на том же builder; guard проверяет, что после исправления разделителей оба канала содержат тот же `resource_metadata` и `error`, без токена и новых полей. В ASGI-стеке наблюдатель этапа 453 остаётся снаружи auth middleware, чтобы видеть HTTP 401 и записать handshake outcome. Guard проверяет это на `initialize`/`tools/list`.
- Для произвольных недействительных bearer ввести ограничение длины и формы до DB lookup, не более 16 одновременных проверок и таймаут 500 мс; отказ по насыщению/таймауту — 503, без `invalid_token`. Не брать токен из query или body.
- Отсутствующий Authorization и чужая схема остаются прежними в 454: опубликованный scope охватывает предъявленный невалидный или истёкший bearer. Расширение политики входа без токена может сломать публичные discovery-клиенты и требует отдельного решения владельца.
- Сбой БД: HTTP 503 с безопасным JSON-телом `{"error":"temporarily_unavailable"}` и без `invalid_token` challenge. Это отдельный транспортный отказ, не изменение runtime обработки сбоя на `tools/call`.

Simplicity review: достаточно одного middleware, общего предиката действительности токена и исправления существующего challenge builder. Флага выката, нового OAuth endpoint, кэша и передачи auth context через ASGI scope не требуется. Изменения PRD после второго сильного раунда закрывают findings проверенными фактами и тестируемыми условиями; бюджет сильного PRD-review исчерпан, дальнейшая проверка — отдельный Spark scout.
