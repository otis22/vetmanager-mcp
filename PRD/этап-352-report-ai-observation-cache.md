# Этап 352. Ответ созданного задания Report AI при сбое наблюдения

## Цель и проверенные факты

После успешного POST `/rest/api/report-ai-job` инструмент теряет ответ: `_observe_report_ai_lifecycle` вызывает общую очистку, которая распаковывает запись кэша часовых поясов как пару. `clinic_timezone.resolve_clinic_timezone` реально пишет тройку `(timezone_name, fetched_at, ttl)`; тест этапа 320 пишет пары вручную. В результате повтор запроса создаёт лишние задания. Прод-факты и пределы наблюдения перечислены в Roadmap 352; прямой доступ к production запрещён.

OpenAPI v6 не содержит `/rest/api/report-ai-job`; контракт Report AI здесь подтверждён существующим инструментом, mock-контрактом этапа 350 и живым ответом devtr6 от 02.10.2026 (HTTP 200, `data.job.id=270`, `status=queued`, `is_deduplicated=false`). Проверка использует тестовые `TEST_DOMAIN`/`TEST_API_KEY`, а не production. Технические требования закрепляют `report_ai.write` для запуска и `analytics.read` для чтения задания. Существующие обёртки ошибок и метрик не гарантируют безопасный результат при сбое наблюдений после успешного upstream-вызова.

## Декомпозиция

- 352.1 (≤2 ч): PRD, Architecture Critique и PRD-review.
- 352.2a (≤150 строк): красный интеграционный сторож с настоящим `resolve_clinic_timezone`; отдельный красный сторож для отказа учёта после ответа апстрима.
- 352.2b (≤150 строк): передать очистку кэша его владельцу и исправить фикстуры общего кэша.
- 352.2c (≤150 строк): защитить учёт lifecycle/queue и метрики вызовов, логировать и отправлять сбой в error tracking.
- 352.2d (≤150 строк): проверить отдельные метрики экспорта и последовательные вызовы после сбоя наблюдения.
- 352.3 (≤2 ч): devtr6, аудит, фокусные и полные mock/real проверки, сильное ревью diff, выпуск и CI.

## Архитектурное решение

**Проблема.** Report AI читает внутренний формат чужого кэша и выполняет побочный учёт на критическом пути ответа после состоявшегося POST.

**Контекст.** Кэш часовых поясов ограничен TTL и размером; resolver проверяет TTL при чтении, но очистка нужна для физического ограничения накопленных записей. Существующие наблюдения Report AI процессные и best effort. Публичный ответ upstream, полномочия и приватность не меняются. Ошибка учёта должна быть видна по `event_name` и в Sentry без текста запроса, тела ответа и секретов. Вызов error tracking сам не должен падать.

**Варианты.** Подогнать распаковку под тройку — оставляет зависимость и ломается при следующей смене формата. Исключить кэш из общей очистки — TTL при чтении работает, но память удерживает старые записи. Выделить в `clinic_timezone` операцию очистки с его TTL/размером — один владелец формата. Выбран третий вариант.

**Граница отказа.** Обернуть запись метрик и обновление процессных наблюдений после ответа upstream в best-effort вызов; очистка кэша выполняется внутри него. Лог содержит только фиксированные `event_name`, операцию из кода и тип исключения; ни `str(exc)`, ни traceback не пишутся. В Sentry передаётся `capture_message` с фиксированным текстом без стека исключения и локальных переменных, с тегами operation и exc_type. Проверка события не допускает текст запроса и ответа. Не скрывать ошибки upstream, валидации и формирования обязательных полей ответа. Если учёт упал, частичная запись наблюдений может дать неточные метрики этого задания, но ответ и `job_id` сохраняются.

**Точки учёта.** Создание: `record_report_ai_job_created`, `_observe_report_ai_lifecycle`, `_observe_report_ai_queue`; статус: `record_report_ai_outcome_code`, lifecycle, queue и возраст/диагностика; подтверждение, отклонение, сохранение: lifecycle. Сюда входит `record_tool_call` в `instrument_call` после ответа upstream. Для него вводится opt-in callback только на вызовах Report AI; поведение остальных callers общего helper остаётся прежним. Для экспорта защищаются только счётчики/длительности `record_report_ai_export*` и `record_report_export_download`. Состояние `_remember_report_ai_export`, `_mark_report_ai_export_poll`, `_complete_report_ai_export` и решение о локальном таймауте влияют на следующий вызов и сохраняют fail-closed семантику; если запись состояния не удалась, инструмент сообщает явный отказ, а следующий poll не должен ошибочно считаться успешным. Красный сторож вводит исключение в точки учёта после успешного ответа и проверяет ответ каждого инструмента. Разбор обязательных полей upstream остаётся вне best-effort обёртки. Дополнительный тест делает status того же `job_id` после частичного сбоя учёта при создании.

**Инварианты.** Формат `_CACHE` известен только `clinic_timezone`; данные клиники не попадают в лог или Sentry; после успешного upstream ответа сбой учёта не превращается в ошибку MCP; прежние метрики пишутся при исправном учёте. Красный сторож использует именно resolver. Лог `event_name` явно называет сбой наблюдения.

**Rollback.** При неожиданной проблеме откатить релиз целиком, сохранив красные тесты; при сбое error tracking ответ остаётся успешным, событие остаётся в локальном логе. Повторный POST автоматически не делать.

Architecture Critique required: меняются production behavior и граница владения между модулями.

## Приёмка

1. Красный тест сначала воспроизводит потерю ответа при заполнении кэша настоящим resolver, затем получает `job_id`.
2. Очистка кэша реализована в `clinic_timezone`, а в Report AI нет чтения `_CACHE` или его формата.
3. Для всех инструментов Report AI, использующих lifecycle/queue accounting, исключение учёта не скрывает успешный upstream ответ; записаны `event_name` и событие error tracking, без текста/traceback исходного исключения даже если в нём есть данные клиники. Отдельно проверены `record_tool_call` и успешная метрика скачивания. Последующий status того же задания успешен.
4. Соседние тесты не подменяют общий кэш записями неверного формата.
5. Живой сценарий devtr6 в одном процессе сначала вызывает настоящий resolver часового пояса клиники, проверяет заполнение `_CACHE`, затем единожды вызывает создание задания и получает `job_id`. Код и безопасное тело ответа записаны в AssumptionLog. API не предоставляет отмену созданного задания; smoke-запрос ограничен одним заданием и не повторяется автоматически.
6. Перед push один полный mock и real suite, сильное ревью Astra/Opus, зелёные Tests и Deploy Prod.
