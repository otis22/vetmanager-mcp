# Этап 344. Изображения для Claude Opus на визуальном гейте

## Цель

Передавать пиксели скриншотов Opus при визуальном ревью, сохранив изоляцию review runner и прежнее поведение вызовов без изображений.

## Проверенные факты и контекст

- `scripts/run_claude_review.sh` сейчас подаёт текст через stdin с `--output-format json` и отключёнными инструментами; `validate_review_result.py` принимает одиночный JSON envelope.
- Claude CLI 2.1.281 принимает `--input-format stream-json` с блоком `image` (base64), но требует одновременно `--output-format stream-json --verbose`. С `--json-schema` совместим: локальный контрольный вызов 24.09.2026 получил структурированный `result` с определением цвета пикселей. Raw evidence: `stage-344/probe.stream.jsonl` во внешнем evidence.
- Продуктовый PRD и технические требования описывают MCP/REST, но этот этап меняет только локальный процесс ревью. Vetmanager API, auth, production, storage и public MCP contract не затронуты; OpenAPI здесь неприменим.

## Архитектурное решение

- Проблема: текстовый stdin сообщает только путь к файлу, поэтому пустой verdict Opus не подтверждает визуальную проверку.
- Вариант A: `stream-json` с base64 `image` в user message, инструменты отключены. Требует распарсить потоковый вывод до прежнего envelope.
- Вариант B: разрешить `Read` и `--add-dir` на скриншоты. Меняет границы изоляции, зависит от того, вызовет ли модель инструмент, и хуже доказывает просмотр пикселей.
- Выбор: вариант A. Только при `--image` строить одно user message из прежнего review text и PNG image blocks; запускать Claude с `--input-format stream-json --output-format stream-json --verbose`; сохранить сырой поток отдельно и извлечь **ровно одно** финальное событие `type=result` в прежний `*.envelope.json` для действующего валидатора. При нуле или нескольких result, повреждённой JSON-строке или не-object result сохранять raw stream и пустой envelope, возвращать non-zero с `invalid_verdict` (либо исходным CLI exit при ошибке CLI). Timeout и crash тоже оставляют пустой envelope и полную диагностику. Без `--image` оставить существующую команду и evidence прежними.
- Ограничения: 1–4 PNG, каждый 1 байт–2 MiB, сумма ≤ 8 MiB, ширина и высота 1–4096 px по IHDR. Проверять regular readable file, PNG signature и IHDR до запуска; консервативный предел учитывает увеличение base64 на 33% и защищает от чрезмерного размера запроса. Пустые/повреждённые входы завершаются с кодом 64 до запуска CLI и создания attempt evidence; это ошибка аргумента, а не infrastructure attempt. В metadata записывать канонические пути, размеры и SHA-256 изображений, не base64. На визуальном гейте сверять SHA-256 с файлами под ревью. `stdin_bytes`/`stdin_lines` в image mode измеряют отправленный JSONL; без изображений — прежний текстовый stdin. `*.prompt.txt` сохраняет только исходную инструкцию, как и раньше; raw output stream лежит в отдельном файле. CLI получает одно user-сообщение через закрываемый после записи stdin-файл.
- Инварианты: `--tools ''`, пустой MCP config и structured schema остаются; итоговый envelope проходит тот же validator; `[]` Opus засчитывается на визуальном гейте только при запуске с изображениями. Astra также обязана дать валидный визуальный verdict.
- Rollback: убрать image branch и одновременно вернуть предыдущее правило визуального гейта; raw evidence оставить вне репозитория.

Architecture Critique: not required — изменение локального runner не пересекает product/API/auth/storage boundaries; единственная архитектурная развилка проверена реальным CLI вызовом, вариант с Read отклонён по конкретному риску изоляции.

Оценка простоты: один условный путь в существующем runner и два коротких Python-фрагмента без нового модуля или дополнительного API. Вызовы без `--image` сохраняют прежний путь. Дополнительная абстракция здесь не нужна.

## Декомпозиция

1. PRD, сверка артефактов и узкий PRD review (≤ 2 ч).
2. Тесты на image protocol, пределы, metadata и изменённый текстовый сторож; показать красный до реализации (≤ 150 строк на подзадачу).
3. `--image` в runner, нормализация stream output и контрольный визуальный вызов Opus на синтетическом PNG (≤ 150 строк кода).
4. Инструкции, фокусные тесты, аудит, committed diff review, один полный mock, выпуск и CI (каждый гейт ≤ 2 ч).

## Приёмка

- Контрольный PNG имеет однозначный цвет, который не следует из имени; Opus называет цвет в валидном structured verdict. Evidence сохранён.
- Вызов без `--image` даёт прежний CLI argv, envelope и metadata; существующие тесты зелёные.
- Тесты покрывают повторяемый флаг, ограничения по числу/формату/размеру/пикселям, image content, итоговый envelope, malformed/missing/multiple result и пути в metadata. Сторожа принимаются после показанного красного.
- Три инструкции согласованно требуют `--image` для Opus на визуальном гейте; `[]` засчитывается только если metadata завершённого запуска содержит непустой `images` с путями, размерами и SHA-256, совпадающими с переданными файлами. Сторож этапа 343 ловит регресс правила.
- Spark перед PRD, визуальным и committed diff гейтами; пары Astra и Opus одновременно, результаты и evidence в AssumptionLog. Неустранённые critical/high блокируют выпуск.
- ShellCheck, Bash syntax, фокусные и полный mock проходят. Real API suite не требуется: инструменты и Vetmanager API не меняются. Production не вызывается.
- Кодовый и закрывающий commits доставлены, Tests и Deploy Prod зелёные, Roadmap `done`, AssumptionLog содержит evidence.
