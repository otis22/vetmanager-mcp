# Этап 423 — fail-closed для Report AI REST write/delete

Дата: 20.10.2026. Источник: `artifacts/review/2026-10-20-full-stage-420.md`, R3.

## Цель и контракт

`required_scope_for_request` не должен возвращать `None` для PUT и DELETE под `/rest/api/report-ai-job` и его дочерними путями: `VetmanagerClient` считает `None` разрешённым неизвестным чтением. Неподдержанные PUT/DELETE получают `REQUEST_NOT_MAPPED` и отказ до сети. GET/POST сохраняют права stage 269. Вне этого entity метрика неизвестных чтений и действующие правила прав не меняются.

Локальный `artifacts/vetmanager_openapi_v6.json` содержит 101 path и **не содержит** `report-ai-job`; поэтому по нему нельзя утверждать, что PUT/DELETE поддерживаются. `artifacts/openapi-diff-2026-06-15-remote-vs-local.md:49-53` фиксирует более поздний удалённый контракт: POST создания, GET задания, POST confirm, GET data, POST save. Исследование `artifacts/report-ai-mcp-research-2026-06-15.md:97-101` описывает те же методы; более поздние исходники/контракт проекта добавили POST reject и GET export. Подтверждения PUT/DELETE в доступных контрактных материалах нет. Если upstream добавит такую операцию, потребуется явное решение о scope и отдельный этап; молчаливый `None` не допускается.

| Метод | Известные пути / действие | Решение второго слоя |
| --- | --- | --- |
| GET | `/report-ai-job/{id}`, `/{id}/data` | `analytics.read`, без изменения; `get_report_ai_job_export` читает job здесь, а запуск выгрузки делает через `/report/StartReport` с отдельным `report_ai.write` |
| POST | `/report-ai-job`, `/{id}/confirm`, `/{id}/save`, `/{id}/reject` | `report_ai.write`, без изменения |
| PUT | Любой путь entity, включая корень и `/{id}` | `REQUEST_NOT_MAPPED`, отказ до сети |
| DELETE | Любой путь entity, включая корень и `/{id}` | `REQUEST_NOT_MAPPED`, отказ до сети |
| Иные методы | Любой путь entity | `REQUEST_NOT_MAPPED` согласно общему правилу |

Матчинг entity в текущем коде регистронезависим и убирает завершающий слэш и query string. Внутри `report-ai-job` неизвестный дочерний GET по-прежнему получает `analytics.read` (это существующая широкая ветка, не метрика неизвестного чтения); соседний `report-ai-jobs` остаётся другим entity. Корень без `/rest/api` для записи закрывает общее правило. Этот этап не меняет широкую ветку GET/POST; её сужение требует отдельного контрактного анализа.

## Архитектурное решение

Проблема: отдельная ветка `report-ai-job` в `token_scopes.py` завершает PUT/DELETE значением `None`, обходя общее fail-closed правило для записи. `VetmanagerClient._require_scope` допускает `None` как временное исключение только для неизвестных чтений.

Контекст и ограничения: права stage 269 на GET/POST, права на удаление `records.delete`, запрет угадывать REST-контракт, общий второй слой stage 274, обратная совместимость известных MCP-инструментов. Дополнительной сети или базы решение не требует.

Варианты: (1) назначить PUT `report_ai.write`, DELETE `records.delete` — необоснованно обещает поддержку неизвестных методов; (2) менять общий `VetmanagerClient` для `None` — шире задачи и затронет метрику неизвестного чтения; (3) вернуть `REQUEST_NOT_MAPPED` для остальных методов в ветке entity. Выбран (3): минимальная локальная правка, возвращающая уже существующую семантику отказа.

Инварианты: GET/POST права неизменны; PUT/DELETE entity не достигают апстрима даже у токена со всеми правами; неизвестное чтение другого entity по-прежнему учитывается метрикой; существующие сторожа stage 268–274 зелёные. Rollback: если после мержа обнаружится подтверждённый поддерживаемый PUT/DELETE, отменить релиз в main штатным revert и выпустить отдельную точную карту method/path→scope с тестом; бессрочно оставлять прежний обход прав нельзя. Диагностика — предупреждение `rest_scope_request_not_mapped` и отказ 403 на вызове; прод-проверки выполняет супервизор после мержа.

Учётные данные (§6.0 `CLAUDE.md`): байты и сохранённые scope уже выданных токенов не меняются. Меняется интерпретация двух неподдержанных методов для любого токена: вместо прежнего допуска будет 403. Количество уже выданных токенов, использовавших такие вызовы, неизвестно; production-read по запросу владельца не выполняется. Миграция записей токенов не нужна — ни один scope не должен разрешать неподтверждённую операцию. Наблюдение возможных отказов после мержа относится к супервизору.

Architecture Critique и PRD-review: единый сильный гейт, который проверяет архитектуру, полноту PRD, контракт, приёмку и rollback; Spark перед ним, Astra и Opus одновременно.

## Декомпозиция и приёмка

1. **423.1, ≤2 ч**: контрактная сверка, PRD, Architecture Critique/PRD review. До кода показать красный сторож: действующий `None` для PUT/DELETE проваливает тест и проходит после исправления. Отдельная мутация возврата `None` после исправления тоже должна валить guard.
2. **423.2, ≤150 строк кода**: заменить fallback entity на `REQUEST_NOT_MAPPED`; тесты через `VetmanagerClient` доказывают 403 без upstream-запроса для PUT/DELETE (корень, дочерний путь, слэш/query/регистр) и сохранение GET/POST прав. Соседний префикс и путь без `/rest/api` проверяют границу entity. Аудит, committed diff review, полный mock+real suite, push в релизную ветку и зелёный CI. Выпуск = зелёный CI ветки, пост-релизные проверки после мержа.

Живой API не вызывается: требуемый результат — локальный отказ до обращения к API. Прикладывается проверка отсутствия outbound-запроса; стенд не влияет на этот контракт.
