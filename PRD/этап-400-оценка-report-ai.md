# Этап 400. Оценка пригодности Report AI

## Цель и границы

После работы с отчётом агент добровольно вызывает `rate_report_ai_job(job_id, score, comment?)`. Мы сохраняем в собственной БД UTC-время, исходный очищенный `intent_text`, оценку и связь с job. Langfuse и API Ветменеджера для оценки не используются. Вызов доброволен: 100% покрытия оценками не будет.

## Проверенные факты

- `create_report_ai_job` отправляет `POST /rest/api/report-ai-job` с `intent_text`; ответ содержит `job.id`, в том числе у позднее неудачных jobs. Исходный текст до добавления требования приватности доступен в инструменте.
- Текущая БД использует SQLAlchemy, Alembic, `get_session_factory`; `depersonalization.sanitize_report_value` чистит свободный текст отчёта, а `agent_feedback_service.sanitize_text_with_metadata` дополнительно скрывает секреты, email, телефоны, контекстные имена и адреса. Это эвристические слои: абсолютная гарантия удаления любых ПД из свободного текста невозможна.
- `tool_access_registry` задаёт права; Report AI create требует `report_ai.write`. `get_report_ai_prompt_helper` доступен базово. Метрики доступны через `service_metrics` и общий backend.
- OpenAPI `artifacts/vetmanager_openapi_v6.json` не определяет нашу локальную оценку; новых вызовов к ВМ нет.

## Контракт

- `score` — целое 1–10 без `bool`; `job_id` — положительное целое; `comment` необязательный короткий текст, очищается той же функцией, что и промпт.
- Шкала в описании инструмента: **1 = отчёт даже не построился; 2 и выше — отчёт построился; 2 = построился, но задачу почти не решил; 5–6 = решил частично; 10 = задача решена полностью, ничего не пришлось добывать другими путями.**
- Оценка разрешена только при наличии локально зарегистрированного job того же `account_id`, `connection_id` и нормализованного домена действующего подключения ВМ. Одна запись на `(account_id, connection_id, domain, job_id)`: повторная оценка заменяет score/comment и обновляет `rated_at`, но не срок хранения; метрика считает успешные вызовы выставления оценки по score, включая повторные. Повторное подключение даже того же домена начинает новую историю jobs.
- Исходный промпт сохраняется только после успешного create с job ID, очищенным обоими слоями до записи. Ошибка POST без job ID не образует оценку; описание явно объясняет эту границу. Для failed job с ID оценка 1 доступна.
- Подсказка о вызове оценщика есть в статическом гайде и описании create до первого запроса, а также в ответах Report AI при наличии job ID. Отсутствие оценки не означает успех.
- После ответа POST с job ID регистрация выполняется до ожидания и аннотирования с общим бюджетом 2 секунды; дедуплицированный/concurrent create атомарно оставляет первую запись и её prompt/rating без изменений. Если `is_deduplicated=true`, но старой локальной записи нет (например, job создан до релиза), новую запись с неверным «исходным» prompt не создаём: возвращаем job ID и `mcp_rating_unavailable`. Если локальная БД недоступна или зависла после успешного POST, инструмент также возвращает полученный job ID и предупреждение `mcp_rating_unavailable`; повторять POST автоматически нельзя. Журналирование ошибок не пишет prompt или домен.

## Архитектурное решение

Проблема: хранить приватный исходный промпт и оценку, не доверяя переданному агентом prompt и не позволяя оценивать чужой job. Рассмотрены расширение `agent_feedback_reports` (смешивает triage и статистическую оценку, допускает чужие категории) и отдельная таблица `report_ai_job_ratings`. Выбрана отдельная таблица с уникальным `(account_id, connection_id, domain, job_id)`, отдельным индексом `created_at`, nullable score до оценки и очищенным двумя слоями prompt, созданная миграцией Alembic. До первого рейтинга это локальный журнал созданных jobs; при оценке выполняется UPDATE только своего account и текущего connection/domain. Регистрация использует `INSERT ON CONFLICT DO NOTHING`: дедупликация не заменяет первоначальный prompt, creation time или score. Инварианты: необработанный prompt не попадает в БД/метрики/логи, чужой job/контур не оценивается, диапазон подкреплён Python и CHECK, повтор не создаёт дубль. Остаточный риск ПД после эвристической очистки принят как ограничение свободного текста; SQL-архивы `backup_postgres.sh` и `backup_daily_cron.sh` получают `umask 077`, приватный каталог и файлы с режимом 600. Удаление account каскадно удаляет строки; архивирование account не очищает их досрочно. `created_at` неизменяем для повторной оценки, а ежедневная фоновая очистка каждого MCP слота удаляет строки старше 180 дней независимо от активности account; сбой логируется и повторяется, проверяется метрикой/тестом. В штатных SQL-резервных копиях запись может сохраняться дополнительно до 60 дней (`scripts/backup_postgres.sh`); pre-deploy rollback dump сохраняет схему таблицы, но исключает её строки через `--exclude-table-data`, иначе prompt хранился бы бессрочно. Поэтому обещание 180 дней относится только к активной БД. Для rollback миграция удаляет таблицу и новый tool; потеря локальной телеметрии не влияет на данные ВМ. Нагрузка — две короткие операции БД на create/rate и одно индексное DELETE в сутки; внешних запросов от оценщика нет.

Право оценщика: `report_ai.write`, то же узкое право, что запускает job. Это не выдаёт права на чтение отчётов и исключает запись из базового анонимного набора.

## Декомпозиция и приёмка

1. Модель, миграция, сервис записи и проверки владения (≤150 строк). Красные сторожа: SQL constraints, очистка prompt/comment, чужой account/connection/domain, идемпотентный/concurrent create и дедуплицированный job без локальной записи.
2. MCP tool, реестр прав, гайд/описания/ответы Report AI (≤150 строк). Красный сторож полного текста шкалы и доступности подсказки до/после провала.
3. Метрика по score, ежедневная очистка, приватность резервных копий, тесты и живой стенд (≤150 строк на часть). Красные сторожа распределения, удаления строк неактивного account без сдвига срока при повторной оценке, подключения фоновой очистки к lifespan и её 24-часового повтора, режима доступа к SQL-архиву, отсутствия строк рейтингов в rollback dump и таймаута регистрации; живой create → rate → read-only DB summary.
4. Аудит, ревью, выпуск и CI.

Стенд заранее выбран: `.env` (`TEST_DOMAIN`/`TEST_API_KEY`) для create, но запрос идёт через реальный bearer token тестового account и connection в изолированной Postgres. Проверяются HTTP create/rate, чтение структуры записи SQL и отказ второго account. Это один контур ВМ под API key через реальную bearer-обвязку MCP; отдельный bearer-стенд ВМ не используется. Если такой end-to-end контур не обеспечен, выпуск блокируется и факт фиксируется.
