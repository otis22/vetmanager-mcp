# Этап 383. Классы отказов Report AI без кода

## Цель и границы

Разделить наблюдаемые отказы Report AI без структурированного кода по HTTP-статусу, показать факт появления нового кода ВМ и дать оператору числовые `account_id`/`job_id` в событии `report_ai_outcome_code`. 383.1 — только PRD; 383.2 — реализация; 383.3 — аудит и выпуск. Подтипы `PREVIEW_FAILED` от `SqlErrorClassifier` остаются задачей ВМ: этого поля в текущем контракте нет.

## Проверенные факты

По разбору супервизора 12.10.2026 за 30 дней девять отказов попали в `unknown`. В `service_metrics.py` все 16 перечисленных в постановке семантических кодов ВМ уже есть в `REPORT_AI_OBSERVED_CODES`; кроме них там локальные `REPORT_AI_CREATE_*` и `unknown`. `record_report_ai_outcome_code` сейчас сводит `None`, неподходящий тип и незнакомую строку в один `unknown`, считает `vetmanager_report_ai_outcomes_by_code_total{operation,code}` и пишет событие без id. `vetmanager_client.py` извлекает непустой `data.error_code` из 404/прочих >=400, но на 403 сохраняет его только для `/rest/api/report/StartReport`; остальные 403 превращаются в `AuthError` без кода. На Report AI job path это теряет структурированный код. Для этих путей наблюдать код отдельно от публичного `exc.error_code`: его изменение повлияло бы на текст и тип MCP-ошибки. Отказ 403 и публичный ответ должны остаться прежними. Для HTTP-ошибки без кода передаётся `error_code=None` и сохраняется `status_code`. Текст ошибки не является источником класса.

В `tools/report_ai.py` счётчик вызывается для failed job, ошибок job/reject, create, запуска и получения экспорта. У failed job в payload обычно есть `id` и `error_code`, но HTTP-статуса отдельного отказа нет; у исключения ВМ есть `status_code`, но `job_id` известен не на каждом пути. `_annotate_report_ai_workarounds` превращает пустой/нестроковый `error_code` в `unknown` до lifecycle-учёта, а shared lifecycle пишет метрику из фонового `dispatch`, где `ContextVar` credentials недоступен. Сырые наблюдаемые код и account id надо захватить до аннотации/dispatch, не меняя безопасный MCP-ответ. Повторный failed status уже ограничивается lifecycle-наблюдением; менять эту семантику этап не должен. Этап 385 перевёл общие счётчики в Redis через `shared_metric_counters`: семейство `report_ai_outcomes_by_code_total` уже там. OpenAPI v6 не описывает Report AI job endpoints; исходить из наблюдаемого контракта клиента, MCP и тестов, не предполагать новые поля ВМ. Главный PRD требует безопасной диагностики и метрик; технические требования закрепляют `/metrics` и структурированные логи.

## Архитектурное решение

**Проблема.** `unknown` смешивает отсутствие `data.error_code` с новым неперечисленным кодом и не даёт понять HTTP-класс. Лог без числовых id затрудняет разбор конкретного отказа.

**Варианты.** Считать кодом произвольную строку ВМ — высокая кардинальность и риск утечки текста. Разбирать сообщение ВМ — ненадёжная эвристика. Ввести закрытые классы по `error_code` и нашему `status_code`, сохранить разрешённые семантические коды и считать появление неперечисленной строки отдельным bounded сигналом — выбранный вариант. Нового process-local накопителя нет.

**Классификация.** Для непустой строки из `REPORT_AI_OBSERVED_CODES`, кроме legacy-метки `unknown`, сохранять прежний label; локальные `REPORT_AI_CREATE_*` также остаются прежними. Локальный `SCOPE_DENIED_ERROR_CODE` классифицировать отдельной закрытой меткой `local_scope_denied`, не как новый код ВМ. Непустая строка вне словаря, включая буквальное `unknown` от ВМ, получает label `unlisted_code_seen` в существующем счётчике `vetmanager_report_ai_outcomes_by_code_total{operation,code}` только при подтверждённом происхождении из ответа ВМ. Это и есть требуемый счётчик появления нового кода; отдельная серия дублировала бы его без новой информации. Её сырой текст не попадает в labels и событие; для расследования остаётся безопасный correlation id и числовые id. `None`, пустая строка и неподходящий тип получают `no_code_http_5xx` при целочисленном статусе 500–599, `no_code_http_4xx` при 400–499, иначе `no_code_no_status`. Последнее название означает «нет применимого HTTP 4xx/5xx для классификации»; в частности, failed job в HTTP 200 несёт статус задания, не статус исходного отказа. У create HTTP 5xx после отправки запроса сохранится существующий локальный `REPORT_AI_CREATE_HTTP_5XX` для неопределённого исхода; `no_code_http_5xx` проверять на обычном job/reject/export пути. В логе и метрике использовать один рассчитанный класс. `unknown` как новый результат не производить; старые накопленные значения остаются историческими до сброса Redis-счётчиков. До выпуска проверить внешние запросы/alerts к старой метке `unknown` по доступной конфигурации мониторинга; если они есть, переходный запрос должен суммировать legacy `unknown` и четыре новых класса во время смешанной версии слотов и возможного rollback. Убрать legacy из запроса только после rollout либо полного rollback и окончания используемого окна rate/increase. В репозитории внешних dashboard/alerts с этим фильтром нет; тесты, ожидающие старый label, обновляются в 383.2. Не публиковать совместимый дублирующий `unknown`: он снова скрыл бы различие классов при анализе.

**Место учёта и приватность.** Расширить единую функцию `record_report_ai_outcome_code` необязательными `status_code`, `account_id`, `job_id` и закрытым признаком происхождения кода, передавать их из мест вызова при достоверном наличии. Для Report AI job 403 клиент извлекает структурированный код и кладёт его в отдельное внутреннее поле исключения `observed_error_code`; `_call_vm` берёт это поле только для метрики, а `_tool_error_from_vm` продолжает читать прежний `error_code=None`. Это явная граница `VetmanagerClient` → `_call_vm`; поле не попадает в MCP-ответ или лог сырой строкой. В failed-job path захватить исходный `error_code` до `_annotate_report_ai_workarounds`; в shared path захватить account id из request credentials до `dispatch` и передать числом в callback, не читать `ContextVar` в фоновой нити. `account_id` и `job_id` — только настоящие `int` (не `bool`), положительные; при отсутствии поле опустить, не подставлять фиктивный id. На create до получения job id его нет. На ошибках экспорта report/file id не выдавать за job id. Логировать только нормализованный класс, operation, уже существующий correlation id и доступные числовые id; не добавлять текст ВМ, intent, payload или ключ. В labels id не появляются. Существующий `report_ai_outcomes_by_code_total` уже записывается через Redis shared metrics; `/metrics` из любого слота показывает общие значения. Отказ Redis остаётся best effort и не меняет MCP-ответ; существующий локальный fallback не становится источником production витрины.

**Инварианты и откат.** Не менять MCP-ответы, права, запросы к ВМ и кратность фиксации отказа. Допустимые labels закрыты и не зависят от произвольного текста или числа статуса. Новые классы заменяют `unknown` в том же счётчике без удвоения отказов. При ошибке классификации можно вернуть прежний `unknown`, сохранив старый счётчик; переходный запрос мониторинга с legacy и новыми метками сохранить до окончания окна rate/increase после полного отката. Поскольку меняются production observability, нагрузка трёх слотов и граница `tools/report_ai.py` → `service_metrics.py` → Redis, Architecture Critique требуется и входит в сильный PRD-review 383.1 с критериями архитектуры и полноты PRD.

## Приёмка и декомпозиция

Каждая подзадача ≤2 ч или ≤150 строк кода. Каждый новый регрессионный сторож до приёмки явно ломается вместе с охраняемым поведением и показывает красный; способ мутации записать в self-attestation 383.2/383.3. В 383.1 нет изменения инструмента, поэтому live-вызовы и красные тесты относятся к 383.2.

| Подзадача | Изменение и красный сторож |
|---|---|
| 383.2a (≤2 ч) | Классификатор в `service_metrics.py`, закрытые labels. Контракт: HTTP 500 с пустым телом на обычном job path → `no_code_http_5xx`; 4xx без `data.error_code` → `no_code_http_4xx`; failed job без статуса → `no_code_no_status`; известный код сохраняется; неперечисленная строка из ВМ → `unlisted_code_seen` в существующей серии; локальный `scope_denied` → `local_scope_denied`, не ложный unlisted. Отдельно: create HTTP 500 после отправки сохраняет `REPORT_AI_CREATE_HTTP_5XX`. Проверить буквальное `unknown`, пустую/нестроковую форму, 2xx как `no_code_no_status`, отсутствие сырого кода в label/log. Красный при удалении status-ветки, превращении нового кода в `unknown`, допуске произвольного label или классификации локального отказа как upstream. |
| 383.2b (≤2 ч) | Прокинуть status и доступные id по job/reject/create/export/failed status без изменения кратности; передать структурированный 403 код Report AI job в observability отдельно от публичного `exc.error_code`. Контрактные тесты реальных call paths и event `extra`: failed job с пустым/нестроковым кодом через аннотацию получает `no_code_no_status`, безопасный MCP-ответ остаётся прежним; job 403 с известным/новым кодом классифицируется по нему при неизменных тексте и типе публичного MCP-ответа; в Redis-dispatch логе есть оба id, захваченные до фоновой нити; локальный scope denial не увеличивает unlisted; отсутствующие id не выдумываются, неперечисленная строка не выводится. Красный при удалении захвата исходного кода, 403-кода, status/account/job или выдаче report/file id за job id. |
| 383.2c (≤2 ч) | Проверить два slot/backend на одном Redis: суммы `no_code_*` и `unlisted_code_seen` в существующей серии видны из обоих, перезапуск slot не обнуляет итог, множество labels ограничено. Красный при обходе Redis или удалении render существующей серии. |
| 383.3a (≤2 ч) | Аудит diff, приватности, вызовов и доказательств красных сторожей; фокусные тесты, затем committed diff review и финальные проверки по workflow. |
| 383.3b (≤2 ч) | Сверить потребителей legacy `unknown` и обновить обнаруженные запросы; AssumptionLog, выпуск и зелёный CI. При изменении инструмента — живой вызов на заранее выбранном devtr6 контуре с кодом и очищенным телом; для искусственных HTTP 500/нового кода достаточно контрактных тестов, ВМ намеренно не ломать. Приложить живую строку `report_ai_outcome_code` с числовыми `account_id`/`job_id` без ПД. |

Для 383.1: Spark candidate-only → Astra structured verdict → Sol xhigh structured verdict по решению владельца 13.10, без Claude Opus; затем simplicity pass, запись в AssumptionLog, структура Roadmap, commit и проверка CI. Сверку словаря при следующих изменениях ВМ делать по наблюдаемому контракту/спецификации: новый структурированный код сначала виден как `unlisted_code_seen`; добавлять его в allowlist только после проверки источника и смысла, с тестом на прежний и новый label.
