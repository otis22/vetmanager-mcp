# Этап 475. Изменение статуса пациента (#162)

## Цель

Дать сотруднику клиники отдельный, явно подтверждаемый способ изменить клинический статус пациента и дату смерти. Предотвратить запись не тому пациенту и сообщать результат по повторному чтению. Работа ведётся только на тестовом devtr6; production не затрагивается.

## Источник и проверенные факты

- Roadmap 475.1 требует отдельную чувствительную write-операцию, права, двойное подтверждение, read-back, красные сторожа и живую проверку.
- Сводка исходного фидбека #162 в `LiveHelperAgent/logs/mcp/2026-11-14-dashboard-feedback-plan.md` указывает: `update_pet(status=...)` уже существует, но даты смерти и специального безопасного workflow нет. Внешний план `workspace/2026-11-14/vetmanager-mcp-action-plan.md` уточняет потребность как дату смерти пациента и предлагает preview/confirm/readback. Полный текст обращения в найденных логах отсутствует; роль автора не установлена.
- OpenAPI v6: `pet.status` имеет enum `alive`, `dead`, `deleted`; `deathdate` — nullable string с типом datetime; `deathnote` — nullable string. `PUT /rest/api/pet/{ID}` и `GET /rest/api/pet/{ID}` описаны. Справочник сущностей подтверждает те же поля. Это допустимые значения схемы, но не утверждённые переходы бизнес-процесса.
- Текущий публичный `update_pet` принимает произвольный непустой `status`, вызывает `crud_update("/rest/api/pet", pet_id, payload)` и не делает preview или read-back. В реестре прав он требует `pets.write`; REST-карта связывает запись `pet` с `pets.write`. Новая отдельная операция без решения о старом пути не даёт гарантии обязательного подтверждения.

## Решение владельца (20.11.2026)

Владелец подтвердил: только `alive → dead` с обязательной датой смерти и исправление даты у `dead`; без `dead → alive`, переходов с `deleted` и `deathnote`. Дата обязательна, будущие даты запрещены, «сегодня» определяется в зоне клиники. Два подтверждения означают два явных согласия сотрудника вокруг preview; технический барьер — два вызова MCP с одноразовым токеном. `pets.write` достаточно. Непустой `status` в `update_pet` отклоняется до PUT и направляет к новому инструменту. Внутренние GET разрешаются узко по этому PRD. OpenAPI перечисляет поля, но не гарантирует атомарного сравнения и записи.

### Переходы и дата

`clinic_id` обязателен: сотрудник выбирает клинику **этой операции**, её зона через GET по этому ID определяет «сегодня»; ответ без ID или с другим ID отклоняется. При отсутствии проверенной зоны операция отказывает. У pet нет контрактной привязки к филиалу, поэтому MCP не утверждает, что выбранная клиника является «клиникой пациента»; её ID виден в preview и повторно согласуется перед записью. При нескольких зонах выбор сотрудника является явной частью операции, как у существующих инструментов с `clinic_id`; выбрать зону из поля пациента невозможно по публичному контракту. Формат REST-записи — локальная дата `YYYY-MM-DD 00:00:00`, которую проверяет живой devtr6.

Read-only devtr6 20.11 вернул `time_zone=Europe/Kiev`; минимальный тестовый образ содержит актуальное IANA имя `Europe/Kyiv`. Нормализуем ровно это наблюдаемое устаревшее имя; неизвестные зоны по-прежнему дают отказ до записи и фиксируются обезличенным событием `clinic_timezone_invalid`.

Read-only `GET pet` на devtr6 вернул ID владельца в `client_id`, хотя OpenAPI описывает `owner_id`; входной `create_pet` принимает `owner_id`. При проверке пациента допускаются оба документированных/наблюдённых ключа, но их конфликт или неверный ID даёт отказ до PUT. Выходная нормализация MCP также публикует `client_id` вместо `owner_id`.

- В первом выпуске разрешить `alive → dead` с обязательной датой смерти и `dead → dead` только для исправления даты смерти. Это не запись того же значения без изменения: при равной дате отказаться от PUT. `dead → alive` (воскрешение/исправление ошибочной записи), любой переход из/в `deleted` и изменение одного `deathnote` оставить вне этого выпуска до отдельного решения. `deleted` — значение enum, а не разрешение на удаление; `delete_pet` остаётся отдельной операцией с `records.delete`.
- Использовать поле API **`deathdate`**, не `edit_date`, `birthday` или новое поле. В MCP принимать только календарную дату `YYYY-MM-DD`, проверять реальность даты, `deathdate ≤ сегодня` в согласованной зоне клиники и, когда `birthday` является реальной календарной датой, `deathdate ≥ birthday`; `null`, пустая и нулевая дата считаются отсутствующими, а иной неверный формат даёт отказ до PUT. Не принимать будущую дату или время с часовым поясом от вызывающего. Для REST передавать локальную дату-время `YYYY-MM-DD 00:00:00` и проверить её на devtr6 до выпуска. При неизвестной зоне отказать до записи.
- При `alive → dead` писать минимальный payload `{status: "dead", deathdate: ...}`. При коррекции `dead → dead` писать только `deathdate`; не затрагивать `deathnote`. Если существующая запись `dead` без даты, разрешить её дополнить тем же защищённым сценарием. Read-back сравнивает `id`, `owner_id`, `status` и нормализованную календарную часть `deathdate`; `success` HTTP PUT сам по себе не подтверждает изменение.

### Два подтверждения средствами MCP

- Один инструмент, `change_pet_status(pet_id, expected_owner_id, clinic_id, target_status, deathdate, confirm=false, confirmation="")`, имеет два вызова. Перед **первым** сотрудник подтверждает агенту выбранных пациента/владельца и намерение. Вызов без `confirm` делает fresh `GET /rest/api/pet/{ID}`, сверяет оба ID, допустимый переход и дату, возвращает читаемый preview: идентификаторы, необходимые для различения пациента сведения с действующей деперсонализацией, текущие и новые статус/дату, предупреждение о клиническом эффекте, срок действия и opaque `confirmation`. Записи нет.
- Перед **вторым** вызовом агент показывает именно этот preview и получает явное второе согласие сотрудника. Вызов `confirm=true` требует тот же набор аргументов и выданный `confirmation`; повторно делает fresh GET, сверяет ID/владельца, alias, тип, породу, дату рождения, статус, `deathdate` и `edit_date` (если есть) с preview, а также дату на момент записи. При наблюдаемом изменении проверяемых полей или истечении срока отказывает до PUT и просит новый preview. После PUT делает fresh GET и сообщает `applied=true` только при совпадении целевых полей. При ошибке PUT или read-back сообщает «исход неизвестен; сначала прочитайте пациента», без автоматического повтора записи.
- Для настоящей **одноразовости**, в том числе при нескольких воркерах и повторе после ошибки, нужен случайный nonce с TTL 10 минут, хранение только хэша nonce/контекста в общем атомарном хранилище и операция consume перед PUT. Привязать его к аккаунту/подключению, `pet_id`, `owner_id`, `clinic_id`, исходному состоянию и целевым полям; значение не логировать. Подпись/HMAC снимка без атомарного consume, как в существующем `set_good_sale_param_status`, проверяет свежесть и состояние, но сама по себе **не делает токен одноразовым**. Предварительная GET-проверка также не является атомарным compare-and-swap в Vetmanager: конкурентное изменение между GET и PUT остаётся риском, который read-back обнаруживает не во всех сценариях. Не обещать транзакционной гарантии без API-контракта.
- MCP может требовать два вызова и токен, но не может доказать, что агент действительно дважды спросил человека. Это правило должно быть в описании инструмента; технический барьер не следует называть подтверждением личности сотрудника.

### Закрытие старого пути и права

- Сохранить имя и остальные поля `update_pet`, но **отклонять любой непустой `status` до PUT** с указанием на защищённый инструмент; пустое значение сохраняет старое «не менять». Одного предупреждения в docstring недостаточно. В описании инструмента явно сказать: «Статус и дата смерти меняются только через `change_pet_status` с preview и подтверждением; `status` здесь не поддерживается». `deathdate`/`deathnote` в общем `update_pet` сейчас отсутствуют; не добавлять их как новый обход. Проверить и другие доступные MCP write-пути к `/rest/api/pet/{ID}`. Это намеренно ломает прежний статусный аргумент по прямому решению владельца: агент получает явный отказ с новым именем и должен выполнить preview/confirm; отдельный переходный режим сохранил бы обход защиты.
- Зарегистрировать новый инструмент в `tool_access_registry.py` с **одним** требованием `pets.write`; реестр и `tools/list` обязаны совпадать с проверкой вызова. Использовать уже существующие `GET/PUT /rest/api/pet/{ID}` и карту `pet → pets.read/pets.write` в `token_scopes.py`; при новом REST-пути карта обязана быть дополнена до вызова, иначе второй слой откажет fail-closed. **Особенность:** текущая REST-карта требует `pets.read` на GET, тогда как принятое владельцем право для всего сценария — `pets.write`. Токен только с `pets.write` разрешает внутренние GET пациента и клиники строго по точному пути внутри запроса `change_pet_status` через локальный контекст; вне контекста обычные GET по-прежнему требуют `pets.read`/`reference.read`; не добавлять молча второе требуемое право к инструменту и не открывать все читающие инструменты группе с одним `pets.write`. Сторож отдельно вызывает обычный GET с `pets.write` вне контекста и GET другого ID внутри контекста — оба должны получить отказ. Предпросмотр выдаёт данные только того пациента, на запись которого уже есть право; alias при деперсонализации заменяется адресным placeholder. Подтверждение не заменяет право. Учитывать, что `pets.write` уже есть у группы регистратуры; никаких новых прав на удаление оно не даёт.

## Архитектурное решение

Один MCP-инструмент исполняет `GET clinics/{ID}` для зоны операции, затем fresh `GET pet/{ID}` и проверяет снимок. Preview возвращает одноразовый opaque token; подтверждение повторяет чтение и проверки, атомарно расходует token до `PUT pet/{ID}`, затем делает fresh read-back. Неуспех PUT или read-back не приводит к повторной записи. Запись содержит только `status` и `deathdate` при первом переходе либо только `deathdate` при исправлении.

Token привязан HMAC к соединению, учётному субъекту, ID пациента/владельца/клиники, снимку и цели. В нескольких воркерах хэш token и HMAC контекста живут в уже используемом Redis с TTL 10 минут (`SET NX EX`/`GETDEL`); при одном воркере допустимо процессное хранилище под lock, а при нескольких без Redis — отказ. Секрет и token не записываются в лог. У правообладателя `pets.write` есть право на запись выбранного пациента, поэтому внутренние GET его и клиники допускаются по точному пути внутри этого вызова; публичные читающие инструменты и обычный REST GET сохраняют `pets.read`/`reference.read`. Деперсонализированный preview не отдаёт сырой alias.

Цена этого решения — дополнительное чтение и общее хранилище подтверждений. HMAC без атомарного consume не даёт одноразовости, а `pets.read` как второе право противоречило бы решению владельца. В API нет compare-and-swap: изменение между последним GET и PUT остаётся явно описанной границей, read-back не заменяет транзакцию.

## План реализации

### Оценка простоты

Один новый инструмент и один небольшой модуль одноразового подтверждения. Простая HMAC-подпись снимка отклонена: она допускает повтор записи с тем же token. Хранение токена в процессе отклонено для нескольких воркеров; Redis уже используется проектом и даёт атомарный consume. Отдельные изменения реестра прав, REST-проверки и wheel allowlist обязательны существующими гейтами; дополнительных слоёв и новых прав нет. При новом клиническом переходе достаточно изменить инструмент и его focused-сторожа, если право остаётся `pets.write`.

1. **475.1a (≤2 ч).** После ответов владельца закрепить окончательные переходы и механизм подтверждения; проверить формат `deathdate`, форму ответа, часовой пояс и семантику записи read-only по OpenAPI и отдельно на devtr6; провести PRD-review и оценку простоты.
2. **475.1b (≤2 ч).** Написать focused сторожа для запрещённых переходов, неверного пациента/владельца, истёкшего или повторного подтверждения, смены состояния между preview и confirm, отсутствия права, REST fail-closed и несовпадения read-back. Каждый сторож показать красным на целевой поломке.
3. **475.1c (≤2 ч).** Минимальная реализация отдельного инструмента и выбранной защиты старого пути. Перед записью проверить идентичность и ожидаемое состояние, после записи прочитать пациента повторно и явно сообщить расхождение/неопределённость, не выдавая успех по одному HTTP 200. Зарегистрировать инструмент и права; новый REST-путь, если появится, добавить в fail-closed карту.
4. **475.1d (≤2 ч).** Пройти focused → owning → fast → аудит → Spark/Astra/Kimi по всему diff → применимые финальные проверки. Для живого вызова на devtr6 создать собственные синтетические client и pet; проверить новый инструмент только на них, затем удалить обе тестовые записи через разрешённые тестовые операции. Не изменять существующих пациентов. Сохранить код и обезличенное тело ответа вне публичного репозитория; затем real aggregate, commit, committed-diff review и push ветки `dev/stage-475-pet-status`. PR/merge — куратор.

## Приёмка и границы

- Запись производится только после утверждённых двух подтверждений и проверки пациента, владельца и исходного состояния; повтор, устаревшее подтверждение и запрещённый переход не вызывают PUT.
- Право на операцию отражено в `tool_access_registry.py`, при необходимости в `token_scopes.py`, в каталоге и в REST-слое. Отказ перечисляет все группы, дающие нужное право, узкие раньше полного доступа.
- Read-back подтверждает именно выбранные поля; при несовпадении результат не объявляется успешным. Ошибки и evidence не содержат персональных данных или секретов.
- Существующий `update_pet` не принимает запись `status` и не предлагает иного пути записи `deathdate`; его описание ведёт к защищённому инструменту. Статусные записи через другие публичные MCP-инструменты отсутствуют либо перекрыты сторожем.
- Не входит: удаление пациента, запись в production, расширение других полей `pet`, изменение клинического смысла статусов без утверждения.
