# Этап 233. Точная причина отказа подключения интеграции

## Контекст и цель

21.08.2026 в четырёх `integration_failed` за 30 дней у трёх нельзя было
восстановить первопричину. Класс `vetmanager_error` объединяет HTTP 4xx/5xx,
сетевые ошибки и внутренний fallthrough resolver-а. Кроме того, при retry
billing resolver записывал upstream-метрику только для последней неуспешной
попытки. Обработанные web-отказы не создают событие error tracking.

Цель — оставить для каждого отказа безопасный, ограниченный по cardinality
след: отдельный продуктовый reason class, upstream metric для каждой попытки,
structured log и (если tracking включён) exception event со stack trace.

## Проверенные факты

- `ActivationEvent.reason_class` — nullable `String(32)` с PostgreSQL/SQLite
  CHECK constraint `ck_activation_events_reason_class`; его исходная миграция
  — `20260710_000018_activation_events.py`.
- `web_routes_account` записывает `integration_failed` только для основного
  submit-flow и уже не логирует `str(exc)`, так как exception message может
  содержать чувствительные фрагменты.
- `host_resolver._resolve_vetmanager_host_uncached` вызывает billing API с
  retry, но для `httpx.TimeoutException` и `httpx.RequestError` до этапа 233
  записывает метрику только после исчерпания retry.
- `error_tracking.configure_error_tracking()` возвращает `False`, не вызывая
  Sentry SDK, когда оба DSN пусты; sanitiser уже подключён через `before_send`.

## Декомпозиция

1. Заменить новую классификацию activation failures, сохранив legacy
   `vetmanager_error` в allowlist и мигрировав CHECK constraint (до 100 строк).
2. Записывать один failure request metric в handler-е каждой неуспешной
   фактической попытки billing resolver-а; подтвердить, что existing probe
   retry wrapper уже делает то же самое, и добавить регрессии (до 100 строк).
3. Добавить безопасный capture helper для handled connection failures,
   `status_code`/`error_class` в route logs и privacy/no-DSN regressions (до
   150 строк).

## Архитектурное решение

### Проблема и ограничения

Нужна диагностика production failures без PII или credential leakage. Labels
Prometheus и reason class БД должны быть bounded. Старые production rows с
`vetmanager_error` должны пережить upgrade. User-visible web response не
меняется при включённом или выключенном tracking. В stack locals connection
flow могут находиться domain, login и credential values.

### Варианты

1. Заменить `vetmanager_error` и переписать старые строки. Это даёт чистый
   набор значений, но ломает history/rollback и создаёт лишнюю migration load.
2. Оставить корзину без новых classes. Backward-compatible, но не решает
   incident diagnosis.
3. Добавить bounded classes, оставить legacy value в constraint, и
   классифицировать только новые события по `status_code`/transport subtype.
   Для handled exceptions добавить узкий helper, который no-op без DSN и
   передаёт только `account_id`; sanitizer redact-ит PII-like locals/values.

### Выбор

Выбран вариант 3. `AuthError` и `HostResolutionError` сохраняют существующие
особые причины. Остальные `VetmanagerError` классифицируются по status:
4xx → `upstream_4xx`, 5xx → `upstream_5xx`; timeout/request transport →
`network`; отсутствие статуса/другая внутренняя ошибка → `internal`. Legacy
`vetmanager_error` остаётся допустимым только для совместимости history.

Billing resolver записывает метрику ровно один раз в handler-е каждой
фактической неуспешной попытки, включая те, после которых выполняется retry.
Existing probe wrapper уже инструментирует каждую попытку и получает
регрессионную проверку. Error tracking capture вызывается
из обоих обработчиков integration submit/reauth и не может изменить response.
В scope/error context допустим лишь `account_id`; не передаются domain, URL,
email, phone, имя, login, credentials или exception text.

### Инварианты

- Новые `reason_class` values — конечный статический набор; Prometheus labels
  не добавляются и dynamic clinic data отсутствуют.
- `vetmanager_error` остаётся valid в ORM allowlist и после DB migration.
- Каждая реально начатая и неуспешная billing/probe HTTP попытка даёт ровно один
  `vetmanager_upstream_requests_total` sample; retry не скрывает попытку.
- Structured failure log содержит `account_id`, `error_class`, `status_code`
  (включая `None`), но не `str(exc)` или form values.
- При пустом DSN capture helper no-op; ошибки capture никогда не меняют HTTP
  status, body или redirect web response.
- Sentry event/stack context не содержит clinic domain, email, phone, name,
  login, password, API key или token; diagnostic identity — только account_id.
  Для captured handled-отказа event processor заменяет exception values и
  удаляет все frame locals, сохраняя сами stack frames.

### Rollback/fallback

Rollback к предыдущему application release безопасен, потому что legacy
constraint допускает старое значение, а new constraint допускает оба набора.
Downgrade миграции перед возвратом narrow constraint детерминированно сворачивает
новые classes в legacy `vetmanager_error`; это осознанно теряет детализацию,
но не блокирует откат на populated production table. Для SQLite используется
Alembic batch alter; PostgreSQL меняет named CHECK constraint напрямую и
валидан для 90-day retention table. Если Sentry SDK/capture недоступен, helper
подавляет исключение и route продолжает прежний response.

## Scope

- `ACTIVATION_REASON_CLASSES`, classifier, ORM constraint и Alembic migration.
- Billing resolver retry metrics.
- Integration failure logs and handled exception capture with privacy tests.
- 233.5: domain клиники остаётся допустимым incident metadata; Sentry keys
  `client_ip`, `x-forwarded-for`, `x-real-ip`, `remote_addr`, `ip_address`
  redacted, а такие structured-log values маскируются до IPv4 /24 или IPv6 /64.

## Out of scope

- Изменение пользовательских текстов, retry policy или публичного MCP API.
- Ретроспективная переклассификация activation events.
- Изменение dashboard queries или production Sentry/DSN configuration.

## Acceptance criteria

1. New events distinguish 4xx, 5xx, network and internal; old
   `vetmanager_error` inserts remain valid after migration.
2. Retryable and terminal billing failures, а также existing probe retries,
   have exactly one upstream metric sample per actual failed attempt; stage
   reviews existing dashboard/alert meaning because counter now observes
   attempts rather than only terminal failures.
3. Both integration failure route logs contain bounded `error_class` and
   `status_code`, with no credentials/form data.
4. Enabled tracking captures handled exception with stack frames and only
   `account_id`; handled-event processor removes exception messages and frame
   locals, and regression serializes the event to prove absence of clinic
   domain, email, phones, names, login and secrets. Empty DSN is an observable
   no-op with unchanged response.
5. No classifier new-write path emits legacy `vetmanager_error`; 4xx, 5xx,
   timeout/request transport and status-less internal `VetmanagerError` each
   have explicit regression coverage.
6. Targeted and full Docker test contours pass; migration upgrade/downgrade is
   tested with a populated row using a new class.

## Architecture Critique

Required: storage constraint, production observability/privacy and web route →
error-tracking ownership boundary are changed.
