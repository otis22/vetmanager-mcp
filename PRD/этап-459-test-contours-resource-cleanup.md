# Этап 459. Тестовые контуры и очистка ресурсов

Поручение владельца 14.11.2026. Ветка dev/test-contours-resource-cleanup (dev/** запускает штатный CI).
База: b9c397def6086b6a5eff8aa42a87cb62c346537e.

## Факты и проблема

Default suite: 4558 passed, 3 skipped. Real suite: один тест отсутствующего
клиента требует client=[], хотя наблюдаемый ответ при success=true и
 totalCount=0 содержит client={"merge_history": []}.
После настройки отдельных PostgreSQL/Redis выявлены ResourceWarning:
многопроцессные тесты не закрывают stderr=PIPE после wait; browser run_async
создаёт HTTP-клиенты в временном event loop и оставляет их открытыми.
Шесть user-token сценариев дают 6 passed, но exit 1 при завершении процесса.
Mandatory PostgreSQL: 6 passed, 0 skipped. Recovery требует управления
остановкой только выделенной БД через файловый handshake. Один из шести
user-token сценариев — браузерный, он использует run_async; остальные
асинхронные сценарии используют стандартные async-fixtures.

Источники: главный PRD (надёжность и безопасность), технические требования
(тестовый Docker, три способа auth), локальный OpenAPI /client/{id} и
/token_auth.php. OpenAPI не гарантирует форму отсутствующей сущности;
второй допустимый ответ подтверждён реальным API на тестовом стенде.

## Границы

Изменяются только тесты, тестовая инфраструктура, документы. Не менять
production-код, инструменты MCP, права, деперсонализацию и токены владельца.
Аккаунты MCP создаются только в временной тестовой БД. Credentials вводятся
через окружение/внешние env-файлы; не коммитить секреты и адреса доступа.
Stage153 placeholder с явным skip не реализуем под видом исправления:
он будет отдельно указан в итоговом отчёте.

## Архитектурное решение

Проблема: тесты теряют владение ресурсами до закрытия event loop/процесса.
Существующие patterns: shared HTTP reset helpers, fixture run_async,
subprocess.Popen(stderr=PIPE), штатные default/real runners и postgres gate.
Варианты: подавлять warnings (отклонено, скрывает регрессии); добавить
production workaround (отклонено, проблема тестового lifecycle); закрывать
ресурсы тестами в том же loop и гарантированно собирать дочерние процессы
(выбрано). При необходимости небольшой общий test-only helper обслуживает
одинаковый subprocess cleanup и сохраняет diagnostics activation-теста.
Изолированное окружение Docker описывается отдельной Compose-конфигурацией
и небольшим Python-оркестратором; production compose не запускается.
Ресурсы принадлежат конкретному тестовому запуску, публикация портов и
подключение к существующим БД не требуются. Recovery выполняется отдельно
и гарантирует возврат своей БД в healthy при исключении. Тест recovery
обязан удалить созданную им upstream-запись также при ошибке до restored:
cleanup использует прямой REST-клиент с тестовым API-ключом, независимый от
остановленной MCP-БД, затем проверяет GET по его ID: отсутствие записи либо ровно тот же ID
со status=DELETED. Живой probe показал success=true на DELETE и последующий
GET totalCount=1, status=DELETED. Проверять физическое удаление было бы
неверным ожиданием API.
Никаких операций с существующими клиентами или кабинетами владельца.

Инварианты: warnings-as-errors сохранён; тест отсутствующего клиента
при success is True и totalCount=0 допускает только client=[] или
client={"merge_history": []}; отвергает настоящую запись, непустую историю
и любое дополнительное поле; diagnostics не теряются;
HTTP shutdown выполняется до закрытия owning loop; child reaped/pipe closed
также после ошибки и таймаута; повтор запуска не зависит от старой БД или
Redis; секреты не выводятся и не попадают в git; успех требует exit 0,
а не только зелёного JUnit. Rollback — revert тестовых изменений; выделенные
контейнеры удаляются только по уникальному Compose project name. Перед
stop/start/down контейнера его label com.docker.compose.project сверяется
с уникальным именем текущего запуска; несовпадение отклоняется сторожем.
Данные PostgreSQL живут в отдельном project-scoped volume: tmpfs потерял
бы их при stop/start и сделал recovery-проверку недостоверной. Finally и
обработка SIGINT/SIGTERM выполняют
down -v --remove-orphans своего проекта, остатки после SIGKILL обнаруживаются
по label проекта и не используются следующим запуском.
Architecture Critique: not required — production/auth/storage contracts
не меняются; все изменения принадлежат тестовой инфраструктуре.

## Декомпозиция (каждая подзадача <=2ч или <=150 строк)

1. Уточнить тест отсутствующего клиента; отрицательные проверки реальной
   записи и неправильных totalCount/success/формы. Показать красный guard.
2. Закрыть shared HTTP clients в run_async до остановки временного loop;
   воспроизвести утечку на локальном HTTP, проверить исключение callback.
3. Закрыть stderr/stdout после завершения дочерних процессов, при timeout
   kill+wait; сохранить activation diagnostics. Красный тест с живым child.
4. Docker Compose и lifecycle up/down, project volume, env handling, label guard
   с отрицательным тестом (отдельная подзадача <=2ч).
5. Recovery-оркестрация: файловый handshake, восстановление БД, прямой
   upstream cleanup и проверка удаления по наблюдаемому контракту (отдельно <=2ч).
6. Фокусные проверки, аудит, commit, Spark и пара Astra/Opus; замечания
   в пределах бюджетов. Финальный полный default+real+postgres и recovery,
   затем push и Markdown-отчёт с SHA/exit/skips/ограничениями.

## Приёмка

- Полный default suite exit 0; real suite exit 0 и 0 skipped при
  настроенных api-key, шести user-token, web/browser, Redis, PG385/400 контурах;
  обязательные postgres тесты реально выполнены и gate exit 0; stage408
  PG выполнен отдельно. В default разрешён единственный skip stage153.
  Real recovery запускается отдельно под supervisor, без пропуска в real suite.
- Recovery выполнен на свежем изолированном окружении с exit 0.
- Для новых регрессионных сторожей записаны конкретные RED/Green мутации.
- ShellCheck и bash syntax при изменении shell, roadmap structure,
  git diff --check; инфраструктурные команды проверены фактическим запуском.
- Код проверен обеими сильными моделями; critical/high закрыты.
- Markdown-отчёт содержит ветку, коммиты, исправления, команды/итоги,
  точные skips и ограничения. Секреты/персональные данные исключены.

## Сильное PRD-ревью, раунд 1

Astra: findings=[]. Opus: приняты два high (независимый от БД прямой REST cleanup
с проверкой отсутствия записи; обязательная сверка ownership label перед
операциями над контейнером) и четыре medium: точный whitelist отсутствующего
клиента, обязательный полный набор контуров без скрытых skips, cleanup project volumes/
контейнеров при прерывании и разделение инфраструктурных подзадач. Все отражены
в требованиях. Это уточнение тестовой инфраструктуры, без production изменений.

Spark pass 2: замечание об автоматическом удалении остатков чужого прошлого
запуска после SIGKILL отклонено: такой сборщик может удалить ещё работающий
параллельный запуск. Ограничение SIGKILL отражается в отчёте; cleanup только
для своего project, прерванные остатки удаляет оператор по точному project
name после проверки labels. Обработка обычных исключений/SIGINT/SIGTERM
обязательна и проверяется. Это не обещание выполнить finally после SIGKILL.

14.11.2026 владелец запретил Opus в оставшейся сессии. Первый Opus PRD-pass
завершился до запрета; далее используется Astra без новых вызовов Opus.

Уточнение перед реализацией: PostgreSQL использует project-scoped named volume,
а не tmpfs, поскольку recovery требует сохранности данных при stop/start.
Volume удаляется down -v в finally. Это сохраняет инвариант изоляции и cleanup.

Фокусный запуск выявил дедупликацию повторённого fixture-intent в guidance:
добавляется уникальная метка без изменения фильтров и явная проверка нового
job ID / отсутствия is_deduplicated перед ожиданием счётчика recreated.
Это исправление тестовых preconditions, production метрики не меняются.
