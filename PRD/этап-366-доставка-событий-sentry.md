# Этап 366. Видимость потерь Sentry

## Цель и границы

Ошибка доставки события Sentry от 04.10.2026 (`Network is unreachable`) не
должна оставлять контур наблюдаемости молчаливым. Учёт отказа находится в
процессе MCP, не зависит от самого Sentry, не меняет ответ инструмента и не
отправляет бизнес-операцию повторно. Содержимое событий, DSN, адреса и ПД не
попадают в диагностические записи. Этот этап не меняет сеть VDS: её состояние
проверяет супервизор по штатным логам после деплоя.

## Проверенные факты

- В проекте `error_tracking.configure_error_tracking` вызывает `sentry_sdk.init`
  с `before_send=_sanitize_event`; счётчики процесса и `/metrics` реализованы
  в `service_metrics.py`.
- Установленный в тестовом образе `sentry-sdk 2.71.0` ставит envelope в
  background worker через `HttpTransport.capture_envelope`; `_send_request`
  обрабатывает сетевой exception, вызывает `_handle_request_error`, затем
  `record_lost_event`. Поэтому capture не ждёт HTTP-ответа Sentry.
- Главный PRD и technical requirements требуют безопасной наблюдаемости и
  санитарной обработки событий; Vetmanager REST/OpenAPI не участвует в доставке.
- По одному тексту `Network is unreachable` нельзя доказать, что виноват DNS,
  маршрут VDS или политика egress. Диагноз требует отдельного read-only осмотра
  DNS и маршрута супервизором без публикации endpoint/DSN.

## Архитектурное решение

**Проблема.** SDK знает об отброшенном событии, но наша независимая метрика
этого не видит. Отладочный лог SDK может содержать чувствительные URL.

**Варианты.** Сканировать текст SDK-лога: хрупко и раскрывает адреса.
Периодически отправлять probe-события: дополнительный трафик, но ответ не
объясняет судьбу реальных событий. Подкласс транспортного `HttpTransport` с
перехватом `record_lost_event`: использует точку, в которой сам SDK
регистрирует потери, без доступа к payload в нашем логе. Выбран последний.

**Контекст и ограничения.** Сохраняются sanitizer, текущая конфигурация SDK,
асинхронный worker и низкая кардинальность меток. Внутренний hook SDK
проверяется интеграционным тестом на установленной версии; при обновлении
SDK тест должен показать несовместимость.

**Решение.** Настроить `transport` как подкласс `HttpTransport`. В нём
`record_lost_event` учитывает только категорию `error` и причины доставки
`network_error`, `send_error`, `queue_overflow`, `ratelimit_backoff`, затем
вызывает базовый hook. `before_send` и другие намеренные клиентские отказы
не являются потерями доставки. Наш учёт выполняется и при отключённом
`send_client_reports`: SDK в этом режиме пропускает свой счётчик. Исключение
перехватывается в `_request`, прежде чем `_send_request` SDK преобразует его
в общее `network`; при сетевом исключении фиксировать
только ограниченный класс (`dns`, `route`, `timeout`, `tls`, `network_other`,
`sdk_error`). Источники: `socket.gaierror` → `dns`, route errno → `route`,
таймаут → `timeout`, TLS → `tls`, иные `OSError`/urllib3 → `network_other`,
ошибка SDK без сетевой причины → `sdk_error`
в thread-local переменной рабочего потока; другие причины SDK нормализовать
до ограниченного словаря. Перед каждой отправкой класс сбрасывается и после
неё очищается. HTTP 429 учитывается отдельно в `_handle_response` по error
items исходного envelope: SDK намеренно не вызывает `record_lost_event` для
первого 429. Повторный backoff учитывается стандартным hook; двойного счёта нет.

Предупреждение содержит только класс отказа и число, не содержит exception
string или envelope. Логи `sentry_sdk.errors` и `sentry_sdk.envelopes` надо санировать, поскольку SDK
пишет traceback и тело HTTP-ошибки. Тот же фильтр для используемых SDK
логгеров `urllib3.*` действует только пока поток исполняет Sentry `_request`, чтобы не скрывать
диагностику других HTTP-клиентов. Фильтр заменяет message/args/traceback
безопасным кодом; тест ищет секреты во **всех** сгенерированных записях.
Предупреждение пишется сразу при первом отказе класса и затем не чаще раза в
минуту с накопленным числом под общим lock; метрика считает
каждый отказ. Штатный runtime-лог переживает сброс process-local метрики,
доступной через `/metrics` до рестарта.

Положительный счётчик ответов ingestion endpoint 2xx считает только error
items отправленного envelope и обозначает их принятие для доставки, не
гарантированное сохранение в Sentry. Служебные client reports, транзакции и
сессии не считаются. HTTP 429 трактуется как локально отвергнутый envelope:
это не счётчик потерь Relay и не доказательство, что сервер не записал
категориальный исход; отдельная метка `rate_limited` сохраняет различие.
После деплоя
супервизор сравнивает его с потерями; отсутствие обоих без известного
тестового события считается неопределённым результатом. Все счётчики и
предупреждения не зависят от Sentry. Исключения в нашем hook не должны влиять
на вызов инструмента.

**Инварианты.** Считаем только потерю `error`, не bytes вложений и не
транзакции. Метки фиксированы. Очередь SDK остаётся фоновой. Ответ MCP при
отказе доставки совпадает с ответом при рабочем транспорте. Повторной отправки
бизнес-запроса нет.

**Откат.** Удаление `transport` возвращает штатный SDK; предупреждения и
счётчик перестанут отражать потери. На сетевую конфигурацию сервис не влияет.

## Приёмка и подзадачи

1. (≤2 ч) Написать сторож: локальный тестовый ingestion endpoint падает;
   после фоновой попытки счётчик растёт, в логах нет payload/DSN, MCP-ответ
   прежний. Проверить DNS failure → HTTP 500 → 2xx без наследования класса;
   429, очередь и намеренный `before_send` отдельно; 2xx повышает только
   error-item счётчик. Тест проверяет все записи SDK/urllib3 на отсутствие
   чувствительных полей. Показать красный на исходной реализации и на мутации
   учёта.
2. (≤150 LOC) Реализовать транспортную классификацию и лог-фильтры.
3. (≤150 LOC) Добавить счётчики в существующий реестр и `/metrics`, не меняя
   публичный MCP-контракт.
4. (≤2 ч) Провести локальные и реальные тестовые проверки, аудит, ревью
   сторонними моделями, штатный push и зелёный CI. Супервизор читает
   production-лог после деплоя и сообщает: успешная доставка или видимые потери.
   При нулевых счётчиках обоих исходов супервизор штатным способом создаёт
   одно безопасное тестовое событие и проверяет его судьбу; без этого
   результат остаётся неопределённым. Агент не обращается к production напрямую.

## Оценка простоты

Новый framework и очередь не нужны: SDK уже владеет фоновой отправкой.
Один транспортный subclass нужен, потому что только transport получает
сигнал потери. Метрика добавляется в действующий реестр. При смене SDK
понадобится проверить этот один hook и связанный тест.
