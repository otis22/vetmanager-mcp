# Этап 365. Диагностика неопределённого создания Report AI

## Цель и факты

Репорт #119: MCP сообщил неизвестную ошибку создания задания. По одному отказу нельзя заключить, была ли создана запись. Повтор POST запрещён до проверки состояния.

Сверка с удалённым HEAD `vetmanager-extjs` `d6da5573b49c94be96788ddb25c126eccfbb8a8b`: `POST /report-ai-job` принимает ровно `intent_text`; успешный ответ содержит `data.job` и `data.is_deduplicated`; `GET /report-ai-job/{id}` читает задание. Поиск по корреляции или списку заданий этим REST-контрактом не предусмотрен. Дедупликация активного задания есть, но её срок и условия не дают права автоматически повторять запись после неопределённого отказа. Локальный OpenAPI v6 не описывает этот extension endpoint. Главный PRD требует приватности; технические требования требуют различать сетевые ошибки и не раскрывать ключи. Текущий MCP POST вызывается через `VetmanagerClient`; `vm_transport/retry.py` задаёт `MAX_RETRIES_WRITE = 0`, и сторож закрепит одиночный POST. `_call_vm` превращает исходное исключение в общий `ToolError` и теряет код для feedback.

## Архитектурное решение

**Проблема.** Timeout, сетевой обрыв и 5xx при POST не доказывают, что запись отсутствует. Сейчас видны только `unknown` и общий текст.

**Варианты.** Повторить POST по дедупликации: может создать дубль, если прежнее задание уже вышло из активного состояния. Искать по тексту намерения: REST-пути нет, текст содержит данные запроса. Выдать ограниченный код и корреляцию, сохранив исключение до слоя feedback: безопасно и не меняет семантику записи. Выбран последний вариант.

**Решение.** Только для `create_report_ai_job` классифицировать неопределённый исход в фиксированные коды `REPORT_AI_CREATE_TIMEOUT`, `REPORT_AI_CREATE_HTTP_5XX`, `REPORT_AI_CREATE_NETWORK_UNKNOWN`, а неожиданный успешный HTTP-ответ без валидного ID задания или с неразбираемым JSON — `REPORT_AI_CREATE_RESPONSE_UNKNOWN`. Безопасный класс (`timeout`, `http_5xx`, `network_unknown`, `response_unknown`) выводится из фиксированного кода без свободного текста. `VetmanagerClient` сохраняет корреляцию, реально переданную в заголовке исходящего POST, и числовой HTTP-статус сразу после получения ответа, до JSON decode; тело при этом не сохраняется. Для create всегда генерируется новый UUID с дефисами: входящий `X-Correlation-ID` может содержать свободный текст вызывающего и не годится для ответа и диагностического лога. Этот UUID не совпадает с шаблоном 32-символьного hex-секрета в feedback sanitizer. Именно эта корреляция используется в ответе и логе. Отказ до отправки (`VetmanagerUpstreamUnavailable`, auth, resolution, scope) не классифицируется как неопределённая запись. Сохранять безопасный HTTP-код ответа, если известен. В `_call_vm` перехватывать ошибку декодирования JSON (`ValueError`) только в create-ветке при доказанном исходящем POST; 200 с невалидным JSON, 204 без тела и 200 с JSON без ID входят в этот случай. Проверка ID использует существующий `_extract_job`, который принимает контрактный `data.job` и сохранённую совместимость с top-level `job`. Не переносить сообщение апстрима, текст намерения или детали исключения. В `_call_vm` ветка создания **минуёт обычное преобразование в `ToolError`** и бросает новый нормализованный `VetmanagerError` с безопасным текстом и фиксированным `error_code`. Обёртка MCP ловит его веткой `REPORTABLE_UPSTREAM_ERRORS`: передаёт оригинал как `incident_source` в feedback, а наружу отдаёт санированный `ToolError`. Так код не теряется на границе `_call_vm`. Записать метрику Report AI ровно один раз в create-ветке `_call_vm` после нормализации, не записывая второй сырой код. Лог содержит только класс, код, HTTP-код и корреляцию. Безопасный текст ошибки явно говорит: исход записи не определён, повторный POST не запускать; если достоверный ID уже известен, вызвать `get_report_ai_job` с тем же ID, иначе передать оператору корреляцию для проверки до нового POST. Не предлагать несуществующий REST-список заданий и в общих подсказках соседних инструментов. Автоматического повторного POST и нового GET без ID нет.

**Инварианты.** Известные 4xx сохраняют прежнюю обработку. Отказ до отправки явно говорит, что POST не был отправлен, и не называется неопределённой записью; подсказка о группах при отказе скоупа сохраняется. Ответ успешного создания не меняется. Инструмент не добавляет запросов к Vetmanager. Значения меток ограничены словарём. ПД и свободный текст отсутствуют в диагностике.

**Откат.** Вернуть прежнюю обработку в `_call_vm`; штатный POST остаётся одиночным. Операторская корреляция после отката недоступна. Уже сохранённые в feedback фиксированные коды остаются историческими фактами; правила сопоставления по ним требуют отдельной проверки, потому что новые ошибки снова получат старые отпечатки.

## Подзадачи и приёмка

1. (≤150 строк) Сторожа на timeout, сетевой обрыв, 5xx, HTTP 200 с невалидным JSON, 204 без тела, 200 с JSON без ID и отсутствие повторного POST; проверить текст с запретом нового POST, одиночный код метрики, весь путь нормализованной ошибки до `build_incident_from_exception` с типизированными `error_code` и `http_status`, равенство корреляции ответ/исходящий заголовок без HTTP-контекста и отсутствие приватного текста. Отдельно открытый breaker: ноль POST, нет неопределённого исхода; известный 4xx и соседний GET сохраняют прежний код. Показать красный на старом коде и на мутации обработчика.
2. (≤150 строк) Сохранить транспортную корреляцию и HTTP-статус в `VetmanagerClient`, реализовать нормализацию только для create, убрать несуществующий список заданий из общей подсказки и сохранить поведение успешного ответа и известных отказов.
3. (≤2 ч) Вызвать инструмент на devtr6 с тестовым ключом, сохранить HTTP-код/тело в приватном evidence без ПД; если отказ не воспроизвёлся, зафиксировать это. Выполнить полный suite, аудит, ревью, выпуск и доступную проверку CI. Проверку production-лога выполняет супервизор: прямой доступ агента к production запрещён инструкцией сеанса.
