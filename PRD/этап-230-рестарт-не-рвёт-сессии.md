# Этап 230. Рестарт не рвёт клиентские сессии

## Цель

Устранить обрывы активных streamable-HTTP запросов и закрытие `asyncpg`-пула
после остановки event loop при штатной выкатке контейнера `mcp`.

## Проверенные факты и scope

- Sentry зафиксировал три PYTHON-1 (`RuntimeError: Event loop is closed`) во
  время deploy: 21.08 в 13:19 и 14:36, 22.08 в 19:44 МСК. Стек идёт от
  `asyncpg.connection.close` через `_cancel_current_command` к проверке
  закрытого loop; транзакция — `GET /readyz`.
- PYTHON-6 (`ASGI callable returned without completing response`) в 19:43:58
  22.08, за десять секунд до третьего PYTHON-1, подтверждает обрыв живого
  HTTP-ответа.
- `scripts/deploy_server.sh` пересоздаёт только `mcp` через `compose up -d
  --force-recreate --no-build mcp`. До этапа у сервиса не было
  `stop_grace_period`; Docker давал лишь 10 секунд.
- Production Dockerfile запускает `CMD ["python", "server.py"]` в exec-form:
  Python является PID 1 и получает SIGTERM без shell-wrapper. Это проверяется
  локальным container evidence test, не на production host.
- В используемых зависимостях FastMCP 3.2.0 создаёт Uvicorn 0.44.0 с
  `lifespan="on"` и по умолчанию `timeout_graceful_shutdown=2`. Uvicorn 0.44.0
  при SIGTERM сначала закрывает listener, ждёт tasks до timeout, при истечении
  отменяет их, затем запускает ASGI lifespan shutdown. Lifespan itself этим
  timeout не ограничен.
- Самый долгий запрос, который этот этап обязан дослать, ограничен текущим
  `vm_transport.pool.REQUEST_TIMEOUTS.read=20s` (connect=5s, write=10s,
  pool=2s); retry не удерживает один active HTTP response дольше этого read
  budget. Поэтому Uvicorn drain=20s покрывает именно существующий upstream
  request contract, а Docker grace=45s даёт 15s bounded cleanup и 10s запас,
  не растягивая штатную выкатку необоснованно.
- Контракт транспорта остаётся `streamable-http`; OAuth, маршруты и MCP path
  не меняются. Прод-сервер не является объектом ручных действий.

## Декомпозиция

1. **230.1 — lifecycle cleanup (≤150 LOC).** Перенести startup и cleanup
   process-level async ресурсов в единственный FastMCP lifespan; добавить
   awaitable disposal cached SQLAlchemy engine до остановки loop, блокировку
   его повторного создания и bounded/idempotent cleanup. Удалить конкурирующие
   `signal`/`atexit` handlers, которые могут повторно запускать cleanup после
   закрытия loop.
2. **230.2 — drain (≤150 LOC).** Сохранить Uvicorn владельцем signal и
   connection-drain, но подклассом отметить draining синхронно в его
   `handle_exit` до закрытия listener. Передать Uvicorn
   `timeout_graceful_shutdown=20`, задать `mcp.stop_grace_period: 45s` и
   зафиксировать отдельные structured logs начала/истечения drain.
3. **230.3 — readiness (≤100 LOC).** Ввести process-local признак draining,
   выставляемый при получении SIGTERM. `/readyz` возвращает 503 с
   machine-readable reason `shutting_down` без обращения к storage; обычный
   readiness contract сохраняется вне draining.
4. **230.4 — воспроизводимая проверка (≤150 LOC).** Добавить integration-like
   test real `uvicorn.Server`: SIGTERM/PID 1 path выставляет draining, active
   request завершается, readiness получает 503 до закрытия listener, cleanup
   выполняется на живом loop и не оставляет созданных приложением tasks.
   Отдельно проверить timeout/failure cleanup одного ресурса и compose render.
   Проверка требует отсутствия `RuntimeError: Event loop is closed` и
   незавершённого ASGI response; её точный запуск и exit code записываются в
   AssumptionLog.

## Архитектурное решение

### Проблема

Текущие `SIGTERM` и `atexit` callbacks запускают async cleanup отдельно от
владельца event loop. Они могут выполниться после того, как Uvicorn/AnyIO уже
закрыл loop; одновременно Docker оставляет недостаточный срок для active HTTP
requests.

### Контекст и ограничения

Один HTTP-процесс обслуживает публичный FastMCP streamable-HTTP transport,
включая долгоживущие интеграции Claude и ChatGPT. SQLAlchemy `AsyncEngine`,
httpx clients, billing resolver и Redis rate-limit backend — async resources.
Нельзя менять endpoint, auth или семантику текущих MCP-сессий. Shutdown должен
оставаться идемпотентным для тестов и не раскрывать secrets.

### Рассмотренные варианты

1. Оставить signal/atexit handlers и только увеличить Docker timeout. Это не
   гарантирует порядок cleanup относительно event loop и не устраняет двойной
   cleanup.
2. Поставить собственный SIGTERM handler, который сам управляет Uvicorn,
   слушателем и всеми task groups. Это дублирует зрелую логику Uvicorn и
   повышает риск сломать streamable-HTTP lifecycle.
3. Использовать lifecycle FastMCP/Uvicorn как единственного владельца async
   cleanup, оставить Uvicorn владельцем signal/drain, увеличить budgets и
   добавить readiness-draining при получении signal.

### Выбранное решение

Выбран вариант 3. Uvicorn остаётся владельцем сигналов и connection-drain,
а его тонкий subclass синхронно выставляет draining в `handle_exit` до
родительского handler; он не делает await и не закрывает ресурсы. Поэтому
`/readyz` успевает вернуть 503 через ещё открытый listener, а Uvicorn затем
перестаёт принимать новые соединения и ждёт активные ASGI tasks до 20 секунд.
Срок выбран как maximum одного in-flight request данного этапа, не как
гарантия бесконечного stream; истечение логируется как forced drain.
В teardown FastMCP lifespan (на живом loop) сначала отменяются/ожидаются
известные application background tasks, затем закрываются cached engine и
прочие клиенты с изоляцией ошибок. Каждый из пяти шагов ограничен тремя
секундами, поэтому последовательный cleanup имеет точный верхний budget 15
секунд и не выбрасывает внешний `TimeoutError` из lifespan.
`stop_grace_period: 45s` оставляет минимум 10 секунд slack сверх 20+15 секунд
для signal delivery, Docker и process exit. `/readyz` в draining возвращает
503 без создания storage connection.

Ручной Uvicorn bootstrap сохраняет настройки FastMCP 3.2.0: `lifespan=on`,
`ws=websockets-sansio`, обычный Uvicorn access log и FastMCP log level.
`proxy_headers=True` и `forwarded_allow_ips` берутся из стандартного
`FORWARDED_ALLOW_IPS` (unset остаётся Uvicorn default), поэтому reverse-proxy
semantics не ослаблены; прикладное доверие XFF по-прежнему ограничено отдельным
`WEB_TRUSTED_PROXY_IPS`. `_run_startup_step("mcp_run", ...)` сохранён для
structured startup-aborted logging.

### Инварианты

- Транспорт остаётся streamable-HTTP, `MCP_PATH` и public routes неизменны.
- Новый lifecycle cleanup никогда не создаёт второй event loop и не вызывает
  `dispose()` из `atexit`/фонового thread.
- Cleanup завершается до закрытия runtime loop; повторный вызов безопасен, а
  после начала draining нельзя создать новый engine или storage connection.
- Во время draining новые readiness probes получают 503, а активные запросы
  получают время на штатное завершение.
- Ошибки cleanup логируются только class/step. Логи drain содержат длительность,
  число tasks и outcome, но не credentials или request data.

### Rollback/fallback

Изменение обратимо одним revert: возвращаются прежние запуск и compose budget.
Если 20 секунд недостаточны для подтверждённого легитимного запроса, новый
отдельный Roadmap пункт определит измеренный timeout; в этом этапе не вводится
непроверенная конфигурация или изменение transport contract.

## Acceptance criteria

- SQLAlchemy cached engine dispose вызывается lifecycle teardown до закрытия
  loop; regression test воспроизводит закрытие при активном запросе и не даёт
  создать engine после начала draining.
- `mcp` имеет `stop_grace_period: 45s`, Uvicorn получает graceful timeout 20;
  local container test подтверждает PID 1/SIGTERM exit path в budget.
- В draining `/readyz` возвращает HTTP 503 и `shutting_down` через ещё открытый
  listener, не exception.
- Test real Uvicorn доказывает: active request завершён, lifecycle cleanup
  идёт на живом loop, один зависший resource cleanup не блокирует engine, и
  нет pending application background tasks, `RuntimeError: Event loop is
  closed` либо `ASGI callable returned without completing response` в output.
- Structured drain logs отделяют forced timeout от PYTHON-1/PYTHON-6; новые
  такие Sentry события после штатного deploy являются trigger для revert.
- Полный default test contour, Bash syntax/ShellCheck и CI PR зелёные.

## Не входит в этап

- Zero-downtime/canary deployment с двумя экземплярами.
- Изменение OAuth, bearer auth, MCP transport и активных клиентских сессий.
- Ручные действия на production host.
