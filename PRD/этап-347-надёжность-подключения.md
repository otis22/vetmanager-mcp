# Этап 347. Надёжность подключения клиники

## Цель и проверенные факты

Жалоба клиники 22.09.2026: форма логина и пароля зависает на создании токена. Этап 339 ограничил каждый `_request_with_retry` 45 секундами, но выдача токена и проверка `GET /rest/api/user` идут последовательно. После сохранения `render_account_dashboard_response` заново вызывает `evaluate_connection_health`, что добавляет ещё одну сетевую проверку и может показать ложный отказ рядом с успехом.

Текущий `_request_with_retry` считает успешным любой статус `<400`; `vm_transport/pool.py` создаёт `httpx.AsyncClient` без `follow_redirects`, а его default — `False`. OpenAPI описывает `POST /token_auth.php` и `GET /rest/api/user` с успешным ответом 200. Схема не обещает безопасного повтора POST после доставки. Продуктовый PRD требует понятного результата подключения; технические требования сохраняют режимы API key и user token. Непосредственный production доступ запрещён. Изменение трактовки 3xx затронет и здоровье уже сохранённых подключений; число таких подключений нельзя выяснять прямым обращением к production. Их состояние станет `unknown` и потребует исправления адреса клиники; это осознанная смена прежнего ложного `active`.

## Scope и декомпозиция

1. Сторожа бюджета: показать, что общая prepare-задача одного submit логин/пароль ограничена 55 секундами от её старта (host resolution, POST и GET), несмотря на вложенные бюджеты 45 секунд. Присоединившийся позже запрос ждёт только остаток этой задачи. Отмена одного ожидающего через `shield` не отменяет общую задачу; при её timeout все ожидающие получают понятную timeout-ошибку и никто не сохраняет подключение. POST не повторяется. Подзадача ≤150 строк.
2. Сторожа редиректов: 3xx от выдачи токена и обеих GET-проверок отклоняется с безопасной причиной, без сохранения подключения и без логирования `Location` или секретов; успешная метрика не пишется. Не следовать редиректу. Каждый сторож намеренно сломать до приёмки. Подзадача ≤150 строк.
3. Сторожа ответа: успешный submit и reauth отображают результат уже выполненной проверки без нового health probe; ошибка submit не запускает ещё один probe существующего подключения. Сторож имитирует отказ повторной проверки после успешного сохранения и требует только `active` на странице. Override действует только на текущий HTTP-ответ, не хранится и не подменяет `compute_activation_state`; последующий GET кабинета и выпуск Bearer выполняют актуальную проверку. Сохранённое подключение при 3xx показывает адресную подсказку вместо общего «позже». Подзадача ≤150 строк.
4. Тестовый контур, аудит, полный mock и opt-in real suite, сильный committed diff-review, push и зелёный CI. Подзадача ≤2 часов.

## Архитектурное решение

**Проблема.** Локальный дедлайн HTTP не ограничивает цепочку из двух запросов и дополнительный health probe при отрисовке.

**Контекст.** Выдача токена не идемпотентна; существующая общая prepare-задача защищена `asyncio.shield` для двух одновременных отправок. Сохранение в БД происходит только после обеих проверок. Редирект является неоднозначным ответом и для `token_auth.php`, и для REST probe. Нельзя переносить неуспех post-save health на уже сохранённое подключение.

**Варианты.** Уменьшить бюджет каждого HTTP-вызова: просто, но не ограничивает всю цепочку. Добавить дедлайн к web route: охватывает рендер и БД, но при истечении после commit создаёт ложный отказ. Выбран один дедлайн 55 секунд внутри общей prepare-задачи до сохранения, плюс отсутствие повторного probe в ответе формы. Он даёт человеку результат за примерно минуту с учётом локальной БД/рендера; внешний дедлайн пресекает GET после медленного POST, а вложенные retry deadlines не расширяются. Сохранение остаётся в каждом waiter после успешного возврата prepare, не внутри общей задачи. Успешная проверка служит основанием для показа `active` только в этом ответе.

**Инварианты.** POST не повторяется после возможной доставки; общий prepare task не отменяется таймаутом отдельного ожидающего; запись только после успешной проверки; 3xx не успех и не переходит на иной адрес; нет секретов и `Location` в логах; обычное открытие кабинета проверяет здоровье как прежде.

**Rollback.** Константу общего бюджета можно скорректировать по стендовым измерениям. При timeout после POST токен мог быть выпущен, но не сохранён; повторная отправка может выпустить ещё один. Ошибка пользователю объясняет неопределённость и предлагает подождать/проверить подключение перед повтором. Это принятый риск при отсутствии idempotency key и возможности безопасно повторить POST. Если поведение upstream изменится, откатить строгую обработку 3xx можно только с новым доказательством безопасности редиректа; прежний ложный успех не является безопасным fallback. По §6.0 перед push необходим read-only снимок супервизора о числе действующих подключений с 3xx на health probe и решение для них; прямой доступ к production запрещён. Существующие Bearer/MCP credentials не меняются, но выпуск новых Bearer через кабинет при `unknown` будет заблокирован.

Architecture Critique required: auth, latency и граница между service и web. Этот гейт должен покрыть полноту PRD и засчитывается PRD-review.

## Приёмка

- Общий deadline подготовки 55 секунд, ясная ошибка при timeout, нет второго POST внутри одного submit.
- 3xx не проходит как успешная проверка доступа или выдача токена.
- На странице после сохранения видны успех и active, без второго сетевого probe и `connection_health_failed`.
- Сторожа доказывают отсутствие `Location`/секретов в логах, отсутствие success-метрики при 3xx, сохранение общей задачи при timeout одного waiter и дедлайн без длительных sleeps.
- Оба стенда не смешиваются: real suite использует только тестовые credentials из `.env`; никакого обращения к production.
- Красные и зелёные сторожа, запись в AssumptionLog, аудит, полный набор проверок, review Astra и Opus, push и зелёный CI.

## Простота

Локальный дедлайн подготовки и явный флаг отрисовки формы. Новых классов, хранилищ и retry-движков нет.
