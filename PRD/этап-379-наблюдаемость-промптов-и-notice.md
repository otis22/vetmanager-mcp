# Этап 379. Наблюдаемость промптов и предупреждения об истечении токена

## Цель и границы

Убрать два пробела аудита 10.10.2026: запросы MCP prompts и выдача expiry notice сейчас не видны в `/metrics`. 379.1 — только PRD; 379.2 — реализация и live; 379.3 — аудит, сильное ревью diff и выпуск. Права, тексты подсказок, rolling-24h claim и DB-схему не менять. `prompts/list` правами не фильтруется (377); метрика лишь наблюдает его текущую выдачу.

## Проверенные факты

`prompts.py` регистрирует 21 статический prompt через `@mcp.prompt`, включая `welcome_first_session` и Report AI helper; у части сценариев есть бизнес-аргументы (`daily_schedule(date, doctor_id)`, `find_client(query)`), а у welcome аргументов нет. MCP `prompts/get` принимает `name` и необязательные `arguments`; аргументы могут содержать свободный текст и никогда не становятся метками. `prompts/list` возвращает каталог. В установленном FastMCP 3.4.7 `Middleware` имеет `on_list_prompts(context, call_next)` и `on_get_prompt(context, call_next)`; у get `context.message.name` доступно до `call_next`, у list имена доступны из успешного результата. `server.py` уже ставит `ToolErrorTrackingMiddleware` после OAuth middleware; `ToolVisibilityMiddleware` реализует только `on_list_tools`, поэтому prompts остаются общим каталогом. Живой HTTP-протокол и очистка тестовых аккаунтов есть в `tests/test_stage375_live.py` и `test_stage376_live.py`.

`tool_error_tracking.py` вызывает `_add_expiry_notice` только после успешного `tools/call` и наличия request-local `(account_id, bearer_token_id)`. Внутри `claim_expiry_notice` срок должен быть 1–14 дней; условный `UPDATE ... RETURNING` выигрывает claim, если с прошлой отметки прошло 24 часа. Весь путь ограничен `asyncio.timeout(0.5)`. `None` возвращается также при отсутствии/неактивности/бессрочности токена и вне окна; исключение из claim или подготовки подавляется middleware, исходный ответ сохраняется. Сейчас эти причины в метрике не различимы. Сам claim не доказывает доставку ответа клиенту.

`service_metrics.py` хранит счётчики с `_LOCK`, сбрасывает `reset_service_metrics()`, отдаёт `snapshot_service_metrics()` и текст `/metrics` с HELP/TYPE. `tools/call` уже имеет счётчик и first-session gauge, но ни prompt series, ни notice series нет. Главный PRD требует prompts и observability; технические требования запрещают передавать credentials через аргументы prompts. OpenAPI v6 здесь не задаёт MCP middleware или notice; контракт проверяется по коду, MCP HTTP и тестам.

## Архитектурное решение

**Проблема и варианты.** Считать на уровне HTTP route означало бы разбирать JSON-RPC вручную и смешать MCP и web; оборачивать каждый prompt отдельно дублировало бы регистрацию и пропускало будущие имена. Выбран общий FastMCP middleware с двумя хуками. После успешного `call_next` list увеличивать счётчик один раз за каждое имя в возвращённом каталоге, get — один раз за подготовленный результат. Отказ/исключение не считать успешной выдачей; если нужен знаменатель ошибок, фиксированный `outcome=error` можно добавить в тот же счётчик, без пользовательских меток. В HELP явно назвать list «каталожное появление», get «подготовленный ответ», а не «прочтено агентом». Регистрационный allowlist строить из реестра prompts при старте/после регистрации, не из произвольного входного имени и не вторым рукописным списком. Неизвестное имя (включая ошибочный запрос) сводить к `other`; `method` только `list|get`, `prompt` только зарегистрированное имя или `other`. Сторож проверяет не только функцию нормализации, но и весь `/metrics` после произвольных имён/аргументов. Метрика best effort, prompt-ответ не зависит от её ошибки.

Для notice нужен учёт на существующей границе `tool_error_tracking.py` + `token_expiry_notice.py`. После успешного claim и формирования `ToolResult` считать `appended` один раз. Бакеты срока: `1d` для `days=1`, `7d` для `2..7`, `14d` для `8..14`; они не меняют существующий текст точных дней. Счётчик `vetmanager_token_expiry_notice_issued_total{threshold,outcome}` имеет только эти threshold и `outcome=appended`; HELP говорит о подготовленном ответе. Отдельный `vetmanager_token_expiry_notice_skipped_total{outcome}` с закрытым набором `claim_recent|deadline|no_subject|ineligible|unavailable` нужен потому, что при `no_subject` или deadline до чтения токена threshold неизвестен. `claim_recent` учитывать только после проверки действующего токена в окне, `ineligible` — остальные ранние `None`, `deadline` — `TimeoutError`, `unavailable` — иная ошибка. `no_subject` считать на успешном `tools/call` без subject; не считать OAuth/ошибочные tool-ответы. Не записывать token/account id, prompt arguments, ошибки целиком, дату истечения, текст ответа или клинические данные ни в labels, ни в logs. Разделение исходов не должно делать лишние DB-запросы или изменять атомарность claim. Если точную причину без дополнительного запроса не различить, выбрать более общий закрытый outcome и явно задокументировать его вместо догадки.

**Инварианты и откат.** MCP ответы, права и claim остаются прежними; сбой телеметрии не меняет ответ и укладывается в существующий deadline. Никакой новой DB-таблицы/cache. Откат — снять middleware/новые вызовы метрик, оставив старые tools и notice. Architecture Critique требуется: меняется общая MCP middleware граница, метки влияют на приватность/кардинальность, учёт notice должен сохранить поведение транзакции. Один Astra PRD-review покрывает архитектуру, scope, альтернативы, риски, приёмку и rollback; второй сильный reviewer — Kimi супервизора после 379.1 по прямому решению владельца.
