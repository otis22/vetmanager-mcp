# Этап 234. Ошибки и логи переживают рестарт

## Цель

Сделать production error tracking фактически включаемым через существующий
`/opt/vetmanager-mcp/.env` и сохранить диагностические application logs после
пересоздания контейнера. Содержимое persistent logs остаётся тем же, что и у
уже существующего Docker stdout sink; доступ к named volume имеют только
Docker-администраторы хоста.

## Проверенные факты

- `server.py:48` вызывает `configure_error_tracking()` при старте; функция
  возвращает `False` без вызова Sentry, если оба DSN пусты.
- `docker-compose.yml` задаёт environment `mcp` поимённо, поэтому значения из
  `.env` не попадают в процесс, пока не перечислены в Compose.
- `json-file` привязан к жизненному циклу Docker container: его ротация
  ограничивает объём, но не сохраняет файл после `docker compose up --force-recreate`.
- Проект уже использует структурные logs в stdout; контейнер исполняется как
  UID/GID хоста. Dockerfile может подготовить каталог до переключения на user,
  а named volume сохраняется при пересоздании сервиса.

## Декомпозиция

1. Пробросить три error-tracking env и описать их значения по умолчанию в
   README (≤30 строк).
2. Добавить persistent file handler с UTC-date filenames, ≤10 MiB на файл и
   максимум 14 файлов/14 UTC-дней, volume и bounded stdout Docker logging (≤150 строк
   вместе с тестами).
3. Проверить Compose config, unit/mock e2e и старт без DSN; 234.3 оставить
   супервизору для real production event (≤2 ч).

## Архитектурное решение

### Проблема и ограничения

Exception tracking готов, но не получает DSN в `mcp`. Docker `json-file`
без ограничений может занять диск, а даже с `max-file` исчезает при удалении
container. Нельзя менять production host, daemon config или `/opt` в рамках
этапа. Логи не должны получить новый format/широкий доступ и не должны
зависеть от внешнего collector/сервиса.

### Рассмотренные варианты

1. Только `json-file` с `max-size`/`max-file`: просто и ограничивает диск, но
   не решает потерю logs при recreate — отклонён.
2. Journald/внешний collector: может пережить recreate, но требует host daemon
   configuration либо новую production-службу и её эксплуатацию — отклонён как
   несоразмерный этому этапу.
3. Оставить stdout и записывать те же formatted records в named Docker volume:
   volume переживает recreate; bounded handler ограничивает объём и число files;
   Docker `json-file` с ротацией дополнительно ограничивает краткоживущий `docker logs`.
   Выбран.

### Выбранное решение

`mcp` получит `ERROR_TRACKING_DSN`, `ERROR_TRACKING_ENVIRONMENT=${...:-production}`
и `ERROR_TRACKING_TRACES_SAMPLE_RATE=${...:-0}`. DSN останется опциональным:
пустое значение не меняет успешный startup.

Compose монтирует named volume `mcp-logs` в подготовленный writable каталог.
При заданном `PERSISTENT_LOG_PATH` structured logging добавляет второй handler
с тем же formatter/filter: UTC-date files, ≤10 MiB каждый, максимум 14
последних files (≤140 MiB) и возраст не более 14 UTC-дней.
Stdout сохраняется; Docker `json-file` log driver с `max-size=10m`, `max-file=3`
не даёт ему бесконтрольно занять диск. Для инцидентов после recreate оператор
читает persistent volume; это application logs, а не гарантированный журнал
Docker daemon/entrypoint.

### Инварианты, риски и rollback

- Пустой DSN отключает tracking и не валит старт; `send_default_pii=False` и
  существующий Sentry sanitizer не меняются.
- Одна запись имеет одинаковые structured fields в stdout и persistent file;
  file handler не создаётся вне Compose без `PERSISTENT_LOG_PATH`.
- Named volume не удаляется при `docker compose up --force-recreate`; удаление
  через `docker volume rm` остаётся явной операторской destructive action.
- Dockerfile создаёт mount point с теми же `UID/GID`, которые Compose передаёт
  в build и `user:`; ошибка подготовки persistent path валит startup, а не
  создаёт тихий degraded режим.
- Rollback: удалить volume mount/env и file handler в следующем release;
  stdout-логи продолжат работать. Не удалять `mcp-logs` до окончания retention.

Architecture Critique: required — меняются production logging/storage behavior
и retention boundary.

## Acceptance criteria

1. Compose `mcp` пробрасывает все три env, environment default `production`,
   trace rate default `0`; README описывает их рядом с runtime env.
2. `configure_error_tracking` по-прежнему вызывается на startup и при пустом
   DSN возвращает no-op без startup error.
3. Structured application logs хранятся на named volume, переживают recreate,
   имеют UTC-date filenames, возраст не более 14 дней, максимум 14 последних
   files и ceiling 140 MiB;
   stdout bounded.
4. Tests проверяют второй handler/ротационные параметры и Compose contract;
   `docker compose config` и полный test suite проходят.
5. 234.3 явно отмечен как pending action супервизора, без реального event и
   без обращения к production.
