# Этап 452. Безопасный опрос активации кабинета

## Цель

Устранить потерю введённых данных при ожидании первого запроса помощника.
Источник: аккаунт 53, ключ 121, повтор фидбека #139. Этапы 453–454
не реализуются. Production-конфигурация вручную не меняется.

## Проверенные факты

`web_html.compute_activation_state` уже определяет четыре состояния по
подключению, действующим ключам и живому OAuth с использованием. Опрос
`web_routes_account._load_activation_state_for_polling` независимо
интерпретирует историю аккаунта: старое auth_succeeded делает новый ключ
использованным. JS перезагружает страницу при расхождении, а также после
20 опросов. Счётчики sessionStorage позволяют зациклить перезагрузки.

## Архитектурное решение

Проблема: две интерпретации активации и безусловная навигация уничтожают
форму. Контекст: signed session, SQLAlchemy, серверный HTML и встроенный
JS; существующие Playwright-тесты и визуальная матрица 345.

Выбранное решение: оставить единственный вычислитель состояния
`compute_activation_state`, вызвать его из DB-only загрузчика опроса
с сырыми датами и статистикой действующего доступа. Общий парсер дат
принимает datetime и ISO-строки из dashboard, сохраняя секунды;
резервный формат отображения используется лишь при отсутствии raw. Не читать историю
TokenUsageLog для определения активации. Наличие подключения в опросе
означает ранее проверенное подключение: health активен без новой
upstream-пробы; отсутствие подключения даёт needs_connection.
Проверка здоровья остаётся на открытии страницы. Опрос включён строго
только в needs_client_use при уже проверенном здоровом подключении:
в needs_connection/needs_token/ready polling-маркера нет. Это не новый
health-check: изменение доступности upstream определяется при открытии.
Переход опроса в более раннее состояние допускает один GET-переход; страница
needs_connection/needs_token уже не опрашивает.

OAuth: учитывать только активный грант активного клиента с живым access
или неиспользованным живым refresh. Для страницы и опроса брать признак
живого доступа на уровне конкретного гранта, ограничивая запрос аккаунтом.
Использованный умерший грант не активирует соседний новый грант.
Владелец правила — oauth_service: общий SQL-конструктор живых грантов
используют и accounts_with_live_oauth_access, и новый запрос grant IDs
по аккаунту; условия живого access/refresh не копируются.

JS: при смене состояния автоматически обновлять страницу только при
отсутствии фокуса внутри любой формы и отсутствии события input/change
в любой форме с момента загрузки. Признак редактирования остаётся до
следующей загрузки; значения полей нигде не сохранять. Проверять
признаки после получения ответа, непосредственно перед обновлением. Автоматическое обновление —
только location.replace('/account'), то есть GET вместо повторной
отправки POST. Проверить также страницу после любого POST без
разового ключа. Если
форма занята — остановить опрос, показать неблокирующее сообщение
«Состояние подключения изменилось. Обновите страницу, когда закончите
работу с формой» и явную ссылку GET /account «Обновить страницу». На странице разового
показа ключа (POST-ответ без PRG, есть issued-token-panel) автоматический
reload всегда запрещён, даже при свободных формах: только уведомление
с явной GET-ссылкой после сохранения ключа. При неизменном состоянии
никаких перезагрузок, включая 20-й опрос. Сохранить предел 80 опросов
на одну загрузку, без sessionStorage. Отказ account_inactive продолжает
обрабатываться существующим способом.

Альтернативы: всегда только уведомление проще защищает формы, но
отменяет ожидаемое автоматическое завершение первого запроса; сохранение
полей в sessionStorage сложнее и хранит секреты; вызов полного загрузчика
кабинета в опросе добавляет побочные записи, предупреждения и лишние данные.
Выбрана узкая DB-загрузка и защита навигации событиями форм.

Инварианты: доступ проверяется действующим ключом/грантом; архивный аккаунт
не активируется; опрос не обращается в Vetmanager, не меняет данные;
первый запрос bearer/OAuth без занятой формы на обычной странице даёт
ready и GET-переход; разовая выдача ключа — явное исключение: вместо
автоперехода уведомление до сохранения ключа пользователем;
ни поля форм, ни персональные данные не попадают в evidence/репозиторий.
Новые тексты и комментарии — на русском.

Откат: штатный возврат предыдущего образа, миграций и изменений
конфигурации нет. При откате возвращается известная проблема; штатного флага отключения
ожидания нет.

## Декомпозиция

1. PRD, чтение артефактов, собственное ревью и простота; Spark, затем
   одновременно Architecture Critique + PRD review Astra/Opus (до 2 ч).
2. Красные DB-сторожа: история отозванного/истёкшего ключа + новый ключ;
   OAuth до/после запроса и умерший грант рядом с новым (до 150 строк).
3. Общий вычислитель в опросе и единый признак живого гранта (до 150 строк).
4. Красные Playwright-сторожа с реальным JS: input/change, фокус,
   изменение формы во время ответа, 20-й опрос без изменения состояния,
   свободная форма и первый запрос; исправление JS (до 2 ч).
5. Фокусные проверки, визуальная матрица и парный визуальный гейт, аудит,
   commit, Spark и парный committed diff gate (до 2 ч).
6. Финальные mock+real на окончательном SHA, push, зелёный CI, merge,
   штатный Deploy Prod, read-only пост-релизный контроль (до 2 ч).

## Приёмка и выпуск

Проверены записи использования: auth/bearer.py resolve_bearer_auth_context
вызывает mark_used, flush, обновление TokenUsageStat и commit audit перед
возвратом контекста; runtime_auth.py синхронно обновляет last_used_at
гранта/access и коммитит перед возвратом OAuth-контекста. Новый сторож
должен вызвать настоящий bearer resolver на тестовой БД и получить ready
без зависимости от TokenUsageLog.

Сравнить page render и GET /account/activation-status на одной БД;
старый auth_succeeded не переводит новый доступ в ready. Проверить
неизменность состояния OAuth, истечение, отзыв и активность клиента.
Playwright должен исполнить встроенный JS с ускоренным таймером и
перехваченным ответом опроса. Ускорение: add_init_script перехватывает
setInterval с delay=15000, сохраняет callback и вручную вызывает его
после подготовки формы; clearInterval фиксирует остановку. Это позволяет
проверить 20-й и 80-й опросы без ожидания реального времени: заполненное поле сохраняется, reload
отсутствует; уведомление видно и его ссылка ведёт GET /account; на разовой выдаче ключа reload также отсутствует, ссылка
обновления ведёт GET /account; в needs_connection нет polling; чистая форма с ready перезагружается. Сторожа показать
красными на исходном коде и описать конкретные причины в AssumptionLog.

Визуальные evidence — только существующие синтетические страницы
матрицы 345, desktop/phone full_page и отдельный первый экран телефона,
с проверкой полноты и хешей; уведомление дополнительно проверить в
Playwright. Для живых API-тестов выбран .env TEST_DOMAIN/TEST_API_KEY,
а не bearer-стенд. Инструменты MCP не меняются, обязательный отдельный
живой вызов изменённого MCP tool неприменим. После деплоя проверить
доступность кабинета без сессии, health/version и успешность rollout;
сессию реального аккаунта не извлекать. Если доступен штатный read-only
контроль в production-контейнере, проверить новый вычислитель по
идентификаторам, без вывода реквизитов. Ограничения проверки фиксировать.

## Связанные артефакты и ревью

После создания прочитаны главный PRD и technical requirements: bearer
принадлежит аккаунту, кабинет работает через session cookie, сырой ключ
показывается один раз. Внешний API Vetmanager не меняется, новые
эндпоинты и поля upstream не вводятся. Собственное PRD-review:
границы задачи и приёмка определены, миграции не нужны. Оценка простоты:
один вычислитель, один sticky-флаг формы, один явный выбор обновления.
Architecture Critique обязателен: меняется production behavior и
граница OAuth/кабинета; объединён с PRD-review и расходует общий бюджет.

## Уточнение среды перед выпуском

Чистая сборка 10.11 выявила отсутствие libatomic.so.1 у Node из
Playwright 1.65.0: test stage падает до установки браузерных зависимостей
(exit 127). Добавить пакет libatomic1 только в test stage перед запуском
Playwright. Production stage не меняется. Красный — реальный build,
зелёный — повторная чистая сборка и suite. Это обеспечение уже
запланированного CI-гейта, не новый продуктовый этап. Проверить diff
отдельным scout вместе с изменениями после PRD-бюджета.

Уточнение визуального гейта: при уведомлении скрывается прежнее ожидание
первого запроса; уведомление располагается перед карточкой активации,
а при разовом ключе — перед ключом. Первый экран телефона проверяется
Playwright. Это устраняет противоречивый текст без автоматической
прокрутки и без потери фокуса.
