# Этап 380. Фильтры персонала в медкартах

## Цель и границы

Дать аудитору маршрут «сотрудник + период» по медицинским картам всех
пациентов без выгрузки всех страниц и локальной фильтрации. В 380.1 создаётся
и проходит review этот PRD; 380.2 реализует два необязательных параметра
`get_medical_cards_by_date`; 380.3 проверяет и выпускает результат. Нового
инструмента, нового upstream-маршрута, записи в Vetmanager и изменения прав не
будет.

## Проверенные факты

Репорт #134 от 12.10.2026 (account 42, `medium/missing_tool`) сообщает, что
для аудита одного врача за период пришлось выгрузить более 40 страниц карт и
фильтровать `doctor_id` локально. Это пробел нашего MCP, не Vetmanager: в
`filters.py` `FILTER_FIELDS_BY_ENTITY["medicalCards"]` уже разрешает
`doctor_id` и `creator_id`, но `get_medical_cards_by_date` их не передаёт.

`/rest/api/MedicalCards` и схема OpenAPI `medicalCards` называют поля ответа
точно `doctor_id` и `creator_id`, оба integer. Справочник сущностей подтверждает
`doctor_id` как внешний ключ на `user`, лечащего ветеринара; `creator_id` в
MedicalCards он не документирует. Семантика `creator_id` («ID пользователя,
создавшего запись») задана постановкой и должна быть подтверждена именно
контрактом/живой проверкой OpenAPI-контура, а не приписана справочнику. Не
заменять эти имена `user_id` или `patient_id` и не выдавать их за одно поле.

Сейчас `get_medical_cards_by_date` в `tools/medical_card.py` строит
полуоткрытый фильтр `date_create >= начало_дня`, `date_create < начало
следующего дня`, при положительном `clinic_id` добавляет equality filter,
после чего передаёт всё через `build_list_query_params`. После ответа он сам
формирует неизменяемую для этого этапа обёртку с `total`, `total_known`,
`truncated`, `medical_cards_count` и `medical_cards`. Поэтому добавление
upstream filters не должно менять форму и расчёт pagination metadata.

Смежный `get_medical_cards` принимает произвольный разрешённый `filter`, но
всегда добавляет обязательный `patient_id` из `pet_id`: он подходит для
конкретного питомца и дополнительных условий, но не для поиска сотрудника за
период среди всех пациентов. Фактическая подсказка `tools/list` берётся из
`tool_descriptions.py`, а не docstring (факт этапа 378), поэтому изменение
текста должно быть там.

## Архитектурное решение

**Проблема.** Нужен discoverable и пагинируемый путь для выборки карт
конкретного лечащего врача или автора за период, не заставляющий клиента
получать все карты.

**Варианты.** (1) Ввести отдельный инструмент поиска по врачу — дублирует
уже корректную date-range, pagination и фильтры. (2) Предложить общий
`get_medical_cards` с raw `filter` — не решает обязательный `pet_id` и не
даёт аудит по всем пациентам. (3) Добавить два typed optional параметра в
существующий date-range маршрут и преобразовать каждый в equality filter —
выбрано. Это минимально расширяет публичный MCP-контракт и использует уже
подтверждённые API-поля.

**Выбранный контракт.** В сигнатуру после `clinic_id` добавить
`doctor_id: int | None = None` и `creator_id: int | None = None`.
Положительное значение каждого параметра добавляет соответственно
`{"property":"doctor_id","value":"<id>","operator":"="}` или
`creator_id` к существующему набору фильтров. Оба фильтра независимы и
сочетаются друг с другом, с date/date_from/date_to и положительным
`clinic_id` как AND. `0`, отрицательное значение и `None` повторяют нынешнюю
семантику optional `clinic_id`: фильтр не посылается; нецелое значение не
проходит MCP input schema и до HTTP не доходит. Возвращать отдельные
`*_filter_applied` или эхо ID не требуется: это расширило бы ответ без нужды;
его текущая форма остаётся прежней.

В `tool_descriptions.py` у `get_medical_cards_by_date` явно назвать оба
параметра и их различную семантику, сказать, что они работают по всем
пациентам внутри периода и могут сочетаться с clinic filter. У
`get_medical_cards` добавить короткое обратное правило: это маршрут
конкретного `pet_id`; для сотрудника по периоду среди всех питомцев —
`get_medical_cards_by_date`. Не обещать, что автор равен лечащему врачу.

**Инварианты и откат.** Маршрут остаётся read-only, права и запись в реестре
доступа не меняются. Без новых параметров query params, сортировка,
полуоткрытая граница дат и ответ остаются byte-for-byte семантически прежними.
Пагинация остаётся обязанностью вызывающей стороны при `truncated=true`.
Фильтры не логируют значения и не меняют деперсонализацию ответа. Если
Vetmanager подтвердит утрату поддержки поля, сохранить опубликованный параметр
и вернуть ясный безопасный MCP-отказ, а не молча выдать неотфильтрованные карты
и не фильтровать локально. Удаление параметра допускается только отдельной
versioning/deprecation-задачей; существующий date-range маршрут не менять.

**Architecture Critique.** Required: этап меняет публичный MCP input contract
и текст, который видит tools/list. Сильный PRD review ниже одновременно
проверяет границу ответственности, совместимость, privacy, простоту и rollback;
отдельный второй Architecture Critique не нужен, если его prompt явно содержит
эти критерии.

## Приёмка и декомпозиция

Каждая подзадача ограничена ≤2 часов и ≤150 строк изменения. В этой постановке
`devtr6` означает локальный HTTP MCP harness с изолированной SQLite и
контролируемым upstream fixture, а не внешний контур Vetmanager. Новый guard
принимается только после показанного красного прогона: он должен ломаться
вместе с охраняемым поведением. 380.1 не меняет код, поэтому его live/red-green
принадлежат 380.2. В live-проверке не писать ключи, токены, имена людей,
клиентов или клинический текст; в AssumptionLog приложить HTTP/MCP код и
очищенное тело ответа.
