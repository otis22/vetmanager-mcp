# Этап 321. Контракт полей инструментов

## Цель

Убрать четыре подтверждённых расхождения между публичными MCP-инструментами и
реальным REST-контрактом Ветменеджера: сохранять причину приёма, фильтровать
госпитализации по питомцу, не считать отпуск/выходной свободным рабочим
временем и возвращать стабильную ошибку ввода для неверной даты табеля.

Изменения делаются только после двойной проверки: по исходникам
`vetmanager-extjs` и живыми вызовами контура `TEST_DOMAIN`/`TEST_API_KEY`.
Finding из супер-ревью сам по себе доказательством не считается.

## Источники и проверенные факты

### 321.1 Admission: `description`, `clinic_id`, `status`, `type_id`

Исходники Ветменеджера:

- `rest/protected/models/Admission.php:11-21,45-59,90-103` объявляет
  `description`, `patient_id`, `type_id`, `clinic_id`; поля `reason` нет.
- `application/src/Entity/Admission.php:37-67` переводит вход только в
  `description` и `type_id`; неизвестные `reason` и `type` не входят в mapping.
- `rest/protected/controllers/AdmissionController.php:258-307` требует
  `client_id`, `clinic_id`, проверяет `patient_id` и передаёт данные в Entity;
  `prepareData()` на строках 246-255 безусловно ставит `status=not_confirmed`.
- PUT на `AdmissionController.php:382-465` требует `clinic_id`, `start`, `end`,
  сливает body с текущей записью и вызывает тот же Entity mapping. В отличие
  от create, этот метод **не вызывает** `prepareData()`; переданный update-
  `status` входит в `getMappingData()` на строке 58 и обрабатывается дальше
  бизнес-проверкой статуса. Поэтому update-`status` остаётся, `description` и
  `type_id` записываются, а `reason` и `type` теряются.
- Модель подтверждает типы: `Admission.php:50-58` — `description` допустим,
  `type_id` числовой. OpenAPI `components.schemas.admission` содержит
  `description`, `type_id`, `clinic_id`, но не `reason`/`type`.

Живой стенд 16.09.2026 (адрес и ключ не публикуются; тела сокращены только до
контрактных полей, без персональных данных):

- `POST /rest/api/admission` без `clinic_id` → HTTP 400,
  `{"success":false,"message":"Clinic id is empty","data":null}`.
- POST с `description=stage321-description-create`, отличающимся `reason`,
  `status=save`, `clinic_id` и `type_id=0` → HTTP 201; body/read-back:
  `description="stage321-description-create"`, `type_id=0`,
  `status="not_confirmed"`, `clinic_id=1`. `reason` в ответе отсутствует.
- `PUT /rest/api/admission/860` с новым `description`, отличающимся `reason`
  и `type=987654` → HTTP 201, `{"success":true,"data":{"admission":860}}`;
  GET → HTTP 200, новый `description`, прежний `type_id=0`: `reason` и `type`
  проигнорированы.
- PUT той же тестовой записи с `type_id=7`, взятым из существующей строки →
  HTTP 201; GET → HTTP 200 с `type_id=7`. Значит проводное поле типа — именно
  числовой `type_id`.
- PUT той же мягко удалённой probe-записи с `status=not_confirmed` и
  обязательным контекстом → HTTP 201; GET → HTTP 200 с
  `status="not_confirmed"`. Повторный `cancelAdmission` → HTTP 201 вернул
  запись в `deleted`. Update-status действительно проходит PUT-path.
- Generic DELETE тестовой записи → HTTP 500 из-за FK `admission_journal`.
  Штатный `POST /rest/api/admission/cancelAdmission` → HTTP 201,
  `{"data":{"canceladmission":{"admission_id":860}},"success":true}`;
  GET подтвердил `status="deleted"`. Тестовая запись мягко удалена.

Следствие для MCP-границы:

- публичный `reason` сохраняется ради понятного пользовательского имени, но
  переводится в `description`;
- `create_admission` получает обязательный `clinic_id`, без которого его
  нельзя честно вызвать на текущем REST;
- выбираемый create-`status` удаляется из схемы: апстрим всегда создаёт
  `not_confirmed`, а отправка любого значения лишь создаёт ложное обещание;
  устаревший вызов, который продолжит передавать `status`, намеренно получит
  schema/input error и должен убрать параметр, а не считать его применённым;
- `update_admission.admission_type` становится числовым id и уходит как
  `type_id`; update-`status` остаётся — PUT его действительно обрабатывает.
- update по-прежнему сначала читает запись и сам строит обязательный body:
  `clinic_id` из read-back, `start=admission_date`, `end=start+admission_length`,
  затем добавляет только запрошенные `description`, `type_id` и другие поля.

### 321.2 Hospital: `pet_id`, не `patient_id`

Исходники Ветменеджера:

- `rest/protected/models/Hospital.php:20-26` объявляет числовой `pet_id`;
  `Hospital.php:29-35` связывает `pet_data` через `pet_id`;
  `Hospital.php:38-54,57-79` подписывает и фильтрует `pet_id`.
- `HospitalController.php:30-64` применяет общий REST filter к модели.
- OpenAPI `components.schemas.hospital` также содержит `pet_id`.
- `artifacts/api_entity_reference-ru.md` ошибочно пишет `patient_id`; артефакт
  будет исправлен вместе с кодом.

Живой стенд, одна и та же существующая `pet_id=6`:

- `GET /rest/api/hospital?...filter pet_id=6` → HTTP 200,
  `totalCount=1`, строка `{"id":2,"pet_id":6,"status":"delayed"}`.
- тот же запрос с `patient_id=6` → HTTP 406,
  `{"success":false,"message":"Invalid filter item name: <patient_id>."}`.

Следствие: convenience-фильтр `get_hospitalizations(pet_id=…)` обязан строить
`pet_id`; существующий `FILTER_FIELDS_BY_ENTITY["hospital"]` уже верен.

### 321.3 Timesheet: рабочее время определяется справочником типов

Исходники Ветменеджера:

- `rest/protected/models/Timesheet.php:6-18,33-45,64-79` отдаёт числовой
  `type`, `all_day`, `night` и абсолютные границы времени.
- relation `Timesheet.php:51-58` связывает `type` с `TimesheetTypes`.
- `Timesheet.php:129-170` в обеих проверках рабочих часов делает
  `JOIN timesheet_types tt ... tt.is_working_hours = 1`.
- `TimesheetTypes.php:6-15,39-51,68-79` объявляет
  `is_working_hours` числовым полем справочника.
- `TimesheetController.php:4-24` по
  `parameters={"attach_timesheet_type":1}` присоединяет relation `ttype` к
  каждой строке; обычный list гарантированно отдаёт только `type`.

Живой стенд:

- `GET /rest/api/timesheet?limit=3` → HTTP 200; каждая показанная строка
  содержит `type=2`, `begin_datetime`, `end_datetime`, `all_day`, `night`.
- `GET /rest/api/timesheetTypes?limit=100` → HTTP 200, `totalCount=6`;
  среди тела: type 2 «Рабочее время», `is_working_hours=1`; type 3 «Выходной»
  и type 5 «Нерабочее время», оба `is_working_hours=0`.
- `GET /rest/api/timesheet?parameters={"attach_timesheet_type":1}` → HTTP
  200, `totalCount=141`; строки содержат вложенное
  `ttype={"id":2,"is_working_hours":1}` вместе с `type`, `all_day`, `night`.

Следствие: `get_doctor_free_slots` запрашивает `ttype` в том же GET табеля и
строит интервалы только для строк с `ttype.is_working_hours=1`.
Отсутствующий/malformed `ttype` fail-closed: свободные окна из него не
публикуются. Флаги этапа 311 не переопределяются: `all_day` уже нормализует
границы при нашей записи, ночная смена остаётся пересекающим полночь
абсолютным интервалом; расчёт по `begin_datetime`/`end_datetime` сохраняется.

Отдельный GET `/timesheetTypes` отвергнут после review: он добавил бы workflow
право `reference.read` и изменил смысл уже выданных custom credentials.
Attached relation использует тот же `/timesheet` и прежний `analytics.read`.
Ответы на §6.0: трактовка выданных ключей **не меняется**, зависимых production
записей нет, миграция не нужна. `paginate_all` получает необязательный `extra`
для постоянного query-параметра и передаёт его на каждой странице; единственный
новый call-site — `parameters` для attach relation.

Полный отказ attach relation нельзя маскировать под «у врача нет графика»:
если табель пуст, результат с нулём слотов корректен; если строки есть, но ни
одна не содержит словарь `ttype` с распознаваемым `is_working_hours`,
инструмент даёт стабильную reportable contract error. При смешанном ответе
валидные строки обрабатываются, отдельные строки без discriminator безопасно
пропускаются.

### 321.4 Неверная дата табеля

`tools/operations.py:get_timesheets` напрямую вызывает
`datetime.strptime(..., "%Y-%m-%d")`; невозможная дата выпускает обычный
`ValueError`. В проекте стабильная ошибка вызывающего — существующий
`exceptions.ToolInputError`; `validators.parse_date_param()` показывает
принятый стиль сообщения, но не используется здесь, потому что дополнительно
разрешил бы relative dates вопреки текущей сигнатуре. Ошибка формата
переводится в `ToolInputError` до HTTP-вызова, без нового типа/хелпера.

## Решение и декомпозиция

- **321.1 (≤150 LOC):** красные payload-guards для create/update; добавить
  обязательный `clinic_id`; `reason -> description`; убрать неработающий
  create-`status`; `admission_type: int -> type_id`; live create/read/update и
  штатный cancel созданной строки.
- **321.2 (≤50 LOC):** красный MCP guard на `pet_id`, заменить единственный
  mapping `patient_id -> pet_id`, исправить справочник сущности.
- **321.3 (≤150 LOC):** красный сценарий с рабочим и выходным типами; получить
  `ttype` через `parameters.attach_timesheet_type` в существующем bounded
  `paginate_all`, исключить нерабочие/неизвестные строки до расчёта интервалов;
  добавить guard передачи `extra` на каждую страницу и guards на all-day и
  ночную рабочую смену.
- **321.4 (≤50 LOC):** красный тест невозможной даты и отсутствия HTTP;
  перевести `ValueError` в существующий `ToolInputError`.
- Обновить tool-schema/docstrings и контрактные artifacts, выполнить полный
  Core Loop, живые проверки изменённых инструментов, commit/review/push/CI.

## Приёмка

- create payload содержит `description` и обязательный `clinic_id`, не
  содержит `reason`/`status`; read-back на стенде сохраняет причину;
- update payload содержит `description` и `type_id`, не содержит
  `reason`/`type`, а также автоматически восстановленные `clinic_id`, `start`,
  `end`; read-back подтверждает изменённые поля;
- `get_hospitalizations(pet_id=…)` отправляет `pet_id`, проходит локальный
  allowlist и возвращает только строки питомца;
- свободные слоты строятся только из типов `is_working_hours=1`; выходной и
  неизвестный type слотов не создают, рабочие all-day/night строки сохраняют
  семантику этапа 311;
- запрос табеля несёт `parameters.attach_timesheet_type=1` на каждой странице,
  но права `get_doctor_free_slots` и смысл уже выданных ключей не меняются;
- непустой табель, в котором attach relation отсутствует у всех строк, даёт
  явную contract error; пустой табель по-прежнему возвращает ноль слотов;
- невозможная дата `get_timesheets` даёт `ToolInputError` до сети;
- каждый regression guard показан красным намеренной поломкой/на старом коде,
  затем зелёным; полный Docker suite и opt-in real suite зелёные;
- изменённые инструменты вызваны вживую, в AssumptionLog записаны HTTP коды и
  сокращённые контрактные тела без секретов/ПД.

## Оценка простоты

Триггеры §4.1 проверены. Новых классов, generic-слоёв, кэшей и dual API нет.
Изменения остаются в четырёх существующих границах и одном stage-test файле.
`ttype` приходит в существующем bounded запросе табеля; отдельный
registry/cache и третий upstream GET не нужны. Единственное расширение общего
`paginate_all` — такой же необязательный `extra`, какой уже есть у `crud_list`.
Табель и приёмы по-прежнему загружаются параллельно.

Самый простой вариант «только переименовать два поля» отвергнут: доказанный
POST без `clinic_id` всё равно не вызывается, create-`status` остаётся ложным,
а свободные слоты без справочника не могут отличить выходной. Более широкий
рефакторинг CRUD/расписания также не нужен.

## Вне рамок

- изменение PHP Ветменеджера или его бизнес-процесса подтверждения приёма;
- добавление отдельного MCP-инструмента подтверждения/отмены приёма;
- исправление generic DELETE admission (для пробы использован штатный
  `cancelAdmission`);
- кэш справочника типов, изменение пагинации или расчёта busy admissions;
- переосмысление исторических `all_day` строк с нестандартными часами;
- findings F1/F4+ из супер-ревью этапа 319.

## Риски и rollback

- Удаление create-`status` и обязательный `clinic_id` меняют input schema, но
  прежняя схема обещала невозможное: без clinic запрос 400, status игнорируется.
  Tool-list guard закрепляет честный новый контракт.
- Fail-closed по неизвестному timesheet type может скрыть слоты при битом
  справочнике; это безопаснее публикации отпуска как доступности.
- Rollback — один git revert; внешняя миграция отсутствует. Созданные живой
  проверкой строки всегда переводятся в `deleted` через `cancelAdmission`.
