# Этап 462. Scalar-проекция клиентов при известном вложенном поле

## Цель

`get_clients(fields=[id,status], include=[], limit=1)` возвращает выбранные скалярные поля на подтверждённой форме ответа #150/#161. На devtr6 проверяется совместимость прежней формы без `client_type_data`; новую ветку доказывает синтетический guard. Известное вложенное `client_type_data` не попадает в scalar-ответ; неожиданные вложенные поля продолжают вызывать fail-closed отказ. Пагинация, очистка и права остаются прежними.

## Факты и границы

- Разрешённый read-only структурный снимок куратора `/home/otis/myprojects/LiveHelperAgent/scratchpad/run-462-20261116/safe-snapshot.json`: #150 и #161 имеют одинаковую структуру (`same_structure=true`). REST envelope: `success:boolean`, `message:string`, `data:object`; внутри `client:array`, `totalCount:number`, одна строка. В строках `id:number`, `status:string`, `client_type_data:object`, `city_data:object`, `registration_index:null`; значения и внутренние ключи вложенных объектов отсутствуют.
- OpenAPI v6 `artifacts/vetmanager_openapi_v6.json`, схема `client`, описывает `client_type_data` как nullable вычисляемый object. `artifacts/api_entity_reference-ru.md` §2.8 перечисляет `city_data`, `street_data`, `pets`, но не `client_type_data`; этот справочник неполон относительно OpenAPI и снимка.
- `list_projection.LIST_RELATIONS['get_clients']` содержит `city_data/street_data/pets`. При `include=[]` проектор проверяет каждое вложенное поле до выбора scalar. Синтетический ответ с `client_type_data:object` воспроизводит текущий `ToolError: Projection found an unrecognized nested field.` На devtr6 снимок этапа 458 содержал только `city_data`/`street_data`, и вызов проходил.
- `identifier_aliases.canonical_tool` вызывает обязательную очистку до проекции. REST не поддерживает подтверждённый `fields`; параметр применяется локально. Новых production-запросов нет.

## Правило и Architecture Critique

`client_type_data` признаётся только как документированное вложенное поле строки `get_clients` с типом object или null. При явном `include` оно исключается из ответа; при `fields` выбираются только перечисленные scalar-поля. `fields=['client_type_data']` и смешанный выбор с ним отклоняются валидатором до I/O. Публичный `include` не расширяется: внутренние ключи объекта не подтверждены, поэтому выдавать его как новую связь преждевременно. Обычный полный ответ без `fields/include/mask_contacts` проходит прежний путь обязательной очистки и возвращается без локальной проекции; новый код не меняет его. Запрос только с `mask_contacts=true` на затронутой форме продолжает fail-closed отказ по неизвестной для публичного `include` связи; `fields=[id,status], include=[], mask_contacts=true` проходит и выдаёт только выбранные поля. При неожиданном типе `client_type_data` в проекции и при любом другом незнакомом вложенном поле в режиме `include` — отказ до отдачи данных. `totalCount`, `limit/offset`, порядок строк и служебное предупреждение о конфликте ID сохраняются.

Вариант «убрать проверку всех незнакомых вложенных полей при `fields`» отклонён: он ослабляет fail-closed для других форм и скрывает новые схемные отклонения. Вариант «добавить `client_type_data` в `LIST_RELATIONS`» отклонён: одновременно разрешил бы `include=['client_type_data']` с непроверенной вложенной схемой. Выбран отдельный узкий список известных, но не публикуемых связей только для `get_clients`. Он служит типовой проверке входа и исключению из проекции, не меняя другие инструменты и REST-вызовы.

Риски: полное содержимое `client_type_data` неизвестно, поэтому scalar-ответ никогда его не выдаёт; новый upstream nested key продолжает блокировать проекцию с `include`. Полный ответ уже существовал и остаётся под обязательной очисткой; этот этап не расширяет его. Обезличенный снимок одной строки на подключение не доказывает отсутствие других форм. Rollback — убрать узкое правило и тесты одним изменением; старый отказ вернётся. Credentials и уже сохранённые данные не меняются, миграция не нужна.

## Декомпозиция

1. Синтетический MCP guard по подтверждённой форме: `fields=[id,status]`, `include=[]`, обычный и обезличенный токен; точные ключи строки, envelope/totalCount, две страницы и сохранение порядка. Позитивный `client_type_data=null` также не выдаёт поле. Отдельные отрицательные случаи: иное вложенное поле при явном `include`, каждый не-object и не-null тип `client_type_data` (строка, число, boolean, array), недопустимые `fields=['client_type_data']` и `include=['client_type_data']`, а также `client_type_data:object` в соседнем list-инструменте при `include=[]` — прежний отказ. Для `fields`/`compact` без `include` закрепить существующее отбрасывание неизвестной вложенности без её выдачи; полный ответ и отказ одной только маски закрепить как существующее поведение. ## Приёмка

- Синтетическая подтверждённая форма возвращает только `id/status` при `fields=[id,status], include=[]`; `client_type_data` и `city_data` не выходят.
- Другие незнакомые nested key дают прежний fail-closed при явном `include`, включая `client_type_data` у соседнего инструмента; `fields`/`compact` без `include` по прежнему отбрасывают незапрошенную вложенность. Неверный тип `client_type_data` в проекции отклоняется; список разрешённых `include` не расширен.
- Полный ответ остаётся на прежнем пути очистки; scalar с `mask_contacts=true` проходит, маска без `fields/include` на затронутой форме остаётся fail-closed. Пагинация, envelope/metadata, очистка и права защищены regression tests.
- На test/devtr6 живой вызов изменённого инструмента и финальный real aggregate зелёные как проверка совместимости; evidence содержит код и безопасное тело без значений клиентов. Новая форма подтверждается синтетическим guard, а не devtr6.

## Простота

Одно локальное правило и одна функция проекции; новых классов, REST-вызовов, настроек и публичных аргументов нет. Разумное добавление ещё одной подтверждённой скрываемой связи потребует изменения списка и теста в двух файлах. Абстракция для одного call-site не вводится.
