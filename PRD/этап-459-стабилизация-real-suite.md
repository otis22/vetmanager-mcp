# Этап 459. Стабилизация полного real suite devtr6

## Цель

Вернуть зелёный полный opt-in real suite точной штатной командой на `.env` тестовом контуре, сохранив проверки ошибок, приватности и fail-closed. Этап снимает блокер приёмки 460; код и WIP 460 не входят в работу.

## Проверенные факты и неопределённость

Сохранённый полный прогон: exit 1, 114 passed, 4 failed, 19 skipped-not-configured, 0 skipped-error. Mock: 4598 passed, 3 skipped. Адресный повтор четырёх отказов на том же `.env` контуре: exit 1, 3 passed, 1 failed (только отсутствующий клиент), 32.96 с; evidence `stage459-focused-baseline.txt` вне репозитория. Прохождение трёх тестов подтверждает непостоянство отказов, но само по себе не доказывает конкретную сетевую причину export и время завершения прежнего job. По каждому traceback:

1. `GET /rest/api/client/999999999`: HTTP-ответ прошёл как `success=true`, `totalCount=0`, `data.client={"merge_history":[]}`. OpenAPI v6 не описывает GET для `/rest/api/client/{ID}` (только POST/PUT/DELETE); значит форма отсутствующего объекта не подтверждена спецификацией. Тест ожидает `[]`. Это наблюдаемое расхождение теста с внешним ответом, но не доказательство изменения upstream во времени. Проверить повторно и сохранить строгую проверку отсутствия записи.
2. Export: конечная ошибка `The export storage address was rejected by MCP security policy` из `resolve_export_target`, после двух промежуточных 409 (`FILE_BUILD_NOT_STARTED`, `FILE_NOT_READY`). HTTP локатор не раскрывать. Нужно различить неразрешение DNS, смену публичного origin и непубличный адрес; неизвестное не добавлять в allowlist и не ослаблять SSRF-защиту.
3. Stage389: сохранение integration вернуло HTTP 400; перед ним cloud и alias connect timeout, затем `HostResolutionTimeoutError`. Это подтверждённый transport-отказ Docker→billing на данном вызове, а не отказ `get_inactive_pets`.
4. Stage396: после восьми 3-секундных опросов job остался `recognizing`. Нет кода ошибки или данных о дальнейшей судьбе job. Временная задержка возможна, но upstream contract drift и постоянная зависшая job не исключены. Адресный повтор с новым job прошёл в прежнем 24-секундном окне; состояние исходного job после отказа неизвестно. Действующий инструмент документирует bounded `wait_seconds` 0–1800 и работу с тем же job ID.

`TEST_DOMAIN`/`TEST_API_KEY` есть в локальном `.env`; это отдельный тестовый контур, не bearer-стенд. Полный штатный suite уже содержит разрешённые тестовые записи: stage389 создаёт изолированный web-аккаунт, integration и bearer; stage396 создаёт job и может сохранять тестовый отчёт; stage276 запускает выгрузку. Владельцем этих данных является тестовый контур проекта. Новых произвольных записей для диагностики не добавлять; при сомнении во владении остановить запуск и эскалировать куратору. В памяти и evidence сохраняются только безопасные статусы, коды и формы, не данные клиники и не секреты.

## Архитектурное решение

Выбранный минимальный вариант после диагностики и strong review: сам host resolver и SSRF-защиту не менять, поскольку адресный повтор подтвердил прохождение export и integration, а сохранённые traces не локализуют дефект runtime. Обновить два устаревших real-теста и точечно закрыть подтверждённый дефект `get_client_by_id`: сейчас живой MCP-вызов на том же тестовом контуре вернул `is_error=False`, `success=True` и `client` с единственным ключом `merge_history` при заведомо отсутствующем ID. Это product regression на границе инструмента, выявленный вторым сильным Opus review; нижележащий универсальный CRUD и другие инструменты не менять. `test_real_nonexistent_client_raises` принимает ровно две пустые формы `data.client`: `[]` и `{"merge_history":[]}`, при обязательных `success=true`, `totalCount=0` и отсутствии иных ключей/записей. MCP-инструмент по точной пустой форме возвращает безопасный NotFoundError/отказ, как и при HTTP 404, а не ложный success; неожиданную форму не нормализует в отсутствие. Негативное свойство для `[]` — ноль элементов; для объекта — единственный ключ `merge_history` с пустым списком, без `id`, данных клиента и иных ключей, при `totalCount=0`. Это совместимость с двумя наблюдаемыми формами, не признание их OpenAPI-контрактом. Stage396 применяет существующий `get_report_ai_job(job_id, wait_seconds=...)` вместо ручного восьмикратного опроса: tool docstring документирует диапазон 0–1800 секунд, единый deadline, сохранение того же job ID и отказ при ошибке; выбрать ограниченное окно 120 секунд и при активном статусе после него падать с диагностикой, не создавать job заново. Выбор 120 секунд — test budget для наблюдавшегося 24-секундного окна, не объявленный upstream SLA. Сохранить существующие терминальные assertions: `ready_to_save` сохраняется и требует success, `existing_report_matched` допускается без сохранения, остальные состояния остаются failure; проверка строк и типов остаётся неизменной. Для export никакие ошибки не превращать в skip и не увеличивать production timeouts без причинного доказательства. После первого полного real 459 подтверждён новый однотипный transport-отказ web integration в stage375/397: `vetmanager_connection_service.resolve_vetmanager_host` вызывает уже существующий resolver с `max_retries=0`, тогда как MCP runtime использует стандартный один ограниченный повтор. Изменить только этот callsite на `max_retries=1` (не лимиты попыток самого resolver), чтобы web validation пользовалась существующим bounded fallback. Проверить красным тестом: первый cloud connect timeout, второй cloud успешен, alias не вызывается; при постоянном отказе обеих служб ошибка остаётся отказом. Изменение затрагивает web validation до записи connection, повторяется только GET billing/probe, POST интеграции не дублируется. HTTP 400 mapping при окончательном отказе не меняется. Предыдущие отказы export и stage389 остаются классифицированными как внешние/transport с неопределённым подтипом export до отдельного причинного доказательства; их адресный pass не доказывает устранение внешней причины. Критерий приёмки требует зелёного полного suite и явного pass stage276 и stage389; текущий красный прогон ему не соответствует. Повторные случайные полные прогоны без новой фактуры не засчитывать как решение.

Защитные сторожа export уже есть в `tests/test_stage320_export_ssrf.py` и покрывают non-global/loopback/link-local, смешанные DNS-ответы, pinned connect и redirect. Их прогнать адресно, не менять. Диагностическое evidence export ограничить категорией результата (timeout, DNS error, non-global, origin mismatch) без host, IP, пути и query; исторический traceback категорию не различает. Сохранённые полные логи остаются вне публичного repo. Для этого этапа новые диагностические записи на тестовом контуре не нужны.

Альтернативы: skip при ошибке сети/экспорта скрывает красный гейт; бесконечный retry может умножить записи и задержки; глобальное расширение allowlist или отказ от DNS pinning создаёт SSRF-риск; замена assert на `isinstance` скрывает возврат клиента. Эти пути отклонены. Инварианты: никаких production вызовов; секреты и ПД не попадают в публичный diff; запись Report AI не повторяется автоматически; download только с проверенного публичного адреса через наш очиститель; реальные постоянные ошибки завершаются failed, не skipped.

Rollback: до merge — точечный `git revert` веточного commit. После merge, если возникнет регрессия, владелец применяет обычную процедуру отката выпуска с backup/health smoke по operations runbook; при этом прежний ложный успех отсутствующего клиента вернётся, поэтому временный откат допустим только с зафиксированным риском и последующим исправлением. Если тестовый контур неисправен, сохранить красный exit и `supervisor_pending`, не выпускать заведомо неверный код.

Architecture Critique совмещается с strong PRD-review и проверяет ownership, privacy/SSRF, compatibility, bounded retries, acceptance и rollback.

Критические stage276 export и stage389 integration обязаны иметь явный `passed` в финальном полном suite: legacy skip export при занятом общем guard или незавершённой сборке не засчитывается в приёмку 459, даже если общий exit равен 0. ## Оценка простоты

Проверены §4.1 triggers: новая абстракция не нужна — одна проверка в одном `get_client_by_id`, два точечных обновления тестов и один аргумент в web billing callsite. Нет новой конфигурации, состояния, dual API или дополнительных hop; правка остаётся в трёх файлах кода/тестов. Универсальный CRUD нормализовать опаснее: другие сущности имеют иной empty-контракт. Точечная runtime-правка меняет только пустой ответ `get_client_by_id` на NotFoundError и не касается выданных учётных данных (§6.0). Простота принята после сильного PRD review и до реализации.

Второй сильный PRD review: Astra валидная 1/2 с `findings=[]` и validator exit 0 при inline PRD; Opus валидный 2/2 с 1 high и 5 medium. High о ложном успехе инструмента принят и доказан живым безопасным ответом `is_error=False, success=True, client_keys=[merge_history]`; внесён runtime fix в план. Medium о диагностике export: для исторического отказа точный подтип не восстановить, последующий read-only probe того же file ID дал публичный валидный адрес (1 IP); при новом отказе сохранить только категорию DNS/адресной валидации, не locator. Medium о 400 web integration принят как отдельная неопределённость контракта: лог доказывает transport причину, но HTTP 400 может быть неверным отображением; менять его здесь без отдельного web-contract теста нельзя, зафиксировать для владельца. Medium о permanent recognizing/timeout принят: проверка активного статуса остаётся красной; existing tool bounded wait уже тестируется в stage369, HTTP client fixture не используется в stage396. Medium о названии «стабилизация» принят: результат этапа — зелёный полный suite на SHA и классификация; внешняя надёжность сети не объявляется доказанной. Medium о simplicity закрыт этой секцией. Opus PRD-бюджет 2/2 исчерпан; после этой существенной правки провести Spark scout и тесты, новый Opus PRD запуск запрещён бюджетом.

## Измеренное уточнение transport budget

Новая постановка куратора разрешила узкий эксперимент: Docker TLS до 4237 мс и GET HTTP 200 до 5506 мс при Docker DNS 66 мс превышают старый billing deadline 2,5 с и connect 1,5 с. Выбран billing deadline 5,6 с и connect/read 5,6 с; write/pool не увеличены. Два clinic probe остаются по 2,5 с. Четыре billing попытки, два probe и две паузы по 0,1 с дают worst case 4×5,6 + 2×2,5 + 0,2 = 27,6 с, оставляя 2,4 с до общего GET budget 30 с. Число попыток, authoritative 4xx, SSRF-валидация и cleanup не меняются. Это объясняет наблюдённый медленный успешный GET на границе, но не гарантирует устранения каждого сетевого отказа; permanent timeout остаётся ошибкой. Сторож 2,7 с был красным при старом пределе; отдельный сторож проверяет новый timeout и предел попыток. Rollback — вернуть три числовых лимита и аргумент billing `_bounded_get`, сохранив старые clinic probe; при красном focused/live или полном real не коммитить и оставить `supervisor_pending`. ## Причинная диагностика незакрытого transport, 14.11.2026

На существующем `.env` test-контуре с `PYTHONTRACEMALLOC=25` оба теста прежнего полного отказа прошли по отдельности (по одному pass). Последовательность первых семи тестов `test_e2e_real.py` до Report AI также прошла без warning (7 pass). В запуске всего файла (59 pass, 6 skip) pytest выдал два `PytestUnraisableExceptionWarning` на `test_real_get_clients_name_search`: незакрытые socket и asyncio transport. Allocation traceback сокета заканчивается в `anyio.connect_tcp` → `loop.create_connection` → `_connect_sock` → `sock_connect`; traceback объекта transport указывает лишь на место определения `__del__`, а не на место сетевого вызова. Таким образом, предупреждение переносится между вызовами/сборками мусора и не принадлежит доказанно двум тестам, названным в предыдущем полном прогоне. Короткая строгая последовательность первых пяти тестов (`-W error`, `PYTHONTRACEMALLOC=10`) прошла без warning; минимальная последовательность, стабильно воспроизводящая утечку, не найдена.

Проверены оба per-loop пула `httpx.AsyncClient` (`host_resolver.py` и `vm_transport/pool.py`), их autouse reset-фикстуры, `asyncio.shield` фонового billing lookup, bounded `wait_for`, Report AI и прямой `VetmanagerClient`. Allocation stack библиотеки не сохраняет вызывающий HTTP-клиент; имеющиеся traces не связывают предупреждение ни с конкретным пулом, ни с cancellation, ни с ошибкой `aclose`. Поэтому причинный lifecycle defect и граница минимального fix не доказаны. Не менять ни runtime, ни assertions, ни warning policy; `gc.collect()` и suppression не применять. Rollback новых документальных уточнений — удалить только этот раздел и соответствующие строки Roadmap/AssumptionLog; сохранённые ранее timeout/client/web/test исправления не откатывать. Следующее действие после решения куратора — трассировка владельца соединения на уровне клиента/пула с безопасными идентификаторами без адресов и данных, затем красный lifecycle guard на старом коде. До этого 459/459.1 остаются `supervisor_pending`, полный mock/real повторно не запускается, commit/review/push запрещены.

## Установленная причина и узкий fix, 14.11.2026

Diagnostic-only pytest plugin присвоил ID клиентам, запросам, задачам и сокетам без записи адресов, тел и данных. На `.env` test-контуре с tracemalloc socket 55 был создан request 51 клиента 49 (`host_resolver._get_shared_client`) на loop 50 в `test_real_get_clients`. HTTP-вызов завершился `CancelledError`; затем `client.aclose()` начался и закончился на том же loop 50, однако `socket.close()` для 55 не вызван, а при следующем тесте сокет финализировался открытым. Vetmanager pool в этой трассе закрыт, Report AI и export ещё не участвовали. Сырые безопасные события — во внешнем evidence.

Установленная версия AnyIO в тестовом образе — 4.15.1. Официальный changelog AnyIO 4.16.0 указывает исправление утечки connected socket, если enclosing cancel scope отменён до выхода из connection task group. По наблюдаемому окну это применимо к сценарию. Минимальный fix — нижняя граница `anyio>=4.16.0,<5` в зависимости проекта; timeout и клиентские lifecycle контракты не меняются. Детерминированный guard моделирует отмену после успешного connect и до выхода из task group: на 4.15.1 красный `connected stream survived cancellation before task-group exit`; зелёный на 4.16.0 и полный real требуются до приёмки. Если guard не станет зелёным, зависимость не считать исправлением.

Сборка образа устанавливает зависимости отдельным списком в Dockerfile, не через `pyproject.toml`; граница AnyIO поэтому внесена в оба места. Это не меняет публичный API. Проверка фактической версии внутри тестового образа обязательна до зелёного guard.
