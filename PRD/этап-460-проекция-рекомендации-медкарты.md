# Этап 460. Рекомендация в проекциях списков медкарт

## Цель

Для `get_medical_cards`, `get_medical_cards_by_date`, `get_medical_cards_by_client_id` запрос `fields=[id,recommendation]` должен вернуть текст из REST-поля `recomendation` под публичным именем `recommendation` без лишних полей. Фидбек #168. Работа ограничена списочной проекцией; полный ответ и запись остаются совместимы.

## Проверенные факты и границы

- OpenAPI v6, схема MedicalCards: `recomendation` — строковое поле; `artifacts/api_entity_reference-ru.md` §2.21 описывает смысл поля под именем `recommendation`, но точное REST-написание берётся из OpenAPI и существующих write-инструментов.
- `tools/medical_card.py` создаёт и обновляет медкарту через payload `recomendation`. `filters.py` допускает REST-сортировку/фильтр `recomendation`. Общий `identifier_aliases.py` нормализует только ID-имена, после очистки `_wrap_tool_with_depersonalization` вызывает `list_projection.py`. Там `recommendation` разрешено, но отсутствующий ключ молча пропускается.
- Этап 444 обещал прежний полный ответ без `fields`; `_mcp_identifier_conflicts` сохраняется при проекции. Этап 449 менял только аргумент `id` у `*_by_id`. Этап 458 касался `get_clients` и не расширял контракт медкарт.
- `depersonalization.py` очищает и `recomendation`, и `recommendation`. Дополнительных REST-вызовов или изменений схемы tool input не требуется.

## Архитектурное решение

Проблема — несовпадение имени одного скалярного поля на границе публичной проекции. В `_project_fields_only(result, tool_name, selection)` имя инструмента уже передаётся; правило включается только для трёх имён медкарт. При выборе `recommendation` читать `row["recommendation"]`, если ключ есть, иначе `row["recomendation"]`, если он есть; выбранное значение выдавать только под `recommendation`. Приоритет определяется наличием ключа даже для `null` и пустой строки: явный публичный ключ считается авторитетным, расхождение источников не разрешается догадкой. Прочие поля, включая `description`, следуют прежнему пути. Оба значения уже очищены, потому что очистка предшествует проекции. Служебный `_mcp_identifier_conflicts` не используется для текстового поля и остаётся без изменений. Полный ответ (`fields` не задан) проходит ранний возврат без изменения. Порядок: очистка → общая ID-нормализация → проекция. `fields=[id,recomendation]` как прежде отклоняется валидатором до I/O: опубликован whitelist с `recommendation`.

Варианты: глобальный alias `recomendation → recommendation` затронул бы полный ответ, write-сигнатуры/аргументы и filter/sort; его нельзя вводить без отдельной миграции и доказательства совместимости. Правка трёх инструментов дублировала бы логику. Локальное правило в общем проекторе ограничено ровно запрошенным контрактом.

Инварианты: нет новых ключей в полном ответе; write-поля и REST filter/sort сохраняют `recomendation`; очищенный текст не заменяется сырым; `description` неизменен; ошибка формы/metadata и предупреждение о конфликте ID остаются прежними. Если REST начнёт отдавать оба написания, явное публичное поле выигрывает; расхождение требует отдельного расследования, не скрытого слияния. Rollback: удалить локальное правило, оставив остальную проекцию и write-контракты без изменений; временный fallback — полный read-only ответ с `recomendation`.

Architecture Critique и PRD-review сторонней моделью обязательны: публичный MCP-контракт и клинический текст.

## Декомпозиция

1. Параметризованный MCP-сторож для всех трёх инструментов с исходным `recomendation="Повторить осмотр. Позвонить +7 999 123-45-67"`: точное совпадение после очистки с ожидаемым текстом и маркером скрытого телефона, `description`, отсутствие посторонних полей и полный ответ; red до исправления. Отдельно проверить строку с обоими именами, включая `null`/`""` у публичного ключа, приоритет публичного значения и старый отказ для `fields=[id,recomendation]`. Отрицательный unit-тест проверяет, что правило не применяется к другим инструментам. ≤150 строк.
2. Локальная проекция и focused green; мутация возвратом старого поведения показывает red. ≤150 строк.
3. На `.env` test-контуре read-only выбрать медкарту с непустым `recomendation`, сверить после очистки текст в ответе всех трёх инструментов; отсутствие подходящей записи блокирует live gate. Зафиксировать безопасный код/ответ. Аудит, mock/real suite, committed review и push ветки.

## Приёмка

- Все три `fields=[id,recommendation]` возвращают полный очищенный текст из `recomendation` под одним публичным ключом.
- Запрошенные поля и обязательная метаинформация — единственные поля проекции; конфликты ID сохраняются.
- Полный ответ, `description`, `recomendation` в write и filter/sort остаются совместимы.
- Красный сторож до кода и при намеренной поломке, зелёный после; live response, полные проверки и два сильных ревью зафиксированы в `AssumptionLog.md`.

## Простота

Одно локальное правило внутри существующего проектора. Новых классов, hooks, REST-параметров и настроек нет. Изменение одной функции и одного тестового файла; оценка после review перед кодом.
