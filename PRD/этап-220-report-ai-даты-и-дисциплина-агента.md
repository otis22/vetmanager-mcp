# Этап 220. Report AI: даты в обезличивании и дисциплина агента

## Контекст

Живая проверка шести Report AI отчётов показала два MCP-наблюдаемых дефекта.
В свободном текстовом поле централизованный обезличиватель заменил даты
`2024-01-01`, `2026-12-31` и фрагмент `2024-10-23 17:50:51` на
`[redacted-phone]`. Одновременно static helper не объясняет агенту, как
работать с нулевым результатом, неоднозначностью без пользователя,
многочастными запросами и обычным временем ожидания очереди.

## Проверенные факты

- `depersonalization.sanitize_text()` применяется только к allowlisted
  free-text keys и сейчас использует один общий phone regex.
- Structured phone fields остаются отдельной key-based маской; их контракт не
  меняется.
- `get_report_ai_prompt_helper` и MCP prompt используют один static artifact
  `artifacts/report-ai-prompt-helper-short-mcp-2026-06-15.md` через
  `prompts.get_report_ai_prompt_helper_text()`.
- `REPORT_AI_LONG_QUEUED_THRESHOLD_SECONDS = 30` — локальная диагностика
  наблюдаемого queued state, а не SLA upstream.
- Наблюдения пользователя на одном контуре: одиночный job доходил до
  `ready_to_save` за 60–90 секунд; три jobs, созданные подряд, — примерно за
  3–3,5 минуты каждый; при плотной работе наблюдалось до 4 минут 43 секунд.
  Это наблюдаемый порядок величины, а не гарантия API.
- `recognized.preview_example_row` — MCP-наблюдаемое preview metadata с
  намеренно выдуманными правдоподобными значениями. Оно позволяет до чтения
  реальных строк проверить состав и типы колонок, группировку и соответствие
  ожидаемой структуре; его значения не являются данными клиники и не должны
  пересказываться пользователю.
- Наблюдение пользователя на одном контуре: terminal job с
  `status="failed"` и `error_code="INTENT_REJECTED"` вернул русское
  объяснение в `error_message_safe`. Это подтверждённое безопасное поле
  контракта для объяснения причины отказа перед изменением intent.

## Scope

- Установить приоритет free-text PII redaction: сначала найти e-mail и phone
  candidates; date/time сохраняются только там, где не пересекаются с принятым
  PII candidate. Защищаются только date/date-time с допустимыми числовыми
  значениями: год 1900–2100, месяц 01–12, день 01–31, а при наличии времени —
  часы 00–23, минуты и секунды 00–59.
- Сохранить redaction настоящего телефона, в том числе когда он находится в
  той же строке, что дата.
- Дополнить короткий русский helper наблюдаемыми правилами: пустой результат,
  проверка записей за период, разумный default без пользователя, один вопрос —
  один узкий последовательный job, назначение выдуманного preview и нормальный
  порядок ожидания.
- Продублировать в всегда видимых описаниях `create_report_ai_job` и
  `get_report_ai_job_data` только guardrails, отсутствие которых приводит к
  ошибочному действию: последовательность jobs и корректная обработка пустых
  строк.
- Дополнить `get_report_ai_job` general rule для `failed`/`rejected`: читать
  безопасное объяснение и не пересоздавать неизменённый intent.
- Дополнять, а не заменять, исходные описания tools проверяемыми privacy
  контрактами; покрыть каждый описанный путь поведенческой фикстурой
  redaction. В `report_problem` исключать только конкретные поля, прямо
  обозначенные в описании соответствующего tool.
- Оценить в этом PRD, но не реализовывать, возможную MCP-защиту от
  параллельного создания незавершённых Report AI jobs одним арендатором.
- Добавить focused regression tests.
- В review-evidence runner отвергать `--evidence-dir` внутри repository working
  tree до чтения review object и создания evidence.

## Out of scope

- Изменение Vetmanager backend, SQL, очереди или API contract.
- Новые MCP tools, автоматический retry/create/save/polling или изменение
  `REPORT_AI_LONG_QUEUED_THRESHOLD_SECONDS`.
- Изменение structured field redaction либо ослабление privacy boundary.
- Утверждения о гарантированном времени выполнения Report AI.
- Изменение MCP для отказа или очереди при втором незавершённом job.

## Архитектурное решение

### Проблема

Телефонная маска допускает цепочки цифр, разделённые дефисами, и поэтому
совпадает с ISO-датой. У агента есть безопасный helper, но без нескольких
правил он может ошибочно пересоздавать job при отсутствии данных либо
перегружать очередь.

### Контекст и ограничения

- Existing sanitizer заменяет только явные PII patterns в free text; false
  negative для настоящего телефона недопустим как побочный эффект.
- Дата и время — business data, которые должны сохраняться в обезличенном
  ответе.
- Helper — статическая инструкция перед каждым отчётом; текст должен быть
  кратким, по-русски и не называть observed timings гарантией.
- Знания о внутренней реализации backend в repository не добавляются; только
  MCP-наблюдаемое поведение.
- Текущий контракт создания job не передаёт проверяемый признак, что второе
  задание пользователь осознанно разрешил; MCP не может достоверно отличить
  такое намерение от того, что агент не дождался первого завершения.

### Рассмотренные варианты

1. Отключить phone redaction в free text.
   - Плюс: убирает ложное совпадение.
   - Минус: открывает PII, неприемлемо.
2. Считать датой любое совпадение по форме `YYYY-MM-DD`.
   - Плюс: небольшая правка.
   - Минус: фрагменты телефонов с четырёхзначным кодом города могут выглядеть
     как дата и остаться открытыми.
3. Сначала собрать e-mail и phone candidates; защитить только date/date-time,
   прошедшие проверку диапазонов значений. Candidate, составленный только из
   таких date tokens и разделителей, не считать телефоном; candidate не
   отбрасывать из-за пересечения с date token.
   - Плюс: при пересечении PII всегда скрывается, включая телефон с
     четырёхзначным кодом города; e-mail не разрезается phone mask.
   - Минус: в неоднозначном пересечении дата может быть замаскирована.

### Выбранное решение

Выбрать вариант 3. При пересечении выигрывает маскировка: искажённая дата —
косметическая помеха, открытый телефон или e-mail — privacy leak. Неверное
значение в date-like форме не защищается и обрабатывается как обычный текст.
Добавить табличные регрессии на оба наблюдённых формата даты, ISO `T`/timezone,
локальную дату, невалидные диапазоны, телефон непосредственно после даты,
phone с четырёхзначным кодом города и phone-like e-mail. Runner должен
отклонять evidence path внутри repo.

### Инварианты

- Настоящий телефон в free text по-прежнему заменяется на `[redacted-phone]`.
- Date/time сохраняется, если проходит проверку диапазонов и не пересекается с
  найденным PII.
- При пересечении телефон/e-mail redacted независимо от соседней даты, пробела
  или дефиса.
- Жадный phone candidate может поглотить соседние dates; это осознанный
  privacy-first перекос, а не defect.
- Поддерживаемые формы защищаемой даты: `YYYY-MM-DD`, то же со временем через
  пробел или `T` и timezone, `DD.MM.YYYY`. Проверяются диапазоны, но не
  календарная длина конкретного месяца и високосность.
- Structured phone fields по-прежнему redacted по ключу.
- Tool helper и MCP prompt возвращают идентичный текст.
- 30 секунд — сигнал локальной диагностики, а не признак поломки и не
  обещание SLA.

### Rollback / fallback

Перед применением новой маски прогнать existing и new focused corpus. Если
observed очередь изменится, обновить helper wording отдельно по новым
наблюдениям, не меняя runtime behavior. Не расширять правило на все возможные
формы дат или телефонов без отдельного наблюдаемого кейса: остаточный риск
принят в пользу простоты и privacy-first приоритета.

### Непроверенные формы и границы

- Реальная календарная валидность (`31.02`, високосные годы) не проверяется:
  используются только заданные диапазоны чисел.
- Не покрыты date forms с другими разделителями/порядком (`DD-MM-YYYY`,
  `MM/DD/YYYY`), неполные даты и время без секунд.
- Не покрыты экзотические timezone-обозначения и все национальные/произвольные
  phone layouts вне существующей phone-маски.

## Оценка MCP-защиты от параллельных jobs (не реализуется)

### Что MCP может и не может определить

По одному вызову `create_report_ai_job` MCP не может надёжно установить,
является ли второй job осознанным решением пользователя или агент просто забыл
дождаться первого: в контракте нет проверяемого признака такого намерения.
Явный параметр наподобие `allow_parallel` мог бы передать заявление агента об
одобрении пользователя, но не доказал бы его и расширил бы публичный MCP
контракт. Без отдельного API-контракта MCP также не должен предполагать, что
может перечислить все незавершённые upstream jobs арендатора; локальная защита
видела бы только jobs, созданные и сохранённые самим MCP.

### Варианты и риски

1. Жёстко отклонять второй job, пока известный предыдущий не terminal.
   - Плюс: непосредственно предотвращает наблюдаемую деградацию от
     параллельного запуска.
   - Минусы: зависший job блокирует работу на неопределённый срок; защита
     неполна для jobs вне памяти/инстанса MCP; legitimate параллельные задачи
     становятся невозможны.
2. Разрешать второй job после фиксированного timeout.
   - Плюс: нет вечной блокировки.
   - Минус: timeout нельзя вывести из наблюдаемого времени без нового
     контракта или продуктового решения; он может как преждевременно пустить
     параллельный job, так и задержать полезную работу.
3. Сохранить последовательное правило в helper и наблюдать эффект; если
   product decision подтвердит необходимость, добавить отдельный opt-in обход
   с явным пользовательским одобрением и ограниченной по времени защитой.
   - Плюс: не вводит ложного различения намерений и не меняет поведение
     текущих клиентов.
   - Минус: агент может всё ещё нарушить инструкцию.

### Рекомендация

Сейчас не реализовывать жёсткий tenant-level отказ. Достаточна явная
последовательная инструкция: она покрывает основной наблюдаемый сценарий без
необратимого блокирования зависшего job и без выдумывания отсутствующего
upstream контракта. Если позднее понадобится защита, проектировать её как
отдельное изменение публичного MCP-контракта: хранить только MCP-наблюдаемые
active jobs по устойчивому tenant identity, считать terminal статусы по
наблюдаемому API, иметь ограниченный срок действия записи и явный bypass,
разрешённый только после пользовательского согласия. При отказе ответ должен
содержать известные `job_id`, последний наблюдаемый status и возраст, объяснять
что создание нового job остановлено для предотвращения замедления, и предлагать
poll/wait либо явный одобренный обход после истечения политики. Нельзя обещать,
что такая защита видит jobs, созданные не через MCP.

Architecture Critique: not required. Задача не меняет public/API/MCP contract,
auth, storage, production behavior или ownership boundary: это локальная
privacy-regex regression и static advisory text.

## Acceptance criteria

1. `2024-01-01`, `2026-12-31`, `2024-10-23 17:50:51`,
   `2024-10-23T17:50:51`, timezone-вариант и `31.12.2026` сохраняются в
   free-text, если не пересекаются с PII candidate.
2. `4852-45-67`, `9999-99-99`, `2026-13-01`, `2026-01-32` и
   `2026-01-01 25:00:00` не считаются датами и проходят обычную phone-маску.
3. Настоящий телефон рядом с датой в одной строке и непосредственно после
   date/time через пробел либо дефис redacted; focused corpus также сохраняет
   маскирование прежних форматов с `+`, скобками, пробелами, дефисами (включая
   `8-999-123-45-67`) и compact digits. ISO date, ISO `T`/timezone date-time,
   local `DD.MM.YYYY` date и date range не маскируются.
3a. Phone с четырёхзначным кодом города и phone-like e-mail маскируются;
    при частичном пересечении phone и e-mail скрываются e-mail и остаток
    phone. При совпадении date-like fragment внутри телефона побеждает
    redaction.
3b. Phone рядом с датой либо перед датами может скрыть соседние ISO dates одним
    жадным совпадением; это ожидаемое безопасное поведение и покрыто
    table-driven test.
4. Helper советует: zero rows — результат; перед повтором проверить прямым
   read tool наличие записей за период; без пользователя выбрать и явно
   записать разумное default; разбивать многочастный запрос; создавать jobs
   только последовательно и не запускать несколько отчётов сразу. Время
   одиночного и параллельных jobs описано только как наблюдаемый порядок, а 30
   секунд диагностики сами по себе не означают failure.
4a. Helper прямо говорит, что `preview_example_row` содержит выдуманные, но
    правдоподобные значения; применяет его только для сверки колонок, типов и
    группировки до получения строк; при несовпадении структуры меняет intent
    до сохранения; никогда не пересказывает значения пользователю.
4b. PRD описывает, почему текущий MCP не может распознать осознанное второе
    задание, обработку зависшего job, обход legitimate параллелизма и
    информативный отказ; рекомендует пока не вводить жёсткий guard.
4c. `create_report_ai_job` всегда видимо требует последовательного запуска
    даже разных отчётов; `get_report_ai_job_data` считает пустые строки
    валидным результатом и запрещает пересоздавать job до direct-read проверки.
4d. `get_report_ai_job` для `failed`/`rejected` требует прочесть
    `error_message_safe`, объяснить причину и изменить intent до новой попытки.
4e. Каждый tool с privacy-contract сохраняет исходное описание и добавляет
    только контрактный суффикс; endpoint-level tests доказывают redaction
    каждого заявленного client/owner или staff context. `report_problem` не
    подавляет сообщения о прочих неожиданно отсутствующих данных.
5. Tool и MCP prompt helper остаются идентичными.
6. Focused и полный Docker suite, ShellCheck и Bash syntax проходят.
7. `run_claude_review.sh` возвращает отказ до вызова `git`/reviewer, если
   evidence directory разрешается внутри repo; regression test это доказывает.
