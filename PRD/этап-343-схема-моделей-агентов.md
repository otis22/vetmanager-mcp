# Этап 343. Постоянная схема моделей агента

## Цель

Закрепить решение владельца от 24.09.2026 после пилота 340–342 в трёх действующих инструкциях и сделать расхождение проверяемым.

## Объём и декомпозиция

1. Сверить действующие инструкции, review runner и evidence этапа 342; уточнить проверяемый контракт (≤ 2 ч).
2. Добавить текстовый сторож с показанным красным состоянием, обновить `AGENTS.md`, все зависимые разделы `CLAUDE.md` и `.cursor/rules/agent-workflow.mdc` (≤ 150 строк кода на подзадачу).
3. Добавить `--plain` в исполняемый валидатор и покрыть его CLI-тестами red/green (≤ 150 строк кода).
4. Проверить инструкции и фокусные тесты, провести аудит и committed diff review, затем полный mock, push и CI (≤ 2 ч на каждый гейт).

## Архитектурное решение

- Проблема: расходящиеся инструкции ведут к разным моделям, последовательному вместо одновременного сильному ревью и ложному визуальному гейту.
- Контекст: `run_claude_review.sh` уже сохраняет Claude evidence и остаётся без поведенческих изменений. Review verdict по Claude проверяет `scripts/validate_review_result.py`. Evidence Astra этапа 342 показывает отдельный CLI вызов с JSON schema. Контракт MCP, API, auth, storage и production не меняется.
- Варианты: отдельный runner для двух моделей увеличит код и риск; ручная сверка трёх файлов не защищает от дрейфа; явные одинаковые правила в файлах со сторожем проще для этого этапа.
- Выбор: описать одну и ту же схему в трёх инструкциях, оставить существующий Claude runner, добавить в `validate_review_result.py` проверку plain JSON Astra с той же findings schema и проверить ключевые инварианты текстовым тестом.
- Инварианты: исполнитель `gpt-6-sol`, scout `gpt-6-luna`, параллельные `gpt-6-astra` и Claude Opus на каждом сильном гейте; отдельные бюджеты каждого, evidence и валидация; Astra получает изображения через `-i` на визуальном гейте, Opus там только текстовый reviewer, его `[]` не подтверждает изображения. Невалидный ответ любой стороны после трёх infrastructure attempts блокирует любой гейт, включая визуальный. После исчерпания двух валидных ревью и последующих правок Spark и тесты проверяют только эти правки; это не замена неуспешному сильному гейту.
- Rollback: вернуть документационный коммит и сторож вместе; исторические evidence не менять.

Architecture Critique: not required — задача меняет инструкции и формат входа валидатора ревью, но не границы модулей и не поведение продукта.

## Приёмка

- PRD: Spark candidate review, затем одновременно Astra и Opus; дождаться обоих, свести findings. После существенных правок повторить сильную пару в пределах отдельных бюджетов; после упрощения PRD повторить соответствующие review gates.
- Diff: Spark перед парой сильных ревьюеров на committed diff, затем одновременно Astra и Opus и сведение findings. У каждого сильного ревьюера по два валидных запуска на гейт и до трёх infrastructure attempts; Spark имеет отдельный лимит три.
- Неустранённые critical/high findings блокируют выпуск; medium после исчерпания двух валидных запусков можно отложить только с явным rationale в `AssumptionLog.md`.
- Astra запускается командой пилота с `--output-schema` и `-o`, хранит prompt, result, stderr, metadata (модель, объект и SHA для diff, CLI version, попытка N/3, время начала/конца, exit и validator exit); plain JSON проверяется исполняемым `scripts/validate_review_result.py --plain`. Путь к result и metadata фиксируется в `AssumptionLog.md`. Невалидный вывод не тратит валидный слот и учитывается как infrastructure attempt.
- В трёх файлах согласованно описаны модели, одновременный запуск с ожиданием обеих сторон, отдельные бюджеты 2 валидных / 3 infrastructure attempts, evidence/validation, визуальный гейт и версия CLI ≥ 0.155; старые слаги не представлены как актуальные. Согласовать также зависимые разделы `CLAUDE.md` о self-attestation и diff review.
- Сторож проверяет в каждом файле модели, параллельность и ожидание обоих, отдельные бюджеты, evidence/валидацию, визуальное ограничение Opus и CLI ≥ 0.155. Красный показать нарушением каждой из этих групп условий в каждом файле; затем восстановить и получить зелёный.
- CLI `--plain`: принимает пустой и непустой findings, отклоняет повреждённый JSON и неверную схему с ненулевым exit; прежняя строгая проверка Claude envelope без флага сохраняется. Для отрицательных случаев показать красный тест до изменения валидатора.
- Spark и пара Astra/Opus проверили PRD и committed diff; findings сведены в `AssumptionLog.md`.
- `check_roadmap_structure.py`, фокусные тесты и полный mock проходят. Real API suite не нужен: инструменты и API не меняются. Production и production DB недоступны для этапа.
- После code push зелёные Tests и Deploy Prod; этап переведён в `done`, архивирован, закрывающий commit создан и для него также получены зелёные Tests и Deploy Prod. Никаких обращений агента к production.
