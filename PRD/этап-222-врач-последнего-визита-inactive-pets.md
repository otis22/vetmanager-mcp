# Этап 222. Врач последнего визита в inactive pets

## Цель

Дать модели проверяемый признак для вопроса «кто не приходил больше полугода,
сгруппируй по врачу»: для каждого питомца в `get_inactive_pets` вернуть
`doctor_id`, человекочитаемое имя врача и состояние его разрешения, не
превращая один список пациентов в N+1 запросов.

## Подтверждённые факты

- Последний визит питомца определяется сначала по счёту, затем по медкарте.
  Счёт содержит вложенный `doctor`, а медкарта — только `doctor_id`.
- `GET /rest/api/user` уважает `limit` и возвращает `totalCount`; первая
  страница из 100 сотрудников не является справочником всей клиники.
  Поэтому запрос «первых 100» не даёт права объявлять 101-го врача
  отсутствующим.
- Вложенные объекты upstream могут содержать учётные и платёжные поля.
  Публичный контракт этого инструмента не должен их транслировать.

## Scope

1. Для invoice-path проецировать только ID и составленное ФИО из уже
   прочитанного вложенного `doctor`.
2. Для medical-card path сохранить `doctor_id` и разрешить все положительные
   неизвестные IDs одним bounded запросом `/rest/api/user` с filter `id IN`.
   Размер штата и pagination справочника не влияют на полноту этого join.
3. Возвращать `doctor_resolution`: `resolved`, `not_specified` (ID отсутствует
   или равен нулю) либо `not_found` (именно запрошенный по ID пользователь не
   вернулся). Не путать штатное отсутствие врача с неполным справочником.
4. Проецировать наружу только `doctor_id`, `doctor_name` и
   `doctor_resolution`; не возвращать `login`, `passwd`, `user_inn`, баланс,
   платёжные или любые другие поля сотрудника.

## Вне scope

- Новый запрос к API на каждого питомца или отдельный запрос к врачу для
  invoice-path.
- Назначение врача по эвристике, если последний визит не содержит его ID.
- Изменение существующей window/limit-семантики `get_inactive_pets` (это
  отдельный этап 223).

## Решение

Invoice path использует вложенный `doctor`; medcard path использует `doctor_id`
и один targeted `user.id IN [...]` lookup. `not_specified` означает отсутствующий
или нулевой ID, `not_found` — targeted lookup не вернул именно этот ID.
Проекция выдаёт только ID, ФИО и состояние, поэтому privacy-wrapper не получает
новые чувствительные поля для маскирования.

## Инварианты

- `not_found` запрещено выставлять из-за лимита/страницы справочника: каждый
  такой ID обязан войти в `IN`-фильтр текущего запроса.
- Для invoice-path отдельный `/rest/api/user` не вызывается, если его имя уже
  вложено в счёт.
- Отсутствующий/нулевой `doctor_id` — обычная информация о визите, а не
  ошибка справочника.

## Acceptance criteria

- Mock regression подтверждает invoice и medical-card пути, состояния
  `not_specified`/`not_found`, targeted lookup при `totalCount > 100` и
  отсутствие учётных/платёжных полей в output.
- На devslon67 фактически находятся и invoice-, и medcard-путь, а наружу
  выходят только ID, имя и resolution врача.
- Изменения проходят целевые тесты; полный Docker suite выполняется перед
  merge владельцем задачи.
