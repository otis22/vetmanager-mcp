# Этап 453. Диагностика handshake MCP по аккаунту

## Цель и факты

По `account_id` и минутному окну оператор должен видеть, приходили ли `initialize` и `tools/list` и какой HTTP-исход получен. Сейчас `mcp_transport_observation.py` считает только ограниченные транспортные отказы без аккаунта и метода JSON-RPC. `RequestContextHeaderMiddleware` создаёт проверенный `request_id` и возвращает его клиенту. Runtime авторизация инструмента происходит позже handshake; Vetmanager REST API этап не затрагивает.

## Архитектурное решение

Добавить наблюдение в существующий ASGI middleware `/mcp`. Для `POST` с одним JSON-RPC объектом распознавать точные `initialize` и `tools/list`; другие корректные методы не записывать. До вызова FastMCP прочитать не более 64 KiB и 128 чанков тела POST с timeout 250 мс; затем воспроизвести downstream ровно те же ASGI чанки, байты и `more_body`, а оставшийся поток передать без изменения. Поэтому метод доступен даже при раннем 400/406 без чтения FastMCP. Пустой POST не считать попыткой handshake. При malformed/oversized/недочитанном непустом POST писать `method=unknown`, `reason=invalid_request`/`body_too_large`/`body_not_read`: оператор увидит попытку MCP, но не может приписать ей конкретный RPC метод. JSON-RPC batch-массивы также `unknown` с `invalid_request`. Для `initialize` брать версию из `params.protocolVersion`, для `tools/list` из `MCP-Protocol-Version`; разрешить только короткий ASCII формат версии, иначе `unknown`. В событии фиксировать UTC время, RPC method, HTTP method, канал `mcp_http`, auth source (`service_bearer`, `oauth_access`, `none`, `other`), auth outcome (`matched`, `unmatched`, `absent`, `lookup_failed`), account_id только при совпадении хеша токена с БД, HTTP status, bounded reason и нормализованный server-generated/request_id. Источник `oauth_access` определяется только фиксированным префиксом OAuth access токена, остальные Bearer — `service_bearer`, неверная схема — `other`. Совпадение токена устанавливает принадлежность записи, но не утверждает, что токен действителен: срок, статус и права остаются в существующей авторизации. Для OAuth account_id брать через grant; orphan access token без grant считается `unmatched` и не получает account_id. После завершающего байта ответа наблюдатель запускает bounded background task, не задерживая возврат ASGI/следующий keep-alive запрос. Перед созданием task слот semaphore на 16 concurrent diagnostics захватывается без ожидания; при насыщении пишется событие `lookup_failed` без DB lookup. Для `unknown` с допустимо оформленным bearer также нужен lookup: это сохраняет account_id у ранних 400, когда метод нельзя восстановить. Любой lookup проходит общий предел 16/250 мс; отсутствие bearer не вызывает DB read. Async DB lookup ограничен `asyncio.timeout(0.25)`; таймаут даёт `lookup_failed` и пустой account_id. В фоновой task локальный структурированный logger пишет после lookup; при отмене task, сбое процесса или недоступном журнале событие может потеряться, а HTTP исход не меняется. Не писать сырые токены, IP, session ID, заголовки или произвольные JSON значения.

Счётчик `vetmanager_mcp_handshake_total{method,auth_source,auth_outcome,outcome}` имеет только конечные метки и отдельный Redis hash для совместимости старых воркеров. `outcome` = `success` для HTTP 2xx без обнаруженной JSON-RPC ошибки, `rpc_error` для bounded JSON/SSE error при HTTP 2xx, `http_4xx`, `http_5xx` или `other`. Ответ наблюдается на лету, без изменения отправки и с жёстким буфером до 4096 байт: после заполнения новые чанки не копируются. Если RPC ошибка не помещается или поток не завершён, событие говорит только о HTTP-исходе. Для SSE событие пишется после завершающего `more_body=false`; при disconnect/cancel без завершения оно не обещается. Account ID, версия и request_id остаются только в структурированном журнале. На 400/404/406 reason берётся из существующего ограниченного классификатора; JSON-RPC ошибка даёт `rpc_error`, прочие отказы — `other`, успешный ответ — `none`. Диагностика best-effort: ошибка БД/Redis/логирования не меняет HTTP-ответ. Shared метрика доставляется асинхронно, live-проверка ждёт её до 5 секунд через `wait_pending`. Ответ и поток не буферизуются.

Варианты: отдельный MCP handler зависит от FastMCP internals; access log содержит лишние данные и не связывает токен с account_id. Existing middleware уже видит HTTP исход и минимизирует новую поверхность. Минус — дополнительный indexed read БД на диагностируемый POST с bearer, включая `unknown`; общий semaphore и таймаут ограничивают нагрузку. Ограничение тела предотвращает неограниченную память. Rollback — вернуть прежний middleware и счётчик; старый reader игнорирует новый отдельный ключ. Никаких миграций и новых пользовательских текстов.

## Приёмка

- Для известного service bearer и OAuth access токена `initialize`/`tools/list` дают событие с account_id и верным каналом/исходом; при неизвестном токене account_id пуст. Revoked/expired известный токен получает `matched`, что означает только принадлежность записи, а HTTP исход записывается отдельно.
- По одному account_id и UTC минуте события показывают наличие и результат обоих handshake; request_id совпадает с заголовком ответа.
- HTTP 400 и JSON-RPC error при HTTP 200 имеют ограниченный reason; из запросов с произвольным текстом, ошибочными/крупными телами и заголовками ничего чувствительного не попадает в лог или labels. Для oversize/malformed запроса видна попытка MCP с `unknown`, но конкретный метод нельзя доказать.
- Shared metric учитывает оба метода и исходы без account_id, старый reader общего hash работает; middleware не меняет ответ, не затрагивает другие пути и fail-open при сбое наблюдения. Guards проверяют насыщенный semaphore, отсутствие DB lookup без bearer, сохранение chunking/body/`more_body` и повторный `receive`, а также отсутствие задержки следующего keep-alive запроса при медленной БД.
- Изолированный тестовый HTTP-контур показывает код и обезличенное тело `initialize`/`tools/list`, события и прирост метрики. Production и инструментальные вызовы Vetmanager не используются.

## Декомпозиция

1. 453.1a: красные guards для формы события, приватности, исходов, раннего 400/406 и метрики; ≤2 ч.
2. 453.1b: parser, account lookup, событие в middleware; ≤2 ч.
3. 453.1c: shared counter и `/metrics`, тесты mixed-reader; ≤150 строк кода.
4. 453.2: тестовый live HTTP smoke, аудит, полный suite, Roadmap/AssumptionLog, committed diff review и выпуск; ≤2 ч.

## Простота

Один middleware, одно событие на завершённый handshake и один bounded counter. Долговременную таблицу handshake, поиск по токену для произвольных MCP методов и UX не добавлять.

## PRD-review и simplicity

Внутренний PRD-review: проверены цель Roadmap 453, граница без этапа 454, факт `RequestContextHeaderMiddleware`, отсутствие изменения UX и Vetmanager REST. Spark #1: приняты timeout lookup и eventual метрика; Spark #2: принят orphan OAuth и жёсткий предел буфера, уточнена потеря события при cancellation; Spark #3: замечание о недоступном `request_id` отклонено — Starlette `Request(scope).state` хранится в общем `scope["state"]`, поэтому вложенный middleware получает то же значение через `get_request_context(Request(scope))`. Astra #1 невалиден: `[]` без чтения PRD. Opus #1: четыре material findings приняты и отражены в архитектуре. Astra #2 и Opus #2: приняты ранний отказ без чтения body и влияние lookup на keep-alive; предварительное ограниченное чтение и фоновая задача описаны выше. Третьего сильного PRD pass не делать: лимит двух валидных Opus verdict исчерпан, допустимых high/critical не осталось.

Simplicity triggers: новых классов/фабрик/dual API нет; изменения локализованы в существующих middleware, metrics и shared counters. Дополнительная буферизация нужна для ранних транспортных отказов, background lookup — для keep-alive, отдельный Redis hash — для mixed-version reader. Таблица handshake и новая очередь событий усложнили бы откат без улучшения минутной диагностики.
