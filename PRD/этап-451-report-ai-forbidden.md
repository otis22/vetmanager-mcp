# Этап 451. FORBIDDEN при HTTP 403 Report AI

## Цель

Отдавать агенту понятный отказ доступа при HTTP 403 Report AI с `data.error_code=FORBIDDEN`, в том числе при создании и чтении задания.

## Проверенные факты

Событие PYTHON-1C: 31.10.2026 17:59 UTC, аккаунт 55, операция job; `report_ai_outcome_code code=FORBIDDEN`, агент получил `Report AI request failed (unknown).` В `vetmanager_client._raise_for_status` HTTP 403 создаёт `AuthError` с `status_code=403`, `error_code=None`; для любого пути с префиксом `rest/api/report-ai-job`, включая POST создания и GET задания/данных, код сохраняется в `observed_error_code`. В `_tool_error_from_vm` ветка понятного отказа этапа 442 требует отсутствия обоих кодов, а следующая классификация смотрит только `error_code`. Поэтому наблюдённый FORBIDDEN проходит в `unknown`.

## Архитектурное решение

В маппере Report AI считать HTTP 403 с отсутствующим кодом или наблюдённым `FORBIDDEN` отказом доступа. Не поднимать любой наблюдённый код в `error_code`: неизвестные явные коды остаются `unknown`, другие коды и HTTP 401 сохраняют прежний смысл. Сырой текст апстрима наружу не выходит. Architecture Critique требуется: публичный контракт ошибок.

## Подзадачи и приёмка

1. Красный тест полного MCP пути create и read при 403 с `FORBIDDEN`; тест неизвестного кода и 401.
2. Исправить маппер, проверить фокусные тесты и вызвать изменённый инструмент на разрешённом стенде. Зафиксировать код и безопасное тело в AssumptionLog. Если тестовый аккаунт не воспроизводит именно 403, отметить этот предел живой проверки и приложить полный MCP-путь с реальным транспортным 403 в локальном тесте; production-вызов запрещён.
3. Полный mock и real suite, ревью committed diff и выпуск ветки.

## Простота

Одна узкая ветка по `status_code` и `observed_error_code` устраняет дефект без изменения транспортного исключения или остальных кодов.
