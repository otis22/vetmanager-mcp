# Этап 298. Запись цены продажи — только с подтверждением

## Цель

Сегодня ни один инструмент не меняет цену продажи: `update_good` трогает только
себестоимость (`prime_cost`), а цена живёт в `goodSaleParam`. Решение владельца
05.09.2026: делать, но **только с подтверждением** — цену сразу видят клиенты
клиники, и ошибка здесь дороже почти любой другой.

## Проверенные факты

Проверено по исходникам Ветменеджера, а не по документации.

- `GoodSaleParamController` — пустой класс, наследующий `ApiController` →
  `ERestController`, то есть получает полный набор REST-действий, включая
  `actionRestUpdate`. Ограничений на запись в `ApiController` нет.
- Модель `GoodSaleParam` объявляет `price`, `min_price`, `max_price`,
  `coefficient` числовыми правилами **без ограничения сценарием**, значит поля
  присваиваются массово.
- Маршрут `/rest/api/goodSaleParam` уже используется на чтение
  (`get_good_sale_params`, `get_good_sale_param_by_id`).
- В таблице `good_sale_param` у `good_id` **обычный индекс, не уникальный**:
  у товара несколько строк цены — по клинике (`clinic_id`) и по единице продажи
  (`unit_sale_id`), плюс `status` = `active` / `disabled`.
- Есть колонка `price_formation` со значениями `fixed` / `increase`. У строки с
  `increase` цена выводится из наценки (`markup`), и запись `price` там либо
  игнорируется, либо затирается пересчётом.
- Есть `min_price` и `max_price` — границы, заданные клиникой.

Отсюда главный риск: **«цена товара» — не одно поле.** Слепая запись почти
наверняка попадёт не в ту строку или не в ту схему ценообразования.

## Цель решения

Не «дать инструмент записи цены», а сделать так, чтобы записать не ту цену было
трудно. Инструмент по умолчанию **ничего не пишет**: он показывает, что
изменится, и ждёт явного согласия.

## Scope

Уточнение владельца 05.09.2026: инструмент должен **предлагать варианты**
обновления — с учётом клиник и групп товаров. Поэтому превью не просто
показывает соседние строки, а перечисляет способы применить изменение.

1. `update_good_sale_price(sale_param_id, new_price=0, change_percent=0,
   scope="row", clinic_id=0, confirm=False)`.
   Без `confirm` — превью и **никакой записи**.
2. Превью перечисляет варианты, у каждого — сколько строк он затронет и какой
   вызов его применяет:
   - `row` — только эта строка (эта клиника, эта единица продажи);
   - `good` — все строки цены этого товара; с `clinic_id` — только в одной
     клинике;
   - `group` — все товары группы, к которой принадлежит товар; с `clinic_id` —
     в одной клинике.
3. **Абсолютная цена для группы отклоняется.** Поставить всем товарам группы
   одну и ту же цену — почти наверняка не то, что имелось в виду; групповая
   переоценка делается процентом (`change_percent`). Для `row` и `good`
   допустимы оба способа: это один и тот же товар.
4. Отказ на строке с `price_formation="increase"`: там цена выводится из
   наценки, и запись `price` — действие, которое выглядит выполненным, а
   результата не даёт. Отказ объясняет, что менять надо наценку. В групповом
   варианте такие строки не пишутся, а перечисляются в превью отдельно.
5. Отказ на выходе за `min_price` / `max_price`, когда они заданы: это границы,
   которые клиника поставила сама.
6. Запись только при `confirm=True`; ответ содержит «было → стало», проверенное
   повторным чтением, а не эхом запроса.
7. Предохранитель на объём: если вариант затрагивает больше строк, чем предел,
   запись отклоняется — такую переоценку делают отчётом и руками, а не одним
   вызовом агента.

### Вне scope

- Новый инструмент чтения цен. Чтение уже есть — `get_good_sale_params`.
  Третий путь к тем же данным повторил бы ошибку этапов 224 и 259.
- Изменение наценки, создание новых строк цены.
- Изменение `min_price` / `max_price`: границы ставит клиника, а не агент.

## Декомпозиция

- **298.1** Превью без записи, со списком соседних строк. ≤ 70 LOC.
- **298.2** Отказы: `increase`, выход за границы. ≤ 40 LOC.
- **298.3** Запись по `confirm=True` с проверкой результата чтением. ≤ 40 LOC.

## Acceptance

1. Без `confirm` не уходит ни одного запроса на запись — проверяется по
   фактическим вызовам, а не по возвращённому тексту.
2. Превью содержит текущую цену, новую и перечень вариантов `row` / `good` /
   `group` с числом затрагиваемых строк у каждого.
3. Строка с `price_formation="increase"` отклоняется с объяснением.
4. Цена вне `min_price`/`max_price` отклоняется.
5. При `confirm=True` цена меняется, ответ показывает «было → стало» из
   повторного чтения.
6. Живая проверка на `devtr6`: цена изменена и возвращена обратно.
7. Абсолютная цена в групповом варианте отклоняется.
8. Вариант сверх предела по числу строк отклоняется даже с `confirm=True`.
9. Полный набор тестов зелёный.
