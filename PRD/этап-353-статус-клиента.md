# Этап 353. Статус клиента в MCP

## Цель и факты

Репорт #114: `update_client(status="INACTIVE")` возвращал успех, а клиент получал пустой статус. По проверенному поведению Vetmanager публичные состояния клиента — `ACTIVE`, `DISABLED`, `DELETED`; перевод в неактивное состояние и обратно — `ACTIVE` ↔ `DISABLED`. В MCP ошибочно рекламируется `INACTIVE`. OpenAPI v6 описывает строковое поле `status`, но не перечисляет enum. Живое чтение devtr6 вернуло HTTP 200 для фильтров ACTIVE (41), DISABLED (30), DELETED (166). Список без фильтра также содержит 4 записи `TEMPORARY`: это внутреннее временное состояние, не предлагаемый агенту переход. Пустых статусов на devtr6 сейчас нет. Живая запись на тестовом клиенте проверяется отдельно.

## Декомпозиция

- 353.1 (≤2 ч): сверить исходники, OpenAPI, devtr6; PRD, Architecture Critique и PRD-review.
- 353.2 (≤150 строк): красный сторож на отказ до HTTP и полноту описаний, затем исправить `get_clients`/`update_client`.
- 353.3 (≤2 ч): аудит соседних статусов питомцев и сотрудников; живой вызов DISABLED → ACTIVE на devtr6, аудит, ревью diff, suite и выпуск.

## Архитектурное решение

**Проблема.** Свободная строка `status` проходит в REST, который может принять неизвестное значение и сохранить неверное состояние.

**Контекст.** Инструменты используют `ToolInputError` для неверных аргументов и вызывают `crud_update`/`crud_list` только после локальных проверок. Публичный MCP-контракт меняется: `INACTIVE` больше не принимается. `status=""` означает отсутствие обновления или фильтра. Произвольные сырые фильтры имеют отдельный контракт. `update_client` имеет `clients.write`, а удаление — отдельное право `records.delete`; поэтому `DELETED` нельзя передавать через `update_client`. OpenAPI не задаёт enum; факты берутся из поведения API и клиента Vetmanager.

**Варианты.** Тип `Literal` в сигнатуре даёт схему, но ошибку может сформировать FastMCP без предметного объяснения. Общий enum-модуль для одного поля создаёт лишний уровень. Локальная проверка строки перед HTTP и одинаковый перечень в описаниях дают агенту понятную ошибку и сохраняют схему вызова. Выбран последний вариант.

**Инварианты.** Публичный фильтр принимает `ACTIVE` (активный), `DISABLED` (неактивный), `DELETED` (удалённый) и пустую строку для всех записей, включая внутреннее `TEMPORARY`. Запись принимает только `ACTIVE`, `DISABLED` и пустую строку как отсутствие действия; `DELETED` остаётся значением чтения и не обходит `records.delete`. Значения сравниваются точно, без изменения регистра и обрезки пробелов. Неизвестный статус не делает HTTP-запрос. Описания фильтра и изменения явно называют доступные значения и смысл `DELETED`. Статусы питомцев и сотрудников оцениваются отдельно по их модели.

**Существующие пустые статусы.** Этап предотвращает новые неверные записи. Исправление уже испорченных production-клиентов и привязка репорта #114 остаются у супервизора; агент не читает production. Проверить на devtr6, возвращает ли список без фильтра пустой статус, и зафиксировать, что исправление конкретного ID возможно `update_client(status="ACTIVE"|"DISABLED")` после решения владельца о нужном статусе. Массовое автоматическое восстановление недопустимо без исходного статуса.

**Rollback.** При несовпадении контракта со стендом откатить изменение и не выпускать этап; тестового клиента вернуть в `ACTIVE` до завершения пробы.

Architecture Critique required: меняется публичный MCP-контракт и поведение записи.

## Приёмка

1. Источники и чтение devtr6 подтверждают перечень.
2. Красный сторож падает при прежнем коде на `INACTIVE`, `DELETED` для записи, `disabled` и ` ACTIVE `; после правки ошибка объясняет допустимые значения и смысл `DELETED` до HTTP.
3. `get_clients` и `update_client` описывают действительные значения, `get_clients(status="DISABLED")` фильтрует их.
4. Аудит питомцев/сотрудников либо находит и исправляет фантомный enum, либо документирует совпадение.
5. Живая запись через `update_client` на devtr6 DISABLED → ACTIVE и чтение после каждого шага; проверить поведение списка без фильтра для пустых статусов без создания новых испорченных записей. Коды и безопасные выдержки ответа записаны в `AssumptionLog.md`.
6. Полный mock + real suite один раз перед push, валидные ревью Astra/Opus, зелёные Tests и Deploy Prod.
