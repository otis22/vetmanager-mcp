# Этап 484. Пригодность existing_report_matched

## Цель

Этап 485 допускает старый matched-отчёт с иной recognized structure, включая
корректный пустой ответ. Этап 484 действует в этих границах и отказывает
только при явной ошибке чтения, нечитаемом ответе или битой ссылке.


По решению владельца 20.11.2026 (вариант В) оставить поведение корректных
пустых matched-отчётов без изменений и отказывать только при явных признаках
непригодности чтения данных или ссылки. Историческая разница пустого match и
непустого seed остаётся задачей upstream semantic match, а не runtime-правилом
MCP.

## Граница

Этап не меняет маску 480, критерии этапа 483, выбор upstream-кандидата,
существующие отчёты или право доступа. Новых Report AI jobs ради проверки
не создаётся.

## Проверенные факты перед архитектурным решением, 20.11

Сохранённая read-only проекция 19.11 (`read-only-semantic-match-deep-dive.json`,
SHA-256 `d489bae7c78204fc8b650d00a123442bc697837a1994e04c173fa1b28550e28c`)
подтверждает для старого match HTTP 200, `columns=[]`, `rows=[]`, `total=0`,
а для seed — HTTP 200, две колонки, 12 строк, `total=12`. У matched job
`preview_summary` отсутствует; у исходного старого saved job preview был
нулевым, у нового seed — ненулевым. В публичный PRD не переносятся ID,
значения строк и служебные адреса.

`artifacts/api-research-notes-ru.md` подтверждает форму наблюдаемого
`GET /report-ai-job/{id}/data`: поля `columns/rows/total/limited/csv_export_url`
в объекте `payload.data` (верхний уровень содержит `success` и `data`).
Локальный OpenAPI v6 не содержит `report-ai-job`. `tools/report_ai.py`
передаёт статус matched и затем читает его `/data`; в этих вызовах нет связи
с seed. Таблица `ReportAiJobRating` хранит intent и job ID, но не ожидаемую
мощность, структуру результата или связь с seed. Текст intent сам по себе не
доказывает эквивалентность исполненных отчётов.

## Решение владельца, 20.11.2026: вариант В

Поведение по пустым результатам **вообще не меняется**. `rows=[]`, `total=0`,
пустые `columns`, `limited` и отличие от исторического seed не являются
runtime-критерием отказа. Даже доказанная историческая неэквивалентность
старого match и seed не даёт MCP доступного эталона в новом вызове.

Fail-closed применяется только к **явным признакам непригодности**: ошибка
чтения `/data`, ответ об ошибке, нечитаемая структура успешного ответа или
битая ссылка, которую MCP собирается передать как пригодную. Возвращать
успешные строки или рекомендацию использовать отчёт в этих случаях нельзя.
Сообщение об отказе не содержит raw URL, данных клиники или служебных ID.
После отказа пользователь может повторно прочитать тот же job позднее;
MCP не создаёт и не сохраняет другой отчёт автоматически.

## Архитектура и граница изменения

Проверка выполняется в `get_report_ai_job_data` на уже существующем GET
`/rest/api/report-ai-job/{id}/data`. Успешный ответ должен содержать `data`
с массивом `rows` из объектов; пустой массив допускается. `columns`,
`total` и `limited` сохраняются как приходят от upstream: их отсутствие или
необычный тип сами по себе не доказывают нечитаемость строк и не вводят
новый отказ. Необязательная
`csv_export_url`: отсутствие, `null` и пустая строка означают отсутствие
ссылки и допустимы; непустое значение проверяется как относительный путь `/rest/api/report/` без
схемы, authority, фрагмента, символов Unicode категорий `C*` и `Z*`
(управляющие, невидимые, пробельные и private-use), обратного слэша и
сегментов `.`/`..` или закодированных разделителей `#`/`?` после
URL-decoding пути до неподвижной точки. Query string
допускается, но не влияет на проверку сегментов пути;
При явно битой ссылке MCP отказывает целиком и не возвращает строки как
успешный результат. Наблюдаемый на devtr6 корректный matched `/data`
имеет относительную ссылку; совместимость с другими формами не доказана.
Ошибки HTTP уже
преобразуются существующим transport. Дополнительных запросов, поиска seed,
сравнения количества строк и новых публичных параметров нет.

Выбор upstream-кандидата, его смысловая эквивалентность, маска 480 и этап 483
остаются вне scope. На devtr6 исторический пустой match остаётся допустимым
по этому контракту, если его `/data` читается; upstream-дефект разбирает ВМ.

## Декомпозиция и приёмка

1. Зафиксировать контракт и выполнить PRD/Architecture Critique: механическая
   проверка → Spark → Astra и Kimi, оценка простоты. ≤ 2 ч.
2. Test-first: красный guard для явной ошибки/нечитаемого matched `/data` и
   битой ссылки; отдельный guard подтверждает сохранение поведения корректного
   пустого matched-отчёта. Каждый guard сломать охраняемой мутацией. ≤ 150 строк.
3. Минимальная правка runtime, каждый красный node отдельно → owning suite →
   fast → аудит → pre-review полного diff: Spark → Astra и Kimi. ≤ 150 строк.
4. После заморозки default и применимые контуры, живой вызов изменённого
   инструмента на devtr6 с кодом и очищенным телом, real aggregate, запись
   evidence, Roadmap/AssumptionLog, commit, committed-diff review и push.
   PR/merge делает куратор.

Приёмка: явная непригодность не выдаётся как успешный результат; корректный
пустой matched-отчёт обрабатывается прежним образом. Права, очистка данных,
число запросов и privacy-границы сохраняются. Существующие тесты
очистки ключей колонок и значений отчёта должны оставаться зелёными;
новая проверка стоит до общего sanitizer и не возвращает raw payload.
