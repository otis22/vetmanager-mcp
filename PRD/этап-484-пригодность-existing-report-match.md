# Этап 484. Проверка пригодности existing_report_matched

## Цель и исходные факты

После выпуска 479 не принимать как пригодный `existing_report_matched`, если
его отчёт возвращает пустой результат, а непустой seed для того же намерения
уже доказан. На devtr6 19.11.2026 старый matched-отчёт вернул 0 строк,
новый seed — 12 строк с zero-fill. Это наблюдение, а не доказательство
внутреннего алгоритма ВМ. Upstream semantic match эскалирован в ВМ;
этап 483 остаётся `supervisor_pending` до ответа.

## Вопросы перед реализацией

1. Определить, где MCP получает надёжный seed и как сопоставляет его с
   matched-отчётом без повторного `StartReport` и раскрытия данных клиники.
2. Уточнить контракт результата: что считать пустым, как учитывать
   `total`, pagination, недоступность `/data`, изменения данных во времени и
   отчёты, где пустой результат корректен.
3. Выбрать безопасный ответ MCP при непригодном или непроверяемом match:
   не рекламировать его пригодным и дать пользователю понятное следующее
   действие. Не запускать автоматическое создание нового отчёта без решения.
4. Ограничить число read-only запросов, задержку и защитить raw payload,
   ссылки, идентификаторы и логи по действующим правилам деперсонализации.

## План и приёмка

После ответа на вопросы оформить полный PRD и Architecture Critique. Показать
красным guard на пустой matched при непустом seed и отдельный guard на
недоступность проверки. Затем реализовать fail-closed проверку, подтвердить
сохранение доступных корректных matches, права и деперсонализацию. Пройти
focused/fast/default, live вызов изменённого инструмента на выбранном стенде,
real aggregate и обязательные review gates. Штатные upstream jobs допустимы
только по утверждённому сценарию; успешный `StartReport` не повторять на retry.

## Граница

Это отдельный поезд после 479. Он не меняет маску имени 480 и не объявляет
upstream выбор кандидата исправленным.
