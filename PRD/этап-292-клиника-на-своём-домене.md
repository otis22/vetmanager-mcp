# Этап 292. Клиника на собственном домене не может подключиться

## Обращение

04.09.2026. Клиника открывает Ветменеджер по собственному адресу, вводит его в
форме подключения и получает:

> Неверный формат домена клиники. Укажите только поддомен из адреса, по
> которому вы открываете Vetmanager: для myclinic.vetmanager.ru это myclinic.

Сообщение выглядит как претензия к вводу — и в этом его вред. Формат ввода тут
не главное препятствие, а подсказка «укажите только поддомен» ведёт в тупик:
поддомена, о котором она говорит, у этой клиники нет.

## Что происходит на самом деле

Три слоя, каждый проверен вызовом, а не чтением кода. Адреса здесь и дальше
условные (`clinic`, `vm.clinic.example`): репозиторий открытый, и настоящий
адрес клиники в нём не хранится — разбор с фактическими значениями лежит в
рабочем журнале, вне этого репозитория.

**1. Форма.** `domain_validation.DOMAIN_PATTERN` принимает только голую метку
(`^[a-z0-9][a-z0-9-]{0,62}$`) и умеет срезать два известных суффикса —
`.vetmanager.ru` и `.vetmanager.cloud`. Адрес с точками отвергается.

**2. Резолв — и вот настоящая стена.** billing-api клинику знает:

```
GET https://billing-api.vetmanager.cloud/host/clinic
{"protocol":"https","host":"clinic.example","url":"vm.clinic.example","success":true}
```

Ключ аккаунта — `clinic`, и он форму проходит. Но
`host_validation.ALLOWED_HOST_SUFFIXES = ("vetmanager.cloud", "vetmanager2.ru")`
отбрасывает ответ: `Resolved host is not allowlisted for domain 'clinic'`.
Пользователь видит «Billing API returned an invalid host response» — то есть
обвинение биллинга в ответе, который биллинг дал совершенно правильный.

Отсюда главный вывод: **клиника на собственном домене не может подключиться в
принципе**, даже введя всё верно. Первая стена прячет вторую за ложной
причиной, и потому обращение выглядит как вопрос про формат ввода.

**3. TLS клиники — уже не наш слой, но приходить будет к нам.** Сервер клиники
отдаёт только листовой сертификат, без промежуточного: `verify error:num=20
unable to get local issuer certificate`. Браузер это скрывает — он докачивает
недостающее звено сам по AIA. Строгий клиент (curl, httpx) соединение не
установит. Без объяснения такая поломка приходит в поддержку как «ваш сервис не
работает».

## Решение

### Где живут адреса

Публичные зоны Ветменеджера остаются в коде: `vetmanager.cloud`,
`vetmanager2.ru` — это не секрет и не наша тайна.

Собственные адреса клиник в репозиторий не попадают. Решение владельца
04.09.2026: они живут в `.env` на сервере. Причина не в конфиденциальности
самого домена (домен клиники не PII — решение 21.08.2026), а в том, что это
**чужие адреса**, состав которых меняется по мере подключения клиник; в
открытом репозитории им нечего делать. В git — имя переменной, разбор формата
и тесты на выдуманных значениях.

### Формат

```
CUSTOM_CLINIC_HOSTS=ключ_аккаунта=хост,ключ_аккаунта=хост
```

Пустая по умолчанию. Пустая карта = сегодняшнее поведение, байт в байт.

### Почему это строже прежнего, а не слабее

Список зон разрешает **любой** хост внутри зоны. Запись `ключ=хост` привязывает
конкретный аккаунт к конкретному адресу: для ключа `X` допустим ровно тот адрес,
который настроен, и никакой другой.

Проверка **добавляется** к существующей, а не заменяет её. Это осознанно:
заменяющая проверка означала бы, что опечатка в `.env` отбирает доступ у
клиники, которая работает сегодня. Добавляющая может только расширить.

### Ключ аккаунта не угадываем

Соблазн вывести ключ из адреса есть: в разобранном обращении второй уровень
домена совпадал с ключом аккаунта, и угадывание сработало бы. Но это совпадение
бренда с ключом, а не правило. Ключ берётся из
настроенной карты — то есть его один раз выяснил человек, спросив billing-api.

## Область

- 292.1 Разбор `CUSTOM_CLINIC_HOSTS`: карта `ключ=хост`, пустая по умолчанию,
  мусорные записи игнорируются, а не роняют старт.
- 292.2 `validate_resolved_vetmanager_origin` принимает адрес, настроенный для
  этого ключа. Остальные проверки (https, без порта, без userinfo, голый
  origin) действуют для него в полном объёме.
- 292.3 Форма принимает настроенный адрес и приводит его к ключу аккаунта.
- 292.4 Неполная цепочка TLS называется словами и с указанием, что чинить.

## Вне области

- Автоматический подбор ключа аккаунта по адресу.
- Отказ от списка зон в пользу общей проверки «публичный IP».
- Самообслуживание: подключение клиники на своём домене остаётся действием
  оператора (строка в `.env` и перезапуск).

## Риск и его граница

Меняются два общих места — проверка резолвленного адреса и нормализация ввода
домена. Через них проходит **каждая** клиника. Граница риска в том, что оба
изменения включаются только непустой картой: при пустой `CUSTOM_CLINIC_HOSTS`
обе функции идут ровно теми же ветками, что и до этапа. Дословно «байт в байт»
это не так — добавились импорт и шаг журналирования на старте; речь про
поведение проверок, и проверяется именно оно. Это и проверяется
отдельным тестом, а не заявляется.

Отдельный риск — эксплуатационный: значение живёт только на сервере, и при
пересборке машины оно теряется молча. Поэтому при старте в журнал пишется
количество настроенных адресов (число, не значения) — по нему видно, доехала
карта или нет.
