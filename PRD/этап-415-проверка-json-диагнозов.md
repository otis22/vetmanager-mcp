# Этап 415. Проверка JSON-диагнозов профиля пациента

## Цель и исходные факты

Фидбек #136 описывает `diagnos` как строковый JSON-массив объектов `{id, type}`. OpenAPI задаёт строковый тип `diagnos`, а `diagnos_text` и `diagnos_type_text` хранит отдельно. Фактический код `resources/pet_profile.py` и сторожа `tests/test_stage391_json_diagnoses.py` уже реализуют этот контракт в этапе 391, выпущенном 15.10.2026: AssumptionLog содержит кодовый SHA `f2771d11` и успешный Deploy Prod. Этап 415 заведён повторно 17.10.2026. Его проверяемый результат — независимое подтверждение уже выпущенного контракта и устранение только воспроизведённого остаточного дефекта. Если текущий код и живой ответ удовлетворяют приёмке, этап закрывается как повторная проверка без переписывания или повторного production выпуска; branch push выпускает лишь документацию проверки.

## Архитектурное решение

Проблема исходного фидбека: сериализованная строка интерпретировалась одним ID. В существующем решении владельцем разбора является агрегатор профиля. `_diagnosis_references` декодирует JSON, сохраняет валидные положительные целые `id` и целые `type`, а `_diagnosis_titles` сопоставляет ID со справочником и использует согласованные текстовые поля для названий. Старый скаляр остаётся на прежней ветке. Битый JSON и непустой массив без валидных ссылок остаются непрозрачным unresolved значением, ресурс не падает; пустой массив не создаёт диагноз. Незаполненное `diagnos_text` само по себе не доказывает диагноз, а заполненное используется лишь вместе с согласованным `diagnos_type_text` и валидной JSON-ссылкой. Это защищает от устаревшего отдельно изменяемого текста.

Варианты: переписать существующий parser (необоснованный риск регрессии); дублировать parser в инструменте `get_medical_cards` (рассинхрон); проверить уже выпущенную реализацию и добавить только недостающий сторож или исправление (выбрано). Ограничения: не менять REST-контракт и права, не выводить личные данные стенда в артефакты, не увеличивать число upstream запросов. Инварианты: JSON-ссылки становятся отдельными ID и типами; справочные либо согласованные текстовые названия попадают в агрегат; legacy scalar сохраняет прежнее разрешение; битый JSON не роняет профиль; пустая форма не придумывает диагноз. Если живые данные опровергнут контракт, откат корректирующей правки должен согласованно вернуть resource, `tool_descriptions.py`, privacy-правила и тесты, если она меняла производные поля или их описание. Architecture Critique включён в PRD-гейт из-за публичного MCP-ответа.

## Декомпозиция

1. **415.1 PRD и проверка контракта** (≤2 ч): проверить OpenAPI, код и живые карты на `.env` test-контуре; Spark → Astra + Sol xhigh по PRD; зафиксировать findings.
2. **415.2a сторожа** (≤150 строк): JSON-массив в отдельные ID и `type`; legacy scalar; заполненный агрегат зарегистрированного `get_pet_profile` при согласованных `diagnos_text`/`diagnos_type_text` даже при полностью пустом справочнике; битый JSON и пустой массив. Согласованность означает равные списки названий из `diagnos_text` и `diagnos_type_text` в форме `<название> (<тип>)`; при наличии известных ID справочные названия должны входить в этот список. Каждый guard принимается через управляемую мутацию охраняемого поведения, если production-код уже зелёный.
3. **415.2b реализация и выпуск** (≤2 ч): только при воспроизведённом пробеле исправить код. На заранее выбранном `.env` test-контуре просмотреть ограниченную выборку карт без вывода ПД, записать количество найденных JSON/legacy форм и сырой `diagnos` только для безопасного синтетического примера либо структурную форму реального значения. Для найденных форм вызвать `get_pet_profile`, записать код и безопасные поля тела. Если legacy-карт нет, зафиксировать ограничение и проверить fixture через зарегистрированный MCP-инструмент в тесте. Затем аудит, committed diff gate, один полный mock и real suite, push в `dev/roadmap-415-417`, зелёный Tests. Пост-релизные метрики после merge супервизором.

## Приёмка и простота

JSON-форма не остаётся целой строкой в unresolved; идентификаторы и типы видны отдельно. Согласованные текстовые диагнозы дают непустой агрегат даже при неполном справочнике. Старый скаляр разрешается как прежде. Битый JSON не вызывает ошибку ресурса, сохраняет исходный unresolved сигнал; `[]` не создаёт диагноз. Живые ответы и ограничения фиксируются без ПД. Уже имеющийся код не переписывается при зелёной приёмке.
