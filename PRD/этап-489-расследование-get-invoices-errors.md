# Этап 489. Расследование `get_invoices` errors без traceback

## Цель

Установить причину двух записей `Error calling tool 'get_invoices'`, найденных
21.11.2026 во время post-release мониторинга. Деградация workers и связь с
релизом не доказаны. Сначала получить достаточные evidence; исправление по
догадке запрещено.

## План

1. По двум временным меткам сопоставить runtime всех workers, nginx и доступный
   audit. Определить error class, HTTP/upstream code, correlation/request ID,
   worker и форму параметров без значений или содержимого счетов.
2. Проверить, был ли это отказ ВМ, transport/timeout, локальная валидация или
   ошибка обработки ответа. Отличить повтор одного сценария от двух независимых
   отказов.
3. Зафиксировать причину и владельца. Если существующих логов недостаточно,
   подготовить отдельный узкий PRD для privacy-safe diagnostic logging; не
   добавлять traceback с данными и не менять retry/timeout без доказательства.

## Приёмка

- Для каждой записи есть класс и источник отказа либо явный пробел evidence.
- В публичных артефактах нет аккаунтов, токенов, свободных параметров, данных
  счетов и внутренних адресов.
- Нет изменения runtime при read-only диагностике. Локальный дефект получает
  отдельный red→green fix; VM-side отказ отмечается без активного ожидания.

## Вне объёма

Не менять release 474, финансовую семантику, права, pagination и таймауты. Не
создавать специальный финансовый агрегат #264 и не расширять расследование до
других инструментов без новых evidence.
