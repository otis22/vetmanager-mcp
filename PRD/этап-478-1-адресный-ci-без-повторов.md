# Этап 478A — строгий docs-only и однократные CI suites на tree SHA

## Цель

Ускорить малые изменения без потери обязательных проверок: документационные изменения проходят Docs Check без продуктовых suites; main повторно не запускает уже зелёный PR suite на том же Git tree; устаревший PR run отменяется; длительность и повторы измеряются на реальных Actions runs. Этот PR не реализует 478B, impact map или nightly.

## Проверенные исходные факты

- На base `d30445b242f3548065e993960eb1a22428f0cbff` `test.yml` запускает build-image, fast, default, postgres-activation-telemetry для PR и main; `docs.yml` имеет path filter и job `validate`; `shellcheck.yml` запускается для `scripts/**/*.sh`.
- Branch protection API возвращает 404, rulesets API — пустой список: настроенных required status checks не обнаружено. Имена текущих checks `build-image`, `fast`, `default`, `postgres-activation-telemetry`, `validate` сохраняются; новый `scope-and-reuse` служит fail-closed решением внутри workflow. Эта фаза не заявляет принудительную блокировку merge настройками репозитория; проверка и изменение merge policy остаются отдельным решением владельца репозитория.
- `deploy-prod.yml` слушает успешный workflow `Tests` на main. Поэтому docs-only main обязан проходить workflow `Tests` успешным без product jobs, а решение о deploy остаётся за существующим deploy scope checker.
- Технические требования описывают тесты только через Docker и обязательную защиту данных. Этап не меняет runtime, API, access или данные. OpenAPI не применяется.
- До изменений фактические Actions runs и jobs сохранены во внешнем baseline; сравнение после merge — по тем же API полям.

## Архитектурное решение

### Граница документации

`Tests` и `Docs Check` запускаются на каждом PR и push в main без path filters. `Docs Check/validate` остаётся всегда. `scope-and-reuse` определяет документационный diff через `git diff --name-status -z` от PR base до проверяемого checkout merge tree или от `before` до main commit. PR сохраняет стандартный merge checkout GitHub: именно он тестируется. Разрешены только `README.md`, `Roadmap.md`, `Roadmap-archive.md`, `AssumptionLog.md`, `PRD/**/*.md` и `docs/**/*.md`; rename, deletion, пустой diff, отсутствующая база, ошибки git, неизвестный путь, смешанный diff или изменение `.github`, `artifacts`, `AGENTS.md`, `CLAUDE.md` — полный продуктовый контур. Директории PRD/docs должны содержать только `.md`; путь нормализуется без обхода `..`. На main docs-only skip разрешён лишь когда для непосредственного предыдущего main commit есть успешный `Tests` run: это сохраняет индуктивное доказательство, что ранее внесённый код прошёл проверки. Иначе выполняется полный контур, включая сценарий красного runtime commit перед документационным.

### Повторное использование результата PR

После успешных build-image, fast, default и postgres PR run job `validated-tree` публикует Actions artifact с именем `validated-tree-<git rev-parse HEAD^{tree}>`; файл внутри содержит SHA фактического checkout commit. Отметка появляется только после завершения всех четырёх jobs. На main `scope-and-reuse` вычисляет tree SHA собственного checkout и ищет неистёкший artifact этого имени. Поле `workflow_run.id` artifact API даёт только ссылку на run; отдельный `GET /actions/runs/{id}` обязан подтвердить тот же repository, workflow ID `test.yml`, `pull_request`, `success` и `run.head_sha`/head repository. Независимый GitHub Git API сообщает tree SHA из artifact commit равным main tree SHA и что merge commit имеет ровно двух родителей и один из них равен `run.head_sha`; blob `.github/workflows/test.yml` в PR head commit равен main blob. В `test.yml` отдельный inline guard до вызова decision script принудительно включает продуктовые jobs, если относительно `github.event.before` (всего push range) изменился любой файл decision surface: `.github/workflows/`, `scripts/ci_scope.py`, `scripts/check_roadmap_structure.py`, `scripts/run_fast_test_suite.py`, `scripts/run_default_test_suite.py`, `scripts/offline_gate_manifest.py`. Выход product jobs вычисляется в YAML как `force_full || script_verdict`: изменение самого script не может отменить force_full. Только тогда продуктовые jobs пропускаются. Другой tree SHA, поддельный marker, изменённый workflow/decision surface или ошибка API запускает все jobs. Доверие к неизменённому PR workflow соответствует действующей модели GitHub Actions; marker без успешного run и независимой проверки коммита не принимается. Общий cache не является доказательством.

### Check names и отмена

Существующие jobs сохраняют имена. `scope-and-reuse` является обязательной зависимостью product jobs: failure не даёт workflow стать зелёным. Он сам выполняет тот же `check_roadmap_structure.py` на точном checkout SHA, что Docs Check; невалидная документация поэтому не даёт успешного Tests и не запускает Deploy Prod. Пропуск product jobs допустим только при docs-only классификации либо проверенном успешном PR run с равным tree SHA; каждая ветка решения проверяется guard. `Docs Check/validate` остаётся отдельным постоянным check. Workflow-level concurrency группируется по PR number только для PR; main и dispatch получают уникальный `run_id`, чтобы третий main run не вытеснял ожидающий второй. `cancel-in-progress` истинен только для PR. Новый run того же PR вытесняет устаревший; если замена не проходит, зелёного актуального check нет. Main и другой PR не отменяются. `workflow_dispatch` остаётся полным ручным запуском.

### Рассмотренные варианты и откат

- GitHub `paths-ignore` для всего `Tests`: не гарантирует появление required check и пропускает неоднозначные изменения; отвергнут.
- Cache marker по branch/commit SHA: не доказывает равенство дерева и успешность всех jobs; отвергнут.
- Сравнение commit SHA PR и main: merge commit меняет commit SHA даже при одинаковом дереве; отвергнуто.
- Откат: убрать `scope-and-reuse` и marker job, вернуть product jobs без условий, вернуть прежние path filters обоих workflow; при сбое API до отката выполняется полный контур.

## Acceptance

1. Строго разрешённый docs-only diff не строит image и не запускает fast/default/PostgreSQL; Docs Check и `scope-and-reuse` появляются и завершаются успешно.
2. Mixed, unknown, empty или невозможный для проверки diff запускает полный контур.
3. На main только успешный PR run с artifact точного tree SHA и независимой проверкой дерева коммита и workflow blob даёт reuse; иной SHA, поддельный marker, неуспех, чужой repository/workflow или API failure запускает полный контур. Первый merge с изменённым workflow или decision script повторяет продуктовый контур.
4. PR concurrency не затрагивает main и другие PR; check names не исчезают; skip возможен только после доказанного решения. Проверяются также правки workflows/validator, удаления и rename, failure Docs Check, отменённый PR run и красная замена.
5. Внешний baseline содержит фактические длительность и число запусков PR/main; после merge сравниваются run/job duration, число product jobs и пары с одинаковым tree SHA, без заранее заданного процента ускорения. Если повторные product jobs на одинаковом tree SHA остаются либо docs-only run не дешевле baseline, куратор возвращает схему на анализ/откат по измерениям.

## Декомпозиция

- 478A.2: test-first guards для classifier, tree/reuse и workflow wiring; focused red → green (до 150 LOC за шаг).
- 478A.3: CI script и workflow изменения (до 150 LOC за шаг).

## Проверки и применимость

Focused guards, owning suite, fast, default и ShellCheck/syntax при изменении shell scripts. `offline_gate_manifest.py` и `check_roadmap_structure.py` обязательны. Workflow YAML и новый Python script входят в common fingerprint, поэтому PostgreSQL применим после freeze; real aggregate применяется только при наличии test credentials в `.env` по правилам проекта (в текущем checkout `.env` отсутствует); browser не меняется по поведению, живой MCP-вызов не нужен, поскольку инструмент не меняется. PRD review атакует scope, альтернативы, риски и acceptance; Architecture Critique обязателен из-за изменения CI/release boundary. Оценка простоты: прямой classifier и один API probe; без новой общей конфигурационной платформы. Не более двух переходов от workflow к решению.

## Оценка простоты

Новый читатель видит одно решение `scope-and-reuse`: `run_product=true` по умолчанию; только два доказательства могут поставить `false`. Реализация затрагивает один Python script и два workflow, плюс сторожа. Общая impact map и конфигурационный движок преждевременны для 478A. Один скрипт вызывается из одного места, но здесь он оправдан тестируемой логикой GitHub API и fail-closed обработкой ошибок; перенос её в YAML сделал бы отрицательные сценарии труднее проверяемыми. Решение требует нескольких API ресурсов: предыдущий main run, artifact listing, run record, Git commit и workflow blob. Каждый отказ запускает полный контур. Такая стоимость планирующего job мала относительно наблюдаемого default порядка 965–1334 секунд и не добавляет продуктовых тестов.
