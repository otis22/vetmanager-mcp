# Этап 339. Повторы пути подключения клиники

## Цель

Сделать проверку подключения устойчивой к кратковременным read timeout и
сетевым отказам на идемпотентных GET, не повторяя потенциально уже
обработанный POST и ограничивая каждый вызов `_request_with_retry` общим
wall-clock бюджетом. Весь submit логин/пароль последовательно включает выдачу
токена и GET-проверку; единый deadline всей web-операции в этот этап не входит.

## Проверенные факты

- В `vetmanager_connection_service._request_with_retry` задано три попытки,
  но сейчас `continue` есть только для `ConnectTimeout` и ответов
  502/503/504. `TimeoutException` и `RequestError` завершают вызов сразу.
- `validate_domain_api_key_connection` и `validate_user_token_connection`
  используют GET; `exchange_user_token` использует POST с multipart `files=`.
- Общий HTTP-клиент задаёт `connect=5`, `read=20`, `write=10`, `pool=2`.
- Production-факт супервизора 22.09.2026: шесть `ReadTimeout` проверки
  подключения без `vetmanager_auth_probe_retry`; через час REST того же
  домена отвечал за 0.27 с. Обращаться к production для этапа запрещено.
- Основной `VetmanagerClient` ограничивает повторяющийся GET дедлайном и
  подрезает timeout отдельной попытки до остатка бюджета. Это проверенный
  локальный паттерн, но connection path не должен заимствовать breaker/cache.
- В репозитории нет request-timeout для account route или Uvicorn (есть только
  graceful-shutdown timeout); timeout внешнего reverse proxy не хранится здесь
  и без production-доступа не проверяется. Поэтому 45 секунд гарантируются
  внутри одного `_request_with_retry`, но внешний hop может оборвать длинный
  login/password submit раньше — известный rollout-риск вне scope этапа.
- Продуктовый PRD требует обрабатывать сетевые timeout понятной ошибкой;
  технические требования закрепляют split timeouts, retry и структурированные
  логи. API-схема сущностей не меняется.

## Scope и декомпозиция

### 339.1. Политика retry и общий бюджет

- Нормализовать метод к верхнему регистру и считать GET идемпотентным.
- Оставить максимум три попытки (первая плюс две повторные).
- `ConnectTimeout` повторять для GET и POST: соединение не установлено.
- Другие `TimeoutException` и `RequestError` повторять только для GET.
- Ответы 502/503/504 повторять только для GET. Для POST вернуть первый ответ:
  HTTP-ошибка могла быть сформирована после обработки запроса, поэтому она не
  доказывает недоставку так, как `ConnectTimeout`.
- `tls_verification_failed` никогда не повторять и сохранять
  `VetmanagerTlsError` с первой попытки.
- Ввести `CONNECTION_REQUEST_BUDGET_SECONDS = 45.0`. Дедлайн создаётся один
  раз до получения shared client, поэтому ожидание pool lock также входит в
  бюджет. Каждая HTTP-попытка выполняется внутри
  `asyncio.timeout(remaining)`: это жёсткий wall-clock предел, в отличие от
  компонентного `httpx.Timeout`, чей read timer перезапускается на чанках.
  Split-timeouts общего клиента не переопределяются: внешний deadline — один
  источник wall-clock истины и не гоняется с равным компонентным таймером.
- Перед сном вычислять delay; если после него не остаётся **больше** 5 секунд
  на осмысленную попытку (текущий connect timeout общего клиента),
  не спать и не начинать следующую попытку, а поднять уже классифицированную
  ошибку/вернуть последний HTTP-ответ. Локальная ошибка бюджета не должна
  подменять последнюю upstream-причину.
- После сна и непосредственно перед каждой попыткой повторно проверить
  остаток: oversleep/scheduler delay не должен запустить HTTP после дедлайна.
  Если остаток исчез после сна, сохранить предыдущую upstream-причину.
- Истечение внешнего `asyncio.timeout` первой/текущей HTTP-попытки обработать
  отдельно от `httpx.TimeoutException`: записать ровно одну метрику попытки и
  terminal `vetmanager_auth_probe_failed`, затем нормализовать в
  `VetmanagerTimeoutError`. Внешний `CancelledError` вызывающего кода не
  перехватывать и не превращать в timeout.
- Результат последней фактически начатой попытки всегда главный: например,
  503, затем начавшийся timeout → `VetmanagerTimeoutError`. Предыдущая причина
  сохраняется только когда budget/backoff/oversleep не позволил начать новую
  попытку.

### 339.2. Наблюдаемость и идемпотентность

- Каждое реально принятое решение о повторе логировать событием
  `vetmanager_auth_probe_retry` с `attempt`, `target`, `error_class` и
  `account_connection_id`; для HTTP-ответа сохранить `status_code`.
- Retry-event писать только после успешного backoff и финальной проверки
  бюджета в начале следующей итерации. Сам event писать, когда повторный HTTP
  await уже вернул ответ или transport/timeout: так синхронный log handler не
  может отодвинуть старт за deadline, а событие доказывает начатую попытку.
  До этой точки хранить предыдущую ошибку/ответ: scheduler delay после backoff
  не должен потерять причину или породить ложный log. Последняя
  попытка и остановка по бюджету дают только terminal failure, не retry.
- Терминальный transport/timeout отказ логировать существующим
  `vetmanager_auth_probe_failed`.
- `record_upstream_request` и `record_upstream_failure` оставить по каждой
  завершившейся попытке. Не добавлять метрику логического вызова.
- POST после read timeout или `RequestError` завершать после первой попытки;
  не допускать повторной выдачи user token.

### 339.3. Сторожа и приёмка

- Тесты GET: `ReadTimeout` → success, `ConnectError` → success, поля retry-лога
  и счётчики метрик по попыткам.
- Тесты POST: `ReadTimeout` и `ConnectError` дают одну попытку; `ConnectTimeout`
  остаётся повторяемым; 502/503/504 не повторяются.
- TLS verification даёт одну попытку и `VetmanagerTlsError`.
- Детерминированным monotonic/backoff тестом доказать 45-секундный дедлайн:
  следующая попытка не начинается, когда delay не помещается; наружу выходит
  прежний `VetmanagerTimeoutError`, а не отдельная локальная budget-ошибка.
- Отдельно смоделировать oversleep: после сна deadline истёк, новый HTTP-вызов
  не сделан, retry-log не написан, предыдущая причина сохранена.
- Отдельным тестом медленного/зависшего await доказать, что внешний
  wall-clock timeout завершает попытку независимо от компонентных таймеров,
  даёт одну metric-запись и terminal failure; внешняя отмена распространяется.
- Добавить последовательность 503 → wall-clock expiry: побеждает timeout
  последней начатой попытки. При исчерпании попыток/HTTP-retry сторожа по timeout,
  `RequestError` и HTTP 502/503/504 проверяют сохранение последней причины,
  отсутствие
  ложного retry-события и ровно одну metric-запись на каждую попытку.
- Прямой boundary-тест фиксирует нормализацию регистра метода, чтобы dispatch
  и retry policy использовали одно и то же значение.
- Живая read-only проверка штатной валидации подключения на devtr6 через
  `TEST_DOMAIN`/`TEST_API_KEY` из `.env`; секреты не печатать. Во внешний
  evidence записать только exit code и безопасную форму ответа.

Каждая подзадача меньше 150 строк и двух часов.

## Архитектурное решение

**Проблема.** Retry-цикл объявляет три попытки, но transport-ветки расходятся:
идемпотентный GET не переживает кратковременный read/network отказ, а простое
включение трёх попыток способно удерживать UI больше минуты.

**Контекст и ограничения.** Функция обслуживает и GET-пробы, и POST выдачи
токена. У upstream нет idempotency key для POST. Метрики уже считаются по
попыткам. Общий клиент разделяет timeout; production/API/MCP контракт менять
нельзя. Изменение ограничено connection service и его unit-тестами.

**Варианты.** (1) Повторять все методы: минимальный diff, но опасен двойной
выдачей/обработкой POST после read timeout или 5xx. (2) Повторять только GET,
включая `ConnectTimeout`: безопасно, но теряет полезный существующий retry
POST, когда запрос заведомо не доставлен. (3) Матрица по фазе отказа:
`ConnectTimeout` для любого метода, остальные transport/timeouts и
retryable HTTP-статусы только для GET, с общим дедлайном.
Выбран вариант 3: он сохраняет доказуемо безопасное текущее поведение и
расширяет retry только там, где запрос идемпотентен.

**Бюджет 45 секунд.** 30 секунд основного клиента слишком мало для двух
полных 20-секундных read-окон, а три полных окна (>60 с) неприемлемы для
интерактивного вызова. 45 секунд позволяют две полные попытки; третья доступна
после быстрых отказов, но не запускается с остатком меньше 5 секунд. Внешний
`asyncio.timeout` делает предел wall-clock даже при trickle-response.
Константа локальна connection path, чтобы не менять runtime tools. Это бюджет
одного `_request_with_retry`, не всего submit, который может содержать два
таких вызова.

**Реализация.** Один deadline и маленькие локальные helpers для остатка,
внешний wall-clock timeout и проверка строгого `remaining > delay + 5s`.
Отдельный retry framework/класс не нужен: есть один call-site и
два метода. Последняя upstream-причина хранится в текущей ветке
исключения/ответа и поднимается при недостатке бюджета. Если первая попытка
сама исчерпала wall-clock deadline, она нормализуется в существующий
`VetmanagerTimeoutError`: предыдущей upstream-причины в этом случае нет.

**Инварианты.** Не повторять POST после возможной доставки; TLS fail-fast;
максимум три попытки; один metric sample на попытку; retry-log только перед
реальным следующим заходом; 401/403/прочие не-retryable ответы и правило
`status_code < 400` не меняются; секреты/URL в новые логи не попадают.

**Rollback/fallback.** Откат возвращает немедленный отказ transport-веток без
изменения storage/API. Если 45 секунд окажутся неприемлемы по измерениям,
меняется одна константа вместе с boundary-тестом; резервный домен в fallback
не добавляется. Неизвестный внешний reverse-proxy timeout проверяется
супервизором после доставки без публикации конфигурации; если он меньше
worst-case submit, это отдельное решение о shared web deadline или proxy.

Architecture Critique required: этап меняет auth connection path,
production retry behavior и latency ceiling. Strong review должен проверить
идемпотентность, точность deadline, сохранение исходной ошибки и per-attempt
observability; этот critique одновременно может засчитаться полным PRD-review.

## Acceptance criteria

- GET повторяется после `ReadTimeout`, иных `TimeoutException` и сетевых
  `RequestError`; успешная следующая попытка возвращается вызывающему коду.
- POST после read timeout/сетевой ошибки имеет ровно одну попытку. POST после
  `ConnectTimeout` может повториться и успешно завершиться; POST 502/503/504
  возвращается после первой попытки.
- TLS verification fail-fast с прежним типом/текстом ошибки.
- Wall-clock дедлайн 45 секунд ограничивает один `_request_with_retry`; если
  после backoff не остаётся больше 5 секунд, следующая попытка не стартует и
  сохраняется уже полученная upstream-ошибка/ответ. Timeout, `RequestError` и
  HTTP-response ветки покрыты отдельно.
- Каждый retry виден как `vetmanager_auth_probe_retry` с обязательными полями;
  terminal failure виден отдельно; метрики остаются по попыткам.
- Сторожа показаны красными до реализации и зелёными после неё; живой devtr6,
  фокусные и один финальный полный mock+real suite проходят.

## Out of scope

- Резервный `vetmanager-reserve.ru`, breaker/cache основного клиента.
- Изменение записи health failure рядом с сохранённым подключением.
- Изменение правила `response.status_code < 400` для редиректов.
- Production-вызовы и изменения API/storage/public MCP contract.

## Простота

Проверены triggers: новый class/protocol, factory, configurable policy,
несколько retry-движков, state machine и cross-module abstraction не нужны.
Минимальное решение — локальный deadline и три небольших вычисления внутри
существующего цикла. Изменяются два production/test файла плюс обязательные
управленческие артефакты.
