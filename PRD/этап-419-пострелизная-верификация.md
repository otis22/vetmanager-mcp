# Этап 419. Пост-релизная верификация

## Цель и факты

Подтвердить сценарии #134, #136, #137 и наблюдаемость механик 408, 409, 413 после выпуска поездов. Код и production-данные не изменять. `artifacts/api_entity_reference-ru.md` описывает `MedicalCards.doctor_id` и строковый `diagnos`; `artifacts/technical-requirements-vetmanager-mcp-ru.md` описывает MCP и локальное хранилище. Для JSON-формы опираться на живой ответ и контракт этапа 415, не предполагать содержимое клиники. Исходные PRD 408, 409, 413, 415 и тесты 416/417 задают конкретные ожидания.

## Архитектурное решение

Проблема — успешный выпуск кода не доказывает поведение конкретного сценария и наличие production-сигнала. Решение: разделить наблюдения: поведение инструмента проверять только на тестовом контуре с читающими MCP-вызовами, production — лишь SELECT по агрегатам/идентификаторам, чтение логов, PromQL query и health. Альтернатива вызвать инструмент на production дала бы доступ к клиническим данным; альтернатива опереться на unit-тесты не подтверждает работающий контур. Никакой новой архитектуры, контрактов, прав, нагрузки сканирующего сервиса или миграций. Инварианты: нет production mutation, секретов и ПД в evidence; различать наблюдаемое и вывод; отсутствие наблюдения = NOT_MEASURABLE. При дефекте остановить проведение, записать FAILED и передать решение владельцу, без исправления. Architecture Critique: not required — решения о контракте или production-поведении не меняются.

## План и критерии

1. **419.1 PRD и gate** (≤2 ч): Spark candidate-only → пара Astra и Sol xhigh с валидатором `scripts/validate_review_result.py --plain`; принять только доказанные medium/high findings. Уточнить команды после read-only introspection схемы.
2. **419.2a стенд** (≤2 ч): выбрать `.env` test-контур заранее. `get_medical_cards_by_date` за известный период с `limit=1` без врача, с существующим и отсутствующим `doctor_id`, проверить `total`, ID врача и вторую страницу; VERIFIED стендового контракта #134 только при различающем свидетеле фильтра до страницы. `get_pet_profile` для питомца с JSON-картой: отдельные `diagnosis_references` и отдельные числовые ID в `unresolved_diagnosis_ids`, если ID нет в справочнике. Непустой агрегат `diagnoses` требовать лишь у свидетеля с подтверждёнными заголовками в карте/справочнике. Строковые либо неверные ID могут закономерно остаться целым unresolved JSON. Сторож 415 на месте. Если подходящего JSON-питомца нет — NOT_MEASURABLE. `tools/list`, `prompts/get report_ai_prompt_helper`, читающий `get_report_ai_prompt_helper`: проверить ПД-оговорку в четырёх описаниях и справке. Тела в журнале свести к безопасным полям, без текста клинических записей.
3. **419.2b production** (≤2 ч): только разрешённые SSH SELECT, PromQL query, `/healthz`. Логи читать лишь при заранее заданном шаблоне безопасных служебных строк, ограниченном окне и подсчёте совпадений без вывода сырых строк; при отсутствии такого шаблона пометить сигнал NOT_MEASURABLE. Сначала `SELECT` по `information_schema.columns` для нужных таблиц; затем агрегаты `report_ai_job_ratings` (`intent_from_create`, `score`). `rated_at > created_at` не доказывает повторный upsert: без законного before/after rating одного ключа его результат NOT_MEASURABLE. Проверить существование, историю post-deploy роста и непрерывность scrape `vetmanager_report_ai_rating_reminders_total`; связь reminder→rating не измеряется без job-level сигнала. Проверить deploy SHA `f5e0c0b+` по read-only факту версии, видимость использования `doctor_id` по агрегированным логам/метрикам (если сигнал есть), а также CI main для сторожей 415/416. Production tools/list и клинические MCP-вызовы без разрешённого prod MCP-вызова не выполнять: production поведение #134/#136/#137/413 отмечать NOT_MEASURABLE, если нет эквивалентного наблюдения. Не подменять его стендовым доказательством.
4. **419.2c выпуск** (≤2 ч): записать точные команды и компактные результаты в AssumptionLog, без адресов, секретов и ПД. Аудит документного diff, архиватор и checker, commit в `dev/roadmap-418-420`, Spark → Astra + Sol xhigh committed diff, push только в ветку и зелёный Tests на её SHA. Полный suite без кода не запускать. Feedback/KI mutation представить владельцу лишь как предложение.

VERIFIED = прямой различающий факт по применимой поверхности. FAILED = прямое противоречие критерию; остановить проведение. NOT_MEASURABLE = поверхность/данные/сигнал недоступны, с явной причиной. Для 408 upsert нужен наблюдаемый повтор оценки одной связки; одно наличие строк доказывает использование, но не upsert. Для 409 post-deploy рост счётчика при покрытии scrape доказывает выдачу, не влияние на последующую оценку без связи события с job. Для 413 стендовая справка подтверждает контракт, production-раздача требует отдельного production-сигнала. Старые зелёные CI main подтверждают сторожей только при точном run/SHA. В публичном отчёте production rating/score/time ячейки менее пяти и восстанавливаемые из дополнения ячейки подавляются; врачебные, клинические и диагностические идентификаторы не переносятся из production, в стендовых итогах допустимы только безопасные идентификаторы без имён и текстов.

Отдельная от контракта 413 отложенная недельная проверка: сравнить равные 7-дневные окна создания до и после deploy по доле оценённых локально зарегистрированных jobs (`intent_from_create=true`, числитель с `score IS NOT NULL`, знаменатель все такие строки), распределению последних `score`, числу rating-only строк и create outcomes `vetmanager_report_ai_jobs_total`. Для честной доли каждой когорте дать одинаковый срок после создания на получение оценки (например, ещё семь дней после конца каждого окна); сравнение одного текущего снимка без равного срока смещено в пользу старой когорты. Если после deploy нет полного окна и срока наблюдения либо нет сопоставимой предрелизной когорты, поставить NOT_MEASURABLE, не экстраполировать короткое окно и не считать `vetmanager_report_ai_ratings_total` числителем покрытия.

## Простота

Один документ результатов и существующие read-only средства. Новые probe-скрипты, метрики и production-записи не нужны.
