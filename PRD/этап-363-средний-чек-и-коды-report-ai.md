# Этап 363. Средний чек и коды ошибок Report AI

## Цель и проверенные факты

`get_average_invoice` сканирует до 1000 страниц по 100 счетов, но общий
построитель запросов MCP запрещает `offset > 10000`. Тест этапа 351
проверил 10001 запись, где последний запрос имеет ровно `offset=10000`;
дефект начинается с 10101-й записи.

Локальная ветка vetmanager-extjs сверена с удалённой без записи в чужой
репозиторий: HEAD совпал. Наблюдаемый контракт REST не показывает верхнего
лимита offset: devtr6 03.10.2026 дал HTTP 200, `success=true`,
`totalCount=784`, 0 строк для offset 10001 и 20000. Проверка пустой
страницы не доказывает ни возврат глубоких строк, ни скорость большой
таблицы. OpenAPI v6 документирует limit/offset/sort/filter и totalCount без
верхнего предела offset. Фильтр `id > value` используется публичным
`get_invoices` и ранее был проверен read-only вызовом на devtr6.
Главный PRD требует фильтрацию/сортировку/пагинацию всех list GET и
безопасные пределы массовых выборок; технические требования сохраняют
публичный offset 0–10000. Справочник сущностей подтверждает invoice.id,
amount, invoice_date и status.

Ответы confirm/reject/save Report AI уже проходят наблюдение жизненного
цикла. Если ответ содержит `status=failed`, ключ задания закрывается в
процессном окне дедупликации до записи кода; последующий status уже его
не учитывает.

## Scope и декомпозиция

- 363.1 (≤2 ч): факт REST-предела, PRD, Architecture Critique и PRD-review.
- 363.2a (≤150 строк): красный сторож 10101+ записей через настоящий
  построитель; keyset-проход по id для поточного агрегата.
- 363.2b (≤150 строк): красный сторож failed из confirm/reject/save и
  повторного status; общая точка наблюдения terminal error code.
- 363.3 (≤2 ч): devtr6 smoke изменённого инструмента, аудит, reviews,
  полный mock + real suite один раз, push и зелёные Tests/Deploy Prod.

## Архитектурное решение

**Проблема.** Публичный безопасный лимит offset ограничивает внутренний
агрегат, у которого уже есть бюджет времени и числа запросов. Раздельные
обработчики Report AI пропускают запись кода terminal failure.

**Контекст.** Публичный `get_invoices` и прочие list tools оставляют предел
10000. Общий `paginate_all` проверяет повторы страниц, totalCount и бюджет;
средний чек не возвращает частичный результат. Имена и labels метрики
`vetmanager_report_ai_outcomes_by_code_total` остаются прежними. В
наблюдениях не хранятся персональные данные.

**Варианты.** (1) Поднять глобальный предел: расширяет публичный доступ и
нагрузку. (2) Разрешить глубокий offset только агрегату: малая правка, но
стоимость страниц растёт на большой таблице, а вставки сдвигают страницы.
(3) Keyset: сортировка `id ASC`, `offset=0`, далее фильтр `id > last_id`
вместе с неизменными фильтрами периода. Выбран (3): он избегает глубокого
offset и сохраняет публичный лимит. Стоимость фильтрации по дате и id
зависит от индексов клиники; подтверждённого плана запроса для большой
таблицы нет. Гарантии нагрузки — только 1000 запросов и 300 секунд.
Опциональный режим находится в
`paginate_all` и вызывается только средним чеком; внешнего параметра MCP
нет. Каждая страница должна строго увеличивать id, иначе весь расчёт
отказывает. Бюджеты 1000 запросов по 100 строк и 300 секунд остаются.
В keyset-режиме `totalCount` относится к текущему фильтру `id > last_id`:
после полной страницы следующий запрос получает новый totalCount. Полная
страница всегда требует продолжения, даже при заниженном totalCount.
Короткая страница завершает проход лишь при отсутствующем totalCount или
`totalCount <= len(page)`; при большем числе проход продолжается. Пустая
страница с положительным totalCount считается ошибкой, пустая с нулём
завершает проход. Тест покрывает ровно кратную размеру страницы выборку,
короткую страницу с большим totalCount и полную с заниженным totalCount.

API не даёт snapshot: новый счёт с большим id и датой внутри периода может
попасть в проход, удалённый после начала прохода — исчезнуть. Строгая
точность при одновременном изменении таблицы не гарантируется; при
подозрении на изменения расчёт повторяется позже. Фильтр `id >` проверяем
на devtr6, глубина >10000 там недостижима (всего 784 счета).

Для Report AI общая функция учитывает код failed при первом терминальном
наблюдении до закрытия ключа, независимо от источника ответа. Метка
`operation=status` обозначает обнаруженное состояние задания, даже когда
оно впервые пришло из confirm/reject/save; словарь значений не расширяется.
В репозитории нет дашборда или алерта, потребляющего эту метрику; её HELP
строка описывает исходы Report AI по коду без привязки к HTTP-операции.

**Инварианты и rollback.** Публичный offset ≤10000, включая `get_invoices`;
только средний чек включает keyset. Один failed job даёт одну запись по
коду в существующем bounded/TTL окне наблюдения; повторный опрос в этом
окне не дублирует. После истечения TTL, вытеснения ключа или рестарта
процесса повторный подсчёт возможен — глобальной exactly-once гарантии
нет. Ошибка наблюдения не скрывает ответ REST. При несовместимости REST с
keyset вернуться к явному отказу и совету разделить период; если кодовые
исходы учитываются неверно, откатить изменение lifecycle observer и
восстановить подсчёт только в status. Ответ инструмента от метрики не
зависит; это проверяет существующий сторож best-effort.

Architecture Critique required: затронуты нагрузка и production behavior.

## Приёмка

- Красный сторож на 10101+ счетах при настоящем построителе запросов;
  после правки вся конечная синтетическая выборка в пределах бюджета
  успешно учтена, суммы и число счетов верны. Запросы используют
  `offset=0`, `id ASC` и нарастающий фильтр `id > last_id`.
- Отдельно проверены отказ без частичного результата при бюджете/ошибке
  upstream, отказ публичного `get_invoices` на `offset > 10000` и неизменный
  offset-режим `paginate_all` для прочих вызывающих (включая точную границу
  `totalCount` и повтор страницы).
- Failed из каждого confirm/reject/save увеличивает outcome-by-code
  `status|CODE` уже на первом ответе ровно один раз до закрытия ключа;
  повторный status его не дублирует. Неизвестный/некорректный CODE даёт
  закрытую метку `unknown`; обычные ответы код не добавляют. Имена и
  labels метрик не меняются.
- Изменённый инструмент вызван на devtr6, код и безопасное тело ответа
  записаны в AssumptionLog. Живой прогон проверяет совместимость фильтра
  `id >`; глубина >10000 покрыта синтетическим HTTP-сторожем. Намеренно
  упавшее задание через confirm/reject/save на devtr6 не создаём:
  реальная форма failed проверяется по контракту и мок-ответу.
- Перед push полный mock и real suite; после push зелёные Tests/Deploy Prod.
