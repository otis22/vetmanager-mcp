# Этап 313. Расписание без тупика с именем врача

## Цель

Расписание за день должно сразу давать приложению безопасное отображаемое
значение врача и не вынуждать модель запрашивать тот же персональный атрибут
через `get_user_by_id`.

## Контекст и факты

- Контракт `admission` содержит `user_id`; объекта пользователя OpenAPI не
  обещает.
- Этапы 308/309 установили формат адресного плейсхолдера
  `[user:<id>:<field>]`: это конечное значение для отображения, а не ссылка для
  нового вызова.
- В деперсонализированном режиме поля личности пользователя уже возвращаются
  этим форматом, но описания user-инструментов не говорили об этом достаточно
  прямо.

## Scope

1. `get_daily_schedule` дополняет каждую строку с положительным `user_id`
   полем `doctor_name=[user:<user_id>:first_name]` без запроса user endpoint.
   Это значение одинаково во всех режимах доступа и предназначено приложению
   для последующей отрисовки. MCP-модель обязана перенести его дословно; только
   приложение-resolver подставляет имя в пользовательском интерфейсе.
2. Докстринги `get_users` и `get_user_by_id` явно описывают смысл адресных
   плейсхолдеров для полей личности сотрудника.
3. Контрактный тест `tools/list` закрепляет описание поля; регрессионный тест
   закрепляет его формат и отсутствие обращения к `/rest/api/user/<id>`.

## Архитектурное решение

**Проблема.** Получать ФИО отдельным запросом нельзя: API не гарантирует
пользовательский объект в приёме, а деперсонализированный ответ всё равно
возвращает плейсхолдер.

**Варианты.** (1) N+1 `get_user_by_id` — дороже, не даёт нового значения и
создаёт цикл. (2) Извлечь реальное имя из неописанного вложенного объекта —
нарушает контракт и приватность. (3) Построить уже принятый адресный формат из
`user_id` — выбранный вариант.

**Инварианты.** Нет запроса user endpoint; реальное ФИО не добавляется;
плейсхолдер строится единственным builder из `depersonalization.py`; строки без
корректного `user_id` не получают выдуманное имя. Режим токена не меняет это
поле: оно никогда не является приглашением к `get_user_by_id`.

**Rollback.** Поле additive: при откате клиент продолжит использовать прежний
`user_id`; при изменении формата builder меняется централизованно.

Architecture Critique: required, потому что меняется публичный MCP contract и
граница privacy.

## Приёмка

- Строка расписания с `user_id=3` содержит `[user:3:first_name]`.
- Запрос к user endpoint не выполняется.
- Описание user-инструментов называет плейсхолдер конечным значением.
- На стенде расписание вызывается одним MCP вызовом; репорт #66 закрыт на проде
  ссылкой на этап после выклада.
