# Этап 369. Report AI доводит задание до сохранения

## Цель и проверенные факты

За 30 дней из ~87 `ready_to_save` не сохранено ни одного задания, из 26
`needs_confirmation` подтверждено одно, 63 ожидания брошены. Это согласованные
production-счётчики из постановки, без прямого доступа к production. MCP сейчас
возвращает одиночный статус и советует не более шести poll за разговор.
Локальный клон Vetmanager подтверждает внешний контракт POST create,
confirm/reject/save и GET view/data. `confirm` принимает только `report_id`,
`reject` не принимает тело, `save` принимает `title`. Успешный confirm делает
задание `existing_report_matched`; reject продолжает то же задание. В OpenAPI v6
этого endpoint нет; контракт взят из локального клона только чтением.

Главный PRD требует безопасного доступа к данным клиники. Технические требования
закрепляют `report_ai.write` за созданием/изменением и `analytics.read` за чтением.
Никакие права и правила дедупликации не меняются.

## Архитектурное решение

Проблема — клиент прекращает серию poll до результата и не совершает явный
следующий шаг. Варианты: заставить агента чаще poll (ненадёжно), автоматически
confirm/save (нарушает осознанный выбор и явную запись), дать одному вызову
ограниченное ожидание только через GET (выбрано). `wait_seconds` — необязательный
параметр create/get с пределом 30 секунд, интервалом 2 секунды и максимумом
16 GET на вызов; create выполняет ровно один POST,
затем GET по полученному id до конечного для ожидания статуса или deadline.
Конечны для ожидания `needs_confirmation`, `ready_to_save`, `saved`,
`existing_report_matched`, `failed`, `rejected`. Timeout возвращает последний
статус и безопасную диагностику с тем же id; неизвестный/ошибочный статус не
заставляет повторить POST. GET без wait сохраняет прежнее поведение. `wait_seconds`
принимает только целое 0–30; bool, отрицательные и превышение отклоняются.
Ноль сохраняет прежний единичный ответ. Описания create/get явно предлагают
`wait_seconds=30` для нового отчёта вместо ручной серии poll. При 429 или
ошибке сети ожидание прекращается без скрытого повторного POST; после начального
ответа create возвращаются последний известный статус и безопасная диагностика.
Повреждённый GET-ответ (не JSON, не объект, без job или с другим id) также
сохраняет последний известный job_id и диагностирует отказ чтения.
Отмена прерывает coroutine: отключившемуся клиенту ответ уже не доставить, но
повторного POST нет. Нагрузку ограничивает потолок GET на вызов; общий
координатор между процессами не вводится, так как нет общедоступного состояния.
GET в цикле вызывается с `retry=False`; каждый await ограничен остатком единого
monotonic deadline через `asyncio.wait_for`, включая транспортное разрешение
хоста и pacing. Сторож считает фактические HTTP GET, проверяет медленный GET,
429 и остановку после cancellation. Первый GET с wait тоже ограничен deadline;
если он не дал ответа, возвращается безопасная ошибка с исходным job_id без
выдуманного статуса. Create с одним лишь `report_ai.write` может пройти POST, но
GET ожидания требует `analytics.read`: в этом случае возвращаются job_id и
диагностика о нехватке прав, без повторного POST. Неизвестный upstream status
прекращает ожидание с безопасной диагностикой и тем же id.

Следующий шаг — поле `job.next_action`, получаемое из безопасных status/id и
candidate report_id. Для `needs_confirmation` даются готовые вызовы confirm
для доступных кандидатов и reject; для `ready_to_save` — save с названием,
которое агент должен выбрать осмысленно.
В `next_action.call` для save передаётся явный шаблон названия, а не
автоматически придуманное имя из `intent_text`: интент может содержать ПД,
которые нельзя переносить в видимый всем отчёт. Шаблон и прежнее общее имя
`Отчёт по заданию N` отклоняются до POST; агент обязан заменить шаблон
названием с целью и периодом. Структура вызова и job_id уже готовы.
Для распознавания только этих запрещённых форм нормализуются регистр и `ё/е`;
выбранное агентом название передаётся без такой замены.
`success:false` в ответе reject
считается отказом: отметка ожидания не ставится, агент читает job перед
повторным решением. После успешного reject ответ должен
рекомендовать только повторный GET того же id: первый статус ещё может быть
старым `needs_confirmation`. Повторный reject/confirm по нему без нового решения
пользователя запрещён; process-local краткая отметка reject подавляет повторную
подсказку записи до `ready_to_save`, `failed` или другого конечного результата.
Промежуточный `queued` может прийти раньше повторного устаревшего
`needs_confirmation` после reject. Ключ — существующий
`(account_id, connection_id, job_id)`; TTL и максимум записей равны lifecycle
cache, проверяется изоляция соединений. Превью — только образец для решения о
создании отчёта, не источник ответа пользователю. Save refusal на
`INVALID_TRANSITION` делает один дополнительный GET того же id и предлагает
confirm/reject только если свежий status = `needs_confirmation` и нет pending
reject; при pending reject предлагается только GET того же задания. При другом
статусе или ошибке GET остаётся прежняя безопасная общая подсказка. Данные
upstream в текст не переносятся. При неопределённом исходе save ответ требует
считать `get_report_ai_job` с тем же job_id и не повторять save автоматически:
статус `saved` подтверждает успех, остальные состояния требуют нового решения.
Успешный HTTP без `report_id` и без job тоже считается неопределённым исходом;
ответ с job сохраняется для наблюдаемости, исход метрики остаётся `unknown`.
Если такой job ещё допускает действие, `next_action` предлагает только GET
того же id и запрещает автоматический повтор save. Не-JSON и JSON не-объект
после POST save тоже считаются неизвестным исходом записи с тем же советом.

Метрика `report_ai_save_attempts_total{outcome}` фиксирует каждый вызов save
с закрытым набором outcome `success`, `error`, `unknown`, `invalid_input`.
`success` — получен успешный ответ save с положительным `data.report_id`, включая
idempotent; `error` —
определённый отказ, `unknown` — timeout/network/5xx после возможной отправки,
`invalid_input` — отклонено существующей `_validate_report_title` после входа в
функцию save; отсутствующий обязательный аргумент, отклонённый схемой MCP до
вызова функции, этим счётчиком не охватывается. HTTP 200 с `success:false`
считается `error`, пустое/невалидное тело и cancellation после валидации —
`unknown`. Это попытки, не уникальные
задания и не подтверждённые изменения состояния. Успешный save и confirm
возвращают `data.report_id` без job; после них lifecycle observer получает
синтетический безопасный status (`saved` / `existing_report_matched`) и тот же
job_id для локального счётчика. Наблюдение best effort, не влияет на ответ.
Доля уникальных сохранённых заданий проверяется по upstream аналитике, а не
вычисляется из process-local попыток. На границе записи метрики неизвестный outcome
нормализуется в `unknown`.
Никаких id, текста, названий отчётов и иных динамических labels. Наблюдение
best effort и не меняет итог записи.

Дополнение владельца: общий текст `report_ai_prompt_helper` и инструмент
`get_report_ai_prompt_helper` описывают тот же bounded journey, что runtime:
один create с `wait_seconds=30`, затем bounded get того же id при ожидании,
осознанный confirm/reject в `needs_confirmation`, save в `ready_to_save`,
реальные строки через `get_report_ai_job_data`. Оба поля превью — только
образец для решения о запуске полноценного отчёта; по ним нельзя отвечать
пользователю, включая вывод о пустом результате. Текстовый сторож краснеет
при удалении шага data или запрета ответа по превью.

Ограничения: ожидание ограничено собственным monotonic deadline и нагрузкой GET;
интервал опроса фиксирован, без плотного цикла. При откате реализацию ожидания
можно выключить настройкой `REPORT_AI_WAIT_ENABLED=0` (default включён):
`wait_seconds` остаётся в схеме, но вызов возвращает первый ответ, как при нуле;
сторож проверяет этот режим и сохранение `next_action` для старых клиентов.
При полном откате старые клиенты переоткрывают tools/list. Созданные upstream задания не
удаляются. Инварианты:
один create POST, никакой автоматической записи после него, прежние права,
безопасная очистка ответа, отсутствие ПД в метриках и evidence.

Architecture Critique требуется: меняется публичный MCP-контракт, время ответа
и production-поведение.

## Подзадачи и критерии

1. Красные сторожа wait: один POST, bounded GET, переходы, deadline, GET без
   ожидания, 429 и диагностируемый timeout; реализовать за ≤150 строк кода.
2. Красные сторожа `next_action`, stale status после reject, save refusal и описаний
   превью и wait; реализовать
   за ≤150 строк кода.
3. Красный сторож метрики на ограниченные labels, отсутствие ПД, количество
   вызовов и lifecycle после save/confirm без последующего GET; реализовать за
   ≤150 строк кода.
4. Синхронизировать helper и описания с bounded journey; красный сторож
   обязательных шагов и границы preview, ≤150 строк текста и тестов.
5. Живые вызовы изменённых инструментов на devtr6, безопасный код/тело,
   полный suite, аудит, review, commit, push и зелёный CI.
