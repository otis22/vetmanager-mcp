# Этап 413. Структура справки Report AI

## Цель и проверенные факты

`get_report_ai_prompt_helper_text()` в `prompts.py` сейчас возвращает общий bearer/placeholder prefix, затем `artifacts/report-ai-prompt-helper-short-mcp-2026-06-15.md`. Поэтому работа с intent начинается поздно. Контракт оценки из `tools/report_ai.py` и этапов 408/409: `rate_report_ai_job(job_id, score, intent_text)` является финальным шагом пути create → poll → data → rate; `score` и `intent_text` обязательны, `comment` необязателен. Старое «добровольно» из MD удалить. Инструменты не меняются.

## Результат и критерии приёмки

1. Первая содержательная часть отрендеренного MCP prompt — короткое ядро: вопрос → русский `intent_text` с периодом, фильтрами, метриками и группировкой → один create → bounded poll → confirm/save → реальные data → rate. Для failed job с `job_id` ветка ведёт сразу к оценке 1; без `job_id` оценка невозможна. `intent_text` формулируется до вызова. Bearer/scopes и длинное руководство по плейсхолдерам/внешнему скрипту остаются в приложении после рабочего руководства. Отдельные prompt, использующие `_bearer_runtime_prefix`, сохраняют прежний prefix.
2. Красные сторожа на **каждый** обязательный блок проверяют именно зарегистрированный MCP prompt, а не только MD: шкала 1/2/5–6/10 и обязательные score+intent_text, необязательный comment; канонический путь и failed-job ветка; оговорки KI 58/59 (ошибка состава комбинаций, `good.id` workaround и clinic-wide остатки); preview — decision samples, not live data; замер 6–10 секунд без гарантии; маршрут `csv_export_url` → export → `report_file_id` → `get_report_export_download`; вакцинации — per-pet `medicalCards`/`vaccinations` или clinic-wide Report AI по `vaccine_pets`. Конечный раздел не противоречит пути и не предлагает остановиться на выдаче интента. Сторожа обязаны падать на исходном тексте или при намеренной порче защищаемого блока.
3. Живой MCP `prompts/get` на заранее выбранном `.env` тестовом контуре: сохранить HTTP-код и очищенные фрагменты начала ядра и приложения. Поскольку меняется только текст, не создавать Report AI job ради smoke.
4. После выпуска супервизор сравнивает равные недельные окна до/после по локальным строкам `report_ai_job_ratings`: знаменатель — уникальные `(account_id, connection_id, domain, job_id)` с `intent_from_create=true` и `created_at` в окне, числитель — такие jobs с `score IS NOT NULL`; отдельно — доля непустых `intent_text` в этой популяции, распределение последних score и количество строк с `intent_from_create=false`. Показатель означает покрытие **локально зарегистрированных** jobs, а не всех upstream созданий. Сверить его с `vetmanager_report_ai_jobs_total` по outcomes: регистрация может не пройти, а rating-only строка получает `created_at` в момент оценки. `vetmanager_report_ai_ratings_total` учитывает повторные вызовы и не служит числителем покрытия. Заполненность `intent_text` почти задана схемой и не измеряет поведение агента; интерпретировать лишь как контроль целостности, не как улучшение справки. Измерение production откладывается до merge/deploy и недели наблюдения; этап не утверждает улучшение метрик заранее.

## Архитектурное решение

Проблема — общий prefix для всех prompts заслоняет специфичную для Report AI последовательность. Варианты: переставить общий prefix у всех prompts (риск других сценариев), дублировать длинное руководство в MD (расхождение), собрать Report AI отдельно из MD + прежнего prefix (выбрано). Сохранить один источник bearer/placeholder инструкций и перенести его только в конец Report AI выдачи. MD перестроить: ядро и формулирование intent, затем подробные уточнения, ограничения, кейсы и приложение. Инварианты: инструкции по безопасности, правах и внешнему скрипту не теряются; все обязательные блоки доступны в одном ответе; инструментальные сигнатуры и права неизменны. Откат — вернуть порядок конкатенации и MD из предыдущего коммита. Architecture Critique: not required — нет изменения MCP контракта, прав, хранилища, нагрузки или границ модулей, только порядок и точность текста.

## Риски и контроль

Модель может пропустить конец длинной справки; ядро поэтому содержит все действия, приложение — детали. Сдвиг текста может сломать завязанные на фразы проверки; сторожа проверяют смысловые маркеры и порядок. Измерение недельной динамики после релиза не входит в до-релизную приёмку и фиксируется как отложенное в AssumptionLog.
