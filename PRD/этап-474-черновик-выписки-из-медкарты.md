# Этап 474. Данные для черновика выписки из медкарты (#159)

## Решение владельца 20.11.2026

MCP только отдаёт сведения Ветменеджера. Выписку составляет агент пользователя в диалоге с врачом. Отдельного write-инструмента нет, автоматического сохранения в медкарту нет. После явного подтверждения в диалоге агент может предложить существующий `create_medical_card`, если пользователь хочет сохранить текст; это отдельное добровольное действие с правом `medical_cards.write`.

«Всё» означает доступную историю **одного пациента за выбранный период**: приёмы, осмотры и карты, диагнозы, лечение/назначения, вакцинации, стационар, услуги. Неполные источники и непрочитанные вложения показываются явно. Подтверждение текста в диалоге достаточно; MCP не хранит состояние подтверждения.

## Проверенный контракт и границы

- OpenAPI v6: GET `/rest/api/pet/{ID}`, `/rest/api/admission`, `/rest/api/MedicalCards`, `/rest/api/MedicalCards/Vaccinations`, `/rest/api/hospital`, `/rest/api/invoice`, `/rest/api/invoiceDocument`. Источники: `artifacts/vetmanager_openapi_v6.json`, `artifacts/api_entity_reference-ru.md` §§2.21, 2.37 и действующие инструменты `tools/{pet,admission,medical_card,clinical,invoice,finance}.py`.
- `MedicalCards` содержит клинический текст, ссылки на диагнозы, назначения и измерения, когда они есть в ответе. Наличие поля в схеме не гарантирует заполнения. Приём в расписании и строка счёта не доказывают проведение лечения.
- Для `hospital` справочник сущностей называет `date_in`/`date_out`, но OpenAPI v6 определяет `start_date`/`end_date`; read-only GET на devtr6 20.11.2026 вернул HTTP 200 и ключи `start_date`, `end_date` в строке. Агрегат использует проверенные поля GET, не переносит в публичный код поведение внутренней реализации.
- `get_vaccinations` ограничен 100 записями и не имеет подтверждённой пагинации. При `truncated` полнота вакцинаций неизвестна. `invoiceDocument` по действующему `get_invoice_documents` и схеме OpenAPI содержит позиции счёта (`document_id`, `good_id`, `quantity`); для каждого счёта пагинация и лимит проверяются отдельно. Содержимое вложений из HTML-ссылок недоступно до API ВМ (этап 432.1).
- В агрегате название вакцины возвращается как `vaccine_name`: это свободное текстовое поле проходит очистку для деперсонализованного ключа; обычный ключ видит исходное значение. Локально сохраняются не более 100 вакцинаций, даже если апстрим игнорирует `limit`.
- Клинические данные и ссылки не записываются в логи и публичное evidence. MCP boundary применяет действующую деперсонализацию ко всему результату **только для ключей с `is_depersonalized`**; обычный авторизованный ключ получает данные пациента по действующим правам. Отчётные строки, если они используются, проходят отдельную очистку ключей и значений.
- Группа «Врач» не имеет `finance.read`. Ей доступен клинический сценарий, а услуги из счетов пропускаются с явным пробелом доступа. При наличии `finance.read` инструмент читает и их. Объявлять результат полным при этом пробеле нельзя.

## Сценарий и acceptance

1. Агент вызывает один read-инструмент с `pet_id`, `date_from`, `date_to`. Период обязателен и показан в ответе. MCP проверяет ID и порядок дат до запросов.
2. Инструмент возвращает профиль пациента, страницы карт, приёмов, стационара и (при финансовом праве) счетов пациента в периоде, строки счетов, вакцинации, ID и даты источников. Для карт сохраняет исходные поля диагнозов, лечения (`treatment`, `healing_process`) и рекомендаций (`recomendation`, `recommendation`) при наличии; не выводит диагноз или факт лечения самостоятельно. Счета маркирует как учётные сведения, не клиническое подтверждение.
3. Период — включительные календарные дни в локальном времени клиники; timestamp сравнивается по дате, сохранённой ВМ. Для поиска связанной карты сканируются **все страницы MedicalCards с фильтром `patient_id`**, затем карта включается по `date_create` **или** по `admission_id` приёма в периоде; если скан неполон, это gap. Приёмы отбираются по `admission_date`, вакцинации по `date`, счета по `invoice_date` родительской записи `invoice` (при пустом/нулевом значении — по её `create_date` с пометкой), стационар — по пересечению `[start_date, end_date]` с периодом. Нулевая дата `0000-00-00`, пустая или некорректная дата не трактуется как доказательство открытого пребывания; запись с потенциальным пересечением включается с gap «граница неизвестна», статус сохраняется как факт, но не служит догадкой о дате. Запись без определимой даты выводится отдельно и создаёт gap. Граница верхнего дня включительна.
4. Для каждого раздела результат содержит число записей и признак полноты; ошибки, неизвестный `totalCount`, невозможность пройти предел API, отсутствие даты и непагинируемый endpoint отражаются в `gaps`. На раздел и на позиции каждого счёта действует ограничение 10 000 строк/100 страниц; на все запросы позиций счетов вместе — 100 GET. При превышении ответ маркируется неполным. Более узкий период **не устраняет** предел скана всех карт пациента, который нужен для связей с приёмами; здесь нужен отдельный контракт/API или постраничное продолжение в следующем этапе. Ответ с пробелами не заявляет «полную историю».
5. Агент составляет черновик, ссылается на полученные ID, отдельно сообщает пробелы и предлагает врачу исправить текст. Сохранение не происходит. В описании инструмента указана только опция `create_medical_card` по отдельному желанию пользователя.
6. Инструмент зарегистрирован с `pets.read`, `medical_cards.read`, `admissions.read`; `medical_cards.read` уже охраняет существующие `get_hospitalizations` и `get_vaccinations` в `tool_access_registry.py`. Финансовый раздел доступен лишь при дополнительном `finance.read`. Вызов и `tools/list` проверяют одни и те же основные права; проверка финансового права перед запросом fail-closed. Все HTTP обращения — GET по известным REST путям.
   После ответа каждая карта, приём, госпитализация и счёт повторно проверяются по ID пациента; позиция счёта — по ID родительского счёта, вакцинация — по ID прочитанной карты или явному ID пациента. Непроверенная принадлежность даёт gap и исключает запись из ответа.
7. Живой вызов на devtr6 с `.env`: код и очищенное тело, без данных клиники. Focused red → green → owning → fast → полный pre-review diff → default/real → commit → committed-diff review → push.

## Подзадачи

1. Сторожа: права и отсутствие записи; период/пациент; полнота страниц и пробелы; деперсонализация. Каждый red показан до реализации.
2. Минимальный агрегат поверх существующих GET контрактов, без изменения существующих инструментов и нового endpoint. Разбить реализацию на функции ≤150 строк.
3. Живая проверка и гейты; AssumptionLog, Roadmap и внешний рабочий журнал с evidence.

## Отклонённые варианты

- Автоматическая запись в `MedicalCards.description`: владелец прямо отказался от сохранения по умолчанию.
- Отдельный write-инструмент и серверный preview/confirm: MCP только отдаёт данные; подтверждение остаётся в диалоге.
- Обещание полного содержания вложений или выполнение услуг по строкам счёта: API этого не доказывает.
