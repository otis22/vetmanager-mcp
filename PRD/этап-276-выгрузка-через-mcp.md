# Этап 276. Выгрузка отчёта проходит через MCP, а не мимо него

## Контекст

Этап 275 закрыл персональные данные в строках отчёта тремя слоями, но честно
записал остаток: «Выгрузка CSV и XLSX скачивается из Ветменеджера напрямую,
мимо этих слоёв». Владелец продукта 01.09.2026 решил остаток закрыть:
выгрузку скачивает наш сервер, чистит и отдаёт агенту собственную ссылку.

## Проверенные факты

Живой прогон на `devtr6` 01.09.2026, отчёт `report_id=84` (значения локаторов
не печатались и в репозиторий не попадают — записана только их форма):

- `GET /rest/api/report/StartReport?report_id=<id>` → `data.report.report_file_id`.
- `GET /rest/api/report/reportFile?file_id=<id>` пока сборка идёт отвечает
  **HTTP 401** с телом `{"success":false,"error":true,"message":"Error: build
  is not started yet."}`, затем `Error: build in progress.`, и только потом
  отдаёт поля файлов. Код 401 здесь означает «ещё не готово», а не отказ в
  доступе.
- Готовый ответ содержит ровно четыре поля: `html_file`, `csv_file`,
  `csv_semicolon_file`, `xlsx_file`.
- **Каждое из них — абсолютный `https`-адрес на публичный CDN** (не на домен
  клиники), путь из шести сегментов вида
  `vetmanager-public-user-files/<домен клиники>/…`, без query-параметров и без
  подписи.
- **Скачивание не требует авторизации**: запрос без единого заголовка вернул
  `HTTP 200`, `content-type: text/csv`, тело в UTF-8 без BOM. Тот же запрос с
  ключом API вернул байт в байт то же самое.

Отсюда исходная оценка в этапе 275 («идёт мимо слоёв») оказалась мягче
действительности: файл со всеми ФИО и телефонами лежал в открытом доступе для
любого, кто знает адрес, всё время жизни на CDN.

Смежное, проверено и **вне scope**: `get_report_ai_job_data` возвращает
`data.csv_export_url` — это относительный REST-путь с query `report_id`, а не
публичная ссылка; получить по нему данные без ключа API нельзя, а инструмента
произвольного REST-запроса у агента нет. Трогать его в этом этапе не нужно.

## Цель

Агент не получает адрес на стороне Ветменеджера. Он получает адрес на нашей
стороне, по которому лежит файл, прошедший те же слои защиты, что и строки
отчёта, и живущий трое суток.

## Scope

### 276.1 Скачивание и очистка

Новый инструмент `get_report_export_download(report_file_id)`:

1. запрашивает `reportFile` — с той же обработкой «ещё не готово» и тем же
   30-минутным пределом ожидания, что и снятый инструмент;
2. берёт `csv_file`, при его отсутствии `csv_semicolon_file`; разделитель
   выбирается по тому, какое поле взято, без угадывания;
3. скачивает файл **в память** потоком, с жёстким пределом 25 МБ; на диск
   исходник не пишется никогда — «исходник удалён» здесь означает, что его и
   не было. Предел заодно ограничивает и работу очистки: 25 МБ CSV — это
   порядка двухсот тысяч строк, а десять тысяч строк этап 275 чистил за
   0,31 с. Считаются **распакованные** байты, поэтому сжатый ответ не обходит
   предел; заголовку `Content-Length` не верим, он может лгать или
   отсутствовать. Переадресации не выполняются: локатор ведёт прямо на файл,
   а переход на другой хост по указанию извне — это чужой выбор адресата.
   Таймаут на соединение и на чтение задан явно; оборванная загрузка — отказ,
   недокачанное содержимое не сохраняется;
4. разбирает CSV — в UTF-8, как отдаёт CDN; если байты в UTF-8 не
   разбираются, вторая попытка в `cp1251`, и только потом отказ, — чистит
   каждую ячейку вместе с её заголовком и записывает результат;
5. возвращает `{download_url, expires_at, rows, columns, sanitized}`.

Очистка — те же слои, что и у строк отчёта: имя колонки из заголовка отдаётся
в существующий разбор по ключу, значение — в `sanitize_report_value`. Для
этого в `depersonalization.py` появляется одна публичная обёртка
`sanitize_report_cell(column, value)` над уже существующим `_sanitize_value`.

Разбор CSV — состояния и решения:

| Состояние | Что делаем |
|---|---|
| пустой файл | отказ с понятным текстом, файл не создаётся |
| одна строка | считаем её заголовком, строк ноль |
| повторяющиеся имена колонок | обрабатываются по позиции, имена не склеиваются |
| в строке больше ячеек, чем в заголовке | лишние чистятся как значения без имени колонки |
| многострочные и закавыченные поля | штатный разбор `csv`, кавычки сохраняются на записи |
| тело не CSV (страница ошибки CDN) | до разбора: код ответа обязан быть `2xx`, а `content-type` — из списка `text/csv`, `text/plain`, `application/csv`, `application/octet-stream`. Иначе `upstream_error`, файл не создаётся |

**Формулы Excel.** CSV открывают в Excel, а ячейка, начинающаяся с `=`, `+`,
`@` или `-`, выполняется как формула — это способ увести данные с чужой
машины. Решение принимается по **первому значимому** символу: ведущие пробелы,
табуляции, переводы строки и управляющие символы сначала отбрасываются, иначе
экранирование обходится одним пробелом. Такая ячейка получает ведущую
одинарную кавычку.

Исключение ровно одно и описано формулой, а не на словах: ячейка, целиком
подходящая под `^-?\d+(?:[.,]\d+)?$`, остаётся как есть. Всё остальное,
начинающееся с `-`, экранируется. Иначе отчёт лишился бы отрицательных сумм, а
попытка описать «число» шире (`-1e3`, `- 1`, `-1 234,00`) даёт правило,
которое нельзя ни проверить, ни повторить.

Нормализация касается **всех** выдаваемых файлов, с деперсонализацией и без:
UTF-8 с BOM, разделитель — точка с запятой, перевод строки CRLF. Это
требование к удобству, а не к приватности: без BOM и точки с запятой Excel в
русской локали открывает файл одной колонкой кракозябр, и человек, ради
которого затевалась ссылка, получает мусор. Единое правило для всех файлов
дешевле двух веток. «Как есть» относится к содержимому ячеек, а не к кодировке
и разделителю.

Чистка применяется, когда у токена включена деперсонализация — ровно то же
условие, что и для строк. Для токена без деперсонализации файл отдаётся как
есть: это сознательный паритет с сегодняшним поведением, где тот же файл и так
лежит публично, но теперь он хотя бы живёт трое суток и по непредсказуемому
адресу.

Скачивание идёт на внешний CDN, а не на домен клиники, поэтому выполняется
отдельным клиентом с таймаутом и без заголовков авторизации: ключ API туда
отправлять незачем, и он туда не отправляется.

### 276.2 Ссылка и отдача

Путь: `/{префикс}/{owner}/{file}.csv`, где

- `owner = HMAC(k, канонизированное представление владельца)`, 32 hex;
- `file  = HMAC(k, канонизированное представление файла)`, 32 hex;

Хеши — это и есть имена на диске: файл лежит по пути
`<каталог>/<owner>/<file>.csv`, спутник рядом. Искать перебором нечего,
случайная часть имени участвует только во входе HMAC и в спутнике.
- `k = HMAC(WEB_SESSION_SECRET, "report-export-link-v1")`.

**Канонизация обязательна.** Склейка через двоеточие неоднозначна: домен может
содержать порт, а идентификатор субъекта — двоеточие, и тогда две разные пары
дают одну и ту же подписываемую строку. Части кодируются с указанием длины:
`v1|len(часть)|часть|…`, где `|` не может появиться внутри длины. Так разные
входы дают разные прообразы всегда.

Идентификатор субъекта — `bearer_token_id`; у доступа по OAuth его нет, там
берётся пара `тип субъекта:идентификатор субъекта`, а если и её нет —
идентификатор аккаунта. Разные субъекты одной клиники получают разные
каталоги.

Имя файла — `<report_file_id>-<16 случайных байт>`. Случайная часть нужна не
для секретности (её даёт ключ), а чтобы повторная выгрузка того же отчёта не
переписывала файл, на который уже выдана ссылка.

`WEB_SESSION_SECRET` в проде задан и уже обязателен для входа в кабинет. Если
его нет (локальный запуск без настройки), инструмент отвечает понятной
ошибкой, а не падает пятисоткой.

**Ключ обязателен именно как HMAC, а не просто хеш.** Домен клиники известен
всем, идентификатор токена — небольшое целое; голый `sha256(домен)+sha256(id)`
перебирается за секунды, и ссылка перестаёт быть секретом. С серверным ключом
путь невозможно вычислить, не имея этого ключа.

Отдача: `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`,
`X-Robots-Tag: noindex, nofollow`, `Referrer-Policy: no-referrer`,
`Cache-Control: no-store`. Имя сегмента проверяется по `[0-9a-f]{32}` до любого
обращения к файловой системе — обход каталога невозможен по построению.

**Спутник.** Рядом с файлом лежит `<file>.json`: `{"v": 1, "subject_type":
"bearer"|"oauth", "subject_id": N, "owner": "<32 hex>", "download_name":
"..."}`. Пишется атомарно и **до** публикации самого CSV, так что готовый CSV
без спутника не существует. Нет спутника, не разбирается, `owner` в нём не
совпал с сегментом пути — пара считается негодной, удаляется, ответ `404`.
Уборка удаляет спутник вместе с файлом.

**Проверка живости доступа.** Перед отдачей проверяется, что субъект из
спутника всё ещё существует и активен:

- `bearer` — строка токена есть, `status` активен, срок не истёк
  (пересчёт тем же методом, что и при аутентификации);
- `oauth` — строка гранта есть и её `status` активен.

Дополнительно owner-хеш пересчитывается из **текущих** домена и субъекта и
сравнивается с сегментом пути: токен, переехавший на другую клинику, своей
старой ссылкой не воспользуется.

Право на отчёты и режим деперсонализации при выдаче **не проверяются**. Файл
уже очищен по правилам, действовавшим в момент выгрузки; снятие права позже не
делает уже отданный файл опаснее, а лишняя проверка добавила бы разбор прав в
публичный маршрут. Проверяется ровно одно: жив ли ещё тот доступ, которым файл
получен.

Запрос в базу делается **только после того, как путь совпал с существующим
файлом**, — иначе публичный маршрут стал бы способом нагружать базу вслепую.
Проверка идёт с коротким таймаутом; **любая** её ошибка, включая недоступную
базу, даёт тот же `404`, а в журнал уходит шаблон маршрута и исход, без пути.

Обещание аккуратно: отзыв токена не даёт начать **новую** выдачу. Скачивание,
уже начавшееся до отзыва, дойдёт до конца — обрывать поток посреди файла ради
этого никто не будет.

Ответ на несуществующий, просроченный, отозванный и синтаксически неверный
путь одинаков: `404` с одним и тем же телом. Разные ответы дали бы оракул для перебора.
Перебирать при этом нечего: путь — 128 бит на каждый сегмент.

**Путь не должен попасть в логи, и по умолчанию он туда попадает.** Проверено
в коде 01.09.2026:

- собственный журнал маршрутов пишет `route` — шаблон пути, а не сам путь;
  здесь всё в порядке;
- `uvicorn` запущен с `access_log=True`, а `PERSISTENT_LOG_PATH` кладёт лог на
  диск: строка доступа содержит полный путь, то есть ключ от файла. Ставится
  фильтр на логгер `uvicorn.access`, который заменяет путь выгрузки шаблоном;
- скрабер Sentry чистит заголовки, cookies, query и тело, но не `request.url`.
  Добавляется замена пути выгрузки на шаблон и там же.

Требование «путь не попадает в логи» относится к тому, чем управляет этот
репозиторий. Журнал обратного прокси на VDS видит путь и пишет его; настройка
прокси живёт вне репозитория, поэтому здесь это **принятый риск**, а не
невыполненное требование. Сузить его можно отдельным решением по конфигурации
VDS.

Счётчики метрик не публичны — `/metrics` закрыт `METRICS_AUTH_TOKEN`, поэтому
раздельные исходы в них оракулом не становятся.

Счётчики: `vetmanager_report_export_download_total{outcome}` для инструмента
(`success`, `too_large`, `upstream_error`) и
`vetmanager_report_export_serve_total{outcome}` для маршрута (`served`,
`not_found`, `expired`).

**Запись на диск атомарна.** Файл пишется во временное имя в том же каталоге
и переименовывается на место. Иначе параллельная выгрузка, кончившееся место
или падение процесса оставят обрезанный файл, который маршрут начнёт честно
отдавать как готовый. Права: каталог `0700`, файл `0600`. При любой ошибке
записи временный файл удаляется, инструмент отвечает отказом.

### 276.3 Срок жизни

Трое суток. Возраст проверяется **на выдаче** — это и есть правило: файл
старше срока не отдаётся и удаляется тут же. Подметание каталога делается при
создании новой выгрузки; оно нужно для диска, а не для приватности, поэтому
его задержка ничего не ломает. Фонового планировщика не заводим — в проекте
его нет, а заводить его ради удаления файлов означает новый режим отказа.

### 276.4 Снятие инструмента локаторов

`get_report_export_file` снимается: из реестра прав, из описаний, из README, из
набора отчётных инструментов. Тест-сторож проверяет, что имя не вернулось —
как для инструментов удаления счетов в этапе 268. `start_report_export` и
`get_report_ai_job_export` остаются: они запускают сборку и локаторов не
отдают.

### 276.5 Формулировка

Из текста в кабинете и на экране согласия уходит предложение про выгрузку мимо
слоёв. На его место — что выгрузка проходит те же слои и живёт трое суток.

Старт выгрузки на `devtr6`, скачивание, очистка, получение файла по выданной

## Acceptance

1. `get_report_export_file` не регистрируется как инструмент; сторож красный,
   если имя вернуть.
2. `get_report_export_download` отдаёт ссылку на наш домен и не содержит в
   ответе ни одного адреса Ветменеджера или CDN.
3. Ячейка с ФИО, телефоном, почтой и адресом в скачанном файле обезличена для
   токена с деперсонализацией; дата, микрочип и штрихкод не тронуты.
4. Файл отдаётся по правильной ссылке и не отдаётся: по чужому `owner`, по
   изменённому на один символ `file`, по пути с `..`, по пути с не-hex.
5. Файл старше трёх суток не отдаётся и удаляется при обращении.
   Файл, выданный отозванному токену, не отдаётся.
6. Файл больше 25 МБ не скачивается: инструмент отвечает понятной ошибкой.
7. Ни один ответ инструмента — ни успешный, ни любой из отказов — не содержит
   адреса Ветменеджера или CDN.
8. Ячейка, начинающаяся с `=`, экранирована; отрицательное число — нет.
9. Строка доступа `uvicorn` для маршрута выгрузки не содержит хеши пути.
10. Полный прогон зелёный; живой прогон на devtr6 приложен.

## Out of scope

- **XLSX.** Собрать настоящий `.xlsx` без новой зависимости нельзя, а тянуть
  её в 512-мегабайтный прод ради второго формата этот этап не будет. Отдаём
  CSV в кодировке UTF-8 с BOM и точкой с запятой — такой файл Excel открывает
  двойным щелчком без диалога импорта. Если XLSX понадобится, это отдельный
  этап с явным решением про зависимость.
- `csv_export_url` в `get_report_ai_job_data` — см. «Проверенные факты».
- Ограничение выгрузки для деперсонализированных токенов: смысла нет, файл
  теперь чистится.

## Оценка простоты

- Абстракций без второго вызова нет: `report_export_store.py` — это четыре
  функции (путь, запись, чтение, подметание), вызываемые из инструмента и из
  маршрута.
- Косвенности больше одного шага нет: инструмент → хранилище → диск.
- Планировщик не заводится, состояние в БД не заводится: адрес файла
  вычисляется из его же имени, а срок жизни — из времени файла.
- Отклонённый более простой вариант: отдавать ссылку Ветменеджера как есть.
  Он не решает задачу — файл остаётся публичным и неочищенным.
- Отклонённый более сложный вариант: таблица выгрузок в БД с явным сроком и
  фоновой уборкой. Она понадобилась бы для отзыва конкретной ссылки; такого
  требования нет, а цена — миграция, планировщик и второй источник правды о
  сроке.

## Риски

- **Ссылка публичная и сама является ключом.** Кто получил адрес — скачает
  файл. Это осознанно: агент должен уметь передать ссылку человеку, а
  заголовок авторизации в браузере тот не поставит. Отсюда следствия, которые
  надо назвать, а не спрятать: адрес остаётся в истории браузера, в журнале
  корпоративного прокси и в журнале нашего обратного прокси; мессенджер может
  скачать файл ради превью; агент может передать ссылку не тому человеку;
  отозвать одну конкретную ссылку нечем — можно только сменить секрет и
  погасить сразу все. Компенсируется непредсказуемостью пути (128 бит на
  сегмент), тремя сутками жизни, проверкой живости токена на каждой выдаче,
  очисткой содержимого и запретом индексации. По сравнению с сегодня —
  строгое улучшение: сейчас ровно тот же файл лежит публично, неочищенный,
  бессрочно и без всякой связи с правами.
- **Диск.** Предел 25 МБ на файл и трое суток жизни; подметание при каждой
  новой выгрузке.
- **Секрет.** Смена `WEB_SESSION_SECRET` делает выданные ссылки нерабочими.
  При сроке жизни трое суток это приемлемо и записано.
