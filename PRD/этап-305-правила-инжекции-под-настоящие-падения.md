# Этап 305. Правила инжекции написаны не на те инструменты

## Цель

Сделать так, чтобы механизм доставки известных проблем сработал хотя бы раз на
настоящем отказе. Сегодня он не срабатывал ни разу с мая 2026 года, и причина
установлена точно: правила написаны на инструменты, которые не падают.

## Проверенные факты

Снимок Sentry за 90 дней, снят 06.09.2026 (`organizations/home-xv3/issues`,
43 issue, 6 096 событий). Распределение по классу исключения:

| Класс | Событий | Доходит до инжекции |
|---|---|---|
| `ToolError` | 6 028 | да |
| `VetmanagerError` | 16 | нет — не подкласс `ToolError` |
| `ValidationError` (FastMCP) | 8 | нет — падает до тела инструмента |
| `FilterPropertyValidationError` | 6 | нет — подкласс `ValueError` |
| `RuntimeError` / `AuthError` / `ValueError` | 6 | нет |
| `ToolInputError` | 1 | нет — `should_skip_report_hint` пропускает намеренно |

Достижимые падения делятся на два неравных класса:

**Предохранитель и таймаут апстрима — 5 994 события (99.4%).**

| Событий | Инструмент | Текст |
|---|---|---|
| 5 181 | `get_invoice_by_id` | `VM API circuit breaker half-open for {clinic}; probe already in flight` |
| 657 | `get_invoice_by_id` | `Timeout requesting Vetmanager upstream. Please retry shortly.` |
| 155 | `get_invoices` | `VM API circuit breaker open for {clinic}; retry after 2s` |
| 1 | `create_medical_card` | `VM API circuit breaker open for {clinic}; retry after 11s` |

**Всё остальное — 28 событий шестью текстами:** контракт фильтра и сортировки
(`get_cassa_closes` 4+2, `get_invoices` 3, `get_users` 3, `get_medical_cards` 1),
клиника не выбрана (`create_medical_card` 5), переход статуса Report AI (4),
экспорт отчёта (4+2).

Снимок правил с прода 06.09.2026 (`known_issues`, 42 записи):

- правил 11, у всех есть валидный playbook;
- семь живут в репозитории (`SEED_ISSUES`), четыре заведены вручную через
  `promote --match-rules-json` и в репозитории не существуют;
- проблема #34 в статусе `wontfix`, а `wontfix` не входит в
  `AUTO_EVENT_STATUSES` — её правило не сработает никогда. Живых правил десять;
- `find_known_issue_match` пропускает кандидата без валидного playbook: правило
  без playbook даёт событие `auto`, но до агента не доходит;
- изменить правила существующей проблемы нечем. `promote --match-rules-json`
  задаёт их при создании, `set-playbook` правит только playbook.

Проверено в контейнере 06.09.2026: `{"version": 1, "all": []}` проходит
`validate_match_rules_json` и совпадает с **любым** инцидентом — `match_rules`
на пустом списке условий возвращает `True`.

Проверено по коду 06.09.2026 (после ревью PRD): запись в
`known_issue_match_events` **не защищена** ни дедуп-окном, ни потолком в минуту
— ни для `injection`, ни для `auto`. `AUTO_EVENT_DEDUP_WINDOW` и
`MAX_AUTO_EVENTS_PER_MINUTE` ограничивают только создание `AgentFeedbackReport`,
а событие пишется **до** них, намеренно и закреплённо тестом этапа 151
(«событие должно пережить дедуп»). Значит на каждое совпадение приходится
**две** строки: `injection` из `augment_tool_error` и `auto` из
`write_auto_feedback_event`.

## Цель решения

Правила пишутся из падений, а не из жалоб, и это свойство прибито тестом,
который сегодня красный. Механизм срабатывает на настоящем отказе — впервые за
всё время существования продукта.

## Ключевое решение по объёму

**Правило на предохранитель в этот этап не входит.** Чтобы механизм сработал,
хватает редких классов: 28 событий за 90 дней. Правило на предохранитель — это
5 994 события, две строки в БД на каждое, на горячем пути отказа, у механизма,
который ни разу не работал. Сначала он должен заработать на безопасном объёме и
показать свою стоимость на живых цифрах; правило на предохранитель заводится
отдельным этапом, после замера.

Это же снимает необходимость трогать контракт `known_issue_match_events` — он
намеренный (этап 151) и на нём стоит метрика эффективности (этап 191). Менять
его вслепую, ради риска, который в этом скоупе не наступает, — работа не по
делу.

## Scope

**305.1 — корпус падений становится фикстурой.** Тексты из Sentry с числом
событий за каждым и с пометкой, доходит ли класс исключения до
`augment_tool_error`. Инцидент собирается как в рантайме
(`error_code="ToolError"`, `http_status=None`, `params_shape=None`), каждый
текст проверяется в двух формах: как его видит наш код и как он выглядит в
Sentry с обёрткой FastMCP (`Error calling tool 'X': ...`). Сторож: у каждого
достижимого класса падений из корпуса есть правило, которое с ним совпадает.
Сегодня совпадений ноль — тест красный до 305.2.

**305.2 — правила под настоящие падения.** Четыре новых записи в `SEED_ISSUES`,
каждая с playbook и с явно заданным `priority`:

1. апстрим отверг имя поля фильтра или сортировки — 13 событий;
2. клиника не выбрана при записи — 5;
3. сохранение отчёта Report AI из статуса `needs_confirmation` — 4;
4. экспорт отчёта недоступен по REST — 6.

Перед заведением каждая сверяется с одиннадцатью существующими правилами на
проде: seed ищет свою строку по маркеру `[seed:{slug}]` и проблему, заведённую
вручную, не увидит — заведёт вторую на тот же класс, и рантайм выберет из них по
сортировке, не обязательно новую.

Правила остаются узкими: `related_tool` задан, текст ищется по характерным
маркерам. Тест закрепляет, что специфичное правило побеждает общее — выбор
кандидата идёт по `priority.asc(), updated_at.desc(), id.asc()` и возвращает
первый с валидным playbook.

**305.3 — `set-match-rules` и запрет правила, совпадающего со всем.** Команда
правки правил у существующей проблемы по образцу `set-playbook` этапа 294.4.
Валидация усиливается: список условий не может быть пустым. Сегодня пустой
список валиден и совпадает с любым инцидентом, а у проблемы с
`related_tool=None` такая запись становится кандидатом почти на каждый отказ и
затеняет остальные. Команда правки без этого запрета делает дефект достижимее.

**305.4 — колонка `injection` учитывает статус.** Проблема в `wontfix` или
`fixed` не может быть доставлена, и разбор не должен видеть у неё `yes`.

**305.5 — выкат и живая проверка.** Первое совпадение правила с настоящим
отказом на бою.

**305.6 — стоимость пути измерена на живых цифрах.** После выката снять, во что
обходится совпадение: сколько запросов к БД добавляет матч и сколько строк
появляется в `known_issue_match_events` на отказ. Замер — вход в отдельный этап
про правило на предохранитель; без него решение о нём принимать нечем.

## Out of scope

- **Правило на предохранитель и таймаут** (5 994 события) — отдельный этап,
  после 305.6.
- Изменение контракта `known_issue_match_events` (дедуп, потолок) — он
  намеренный, на нём стоит метрика 191, и в этом скоупе риск не наступает.
- Сверка успешных ответов (283.4) — решение владельца `stop` от 06.09.2026.
- Сведение счётчика Prometheus с продуктовым отчётом (283.5) — до первого
  совпадения считать нечего.
- Классы исключений, не доходящие до `augment_tool_error` (36 событий, 0.6%).
  Расширять перехват на `VetmanagerError` и `FilterPropertyValidationError` —
  отдельная работа с собственным риском, и она не нужна, чтобы механизм
  заработал.

## Декомпозиция

| Подзадача | Объём |
|---|---|
| 305.1 фикстура корпуса + красный сторож | ~120 строк теста |
| 305.2 четыре правила с playbook + тест приоритетов | ~110 строк данных, ~40 теста |
| 305.3 `set-match-rules` + запрет пустых условий + тесты | ~80 строк |
| 305.4 статус в колонке `injection` + тест | ~20 строк |
| 305.5 выкат, применение seed, живая проверка | без кода |
| 305.6 замер стоимости на бою | без кода |

## Acceptance

- Тест корпуса красный до 305.2 и зелёный после — и это показано, а не заявлено.
- Каждое новое правило совпадает хотя бы с одним настоящим текстом из корпуса в
  обеих формах.
- Ни одно существующее правило не сломано: прежние семь seed-правил продолжают
  совпадать со своими текстами.
- Для инцидента, попадающего под два правила, агент получает специфичное, а не
  общее — проверено тестом на порядке кандидатов.
- `set-match-rules` отказывается писать невалидные правила, отказывается писать
  пустой список условий и не стирает рабочие правила при отказе.
- Колонка `injection` показывает `no` для проблемы в закрытом статусе.
- Ни одно новое seed-правило не дублирует класс, уже закрытый существующей
  проблемой на проде.
- На бою после выката — событие в `known_issue_match_events` с источником
  `injection`.
