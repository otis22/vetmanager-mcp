# Этап 412. Пакетное чтение складских остатков

## Цель и факты API

Агенту нужен один вызов MCP для нескольких заранее известных товаров одной клиники; выбор чужой клиники через скрытый `clinic_id=1` недопустим. `GET /rest/api/stores/RestOfGoodInWarehouse/` возвращает `data.rest_good_in_warehouse.quantity` для пары `good_id`, `clinic_id` (artifacts/api_entity_reference-ru.md, §2.36). Справочник фиксирует обязательность обоих параметров и отсутствие поддержки `filter`/`sort`/`limit`/`offset`, хотя OpenAPI v6 ошибочно перечисляет общие параметры и не определяет пакетную форму. Значит, пакетный инструмент выполняет отдельный REST GET для каждого товара; агрегат «все остатки ниже порога» не обещаем: полного серверного сканирования API не предоставляет. Пример отчётной колонки суммирует все склады базы (artifacts/report-ai-prompt-helper-short-mcp-2026-06-15.md:162), поэтому она не источник остатков по клинике.

## Контракт и критерии приёмки

1. `get_good_stock_balance(good_id, clinic_id)` требует явно передать положительный `clinic_id`; прежние вызовы с одним аргументом теперь отклоняются схемой MCP, без запроса к ВМ. Это намеренный breaking change ради верной клиники; текст инструмента и подсказка ведут агента к явному ID.
2. `get_goods_stock_balances(good_ids, clinic_id)` принимает 1–20 уникальных положительных ID, сохраняет порядок и возвращает `clinic_id`, `balances` с `good_id`, `quantity`, `quantity_str`. Один ID вызывает один GET; без `clinic_id` отказ до REST. Ошибка любого GET или отсутствующая/нечисловая `quantity` завершает вызов ошибкой, чтобы неизвестный или частичный остаток не выдавался за ноль или полный результат. Одиночный инструмент использует ту же проверку ответа.
3. Новый инструмент имеет `inventory.read` в реестре прав, использует уже внесённый GET-путь в fail-closed карте. `tools/list` скрывает его для групп без права.
4. Красные сторожа доказывают отсутствие default и пакетный вызов, права и путь. Живые вызовы на контуре `.env` показывают несколько good_id и отказ без clinic_id: код и фрагмент тела в AssumptionLog.
5. Все запросы остатков передают `fresh=True`, минуя 900-секундный GET-кэш клиента. Пакет имеет общий лимит 60 секунд и прекращает оставшиеся запросы при исчерпании. Сторожа показывают обход заранее прогретого кэша и остановку при медленном ответе.
6. MCP prompt `low_stock` тоже требует явный `clinic_id`, использует пакетные вызовы порциями до 20 товаров и не подставляет 1. При просмотре каталога он листает `get_goods(limit=100, offset=...)` до `totalCount` или явно говорит о неполном охвате. Проверяется опубликованная схема prompt и отрендеренный текст. Нулевой остаток услуги — корректный ответ этого REST endpoint; инструмент сообщает число для переданного ID, не классифицирует товар как дефицитный. Prompt исключает услуги по `is_warehouse_account` из каталога.

## Архитектурное решение

Проблема: текущий инструмент создаёт N MCP-вызовов и молча принимает ID клиники 1. Контекст: upstream поддерживает только одну пару ID на REST-запрос; доступ к складу определяется существующим `inventory.read`; объём ответа и число запросов должны быть ограничены. Варианты: (а) передавать список прямо upstream — контрактом не подтверждено; (б) читать Report AI — агрегат не ограничен клиникой; (в) композиция проверенных одиночных GET — выбрано. Выполнять последовательно, максимум 20 запросов и 60 секунд на весь batch: простая граница нагрузки и остановка при ошибке или дедлайне. `fresh=True` обходит GET-кэш клиента для актуального остатка. Существующий инструмент остаётся для одиночной пары, но явный clinic_id меняет его схему. Инварианты: нет запроса без клиники; каждый результат относится к запрошенной паре; нет нового REST-пути, записей или расширения доступа. Если upstream изменит контракт, batch-инструмент можно отключить без изменения одиночного; возвращать молчаливый default нельзя.

## Риски и откат

Старые агенты могли полагаться на default 1; они получат явную ошибку схемы и должны получить ID клиники из контекста. Batch делает до 20 последовательных запросов и может занять больше времени; не увеличивать лимит без фактов о нагрузке API. При ошибке в середине не отдавать неполный список.
