# Этап 327. Метрики сообщений и клиник-локальные даты

## Цель

Сделать отправку сообщений наблюдаемой на уровне MCP-инструмента и вычислять
относительные даты по локальному дню клиники, а не по дню процесса.

## Проверенные факты

- `send_message_to_all`, `send_message_to_users` и `send_message_to_roles` в
  `tools/operations.py` вызывают `VetmanagerClient.post` напрямую. Поэтому
  клиентские upstream-метрики есть, но `instrument_call` не создаёт
  `tool_calls_total` и `tool_call_latency_seconds`.
- Остальные CRUD-инструменты используют `service_metrics.instrument_call`.
  Его серии имеют labels endpoint (с `:tool_name`, если передан), HTTP method
  и outcome `success`/`error`; latency использует тот же endpoint и method.
- Все поддерживаемые относительные формы парсит `validators.parse_date_param`:
  `today`, `yesterday`, `tomorrow`, `+/-N[dwm]`. Сейчас его default и
  `calculate_inactive_window`, а также default-период `get_average_invoice`,
  получают дату через `date.today()` процесса.
- Вызовы `parse_date_param` находятся в tools admission, client, finance,
  invoice, medical_card и schedule. Относительные даты там должны получать
  clinic-local anchor до построения фильтров.
- Report AI уже хранит ограниченный TTL/LRU-кэш таймзон. Он получает
  `time_zone` из `GET /rest/api/clinics/{id}`. OpenAPI описывает его как
  nullable string; read-only Vetmanager extjs подтверждает поле таблицы
  `clinics.time_zone` и передаёт его в timezone factory. Формат — IANA name
  (в OpenAPI example `Europe/Kiev`), не offset.
- Текущий ключ кэша Report AI содержит id job, поэтому общий кэш должен быть
  переформулирован как key текущего подключения + clinic id; второй кэш не
  создаётся. `time_zone = null` — валидный OpenAPI случай, а не transport
  failure.

## Scope

1. Обернуть три отправки сообщений в `instrument_call` с точными endpoint,
   `POST` и `tool_name`, не трогая payload, ответ или исключения.
2. Добавить runtime-сторож: реестр трёх инструментов обязан при success и
   error создать outcome и latency-серию с теми же labels, что Grafana.
3. Выделить из Report AI единый bounded TTL/LRU resolver IANA-таймзоны по
   подключению и clinic id; использовать `/rest/api/clinics/{id}` как источник.
   Owner — один модуль `clinic_timezone` с одним module-level cache; Report AI
   и date-anchor импортируют resolver, а не создают свои cache instances.
4. Передавать clinic-local date anchor во все пути relative/default dates,
   когда clinic id есть во входном контракте. Для мультиклинических вызовов
   без такого id он не может быть получен из будущего ответа; применяется
   явно документированный fallback `date.today()` процесса. Для пустого или
   невалидного `time_zone` (включая `ValueError`, `TypeError` и
   `ZoneInfoNotFoundError` при разборе значения) кэшируется negative result с тем же bounded TTL и
   один warning на cache miss; transport failure не кэшируется. Это не UTC
   fallback и завершается process-local fallback с warning на каждую попытку,
   потому что retry следующего запроса может восстановить верный clinic day.
5. Добавить тест на границе суток: одинаковый instant для двух клиник с
   разными timezone даёт разные `today`; проверить cache reuse и fallback.

## Не входит в scope

- Изменение timezone в Vetmanager или хранение timezone у нас в БД.
- Конвертация timestamp-значений API: этап меняет только anchor date для
  пользовательских relative/default периодов.
- Изменение формата успешных ответов или ошибок message-инструментов.

## Архитектурное решение

Одна общая async-функция разрешения clinic-local date должна жить рядом с
существующим Report AI cache, а не создавать второй cache или выполнять
синхронную сетевую операцию в validators. `parse_date_param` остаётся pure и
получает уже вычисленный `today`; это сохраняет его public/test contract.
Ключ cache: `(account_id, connection_id, clinic_id)`, чтобы разные tenants с
совпадающим числовым clinic id не смешались. Пустой/невалидный `time_zone`
даёт bounded negative cache, чтобы валидный nullable контракт не превращался
в GET и warning на каждый вызов; transport fault не кэшируется.
Invalid timezone value (включая path-like) negative-кэшируется и даёт warning.
Отсутствие tzdb — отдельная deployment/runtime fault: test startup-resolver
известной `UTC` zone, failure логируется как error и не скрывается под
clinic-specific warning. Docker image/test environment обязан содержать
timezone database. В production используется тот же application image;
resolver не меняет MCP response/error contract.

Для операций без явного `clinic_id` нельзя использовать id из их будущего
ответа. Они получают process-local fallback с observability event; добавлять
новые обязательные MCP-параметры этап не будет. Для имеющегося `clinic_id`
relative/default anchor считается по именно этой clinic; отсутствие timezone
видно в single cache-miss warning, не как молчаливый UTC.

## Декомпозиция

1. ≤100 LOC: тесты F25, красная демонстрация сторожа, затем обёртки трёх
   message-инструментов.
2. ≤150 LOC: вынести/re-key TTL/LRU resolver timezone и его tests, включая
   два tenants и invalid/missing timezone.
3. ≤150 LOC на подзадачу: внедрить local anchor во все relative/default date
   paths с clinic id и documented fallback в остальных; tests на границе
   суток, negative cache, deployment timezone database и отсутствие нового
   кэша.

## Acceptance criteria

- Каждая из трёх отправок создаёт success/error outcome и latency series с
  endpoint соответственно `/rest/api/messages/all`, `/users`, `/roles`,
  method `POST`, outcome `success`/`error` и tool label соответственно
  `send_message_to_all`, `send_message_to_users`, `send_message_to_roles`;
  payload, response и ошибка совпадают с прежними. Grafana derives `tool`
  from `:tool_name` suffix, as does the existing exporter.
- Сторож действительно падает, если снять instrumentation хотя бы с одного
  зарегистрированного message-tool; после возврата кода он зелёный.
- Две клиники с разными IANA timezone при одном instant на границе суток
  получают разные результаты `today`.
- Relative forms и default periods с clinic id используют тот же
  clinic-local anchor; отсутствие clinic id отмечено documented fallback.
- Missing/invalid timezone имеет явный process-local fallback и ровно один
  warning на negative-cache miss, не превращается молча в UTC.
- Path-like/некорректное `time_zone` не меняет MCP error contract: это
  negative-cache fallback, а не escaped exception.
- Тестовый Docker image разрешает известную IANA zone; отсутствие tzdb для
  непустого имени — error signal, а не тихая деградация.
- Один bounded Report AI cache используется обоими потребителями.

## Architecture Critique

Required: меняются public MCP behavior, multi-tenant cache boundary и
наблюдаемость production. Strong review проверяет ownership cache, tenant key,
fallback и сохранение message error contract.

## Простота

Новая абстракция нужна только потому, что уже есть два независимых call-site:
Report AI и relative-date tools. Pure `parse_date_param(today=...)` остаётся
одним простым уровнем; отдельное хранилище, middleware либо timezone в БД не
нужны.

## Результаты ревью PRD

Spark: два запуска не вернули разбираемый verdict из-за runtime/tool liveness,
поэтому findings не приняты. Ревью сторонней моделью, попытка 1/2: приняты
все три warning — negative cache для nullable `time_zone`, отказ от
невозможного получения clinic id из будущего list response и явный test/deploy
контракт tzdb. Повторный Spark принял: один module-level cache owner,
process-local fallback на transport/ZoneInfo failure с observability event и
literal labels трёх message tools. Ревью сторонней моделью, попытка 2/2:
приняты two warnings: invalid value (все ZoneInfo-construction exceptions)
negative-кэшируется, а отсутствие tzdb отличено startup-проверкой known zone.
