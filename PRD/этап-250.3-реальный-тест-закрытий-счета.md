# Этап 250.3. Реальный тест закрытий счёта с двух сторон

## Цель

Закрепить на opt-in devtr6 контуре, что `get_closing_of_invoices(invoice_id=8)`
возвращает объединение закрытий счёта, который находится и на minus, и на plus
стороне.

## Проверенные факты

- На devtr6 у invoice id `8` есть по одной записи closingOfInvoices с каждой
  стороны; односторонний raw REST filter возвращает только одну из двух.
- Реализация 250.1 делает два запроса, dedupe по `id` и pagination после merge.
- Real contour уже opt-in через `TEST_DOMAIN`/`TEST_API_KEY`; test помечен
  `real_api` и дополнительно ограничен devtr6.

## Scope

1. Добавить real regression, который получает raw IDs обоих filters.
2. Вызвать MCP tool с `invoice_id=8` и проверить, что объединение содержит
   оба набора без дублей.
3. Закрыть 250.2 и 250.3 в Roadmap только после успешного opt-in прогона.

## Архитектурное решение

Architecture Critique: not required — меняется только opt-in integration test;
public contract и runtime code уже реализованы и не меняются.

Тест фиксирует fixture id 8, а не выбирает случайный счёт: это проверенный
контрактный data fixture, который гарантирует нужный двухсторонний случай.
Raw requests перед вызовом tool явно подтверждают fixture и дают понятный
`skip`, если владелец стенда когда-либо её удалит. Инвариант: MCP result
содержит union raw ID с обеих сторон ровно по разу. Rollback — fixture может
быть заменена другим подтверждённым двухсторонним invoice id без runtime
изменений.

## Декомпозиция

1. Добавить один opt-in real test (≤150 строк).
2. Запустить opt-in suite и закрыть Roadmap (≤150 строк).

## Acceptance criteria

- Test выполняется только при credentials devtr6.
- Он доказывает наличие raw records на обеих сторонах и их union в MCP ответе.
- Нет записи секретов или фикстуры в production.
