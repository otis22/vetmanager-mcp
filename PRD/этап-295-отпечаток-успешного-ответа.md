# Этап 295. У успешного ответа с неверными данными нет отпечатка

## Обращение

03.09.2026 пришёл отчёт #62: Report AI отдал ровно 1000 строк с `limited=false`
и оборвался, не дойдя до конца периода. Отчёт автоматически привязался к
известной проблеме #42 — «Report AI отдаёт идентификатор сотрудника в колонке,
распознанной как ФИО врача». Это другой дефект.

Привязка не осталась внутри базы: `record_feedback_report` возвращает
`known_issue` вместе с playbook, то есть агент, сообщивший про обрыв выгрузки,
получил в ответ инструкцию подставлять имена врачей через `get_users`.

## Что происходит на самом деле

Отпечаток считается по пяти полям (`build_error_fingerprint_hash`):
`related_tool`, `http_status`, `error_code`, нормализованный текст ошибки,
`params_shape`. У отчёта про **успешный** вызов с неверными данными первых
четырёх нет вовсе: HTTP-статуса нет, кода нет, текста ошибки нет. Остаётся
`related_tool` + `params_shape`.

Для отчёта #62 это `get_report_ai_job_data` + `["job_id"]`. Тот же хеш получит
любой отчёт про этот инструмент, вызванный с одним `job_id`, — про что бы он ни
был.

Проверено на боевой базе 04.09.2026:

```
fingerprint 5513373945e3… → отчёты #55, #56, #62
   #55, #56 — идентификаторы вместо имён врачей
   #62      — обрыв выгрузки на 1000 строк
```

Ещё шесть отчётов по пяти разным инструментам имеют пустой отпечаток и не
найдутся никогда.

**Почему это не лечится починкой playbook.** 04.09.2026 был исправлен playbook
проблемы #11 (этап 294.1) — той самой, что дословно описывает предел в 1000
строк. После починки повтор поиска по инциденту той же формы, что у отчёта #62,
всё равно возвращает **#42**:

```
fingerprint: hmac-sha256:5513373945e3…
match -> known_issue #42 [acknowledged] Report AI отдаёт идентификатор сотрудника…
tools: ['get_users']
```

Совпадение по отпечатку имеет приоритет над правилами; отпечаток `5513…`
принадлежит #42, а у #11 свой — `4172e4…`, полученный в июне от отчёта, у
которого признак ошибки был.

## Цель

Отпечаток, у которого нет ни одного признака ошибки, перестаёт быть основанием
для автоматической привязки. Отчёт про «ответ пришёл, данные неверные» остаётся
неразобранным и попадает к человеку, а не привязывается к первой проблеме с тем
же инструментом и той же формой параметров.

**Неверная привязка хуже отсутствия привязки.** Отчёт помечается разобранным,
в метрике появляется совпадение, а агенту выдаётся чужой playbook. Пустой ответ
честнее: он виден в `recent` как `new` и попадает в еженедельный разбор.

## Scope

1. `_ordered_known_issue_candidates` использует отпечаток для сопоставления
   только тогда, когда у инцидента есть признак ошибки: непустой
   `http_status`, непустой `error_code` или непустой нормализованный текст
   ошибки. Иначе кандидаты остаются только те, что совпали по **написанным
   человеком** правилам `match_rules_json`.
2. Отказ перестаёт быть немым: структурное событие в лог с причиной, чтобы
   разбор видел, что привязки не было и почему.
3. Пересмотр уже сделанных привязок по отпечатку без признака ошибки —
   операционный шаг на боевой базе, вне репозитория.

### Вне scope

- **Формула отпечатка не меняется.** В роадмапе 295.2 был записан как «отчёт
  получает отпечаток, который различает такие отчёты между собой». От этого
  отказываюсь осознанно: различить их можно только подмешав свободный текст
  отчёта, а это выдуманная точность — два агента опишут одну и ту же поломку
  разными словами и всё равно не совпадут, зато сломается склейка настоящих
  повторов одного и того же отчёта. Честный ответ здесь — не привязывать,
  а не привязывать точнее.
- Отпечаток остаётся записанным в отчёте: он нужен для склейки повторов и для
  ручной привязки. Меняется только его право быть основанием для матча.
- Путь `augment_tool_error` не затрагивается по смыслу: там всегда есть
  исключение, то есть признак ошибки, — но проверяется тестом.
- Правила `match_rules_json` для #11 — работа триажа, не кода.

## Декомпозиция

- **295.1** `_has_error_signal(incident)` и его применение в
  `_ordered_known_issue_candidates`. ≤ 30 LOC.
- **295.2** Событие лога `known_issue_match_skipped_no_error_signal`
  с `related_tool` и числом кандидатов, которые были бы выданы раньше. ≤ 20 LOC.
- **295.3** Операционный пересмотр привязок на бою. Вне репозитория.

## Acceptance

1. Инцидент вида отчёта #62 (`related_tool=get_report_ai_job_data`,
   `params_shape=["job_id"]`, ни статуса, ни кода, ни текста) **не**
   привязывается к проблеме с тем же отпечатком.
2. Инцидент с признаком ошибки привязывается по отпечатку как раньше —
   регрессии в основном пути нет.
3. Инцидент без признака ошибки по-прежнему привязывается, если сработали
   написанные человеком правила `match_rules_json`.
4. `record_feedback_report` для инцидента без признака ошибки возвращает
   `known_issue: null`, а отчёт сохраняется со статусом `new` и со своим
   отпечатком.
5. Отказ виден в логе отдельным событием.
6. Полный набор тестов зелёный.
