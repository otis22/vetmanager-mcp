# Этап 376. Предупреждение об истечении bearer-токена в ответах инструментов

## Цель и границы

При успешном вызове любого MCP-инструмента токеном с истекающим сроком показать агенту короткое предупреждение: «Токен истекает через N дней. Сообщите человеку: продлите доступ — выпустите новый токен в кабинете с теми же правами, настройкой очистки данных и IP-ограничением, затем замените им старый в подключении». Пороговые окна — 14, 7 и 1 день; один подготовленный ответ с предупреждением на токен за скользящие 24 часа. 376.1 — только PRD; 376.2 — код, красные сторожа и live; 376.3 — аудит и выпуск. Предупреждение не блокирует вызов, не меняет права и не раскрывает ключ, id токена, его префикс или ссылку с ключом.

## Проверенные факты

Срез из постановки 09.10.2026: 35 `token_expiry_warning_7d/14d/1d` за 30 дней, dead_30d = 18 аккаунтов, 3 токена истекали в следующие 7 дней. `scan_token_expiry_warnings` в `token_cleanup.py` вызывается при открытии кабинета (`web.py`); он записывает по одному событию на пересечённый порог в `token_usage_logs`, а не посылает предупреждение в MCP. Его семантику и события этот этап не меняет. `ServiceBearerToken.expires_at` nullable; `None` означает бессрочный токен. `issue_service_bearer_token(..., expires_in_days=1)` реально создаёт короткоживущий bearer. В кабинете (`web_routes_account.py`) есть выпуск и отзыв токена, но нет операции продления существующего; текст не должен обещать кнопку продления. OAuth access token имеет короткий TTL и refresh flow (`oauth_service.py`), поэтому предупреждение о его истечении каждый день бессмысленно; OAuth и срок refresh token вне scope. Истёкший, отключённый и отозванный bearer не получает успешного ответа по обычному auth.

`ToolErrorTrackingMiddleware.on_call_tool` в `tool_error_tracking.py` получает общий FastMCP `ToolResult` после `call_next`, различает `is_error` и payload `success=false`. Он зарегистрирован после OAuth middleware в `server.py`. Все инструменты регистрируются через `_wrap_tool_with_depersonalization` (`tools/__init__.py`), где известен проверенный `RuntimeCredentials.bearer_token_id`; текущий `use_runtime_credentials` завершается внутри wrapper до возврата в middleware. Поэтому нельзя без проверки рассчитывать, что `get_current_runtime_credentials()` после `call_next` вернёт token id. Аннотации Report AI в `tools/report_ai.py` относятся только к job payload, не охватывают остальные инструменты. `activation_events` хранит события в БД, но локально ограничивает лишь частоту cleanup; `token_usage_logs` — аудит событий, а не атомарное право на одну выдачу. `token_usage_stats` имеет уникальную строку на bearer и атомарное обновление счётчика при auth; эту схему можно расширить для дедупликации без новой таблицы.

## Архитектурное решение

**Проблема и граница.** Нужно добавить уведомление один раз на токен за 24 часа при конкуренции нескольких воркеров и рестартах, не меняя предметные результаты и аутентификацию. Выбираем общий `on_call_tool` для добавления отдельного текстового MCP content block к успешному `ToolResult`; существующий `structured_content` и уже готовые content blocks не переписывать. Это охватывает обычные, baseline и Report AI инструменты без модификации каждого payload. На 376.2 проверить реальную модель `ToolResult` установленной FastMCP и сериализованный `tools/call`: новый блок должен быть виден агенту, включая ответы со структурированным содержимым. Если библиотека не поддерживает безопасное добавление блока, использовать её документированный конструктор нового `ToolResult` с сохранением `structured_content`, `is_error` и существующего `content`; несовместимую форму не выпускать.

**Передача идентичности.** Middleware открывает и в `finally` сбрасывает отдельный request-local слот для безопасной пары `(account_id, bearer_token_id)`; wrapper после успешного auth/проверки scope кладёт туда только эти числовые значения. Из raw Authorization, текста ответа и `get_current_runtime_credentials()` после `call_next` токен не восстанавливать. OAuth записывает в слот `None`; отсутствие проверенной пары означает отсутствие аннотации. Данные не переходят между запросами. Путь ошибок не аннотируется: auth, scope, validation, `is_error=true` и `success=false` сохраняют прежний контракт. Успешный ответ с пустыми данными всё равно получает предупреждение.

**Срок и частота.** После успешного `call_next` одна DB-транзакция читает активный bearer по `bearer_token_id` и `account_id`, проверяет `expires_at > now` и вычисляет `ceil((expires_at_utc-now_utc)/86400)` как в `token_cleanup.py`. Предупреждать только при `1 <= days <= 14`; фраза содержит фактический `N` с корректным склонением, а не номер пересечённого порога. В тестах границы 14/7/1, 15, 8, 2, 0, `None`, timezone-naive и aware; 7/1 — смена срочности текста после следующих разрешённых суток, не три уведомления за день. В `token_usage_stats` добавить nullable `expiry_notice_at`. При отсутствии строки применить имеющийся conflict-safe insert; затем условный атомарный `UPDATE ... WHERE bearer_token_id=:id AND (expiry_notice_at IS NULL OR expiry_notice_at <= :now-24h) RETURNING ...`, commit. Только победивший запрос добавляет блок. При продлении токена или смене его срока эта отметка остаётся за тем же токеном; новый токен имеет новую строку. Подготовка блока идёт до claim; если она не удалась, отметка не расходуется. Сбой чтения/claim/commit или аннотации — best effort: сохранить исходный ToolResult, записать лишь класс сбоя без токена/сырого ответа, не менять auth. Если claim состоялся, но транспорт не доставил ответ, повтор возможен через 24 часа: гарантия относится к подготовленным ответам, доставка человеку не наблюдаема.

**Варианты.** Process-local cache дешевле, но дублирует уведомление между воркерами и после рестарта. Поиск последнего `token_usage_logs` без уникального/атомарного claim допускает гонку; новый event type и журнал не нужны для выдачи. Новая таблица дала бы строгую гарантию, но добавила бы миграцию, очистку и дублирование уже уникальной строки `token_usage_stats`. Выбранное nullable поле и условный update используют существующий per-token агрегат; проверка и claim должны быть в одной транзакции, с повторной проверкой статуса и срока внутри неё. Индекс PK/unique по bearer уже есть; дополнительный index не нужен. На каждый успешный bearer-вызов — одно точечное чтение, при близком сроке — один условный update, без обращения к Vetmanager API. Необязательная операция от получения соединения из пула до commit/rollback ограничена одним end-to-end deadline 500 мс (например, `asyncio.timeout` снаружи session context, без сброса бюджета на отдельных SQL); в PostgreSQL транзакционно ограничить ожидание блокировки 250 мс и SQL statement 400 мс, чтобы занятый `token_usage_stats` не задержал успешный ответ до клиентского таймаута. При таймауте/DB-недоступности откатить необязательную транзакцию, ответ оставить прежним, уведомление временно пропустить; внешнюю отмену tools/call не подавлять. Для SQLite в тестах проверить ожидание блокировки и отмену через deadline, не менять глобальный busy timeout соединения.

**Инварианты и откат.** Не менять `token_access_registry`, scopes, auth checks, исходные payload и `token_cleanup` threshold telemetry. Ни в блоке, ни в диагностике нет raw bearer, `token_hash`, token id/prefix, клинических данных или URL с ключом. Откат кода отключает аннотацию; nullable колонка остаётся совместимой со старым кодом, затем может быть снята отдельной миграцией. Architecture Critique обязателен: изменяется общий MCP-ответ и граница middleware↔wrapper↔storage. В 376.1 объединить его с Astra PRD-review: проверить ownership, гонки, приватность, совместимость FastMCP, нагрузку, rollback, критерии приёмки. Второй сильный reviewer — супервизор Kimi после этого хода по прямому указанию владельца; до него 376.2 не начинать.

## Приёмка и декомпозиция

Каждая подзадача ≤2 ч и ≤150 строк изменения. Сторож принимается только с показанным красным прогоном после удаления охраняемого условия; поломку указать в self-attestation. Для каждого изменённого инструмента нужен live `tools/call` с HTTP-кодом и очищенным телом. Миграции проверить upgrade/downgrade. В 376.1 инструментов и тестов не менять, поэтому red/live — для 376.2.
