# Этап 316. Жалоба на ответ агента из кабинета

## Цель

Дать владельцу аккаунта постоянный, независимый от поведения модели способ
передать жалобу на ответ агента в общую очередь `agent_feedback_reports`.
Жалоба сохраняется с `source=human`, принадлежит текущему аккаунту и не
раскрывает своё содержимое в логах или Sentry.

## Границы

- Только `GET /account` и новый CSRF-защищённый `POST` внутри кабинета.
- Три обязательных ограниченных по длине поля: что спросили, что получили,
  чего ждали. Их значения сохраняются в `details` как введены человеком;
  triage отображает их только после существующей маскировки.
- Категория и severity фиксированы безопасными значениями по умолчанию;
  `account_id` берётся только из signed session.
- Частота ограничивается на аккаунт существующим feedback rate limit.
  Для source=human это отдельное per-account ведро: всплеск model/auto не
  может закрыть человеку канал жалобы.
- Контакт владельца — необязательная строка из `FEEDBACK_CONTACT_EMAIL`.
  При пустом значении строка не рендерится. Адрес не попадает в код, шаблоны,
  README или `.env.example`; в compose переменная передаётся как
  `${FEEDBACK_CONTACT_EMAIL:-}`. Читатель принимает только валидный email,
  а шаблон всё равно HTML-экранирует значение.
- В production значение задаётся только в `/opt/vetmanager-mcp/.env` перед
  выкатом; production-код и compose-файлы вручную не меняются.

## Не делаем

- Не выводим форму на лендинг и не создаём отдельный публичный endpoint.
- Не меняем реестр фильтров, `delete_invoice*` и правила деперсонализации.
- Не пересылаем текст жалобы в логи, Sentry, метрики или внешний API.
- Не добавляем новый тип очереди и не меняем семантику model/auto feedback.

## Декомпозиция

1. Добавить в feedback service отдельный account-web writer: он применяет
   rate limit, пишет `source=human`, текущий `account_id`, default category /
   severity и объединённый `details` без sanitizer при хранении. Обновить
   triage: summary/details существующих и новых отчётов перед выводом проходят
   его текущий маскирующий путь. Единственное сырое хранилище — БД для
   авторизованного операционного triage; новых reader/export consumer-каналов
   этап не создаёт. Инвентаризация подтверждает, что product metrics читает
   только aggregate/status/source, а seed/retention не печатают details. ≤150 LOC.
2. Добавить форму и POST route: session/CSRF как у соседних форм, валидация
   обязательности и длины до записи, нейтральные сообщения без echo текста.
   В шаблон передать только безопасный success/error и необязательный contact
   email из runtime helper. `before_send` удаляет request data и stack vars
   для этого POST до передачи события в Sentry; это покрыто тестом. ≤150 LOC.
3. Пробросить env в runtime/test compose, описать пустую переменную в README
   и `.env.example`; добавить guard, который запрещает личные почтовые домены
   в tracked files, кроме example-доменов. Сам адрес не является эталоном теста.
   ≤150 LOC.
4. Тесты: CSRF, unauthenticated redirect, лимиты/длина, account/source/details,
   маскирующий triage, пустой/заданный env и отсутствие утечки. Сторож перед
   приёмкой ломается изменением source либо удалением CSRF из формы.

## Приёмка

- Авторизованный пользователь получает форму с тремя полями; POST с валидным
  CSRF создаёт human-report для его account, без текста жалобы в logs/Sentry.
- Невалидный CSRF не создаёт запись; превышение лимита и слишком длинные поля
  получают безопасную ошибку.
- `FEEDBACK_CONTACT_EMAIL` пустой — контакта нет; заданный — contact виден
  только в `/account`.
- Живой стендовый POST создаёт запись, которую `triage ... recent --source
  human` показывает замаскированно. После production rollout `/account`
  отдаёт 200 с блоком; при наличии тестовой session создаётся и закрывается
  одна synthetic запись.

## Простота

Используются существующие session, CSRF, account dashboard, feedback storage,
rate limit и triage sanitizer. Единственная новая доменная функция нужна из-за
явного требования хранить введённый текст как есть: общий writer этапа 315
преднамеренно редактирует текст до записи и для этой формы не подходит.
