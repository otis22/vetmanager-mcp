# Этап 333. Скрипт применения 332 не рассчитан на KI-45 без отпечатка

## Цель

Исправить supervisor-скрипт этапа 332 так, чтобы он применял и полностью
откатывал конфигурацию как при наличии отпечатка у KI-45, так и при его
отсутствии, не ослабляя fail-closed проверку действительно неожиданного
состояния.

## Проверенные факты и ограничения

- Первый production-запуск 19.09.2026 13:28 сохранил обязательный before-state
  и завершился до мутаций с exit 65: KI-45 не имела отпечатка. Снимок
  `/home/otis/.local/share/vetmanager-mcp-review-evidence/stage-332/ki45-before.json`
  имеет SHA-256 `0eb9439ac0fc35b36ed71c9fe4a81ad3c78c5792e80b47783b2c4a4f28b4d182`
  и остаётся только для чтения.
- KI-45 — seed-запись `[seed:report-export-not-available] Report cannot be
  exported over REST`, `related_tool=null`, `error_fingerprint_hash=null`.
  Репорт #80 был связан с ней текстовым правилом, а не exact fingerprint;
  предпосылка PRD 332 о переносе отпечатка была ошибочной.
- Production before-state содержит тексты `getting report export file failed`
  и `not rest-exportable`; постоянный HTTP 401 должен быть исключён из KI-45.
  Его playbook ведёт через `get_report_ai_job` к `create_report_ai_job`.
- `agent_feedback_service._ordered_known_issue_candidates` сначала допускает
  запись только по совпадающему `related_tool`, по `related_tool IS NULL` либо
  по exact fingerprint. Поэтому KI-45 должна сохранить `related_tool=null`:
  один скаляр не может представить оба инструмента, а точное ограничение уже
  находится в `match_rules_json` как `related_tool in [...]`.
- `promote 80` создаёт отдельную 401-запись с отпечатком репорта #80.
  Существующий `move-fingerprint` атомарен, идемпотентен после успешного
  переноса и отклоняет разные отпечатки без частичной записи.
- Агент не обращается к production и не меняет production DB/`known_issues`.
  Применение выполняет только супервизор после успешного Deploy Prod.
- Главный PRD требует понятной обработки upstream-ошибок; technical
  requirements требуют воспроизводимый production rollout/rollback и не
  допускают секреты в артефактах.

## Scope и декомпозиция

### 333.1 — test-first контракты миграции (≤150 LOC)

1. Сторож скрипта моделирует before-state с отпечатком и без него: в первом
   случае прямой и обратный `move-fingerprint` обязательны, во втором оба
   вызова пропускаются, а существующий before-state не перезаписывается.
2. Отдельный сторож доказывает отказ до `promote` и любых последующих операций,
   когда fingerprint KI-45 отличается от fingerprint репорта #80; ещё один
   проверяет отказ первого apply при live drift относительно before-state.
3. CLI DB-тесты сохраняют контракт двух состояний: допустимый перенос и
   идемпотентный target; отсутствие source без разрешающего флага остаётся
   ошибкой. Добавить только read-only `show-feedback-fingerprint 80`, который
   печатает JSON с report ID, текущей связью и fingerprint, но не текст
   репорта: он нужен для preflight до первой записи.

### 333.2 — минимальная правка скрипта и фикстур (≤150 LOC)

1. Читать `error_fingerprint_hash` из сохранённого before-state один раз.
   Если это валидный отпечаток, выполнять существующий `move-fingerprint`
   с `--expected-fingerprint`; если значение `null`, явно сообщать о пропуске.
   Любой иной тип/формат before-state остаётся fail-closed.
2. На каждом apply/rollback `show-feedback-fingerprint 80` получает точный
   ожидаемый fingerprint. В present-ветке он обязан совпасть со snapshot; в
   null-ветке обязан быть валидной непустой строкой. До первого `promote`,
   когда сохранённого target ID ещё нет, дополнительно прочитать live KI-45 и
   потребовать совпадения с before-state ровно по полям `id`, `status`, `title`,
   `related_tool`, `error_fingerprint_hash`, `match_rules_json` и
   `agent_playbook_json`; так snapshot первого неуспешного запуска принимается,
   но более поздний drift не перетирается.
3. После `promote`/чтения сохранённого ID и до любых изменений KI-45 прочитать
   target через `show-known-issue-config`. В обеих ветках проверить ID, title,
   точный literal `Report export file download is unauthorized`,
   `related_tool=get_report_export_download`. В null-ветке target fingerprint
   всегда равен #80. В present-ветке допустимы только пары live KI-45/target:
   `#80/#80` (после promote до forward move), `#80/null` (после rollback) и
   `null/#80` (forward move уже завершён); остальные пары отклоняются. Такой же
   identity/state preflight обязателен перед rollback, а окончательную парность
   атомарно проверяет CLI.
4. Apply после target preflight переносит fingerprint только в present-ветке,
   ставит rules/playbook KI-45, затем идемпотентно переводит target в
   `workaround_available` и вызывает `link TARGET 80`. Поэтому повтор после
   частичного apply и новый apply после завершённого rollback используют тот
   же сохранённый ID, не создавая вторую запись.
5. Rollback следует той же ветке: обратный перенос только если отпечаток был в
   before-state, затем `restore-known-issue-config` полностью возвращает
   status/title/related_tool/fingerprint/rules/playbook. Для `null` target
   сохраняет отпечаток #80 до деактивации отдельной записи, а KI-45 после
   restore остаётся без отпечатка, как до миграции. После restore скрипт явно
   вызывает `mark TARGET wontfix` и `link 45 80`; эти операции идемпотентны.
6. Расширить KI-45 rules точным старым маркером `not rest-exportable`, сохранив
   общий старый маркер `getting report export file failed` и исключение
   `getting report export file failed http 401`. В playbook сохранить путь
   `get_report_ai_job` → `create_report_ai_job` для permanent REST refusal.
7. Не вызывать `set-related-tool`: `null` нужен для предварительного отбора
   обоих инструментов; правила сами ограничивают область совпадения.

### 333.3 — проверки и передача супервизору (≤2 ч)

1. Показать красными новые сторожа, затем зелёными focused tests.
2. Пройти ShellCheck v0.9.0, `bash -n`, roadmap structure, полный mock suite и

3. Живо выполнить CLI на локальной контейнерной БД для обеих веток и rollback,
   без production; сохранить код и тело ответа.
4. После audit/commit пройти Spark committed-diff и Opus committed-diff review,
   push, Tests и Deploy Prod. Затем зафиксировать ошибочную предпосылку 332,
   production before-state и supervisor-only apply-команду; закрыть 333, не
   меняя `supervisor_pending` у 332, архивировать окно и выполнить закрывающий
   коммит `Stage 333: record production completion`.

## Архитектурное решение

Проблема — источник миграции имеет два допустимых production-состояния, но
скрипт ошибочно считал допустимым только одно. Storage schema, matcher и
публичный MCP-контракт менять не требуется.

Рассмотрены варианты:

1. `move-fingerprint --allow-missing-source`: переносит знание конкретной
   миграции в общий CLI, расширяет опасную DB-команду и требует определить
   неоднозначную семантику target для всех будущих вызовов.
2. Отдельная CLI-команда миграции 332: дублирует orchestration и создаёт
   одноразовую поверхность.
3. Ветка в supervisor-скрипте по immutable before-state плюс одна read-only
   CLI-команда для fingerprint репорта: выбранный вариант. До первой записи
   shell сравнивает snapshot с live KI-45 и fingerprint #80; после `promote`
   связывает сохранённый target с тем же fingerprint. Пишущий CLI остаётся
   строгим: когда source существовал, он атомарно переносит отпечаток. Когда
   source был `null`, перенос семантически отсутствует.

Инварианты: before-state никогда не перезаписывается; `null` и корректная
строка отпечатка — единственные допустимые состояния; первый apply проверяет
live KI-45 против snapshot; fingerprint #80 известен read-only до `promote`;
target до KI-45 writes проверен как отдельная 401-проблема #80; допустимая
пара source/target принадлежит явной state machine; mismatch исходного
snapshot с #80 падает до первой DB-записи; при `null` KI-45 не получает отпечаток
ни при apply, ни после rollback; полный restore возвращает все поля snapshot;
правила KI-45 узнают оба исторических текста, но не постоянный 401; отдельная
401-запись получает отпечаток #80; production доступ остаётся supervisor-only.

Rollback/fallback: сохранённый snapshot — единственный источник rollback.
Ветка выбирается по его исходному fingerprint: обратный перенос выполняется
только для исходно непустого значения, затем CLI restore возвращает snapshot,
`mark TARGET wontfix` деактивирует отдельную запись, а `link 45 80` явно
возвращает связь #80 к KI-45. Сохранённый target ID остаётся для безопасного
повторного rollback и последующего re-apply; re-apply явно реактивирует и
перелинковывает ту же запись. Если snapshot невалиден, live KI-45 дрейфовала
до первого apply, ID отдельной записи неизвестен или CLI видит неожиданные
отпечатки, скрипт останавливается и не угадывает состояние.

Несколько CLI-команд не образуют распределённую транзакцию. Гарантия этапа —
каждый завершённый шаг можно безопасно повторить, сохранённый ID переживает
повтор, а supervisor может явно запустить rollback после любого прерывания.
Автоматический trap с компенсирующими production-записями не применяется: он
скрыл бы исходный сбой и сам мог бы оборваться между теми же CLI-коммитами.

Architecture Critique требуется, потому что меняется production migration
behavior. Совмещается с первым Opus PRD-review: prompt проверяет ownership
ветки, fail-closed границы, идемпотентность и полноту rollback.

## Acceptance criteria

- Красные сторожа отдельно доказаны для source fingerprint present, absent и
  mismatch; в attestation указано, чем каждый ломался.
- Существующий `ki45-before.json` принимается как before-state и не
  перезаписывается; live-state до первого apply обязан ему соответствовать;
  apply в null-ветке проходит без `move-fingerprint`.
- В present-ветке прямой/обратный перенос остаётся; mismatch source/target
  завершается non-zero до `promote` и любой DB-записи.
- Исполняемый fake-SSH harness проверяет порядок удалённых команд и
  моделируемое состояние для apply/rollback/retry обеих веток, immutable
  before-state и отсутствие KI-45 writes после preflight mismatch.
- Rollback в обеих ветках возвращает snapshot целиком; в null-ветке KI-45 не
  приобретает fingerprint.
- KI-45 rules включают `not rest-exportable` и `getting report export file
  failed`, исключают постоянный HTTP 401; playbook сохраняет Report AI путь.
- `related_tool` KI-45 остаётся `null`, `set-related-tool` не вызывается.
- Focused, ShellCheck/Bash, mock, real и локальная live CLI проверки зелёные;
  review evidence и suite exit-файлы лежат в `stage-333`.
- Tests и Deploy Prod для code commit зелёные; после закрывающего коммита
  финальный CI зелёный. Этап 333 — `done`, этап 332 — `supervisor_pending`.

## Оценка простоты

Выбран один shell-branch вокруг существующей строгой пишущей CLI-команды и
одна узкая read-only команда, не раскрывающая текст отчёта. Новый write-флаг,
миграционный класс и matcher-слой не нужны. Дополнительная read-only поверхность
необходима, чтобы mismatch был доказан до `promote`, а target был связан с
точным fingerprint #80, а не только с форматом хеша.

## Review findings

- Spark PRD 1 (read-only): невалиден, sandbox/runtime отказ до чтения файлов,
  `files_read=[]`; review-слот не расходует.
- Spark PRD 2 (danger-full-access review-only fallback): приняты high о
  mismatch после преждевременных writes и high о проверке target ID в
  null-ветке; принят medium о необходимости executable fake-SSH harness.
  Отклонён high о distributed transaction/compensating trap: отдельные CLI
  commit остаются существующей операционной границей, а этап гарантирует
  идемпотентный повтор и явный rollback после прерывания.
- Opus Architecture Critique + PRD review 1/2: приняты high о невозможном
  rollback после post-promote mismatch и три medium — live drift snapshot,
  явные link/re-apply semantics и точная привязка target к fingerprint #80.
  Добавлена read-only команда fingerprint preflight до `promote`, полный
  live/target preflight и явные идемпотентные `mark`/`link` переходы.
- Opus PRD review 2/2: приняты high о re-apply present-ветки и два medium —
  источник fingerprint #80 на retry/rollback и точный набор snapshot-полей.
  Read-only report preflight выполняется на каждом запуске, present state
  machine допускает только три ожидаемые пары, snapshot сравнивает ровно поля
  `show/restore-known-issue-config`. Бюджет PRD-review 2/2 исчерпан.
