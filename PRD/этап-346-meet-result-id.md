# Этап 346. Совместимость создания медкарты по `meet_result_id`

## Цель и факты

`create_medical_card` объявляет `meet_result_id` необязательным с default `0`, но при нуле удаляет ключ из POST. Тестовый контур ответил HTTP 400 `meet_result_id is required` без ключа; активное значение принял. OpenAPI v6 показывает `meet_result_id` как non-null integer с default `0`. Справочник сущностей ошибочно помечает поле nullable. Внешнее поведение тестового API требует само поле. Предрелизный вызов с явным нулём вернул HTTP 201; повторное чтение сохранило `meet_result_id=0` (тестовая карта 918, дата 24.09.2026).

Источники публикуемого контракта: `artifacts/vetmanager_openapi_v6.json` (схема `medicalCards`), `artifacts/api_entity_reference-ru.md` §2.21 и наблюдаемые ответы тестового API. Живой тест нуля на выделенном тестовом контуре обязателен до выпуска.

Главный PRD §4 и технические требования §3 требуют точных входов и ошибок MCP; задача касается только POST медкарты. Тестовые контуры различны: живой прогон выполняется на контуре из `.env`, а не на bearer-контуре.

## Архитектурное решение

Проблема: наш условный payload превращает допустимый пользовательский default `0` в отсутствующее обязательное для части версий поле. Варианты: (A) сделать параметр обязательным — заставляет агента выбирать формальный ноль, ломает существующих клиентов; (B) всегда передавать `meet_result_id` с default `0` — сохраняет MCP-схему и удовлетворяет обеим версиям; (C) подбирать активный результат автоматически — меняет клинический смысл записи. Выбран B. Значение >0 остаётся выбором вызывающего агента по справочнику клиники. Ноль передаётся явно, без поиска и без подмены клинических данных.

Инварианты: ключ есть в каждом POST; ноль не превращается в ID справочника; положительный ID передаётся без изменений; существующее поведение отрицательного `int` не меняется этим этапом (отдельная валидация вне scope); другие поля и права остаются прежними. Если тестовый API отвергнет явный `0` или сохранит его как реальный клинический результат, этап останавливается в `supervisor_pending` до уточнения контракта. Триггер отката после выпуска: реальный ответ API на явный `0` с отказом именно по `meet_result_id` либо подтверждённый рост таких отказов. Откат обычным revert, после фокусного теста и CI; он вернёт прежний отказ для пропущенного поля на строгой версии API, поэтому создание карты без результата временно будет недоступно на такой версии. Автоматический выбор результата запрещён.

Architecture Critique требуется: меняется публичный MCP контракт и production-поведение. Сильный PRD review одновременно оценивает архитектуру, полноту критериев, тесты и откат.

## Декомпозиция

1. Сверить внешний контракт, версии API и живую реакцию на отсутствие/ноль (≤2 ч).
2. Красный сторож исходящего payload и схемы, затем правка `create_medical_card` и справочника (≤150 строк).
3. Живой вызов изменённого инструмента, фокусные тесты, аудит, полный suite, review, commit, push и CI (этап выпуска; кодовые изменения ≤150 строк).

## Критерии приёмки

- Без аргумента и с `meet_result_id=0` инструмент посылает `0`; положительный и отрицательный `int` сохраняются как сейчас. Иная валидация не вводится скрыто.
- Схема и описание дают агенту понять, что `0` означает «результат не указан», а при указании результата нужен код из `admission_result` клиники.
- Красный сторож падает, если убрать отправку нуля; живой вызов изменённого инструмента на выделенном тестовом контуре из `.env` возвращает код и тело, записанные в `AssumptionLog.md`. Для проверки используется существующий тестовый пациент с владельцем, врачом и клиникой и явный маркер в описании; чужие записи не меняются. Созданную тестовую карту читаем обратно и проверяем сохранённый `meet_result_id=0`; её последующее удаление возможно лишь после отдельной проверки безопасного способа, поэтому разовый маркер остаётся на тестовом контуре.
- Решение о `known_issue` записано: если исправление полностью снимает отказ, отдельный issue не нужен; если нет, фиксируется доказанный остаточный сценарий.
- Все обязательные проверки, сильные гейты, push и штатные CI/Deploy Prod успешны.
