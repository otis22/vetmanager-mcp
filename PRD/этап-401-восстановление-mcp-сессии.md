# Этап 401. Самовосстановление MCP-клиента после потерянной сессии

## Цель и проверенные факты

На проде 16.10.2026 за семь суток наблюдалось 556 `session_not_found` и 177 `missing_session`; один клиент продолжал повторять запросы со старой сессией. Документ этапа 386 не виден агенту в момент отказа. FastMCP отдаёт HTTP 404 и JSON-RPC ошибку с сообщением `Session not found`; тем же ответом скрывает несовпадение владельца сессии. Существующий `MCPTransportObservationMiddleware` читает не более 4096 байт тела отказа и публикует bounded reason в общем Redis. Streamable HTTP `/mcp` закреплён техническими требованиями; OpenAPI Ветменеджера к этому отказу не относится.

## Требования и приёмка

- Для точного HTTP 404 JSON-RPC `Session not found` добавить к `error.message` короткий общий совет: закрыть прежнюю сессию и повторить `initialize` без старого `Mcp-Session-Id`. Не раскрывать адреса, токены, ID сессий и инфраструктуру. HTTP status, JSON-RPC `code`, `id` и остальные поля неизменны. Классификация 386 сохраняется.
- Считать повторные 404 от того же клиента при повторе в течение 24 часов после последнего отказа. В `/metrics` публиковать только агрегатный counter без client label. Идентификатор предъявленного подключения — HMAC-SHA256 от bearer-ключа с серверным `WEB_SESSION_SECRET`; в Redis хранить только digest в одном из 4096 фиксированных слотов и TTL 24 часа. Номер слота вычисляется из digest; несовпадение digest в занятом слоте пропускается без записи и без ложного повтора. Сырой ключ используется только в памяти запроса для вычисления HMAC, не логируется и не попадает в метки. Не использовать session ID, IP и тело запроса. При отсутствии синтаксически корректного bearer-заголовка разумной длины или секрета ответ работает, повторы не атрибутируются. Один ключ может использоваться несколькими клиентами, поэтому это приближение по подключению.
- Первый отказ создаёт TTL-маркер; следующий отказ того же адреса увеличивает агрегат и продлевает TTL. Счётчик не хранит количество для отдельного клиента. Проверить два клиента, повтор одного, общий снимок Redis, истечение TTL, безопасный ответ, нецелевые 404/400/406, SSE и ошибку Redis. Метрика оценивает повторение отказов, но не доказывает, что агент прочитал совет или переподключился; NAT может объединить клиентов.
- Живой стенд: до запуска выбрать `.env` контур `TEST_DOMAIN`/`TEST_API_KEY` для создания bearer-связи и изолированного MCP сервера. Запрос с несуществующим ID → 404, точный безопасный ответ и прирост повторов после второго запроса; новый initialize → 200. Ни адрес, ни токен, ни session ID в артефакт не писать. Прямой HTTP вызов проверяет доступность подсказки в ответе и метрику. Установленный Python MCP client при POST 404 заменяет тело собственной ошибкой `Session terminated`; для него инструкция недоступна. Это ограничение подтвердить тестом/сверкой client-path и явно указать в выпуске: этап помогает только клиентам, показывающим тело HTTP отказа, и не гарантирует автоматический reconnect.

## Архитектурное решение

**Проблема:** текст FastMCP не содержит действия для клиента; существующий общий счётчик не показывает, продолжает ли тот же клиент отправлять запросы после подсказки.

**Варианты:** патч FastMCP handler связывает нас с внутренним API библиотеки; отдельный endpoint восстановления агент не прочитает; ASGI middleware видит сформированный ответ и позволяет точечно заменить JSON-RPC сообщение. Выбран middleware этапа 386: только точная сигнатура 404, без разбора request body. Для целевого 404 задержать `response.start`, собрать не более 4096 байт до последнего `response.body`, переписать только некодированный JSON и пересчитать `Content-Length` при наличии. Многокусковое тело допустимо. При сжатом, некорректном или чрезмерном теле исходные start/body выпускаются без изменений. Для 200/SSE и иных статусов start/body передаются сразу. Агрегат повторов вести в отдельном Redis ключе, а HMAC-маркеры — с TTL, чтобы старые reader при rolling deploy не увидели неизвестную метрику в `COUNTERS_KEY`.

**Ограничения:** 404 может означать несовпадение владельца; совет не утверждает причину и не предлагает повторять пишущий вызов. Серверный `WEB_SESSION_SECRET` уже обязателен для web-сессий; при отсутствии идентичности/секрета повтор не считается. Общий bearer-ключ может объединять несколько клиентских процессов; заголовок на уровне middleware не проверяется по БД, поэтому произвольные токены могут увеличивать метрику. Это диагностический агрегат по предъявленному ключу, а не доказательство аутентифицированной личности или достижения восстановления. Максимальную длину ключа ограничить 512 байт; TTL ограничивает срок хранения маркеров, а число слотов ограничивает их максимум до 4096 ключей. Коллизия или заполнение слотов могут недосчитать повторы; это диагностическая метрика без гарантии полноты. Новая реализация не записывает сырые идентификаторы в собственные ключи, метрики и логи; существующие access log и логи MCP вне scope этого этапа. Redis-запись асинхронна для ответа: `SET NX EX` делает маркер уникальным между slot, каждый повтор продлевает TTL и увеличивает общий counter. Очередь доставки best-effort; переполнение или ошибка Redis могут недосчитать повторы, а отдельные операции маркера и counter не образуют одну транзакцию. Ответ не меняется. Не добавлять client hash в Prometheus labels.

**Инварианты:** прежние HTTP статусы и JSON-RPC коды, bounded reasons этапа 386, потоковая отдача SSE и отсутствие ПД/секретов в новых ключах, метриках и публичных артефактах. Откат: старая версия игнорирует отдельные ключи; TTL-маркеры истекут, агрегат можно оставить до штатной очистки. При rolling deploy новая серия появляется только на обновлённых slot; оценивать агрегат после обновления всех slot и сверить одинаковый `/metrics` на каждом. Если FastMCP изменит сигнатуру, новый текст и повторная метрика не применяются, исходный ответ проходит без изменений.

## Декомпозиция

1. PRD, архитектурный и PRD-гейт, красные сторожа на текст, совместимость и повторы — до 2 часов, до 150 строк тестов.
2. Точечная правка middleware и общий Redis counter с TTL — до 2 часов, до 150 строк кода на подзадачу.
3. Изолированный живой вызов, аудит, committed diff-гейт, один полный mock и real suite по финальному SHA, выпуск и CI — до 2 часов на подзадачу.

## Оценка простоты

Используется уже имеющаяся точка наблюдения; отдельный сервис, БД и новые клиентские протоколы не требуются. Агрегат имеет одну серию, не более 4096 маркеров автоматически исчезают через 24 часа.
