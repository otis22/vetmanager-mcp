# Этап 267. Сборка образа зависела от сети, которой у прода нет

## Оговорка о порядке

**PRD написан после реализации, 28.08.2026.** Работа шла как разблокировка:
прод не принимал выкатку, изменения этапа 265.6 в бою не стояли, и решение
принималось на месте. Гейты добираются задним числом, и это записано здесь
честно, а не подано как нормальный ход: PRD-review сторонней моделью до кода
не проводился, ревью на committed diff проводится сейчас.

## Цель

Убрать из сборки образа зависимость от сети, которой у прод-машины нет, и
сделать это так, чтобы отказ этой сети больше не мог остановить выкатку.

## Контекст и проверенные факты

**Что случилось.** `Deploy Prod` для `4298c17` упал дважды подряд на
`apt-get install curl` (Dockerfile, строка 16). Повторный запуск не помог.

**Почему обманулась первая диагностика.** С прод-VDS
`curl http://deb.debian.org/` отдаёт **200**, то есть «сеть работает». Это
ложный сигнал: разделение по семействам адресов показывает `curl -4` — таймаут,
`curl -6` — 200 с `2a04:4e42::644`. Хост проходит только по IPv6. У контейнеров
IPv6 нет, поэтому `apt` уходит на IPv4-адреса Fastly и висит до таймаута.

**Почему не всплывало раньше.** Слой с `apt` брался из кеша сборки. Как только
кеш слоя обновился, зависимость от чужой сети стала блокирующей — она была там
всегда, просто не исполнялась.

**Что проверено на месте.** `ip_forward=1`, NAT для docker0 есть, FORWARD
пропускает docker0; живой контейнер сервиса здоров и ходит в Ветменеджер. То
есть выход в интернет у контейнеров работает — не работает конкретно маршрут
до Fastly по IPv4.

**Зачем в образе был `curl`.** Ровно для `HEALTHCHECK`. Больше нигде в образе
он не используется — кроме, как выяснилось позже, `post_deploy_smoke_checks.sh`
(см. «Что пошло не так»).

## Решение

Убрать зависимость, а не чинить чужой маршрут. В образе уже есть Python,
который делает тот же запрос. Шаг `apt` удалён из стадии `base`, а выкатка
собирает только `--target production` (`deploy_server.sh:207`) — значит путь,
который идёт через прод-VDS, к пакетным репозиториям не обращается.

**Граница, которую нельзя размывать.** Тестовая стадия образа **по-прежнему
тянет пакеты**: `python -m playwright install --with-deps chromium` ставит
системные библиотеки для chromium через apt. Собирается она на раннерах GitHub
и на машинах разработки, где IPv4 до Fastly работает; на прод-VDS она не
собирается никогда. Ревью проверило это сборкой `--target test --no-cache`.

## Декомпозиция

1. `HEALTHCHECK` на `urllib` вместо `curl`; шаг `apt-get` убран. (~10 строк)
2. `post_deploy_smoke_checks.sh` — запрос через Python; поле диагностики
   переименовано в `request_exit`, потому что оно больше не про `curl`. (~45)
3. Тест ярлыка диагностики обновлён вместе с полем.
4. Сохранить две черты `curl`, потерянные при переводе: дедлайн на весь
   запрос (`--max-time`) и отказ следовать редиректам (вызов был без `-L`).
   Обе закреплены тестами и приняты красными. (~35)

## Acceptance

- Сборка `--target production` — та, что идёт на проде, — не обращается к
  пакетным репозиториям. Для тестовой стадии это не обещается.
- Обе ветки healthcheck проверены в собранном образе: 0 при ответе 200,
  ненулевой код, когда сервис не отвечает.
- Полный прогон зелёный в образе, где `command -v curl` пусто.
- Ответ `302` на `/healthz`, ведущий на здоровую страницу, роняет проверку.
- Тело, отдаваемое по байту раз в 0.6 с, обрывается по дедлайну, а не через
  десять секунд.
- `Deploy Prod` проходит на самом VDS, контейнер поднимается `healthy`.

## Что пошло не так при реализации

Поиск `curl` был сделан по `Dockerfile` и `docker-compose*.yml` и пропустил
`scripts/post_deploy_smoke_checks.sh`, который **гоняется внутри того же
образа**. Локально это не всплыло: образ собирался из кеша, где `curl` ещё
лежал. Поймал чистый прогон в CI.

Рядом вскрылось то, ради чего написано правило §4.0: тест
`test_post_deploy_smoke_checks_fail_with_attempt_context` оставался зелёным на
сломанном скрипте — он ждёт отказа, а `curl: command not found` тоже отказ.

## Оценка простоты

- **Читаемость.** Убрана целая стадия сборки; ничего не добавлено.
- **Поддерживаемость.** Одна реализация запроса на хост и на контейнер вместо
  двух инструментов.
- **Отклонённый вариант.** Включить IPv6 в докере — NAT66 и правки демона ради
  одной команды `apt`, причём зависимость от чужой сети остаётся.
- **Отклонённый вариант.** Подменить зеркало apt на российское — сборка на
  раннерах GitHub пошла бы через то же зеркало, то есть проблему переносим,
  а не убираем.

## Вне рамок

- Чинить маршрут до Fastly по IPv4 — это сеть провайдера, не наш слой.
- Остальные пользователи `curl` (`deploy_server.sh`, workflow) — они работают
  на хосте, где `curl` есть, и в образ не попадают.
