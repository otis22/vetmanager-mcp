# Этап 322. Безопасная массовая переоценка

## Цель

Не допускать молчаливо неполной выборки цен и сделать частичный результат
массовой переоценки безопасно восстанавливаемым: вызывающий должен знать, какие
строки подтверждённо записаны, какая строка завершилась ошибкой, какие строки
не были затронуты и какими абсолютными ценами можно закончить операцию без
повторного наложения процента.

Finding F4/F5 из супер-ревью 16.09.2026 рассматривается как указатель. Ниже он
проверен по исходникам Ветменеджера и живому контуру до изменения MCP-кода.

## Проверенные факты

### F5: штатный list всегда формирует `totalCount`, но MCP fail-open

`rest/protected/controllers/GoodSaleParamController.php:3-5` не переопределяет
list и дословно содержит только:

```php
class GoodSaleParamController extends ApiController {
}
```

Значит список идёт через базовый
`rest/protected/extensions/restfullyii/components/ERestController.php:497-539`.
Там `doRestList()` вызывает `count()`, а `outputHelper()` безусловно кладёт
переданное число в `data.totalCount`:

```php
'data' => ['totalCount' => $totalCount, $model => ...]
```

OpenAPI подтверждает только `GET /rest/api/goodSaleParam` и
`PUT /rest/api/goodSaleParam/{ID}`; отдельной формы list без счётчика нет.

Живой контур 16.09.2026, без адреса, ключа и строк клиники:

- `GET /rest/api/goodSaleParam?limit=1&offset=0` → HTTP 200,
  `{"success":true,"message":"Records Retrieved Successfully","data":{"totalCount":486,"goodSaleParam":["<1 row>"]}}`;
- тот же GET с `limit=0` → HTTP 200, числовой `totalCount=486`, пустой массив;
- тот же GET со смещением за концом → HTTP 200, числовой
  `totalCount=486`, пустой массив.

Спровоцировать штатный ответ без `totalCount` параметрами list не удалось и
исходники такого режима не показывают. Поэтому F5 — не доказанный обычный
ответ ВМ, а подтверждённый fail-open на нарушении контракта: текущий `_all_rows`
заменяет отсутствующее/неразбираемое значение на `len(collected)` и после
первой полной страницы возвращает неполную выборку как полную.

Решение 322.2: только локальный `_all_rows` переоценки требует неотрицательный
JSON integer `totalCount` на каждой странице и до любой записи выдаёт явную
reportable contract error. Строки, float, bool и отсутствие поля не считаются
числом. Первое число фиксируется: его изменение между страницами, пустая или
короткая страница до набора объявленного количества, batch больше запрошенного
limit, повтор `sale_param_id` и накопление больше `totalCount` также дают отказ. Общий
`paginate_all` и обработка заниженного, но внутренне согласованного счётчика
относятся к этапу 323 и здесь не меняются.

### F4: атомарной массовой операции цен в доступном REST нет

`GoodSaleParamController` не содержит custom action; базовый
`ERestController.php:564-577` обновляет ровно один загруженный id:

```php
$model = $this->loadOneModel($id);
$this->saveModel($model, $data);
```

Поиск custom actions цен и переоценки в REST-контроллерах нашёл только
`GoodController::doCustomRestPostSimpleUpdateProduct()`
(`GoodController.php:1356-1459`). Он действительно обёрнут в транзакцию:

```php
NDatabase::startTransaction();
...
NDatabase::commitTransaction();
```

но контракт принимает один `product_data.id`, один `sale_param_id` и полный
контекст товара (`title`, `price`, `is_service`, `clinic_id`, `user_id`);
`simpleUpdateProduct()` меняет цену только совпавшей строки этого одного
товара. Это не batch по нескольким товарам/строкам и не замена scope `group`.
OpenAPI также публикует для `goodSaleParam` только одиночный PUT по `{ID}`.
Следовательно, атомарную массовую переоценку через доступный REST построить
нельзя; последовательная запись и явный recovery-контракт необходимы.

Безопасная живая ошибка одиночного PUT подтверждена без мутации:
`PUT /rest/api/goodSaleParam/2147483000` → HTTP 404,
`{"success":false,"message":"Record not found"}`. При сетевом timeout нельзя
делать вывод, что сервер ничего не записал: состояние строки сбоя остаётся
неопределённым до повторного GET.

## Архитектурное решение

### Проблема и ограничения

- ВМ не даёт атомарного batch endpoint; rollback поверх тех же ненадёжных
  одиночных PUT создаст ещё одну частичную операцию.
- Цели уже считаются от словарей снимка `before`, загруженного до первого PUT;
  двойного процента внутри одного вызова нет. Он появляется при слепом повторе
  всего вызова после partial result.
- Существующий preview/confirm и успешный ответ сохраняются совместимыми:
  старые поля `applied`, `updated`, `before`, `after`, `updated_rows` остаются.
- До первого PUT выборка обязана быть полной и bounded: максимум 500 читаемых
  и 50 пишущихся строк остаётся прежним.

### Рассмотренные варианты

1. **Использовать атомарный upstream batch.** Лучший вариант, но такого REST-
   контракта нет; `simpleUpdateProduct` атомарен только для одного товара.
2. **Компенсирующий rollback.** Не выбран: timeout не говорит, применён ли PUT,
   а rollback сам может оборваться и уничтожить более свежую конкурентную цену.
3. **Сделать процентный retry идемпотентным через server-side operation id.**
   Потребовал бы нового durable storage/cross-worker protocol и изменения
   публичного confirm-контракта; upstream не поддерживает compare-and-set.
4. **Явный partial report и запрет исходного процентного retry.** Выбран как
   наименьшее честное изменение. Все targets вычисляются до первого PUT. При
   первой ошибке инструмент возвращает подтверждённо записанные строки,
   failed row с фазой/причиной и неопределённостью состояния, untouched rows с
   before/target и row-scoped recovery-вызовами с абсолютным `new_price` и
   best-effort optimistic guard `expected_price=before`.

### Выбранный контракт

План `{sale_param_id, clinic_id, before, target}` целиком строится из
прочитанных до записи строк и после построения не меняется. Это локально
immutable plan, но не транзакционный snapshot ВМ: list API не даёт snapshot-
изоляции или CAS. После каждого PUT остаётся контрольный GET, и строка считается
подтверждённой только когда `Decimal(str(after))` численно равен target,
округлённому до `0.01` через `ROUND_HALF_UP`; различный текстовый scale вроде
`2500.0000000000` и `2500.00` не является расхождением. Target округляется при
построении плана, и PUT отправляет строковое представление именно этого target,
а не исходный неокруглённый результат процента. `expected_price` сравнивается
тем же числовым `Decimal`-правилом без требования одинакового scale.

При ошибке PUT или контрольного GET возвращается обычный структурированный
результат, а не исключение без payload:

- `complete=false`; `status="partial"` при наличии хотя бы одного успешного
  PUT, иначе `status="failed"`;
- `applied=false` для любого незавершённого результата, чтобы legacy caller не
  принял partial за полный success; факт записи отражают
  `partially_applied=true` и `acknowledged_writes`;
- `updated` — только подтверждённые GET строки с `before`, `target`, `after`;
- `failed` — текущая строка с `before`, `target`, `phase`, `reason`,
  `write_acknowledged`, `write_state`. Только HTTP 404 на PUT означает
  `write_state="not_written"`: исходники показывают отказ `loadOneModel` до
  `saveModel`, это подтверждено живым вызовом. Любой другой PUT failure и любой
  сбой verification означают `write_state="unknown"`;
- `untouched` — ещё не начатые строки с `before`, `target`;
- `resume_calls` — только для untouched: отдельные `scope="row"`,
  `confirm=true`, `new_price=target`, `expected_price=before`; инструмент
  перечитывает строку и отказывает до PUT, если цена уже изменилась; failed row
  сюда не входит;
- `retry_policy.repeat_same_percentage_call=false` и `next_step` требуют не
  повторять исходную массовую процентную операцию, сначала перечитать failed
  row, затем применить абсолютную target при необходимости и выполнить
  `resume_calls`.

`reason` не содержит `str(exc)`, URL, домен, query или raw body. Это словарь с
коротким code из закрытого набора (`http_<status>`, `timeout`, `connection`,
`verification_mismatch`, `malformed_response`, `upstream_error`) и безопасным
общим message. Статус берётся только из числового `status_code` исключения.

На partial/failed прежние поля определены явно: `updated_rows=len(updated)`,
`before`/`after` берутся из первой подтверждённой строки или равны `null`, если
таких строк нет. `complete`, а не `applied`, является сигналом полного успеха.
На completed оба поля равны `true`.

Новый необязательный `expected_price` допустим только вместе с
`scope="row"` и `confirm=true`; в preview, `good` и `group` комбинация явно
отклоняется до записи. Совпадение проверяется числовым Decimal-равенством с
ценой начального read-back. Параметр не может быть молча проигнорирован.

Успешный ответ дополнительно получает `complete=true`, `status="completed"`,
а все прежние поля сохраняет. Preview не меняется.

### Инварианты

- отсутствие/нечисловой `totalCount` останавливает вызов до первого PUT;
- ранний конец страницы или изменение `totalCount` во время локального обхода
  останавливает вызов до первого PUT;
- все targets вычислены из загруженного до мутаций набора строк;
- строка не считается подтверждённо обновлённой без read-back, равного target;
- после partial result исходный процентный вызов не является допустимым retry;
- ни failed row с неопределённым состоянием, ни уже updated rows не попадают в
  автоматические `resume_calls`;
- перед recovery PUT `expected_price` обязан совпасть с новым read-back. Это
  best-effort optimistic check, не CAS:
  ВМ всё ещё может принять конкурентную запись между нашим GET и PUT;
- этап 323 и общий `paginate_all` не затрагиваются.

### Результат Spark-review PRD №1

- **F322-001, high — принят:** абсолютный target без compare-before мог
  перезаписать конкурентное изменение. В контракт добавлен необязательный
  `expected_price`, обязательный в сгенерированных recovery-вызовах.
- **F322-002, high — принят:** успешный GET сам по себе не подтверждает цену.
  Теперь `after` обязан денежно равняться target; расхождение идёт в failed
  verification row.
- **F322-003, medium — принят как уточнение ограничения, код не расширяется:**
  offset-list не является транзакционным snapshot при конкурентных вставках и
  удалениях. ВМ не предоставляет snapshot/CAS, а общий pagination hardening —
  этап 323. Формулировка исправлена на локально immutable plan; обещание
  snapshot-изоляции удалено. Этот остаточный риск не лечится сортировкой без
  server-side snapshot и не связан с fallback отсутствующего `totalCount`.

### Результат Spark-review PRD №2

- **F322-004, high — принят:** отдельные GET и PUT не образуют CAS. Обещание
  невозможной гарантии удалено; `expected_price` назван best-effort guard, а
  остаточное TOCTOU-окно явно сохранено как upstream limitation.
- **F322-005, medium — принят:** денежное сравнение определено как числовое
  `Decimal`-равенство с target, округлённым до копеек `ROUND_HALF_UP`; scale
  строкового представления игнорируется.
- **F322-006, medium — отклонён как неподтверждённый:** текущий `_all_rows`
  уже проверяет `total > _PRICE_UPDATE_FETCH_LIMIT` сразу после первой страницы
  и до цикла PUT; существующий guard `test_mass_variant_refuses_instead_of_silently_truncating`
  подаёт `totalCount=4000` и проверяет отказ. Этап сохраняет этот код и тест.

### Результат Architecture Critique + Opus PRD-review №1

- **High, округление write/read — принят:** plan target округляется до копеек,
  PUT отправляет ровно его; comparison и `expected_price` используют числовой
  Decimal. Добавлен non-terminating-percent guard.
- **Medium, legacy partial ambiguity — принят:** incomplete всегда имеет
  `applied=false`; отдельные `partially_applied`/`acknowledged_writes`, а также
  значения `updated_rows`, `before`, `after` определены явно.
- **Medium, область `expected_price` — принят:** только row+confirm, остальные
  комбинации отказывают до PUT.
- **Medium, ранний конец pagination — принят:** local `_all_rows` проверяет
  стабильность `totalCount` и short/empty page до объявленного конца.
- **Medium, утечка reason — принят:** только закрытая безопасная классификация,
  без сырого исключения/URL/body.
- **Medium, неполная матрица тестов — принят:** в декомпозицию и acceptance
  добавлены first-PUT, timeout/4xx state, mismatch и состав resume calls.

### Результат Spark-review PRD №3

- **F322-007, high — принят:** pre-write доказан только для HTTP 404. Значение
  `not_written` ограничено этим кодом; все остальные 4xx/5xx/transport failures
  получают `unknown` и требуют read-before-retry.

### Результат Architecture Critique + Opus PRD-review №2

- **Medium, pagination inconsistencies — принят:** local `_all_rows` также
  отказывает на duplicate id, batch больше limit и accumulated > totalCount;
  это наблюдаемые противоречия, а не общий undercount этапа 323.
- **Medium, expected-price test slice — принят:** добавлена отдельная 322.1c с
  матрицей неподдерживаемых комбинаций, mismatch/no-PUT, равного Decimal с
  разным scale и безопасного live no-op.

### Rollback / fallback

Изменение откатывается одним git revert; миграций и внешнего состояния нет.
Если ВМ добавит документированный атомарный batch/CAS endpoint, отдельный этап
может заменить цикл, сохранив partial envelope как защиту транспортной границы.

## Декомпозиция

- **322.1a (≤150 LOC):** regression tests для ошибки первого/второго PUT,
  timeout, HTTP 404/прочие 4xx, ошибки read-back после успешного PUT и mismatch; проверить
  updated/failed/untouched, write state, отсутствие raw detail и состав
  абсолютных resume calls с `expected_price`.
- **322.1b (≤150 LOC):** заранее построить immutable plan, добавить partial
  envelope и сохранить успешный/preview контракт.
- **322.1c (≤120 LOC):** guards `expected_price`: preview/good/group refusal до
  PUT, mismatch refusal, совпадение с разным scale, recovery call и live no-op.
- **322.2 (≤100 LOC):** guards absent/string/float/bool `totalCount`, его смены
  и ранней short/empty page, oversized batch, duplicate id и overshoot;
  доказать отсутствие PUT и заменить fallback в локальном `_all_rows` на
  fail-closed.
- Полный Core Loop: красные сторожа, suite, opt-in real suite, живой вызов
  изменённого инструмента, аудит, review, commit, push, CI и deploy.

## Приёмка

- ошибка на строке N возвращает все подтверждённые `updated` с before/target/
  after, одну `failed` с причиной и фазой, остальные `untouched` с before/target;
- PUT-success + GET-failure помечает `write_acknowledged=true`, но не выдаёт
  строку за подтверждённую и требует read-before-retry;
- ошибка первого PUT возвращает `status="failed"`, `applied=false`, пустой
  `updated`, failed row и только следующие строки в untouched/resume calls;
- HTTP 404 PUT имеет `write_state="not_written"`; прочие 4xx, timeout,
  connection и 5xx — `write_state="unknown"`; raw exception detail не попадает
  в результат;
- `resume_calls` используют абсолютные target только для untouched; ответ явно
  запрещает повтор исходного процентного вызова и никогда не включает updated
  или failed row;
- recovery-call отказывает без PUT, если прочитанная цена не равна
  `expected_price`; совпадающая цена позволяет запись, но ответ честно не
  обещает отсутствующий в upstream атомарный CAS;
- успешный read-back с ценой, не равной target, попадает в failed verification,
  а не в `updated`;
- процент с результатом более двух знаков округляется до копеек до PUT и
  проходит verification по тому же target;
- incomplete result сохраняет `updated_rows=len(updated)`, first-confirmed
  `before/after` либо `null`, и всегда имеет `applied=false`, `complete=false`;
- `expected_price` с preview/good/group отклоняется до PUT;
- успешный confirm и preview сохраняют прежние поля/смысл;
- missing/malformed `totalCount` даёт явную ошибку до PUT; guard показан
  красным на старом fallback;
- изменившийся `totalCount` и short/empty page до объявленного конца также
  дают явную ошибку до PUT;
- oversized page, duplicate `sale_param_id` между страницами и accumulated >
  `totalCount` дают явную ошибку до PUT;
- `totalCount` на штатном живом GET подтверждён, изменённый инструмент вызван
  на стенде без изменения цены (абсолютная цена равна read-back);
- полный Docker suite и opt-in real suite зелёные; известный ReadTimeout
  `test_stage245_live_update_medical_card` при появлении фиксируется как flake,
  но тест и timeout не ослабляются.

## Оценка простоты

Решение меняет один tool module и компактные stage-test files, не добавляет классы,
storage, background cleanup или общий pagination helper. Helper для plan/report
допустим только если имеет минимум два call-site либо заметно сокращает основной
цикл; иначе логика остаётся рядом с единственным циклом. Durable idempotency и
компенсирующие транзакции отвергнуты как сложнее и менее честны без поддержки
upstream. После review triggers §4.1 проверяются повторно.

## Вне рамок

- общий `paginate_all`, ложный/заниженный `totalCount` и этап 323;
- PHP-код Ветменеджера, новый upstream endpoint или DB-транзакция между HTTP;
- массовая переоценка свыше существующих лимитов 50/500;
- изменение модели прав, preview variants или scope `row/good/group`.
