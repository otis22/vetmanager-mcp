# Этап 420 — машинный следующий шаг Report AI

## Цель

Этап 418 не подтвердил гипотезу остановки после чтения строк: доказанное пересечение 0, но счётчик без `job_id` не позволяет её опровергнуть. Из 27 рейтинговых записей 18 без `score`; наблюдалось ≈6 переходов `ready_to_save→abandoned_wait`. Даём машине конкретное продолжение всего маршрута create → poll → выбор/сохранение → data → rate, сохраняя существующие поля и смысл текстов.

## Проверенные факты и граница

- `tools/report_ai.py` уже записывает `job.next_action` для `needs_confirmation` и `ready_to_save` в форме `type`, `call` или `calls`, `guidance`. Эти формы сохраняются.
- `create_report_ai_job` и `get_report_ai_job` получают job в `data.job`; `/data` получает строки в `data`. В локальном OpenAPI v6 нет пути `/rest/api/report-ai-job`: подтверждение формы опирается на действующий код и живой стенд, не на выдуманную схему OpenAPI. Главный PRD требует полезный MCP контракт; технические требования фиксируют права `report_ai.write` на запуск и оценку.
- Канон 400/408/409: оценка 1–10, `rate_report_ai_job(job_id, score, intent_text)`, `comment` необязателен; балл 1 применим и к несобранному отчёту. 409 показывает `mcp_rating_reminder` лишь для принадлежащего подключению неоценённого готового job. `next_action` не утверждает, что этот lookup прошёл, и не подменяет reminder.
- Канон 417: Report AI может заменить ФИО/телефон плейсхолдерами даже при токене с ПД; это само по себе не основание снижать оценку, если задача решена. Для контактного действия недостающие ПД получают отдельными прямыми инструментами при наличии права; никакого обещания восстановить ПД из отчёта.

## Контракт и матрица

Дополняем существующее `data.job.next_action` для успешных create/status ответов и `data.next_action` для успешных save/confirm и чтения строк. `call: {tool, arguments}` задаёт известные аргументы; `required_args: [имена]` перечисляет все обязательные аргументы целевого инструмента, даже если значение нужно выбрать (`score`, `intent_text`, `title`). В форме `calls` каждый вариант содержит свой `required_args`; общий список оставляет пересечение (`job_id`). `guidance` использует существующие константы рейтинга и приватности там, где нужен текст. Для тупика `type=terminal`, `call` отсутствует, `guidance` объясняет дальнейшее действие без повтора job; `failed` с валидным ID — отдельное исключение `type=rate_failed_job` и вызов rate с `score=1` после чтения ошибки. При неизвестном статусе, неуспешном ответе или невалидном ID поле не добавляется: продолжение нельзя определить честно. Существующие поля, HTTP и формы `next_action` для выбора/сохранения не изменяются, добавляется только `required_args`.

Для активных статусов `mcp_queue_diagnostics.stop_automatic_polling=true` имеет приоритет над poll: `type=poll_paused`, без `call`, с указанием вернуться к этому ID позже. Bounded wait считает наблюдённый MCP возраст того же job/stage, включая общий Redis возраст рабочей стадии между worker, без дополнительного REST-вызова; обычный status может использовать подтверждённый upstream `created_at` для очереди и остановить раньше. Различие источников возраста очереди не обещает одинаковое число секунд; `mcp_wait_diagnostics.code=wait_timeout` не отменяет будущий poll, но текущий ответ предлагает паузу вместо немедленного цикла; `missing_analytics_scope` и `poll_failed` запрещают автоматический poll до исправления доступа/ошибки. Если у текущего токена нет `analytics.read`, poll или чтение строк заменяется `type=access_required` без `call`, с названием требуемого права. Не изменяем upstream job и текст диагностик.

| Статус/ответ | Машинный шаг |
| --- | --- |
| `queued`, `recognizing`, `building_preview` | `get_report_ai_job(job_id, wait_seconds=30)`, bounded poll того же ID, если нет stop/ошибки/таймаута |
| `needs_confirmation` | существующий выбор confirm (`job_id`, `report_id`) или reject (`job_id`); нужен осознанный выбор человека, после reject — существующий poll |
| `ready_to_save` | существующий save (`job_id`, осмысленный `title`) только после явного согласия человека |
| `saved`, `existing_report_matched` | `get_report_ai_job_data(job_id)` до оценки |
| `built` | Нет доказанного перехода к `/data` в действующем контракте. `type=unknown_transition` без `call`: показать статус человеку и не обещать строки. |
| `failed` | тупик строительства, не poll/save; с ID финальный `rate_report_ai_job(job_id, score=1, intent_text)` допустим |
| `rejected`, `cancelled` | терминальный тупик, сообщить человеку/выбрать иной маршрут; без ложного повтора. Bounded waiter узнаёт `cancelled` как терминальный статус. |
| Успешный save/confirm с подтверждённым `report_id` | `get_report_ai_job_data(job_id)` в `data.next_action`; иначе опираться на status/verify текущего job, не обещать строки. |
| Успешный `/data`, все строки доступны | По локальному состоянию оценки: `unrated` или `absent` → `rate_report_ai_job(job_id, score, intent_text)` (stage 408 допускает upsert отсутствующей записи); `rated` → `type=complete` без `call`; ошибка/таймаут lookup → поле отсутствует. Успешный upstream `/data` без списка `rows` не получает машинный шаг оценки. `mcp_rating_reminder` остаётся только для `unrated`. Score выбирается после реальных строк; нужен `report_ai.write`, иначе `access_required` без `call`. Для контактной задачи при отсутствующих ФИО/телефоне direct read с соответствующим доступом и оговорка 417, затем оценка по решённости задачи. |
| Успешный `/data`, `limited=true` | Сначала `get_report_ai_job_export(job_id)` при `report_ai.write` или `type=access_required`; структурированный план `after_export` указывает `get_report_export_download(report_file_id)` из `data.report.report_file_id`, а `after_download` — rate только если job ещё не оценён. Не оценивать обрезанные строки как полный результат. Старое поле `mcp_rating_reminder` независимо. |

## Архитектурное решение

**Проблема:** описания и reminder не гарантируют, что агент после каждого ответа увидит исполнимое продолжение. **Варианты:** новый top-level конверт во всех инструментах ломает привычное место job; только переписать тексты не даёт машинный сигнал; расширить действующий `job.next_action` и добавить такой же сигнал к успешным transition и `/data` — выбранный минимальный вариант. Аннотация выполняется локально после ответа API, без нового REST-вызова и хранения ПД. Не подставляем guessed `score` или `intent_text` и не выдаём прямой tool как универсальный путь к ПД: доступ и требуемая сущность зависят от задачи. Откат — убрать новые ветки аннотации и `data.next_action`, оставив прежние поля. Инварианты: прежняя форма выбора/сохранения и согласие человека; прекращение немедленного poll при диагностике; неуспешный/неполный ответ без выдуманного шага; приватность строк; отсутствие дублирования текста шкалы и подсказок.

## Декомпозиция и критерии

1. 420.1 (≤2 ч): PRD, сверка канона, Architecture Critique и PRD review Spark → Astra + Sol xhigh; findings в AssumptionLog.
2. 420.2a (≤150 строк): сторожа на матрицу статусов, required_args, терминальные статусы и отсутствие при невозможности продолжения, согласие; сначала красный исход, затем код и зелёный исход. Отдельная мутация каждого сторожа для self-attestation.
3. 420.2b (≤150 строк): сторожа на диагностический приоритет в обычном и bounded poll, `/data` (truncated, rated, absent), save/confirm, доступ, create, обратную совместимость, reminder до/после rate и ПД-оговорку; красный → зелёный. Живой create → poll → saved → data → rate на заранее выбранном контуре с кодами и очищенными телами. Отдельно живой needs_confirmation → confirm → existing_report_matched → data с next_action, кодами и очищенными телами; если стенд не предложит кандидата, явно зафиксировать непокрытый путь и не объявлять изменённый confirm проверенным.
4. Аудит, commit, Spark → Astra + Sol xhigh committed diff, полный mock + real suite по финальному SHA, push в ветку и зелёный Tests. Merge/deploy и прод-проверки вне этапа.
