# Этап 364 — согласованность FAQ, ключа и инструкции агенту

## Цель и границы

Адресно исправить SR360-4 и SR360-5 в утверждённом FAQ этапа 360. Не менять сервер, права, инструкцию агенту, тон и структуру остальных ответов. Решение владельца от 03.10.2026 разрешает реализацию без отдельного согласования текста.

## Проверенные факты

- `placeholder_resolution_guidance.py` разрешает агенту предложить скрипт только для имён клиентов и сотрудников: одобренные ID, GET `/rest/api/client/{ID}` и `/rest/api/user/{ID}`, поля `last_name`, `first_name`, `middle_name`. Иные сущности и поля оставляются плейсхолдерами.
- `landing_page.py` перечисляет REST-ключ и отдельное подключение без обезличивания как варианты ключа 2, но следующий ответ для обоих предлагает `get_*_by_id` и обещает скрипт для всего описанного алгоритма.
- `artifacts/technical-requirements-vetmanager-mcp-ru.md` задаёт MCP-вход через `Authorization: Bearer <service_token>`, REST-ключ используется для Vetmanager REST. Справочник API указывает сущности `/rest/api/client`, `/rest/api/user`, `/rest/api/pet`; код инструментов вызывает соответствующие пути с ID.
- Главный PRD и технические требования описывают MCP-сервер и кабинет. Эта задача меняет только публичное описание; поведение внешнего приложения клиники не меняется.

## Архитектурное решение

**Проблема.** FAQ смешивает два способа авторизации и обещает более широкую генерацию скрипта, чем допускает инструкция агенту.

**Контекст и варианты.** Можно расширить агентскую инструкцию или сузить формулировку FAQ. Владелец предписал второй вариант. Для REST-ключа указать прямые GET к REST Vetmanager, для подключения без обезличивания — MCP-инструменты. В предложении о скрипте оставить только имена клиентов и сотрудников; остальной алгоритм описывает приложение клиники.

**Инварианты.** REST-ключ не представлен как авторизация MCP. Агент не получает ключ 2 и не генерирует сценарии для `pet` и контактов. Остальной утверждённый FAQ неизменен; новые возможности не обещаются. Результат подстановки не возвращается модели. Контракт API, безопасность, хранение, совместимость и нагрузка не меняются.

В описании работы **приложения** при варианте MCP остаются три существующих инструмента: `get_client_by_id`, `get_user_by_id`, `get_pet_by_id`. Ограничение **скрипта агента** берётся из `AGENT_RESOLUTION_GUIDANCE`: только имена клиентов и сотрудников. Тест извлекает разрешённые REST-пути из инструкции, сверяет их с этим ограничением и падает при неизвестной сущности. Публичный FAQ не содержит примеров ключей, значений заголовков или доменов.

**Откат.** Текстовый revert возможен без миграции, но вернёт оба расхождения; при неверном контракте источником коррекции служат технические требования и инструкция агенту.

Architecture Critique: not required — изменение статического FAQ и сторожа не меняет границы модулей, авторизацию или API.

## Точная редакция

- Шаг 3 ответа «Как устроена подстановка значений (резолв)?», было: «Для каждой пары получить запись по второму ключу: `get_client_by_id`, `get_user_by_id` или `get_pet_by_id`.» Стало: «Для каждой пары получить запись по второму ключу: с REST-ключом Vetmanager — прямым GET-запросом к REST API Vetmanager; с отдельным подключением без обезличивания — через инструменты подключения `get_client_by_id`, `get_user_by_id` или `get_pet_by_id`.» В публичном тексте используется привычное название без сокращения MCP по существующему сторожу лендинга.
- Абзац о скрипте, было: «Помощник может подготовить такой скрипт по этому описанию. Сотрудник клиники проверяет скрипт и запускает его в своём окружении.» Стало: «Помощник может подготовить скрипт только для подстановки имён клиентов и сотрудников; этот скрипт не охватывает метки питомцев и контактов. Сотрудник клиники проверяет скрипт и запускает его в своём окружении.» Уточнение принято после визуального Opus-review: прежнее «по инструкции агенту» можно было прочесть как обещание всего сценария.

## Простота и уже выданные ключи

Редакция ограничена двумя предложениями; новая абстракция не нужна. Трактовка уже выданных учётных данных не меняется: меняется только текст FAQ.

## Подзадачи и приёмка

1. До 2 ч: красный сторож, который извлекает ответ FAQ и сверяет варианты ключа с авторизацией, а обещание скрипта с фактической инструкцией агенту. Показать падение на исходном тексте и на контролируемой мутации, возвращающей общий вызов `get_*_by_id` для REST-ключа и обещание «такого скрипта».
2. До 2 ч: минимальная редакция двух абзацев FAQ; фокусные тесты и аудит diff.
3. До 2 ч: локальная матрица состояний и отдельный раскрытый FAQ для desktop и phone, визуальный Spark и сильная пара Astra/Opus; committed diff review, полный mock и real suite, push и зелёные Tests/Deploy Prod.

## Критерии выпуска

В каждом варианте ключа назван собственный способ чтения. Формулировка о скрипте ограничена именами клиентов и сотрудников. Сторож краснеет при возврате обоих расхождений. Визуальный гейт и обязательные проверки зелёные; итоговый отчёт содержит полные пары «было → стало» и указания супервизору для проверки после выката.
