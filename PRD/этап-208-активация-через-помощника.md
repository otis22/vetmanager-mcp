# PRD — Этап 208: Активация через ИИ-помощника

## Контекст и цель

Основной пользователь — сотрудник ветклиники, который уже пользуется ChatGPT,
Claude или Manus. Ему нужно подключить данные Vetmanager и сразу задать первый
вопрос. Технический сценарий с ключами остаётся доступным, но вторичным.

Цель этапа: сократить путь до первого успешного запроса, сохранив существующие
OAuth, токены, права и runtime-контракт без изменений.

## Scope

1. Зафиксировать baseline существующей агрегатной воронки; в этом этапе не
   добавлять новый telemetry event или session correlation. Срез по помощнику —
   последующая задача только при подтверждённой потребности.
2. Обновить landing: короткий заголовок, выбор ChatGPT/Claude/Manus, три шага.
3. После завершения подключения показать в кабинете блок успеха с пятью
   готовыми фразами; OAuth callback остаётся текущим внешним redirect.
4. Упростить верх кабинета: статус связи, клиника, доступ, активность и
   подключение/переподключение/отключение; технические настройки свернуть.
5. Проверить mobile и desktop через существующий browser stack и production
   smoke с отдельными локальными credentials, не сохраняя секреты в репозитории.

## Не в scope

- Новые OAuth-провайдеры или особые серверные контракты для Manus.
- Изменение scope/preset, OAuth протокола, данных Vetmanager и MCP tools.
- A/B-тесты, аналитика персональных запросов, редизайн вне landing/account.

## UX и тексты

- Один экран — одно основное действие; максимум три шага.
- Не показывать пользователю слова MCP, OAuth, API, token или scope.
- Основной заголовок: «Ваш ИИ-помощник теперь знает вашу клинику».
- Основная кнопка: «Подключить за 2 минуты».
- Статусы: «Связь активна», «Связь прервана», «Не подключено».
- Стартовые фразы: «Покажи записи на сегодня», «Найди карточку клиента по
  фамилии», «Сколько приёмов было на прошлой неделе?», «Кого напомнить о визите
  завтра?», «Кто не приходил больше полугода?».

## Архитектурное решение

### Проблема и ограничения

Existing web flow uses signed account cookies; OAuth consent creates grants and
runtime credentials. `activation_events` and existing aggregate activation
metrics must not receive prompts, patient data, tokens, account email, clinic
name or other personal data. Existing dashboard already exposes activation
funnel metrics. The
flow must remain usable on small phones and desktop browsers: tap targets are at
least 44px; buttons and starter prompts wrap without horizontal scrolling; copy
has a visible text-selection fallback when Clipboard API is unavailable.

### Варианты

1. Отдельный per-agent backend flow: больше контрактов, риски OAuth и лишняя
   работа.
2. Один UI с выбранным помощником как presentation state: использует текущий
   OAuth flow и не меняет безопасность.
3. Только новый landing: не закрывает consent → первый запрос.

### Выбор и инварианты

Выбираем вариант 2. Agent selection остаётся presentation-only на landing и
ведёт в общий onboarding; OAuth callback и account state не меняются. Реальная
авторизация остаётся текущим generic OAuth flow. Блок подсказок в кабинете не
выдаёт новые credentials и не
меняет grant. Telemetry хранит только event + bounded agent, а activity в
кабинете рендерит только timestamp, success/error и request count; tool names,
arguments, query text, client/patient identifiers никогда не рендерятся.

### Rollback

Landing и кабинет можно вернуть к текущим server-rendered sections одним
revert; OAuth grants, tokens и данные клиники не мигрируются и не меняются.
Никаких новых event schemas или storage migrations нет.

## Acceptance criteria

- На mobile и desktop landing показывает ChatGPT, Claude, Manus и одну главную
  кнопку; вне свёрнутого «Для разработчиков» markup не содержит MCP, OAuth,
  API, token или scope.
- После успешного consent пользователь видит клинику, выбранный помощник и пять
  стартовых фраз; ни одна фраза не записывается в telemetry.
- Кабинет показывает статус связи, клинику, простой доступ и безопасную
  активность; disconnect/reconnect доступны; прежние technical controls
  остаются в явно названном свёрнутом разделе «Для разработчиков».
- Existing aggregate funnel metrics сохраняют текущую семантику; этот этап не
  заявляет новый agent breakdown или time-to-first-request.
- Browser tests проверяют 375px и desktop; full Docker suite, reviews and
  production login smoke pass. Smoke использует отдельный test account только
  локально, не пишет email/tokens/screenshots в logs, и отзывает созданный grant.

## Review gates

Architecture Critique required: production web behavior, OAuth-adjacent UI and
cross-module ownership. Spark then external-model review are required before
implementation and for committed diff.
