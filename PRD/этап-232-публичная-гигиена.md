# Этап 232. Публичная гигиена репозитория

## Цель

Не допустить нового переноса маркеров закрытой реализации Vetmanager в
публичный репозиторий, убрать локальные абсолютные пути из Markdown и заменить
bearer-значение в browser-фикстуре на очевидно синтетическое.

## Контекст и проверенные факты

- Репозиторий, включая `Roadmap.md`, `AssumptionLog.md` и `PRD/`, публичен;
  правило `CLAUDE.md` §6.2 разрешает переносить только наблюдаемый API-контракт.
- Владелец осознанно оставляет уровень 2: логические пути, имена файлов и
  классов закрытого репозитория. Проверка не должна блокировать их.
- Точный текст ошибки, который API возвращает внешнему клиенту, является
  наблюдаемым контрактом и не считается переносом реализации.
- Текущий installer генерирует `.git/hooks/pre-commit`; в тестовом контейнере
  нет `git`, поэтому hook-тесты должны подменять его, как существующие workflow
  tests.
- Технические требования закрепляют запуск проверок через `docker compose` и
  запрещают хранить runtime credentials в репозитории.

## Декомпозиция

1. Добавить версионируемый pre-commit hook с проверкой только добавленных
   строк staged diff и точечным явным исключением на один файл; подключить
   его к installer.
2. Добавить unit-тесты: блокировка добавленной PHP-конструкции, разрешение
   добавленного класса уровня 2 и цитаты ошибки API, имя с пробелом, точечный
   bypass и отсутствие реакции на уже существующую строку с git-заглушкой.
3. Заменить абсолютные локальные пути во всех tracked Markdown на логические
   repo-relative пути либо нейтральное описание источника.
4. Заменить browser-фикстуру bearer-значением нужного формата и длины, явно
   синтетическим по тексту.
5. Выполнить shell, targeted и полный container checks; провести required
   review gates, commit, push и открыть PR.

## Архитектурное решение

### Проблема и ограничения

Hook обязан проверять добавленные строки staged diff, а не весь рабочий файл:
исторические публикации владелец решил оставить. Он должен быть совместим с
POSIX-доступными инструментами в Git hook и не должен превратить согласованный
уровень 2 или наблюдаемый ответ API в запрет.

### Варианты

1. Встроить ещё один heredoc в installer. Это сохраняет один файл, но делает
   hook непроверяемым как отдельный версионируемый артефакт.
2. Проверять весь рабочий каталог или весь staged blob регулярным поиском. Это
   ложно блокирует исторические публикации и не соответствует новой строке.
3. Хранить hook в `scripts/git-hooks/pre-commit`, а installer копирует его в
   `.git/hooks`, предварительно сохранив существующий hook в timestamped
   backup; брать только добавленные строки из `git diff --cached`.

### Выбранное решение и инварианты

Выбран вариант 3. Hook получает NUL-разделённый список staged файлов и для
каждого анализирует только добавленные строки `git diff --cached --unified=0`.
Он ищет шесть согласованных PHP-конструкций, но не ищет пути, имена классов или
цитаты API-ошибок. Исключение требует переменную
`ALLOW_FOREIGN_IMPLEMENTATION_FILE` с ровно одним точным repo-relative путём;
оно не отключает проверку для остальных файлов. Ошибка hook сообщает только
путь и имя правила, не содержимое строки.

### Rollback/fallback

Если marker окажется слишком широким, его можно сузить в версионируемом hook и
переустановить через `./scripts/git-hooks/install.sh`. До корректировки
допускается только точечное исключение для одного файла с явным путём. Как и
любой local Git hook, этот guard не является контролем доступа: коммиттер может
применить `--no-verify`. Точечная переменная делает исключение заметным в
команде и не ослабляет проверку прочих staged файлов. `core.hooksPath` не
выбирается: проект сохраняет существующую установку в `.git/hooks` и не меняет
пользовательскую Git-конфигурацию.

Перед перезаписью installer создаёт timestamped backup уже существующего
`.git/hooks/pre-commit`; повторная установка поэтому не уничтожает локальную
проверку без возможности восстановления.

Architecture Critique: required — этап меняет публичный commit gate и политику
раскрытия.

## Acceptance criteria

- Commit блокируется на каждом заданном PHP-маркере, только если маркер есть в
  добавленной строке, и сообщает только путь и имя правила.
- Добавленные имя класса уровня 2 и точная цитата API-ошибки проходят hook.
- Существующая строка с маркером вне добавленного diff не влияет на commit.
- Bypass принимает ровно один staged repo-relative путь; другое значение не
  отключает проверку.
- Все tracked Markdown больше не содержат абсолютный локальный префикс
  разработчика; имена стендов не изменены.
- Фикстура имеет `vm_st_` плюс 43 символа и по виду очевидно тестовая.
- Полный test-compose прогон завершён с exit code 0.

## Out of scope

- Удаление согласованной карты закрытого репозитория (уровень 2).
- Ротация секретов и любые обращения к production или тестовым стендам. Старое
  fixture-значение считается потенциально чувствительным и не воспроизводится
  в новых документах, сообщениях или review prompt; проверка его происхождения
  и возможная ротация требуют действий владельца вне этого этапа.
- Изменение поведения MCP/API.

## Оценка простоты

Новая абстракция не нужна: один короткий shell hook и один installer-copy
достаточны. Factory, конфигурационный слой и общий scanner не вводятся.
