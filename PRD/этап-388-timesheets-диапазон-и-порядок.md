# Этап 388. Диапазон дат и порядок `get_timesheets`

## Цель и критерии приёмки

`get_timesheets` принимает необязательные `date_from` и `date_to` в формате `YYYY-MM-DD`. Диапазон включает оба календарных дня и выбирает смены, пересекающиеся с ним: `end_datetime > date_from 00:00:00` и `begin_datetime < (date_to + 1 день) 00:00:00`. Односторонние границы разрешены. Существующие `date`, `doctor_id`, сырой `filter`, пагинация и явный `sort` продолжают работать; все фильтры соединяются через AND. Если `sort` не передан, инструмент посылает `begin_datetime DESC, id DESC`: второй ключ стабилизирует порядок одинаковых начал смен на границе страниц. Переданный список сортировки имеет приоритет. Неверные даты, `date_from > date_to` и `date_to=9999-12-31` (нет следующего дня) отклоняются до HTTP. Пустой явный `sort=[]` считается явным выбором апстрим-порядка без параметра `sort`.

## Проверенные факты

- `artifacts/api_entity_reference-ru.md`, §2.32: `/rest/api/timesheet`, `begin_datetime` и `end_datetime` — колонки расписания, формат времени `YYYY-MM-DD HH:MM:SS`.
- `artifacts/vetmanager_openapi_v6.json`: timesheet включает `begin_datetime` и `end_datetime`.
- По проверке супервизора vetmanager-extjs master `6fbabdc452`: стандартные LIST_PARAMS — `filter`, `sort`, `limit`, `offset`; list принимает `{property,value,operator}` и сортировку с направлением, валидирует поля модели. Это контракт, а не перенос реализации.
- `tools/operations.py` уже использует для `date` условия пересечения смены с днём; `crud_list` кодирует сырой фильтр и сортировку и проверяет поля по allowlist.

## Архитектурное решение

Проблема: клиенту нужен типичный выбор по периоду без ручного составления REST-фильтров, а текущий порядок ухудшает поиск свежих смен. Контекст: единичный `date` уже выбирает по пересечению, `filter`/`sort` — публичные параметры, поэтому новые ограничения должны дополнять их без переопределения. Рассмотрены (1) отдельный REST-вызов и сортировка результата на нашей стороне — неверно при пагинации и лишняя нагрузка; (2) формирование условий в `get_timesheets` и передача сортировки апстриму — одна выборка с верной пагинацией. Выбран вариант 2. Инварианты: явный `sort` не меняется; raw `filter` сохраняется; `date` продолжает использовать прежние условия; права и схема ответа не меняются; ПД не попадают в evidence. Откат: удалить два параметра и дефолтный `sort`, вернуть прежний вызов `crud_list`. Если сортировка апстрима окажется неверной, диагностировать живым вызовом, не сортировать страницу после лимита.

## Проверки и выпуск

Сторожа принимаются красными на исходной реализации. После правки — фокусный набор, живые вызовы с диапазоном и без параметров: при наличии смен диапазон выбирается по дате найденной смены, проверяются обе границы пересечения и убывание `begin_datetime` (при равенстве — `id`). Если пересекающих полночь смен нет, это ограничение живого evidence фиксируется, а семантика границы проверяется сторожем. Безопасное тело содержит код, количество, порядок дат начала/окончания без персональных полей. Затем committed diff review, один полный mock и real suite, проверка структуры Roadmap, push и CI Tests + Deploy Prod.

## PRD-review и простота

Spark указал на переполнение при `date_to=9999-12-31`; принято, верхняя граница отклоняется до HTTP и покрывается тестом. Архитектура оставляет один REST-запрос и использует существующий `crud_list`; вспомогательный слой и постраничная пересортировка не нужны.

Astra: `findings=[]`. Sol: приняты три medium — вторичный ключ `id DESC` для одинакового начала, отдельный сторож на явный `sort=[]`, диапазон по реально найденной смене с проверкой условий пересечения. Неустранённых critical/high нет. Решение осталось однозапросным; изменения уточняют контракт и приёмку.
