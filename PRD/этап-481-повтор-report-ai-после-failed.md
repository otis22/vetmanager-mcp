# Этап 481. Новый intent #170 после terminal failed

## Цель и граница

По решению владельца 21.11.2026 этап сведён к **unit-тесту без реального вызова
ВМ**. Защищается только контракт MCP: после сообщения upstream о terminal
`failed` новый, более простой intent отправляется отдельным запросом; MCP не
блокирует его по прежнему job и не подменяет ответ upstream. Изменчивое
поведение самого модуля ВМ и наличие реального recovery не проверяются.

## Исходные факты

- Исходная жалоба #170 относится к новому, более простому intent после
  `PREVIEW_FAILED`, а не к точному повтору того же intent.
- Диагностика 471 видела три terminal `failed/PREVIEW_FAILED/OTHER` jobs с
  разными intent digest. Это историческое наблюдение, не доказательство текущего
  контракта ВМ.
- Разрешённый 19.11 сценарий на devtr6 подтвердил active exact dedup, но job
  завершился `ready_to_save`; ветка после failed осталась неизмеренной. Это
  историческое evidence, а не обязательный gate данного этапа.
- `create_report_ai_job` передаёт intent в `POST /rest/api/report-ai-job` и
  читает `is_deduplicated` из ответа. Локального поиска или блокировки по
  прежнему failed job в этом пути нет.

## Unit-сценарий

Использовать существующий mock/seam `_call_vm` или ближайший эквивалент без
сети и новых абстракций.

1. Первый ответ upstream описывает failed job с ID A. Следующий ответ на новый,
   более простой intent описывает другой job с ID B и `is_deduplicated=false`.
2. Вызвать `create_report_ai_job` последовательно с двумя разными intent.
   Проверить два POST на один endpoint, разные переданные intent и отсутствие
   локального отказа второго вызова. Результат второго вызова должен содержать
   ID B и переданные upstream статус/флаг.
3. Отдельный случай: upstream на новый intent возвращает прежний failed ID A с
   `is_deduplicated=true`. MCP должен передать этот ответ без автоматического
   retry, fabricated recovery или замены ID. Тест не оценивает правильность
   такого решения ВМ.
4. Данные ответов синтетические; Report AI jobs, прямые API-вызовы, devtr6 и
   production не используются.

## Красные сторожа и приёмка

Доказать ценность теста мутациями текущего контракта: локальный отказ второго
intent, пропуск второго POST или принудительная подмена ID B на ID A должны
дать красный соответствующий node. Мутации откатить. Если текущий код уже
соответствует контракту, изменение ограничивается тестами; найденный локальный
дефект исправляется минимально по обычному red→green.

Focused, owning, fast и полный default выполняются по затронутым входам.
Real API, live ВМ и production smoke для unit-only изменения не требуются по
решению владельца. Обновить Roadmap, AssumptionLog и внешний work log с
фактическими counts, mutation evidence и SHA.

## Вне объёма

Не проверять active exact dedup, semantic match, выбор upstream-кандидата,
изменение поведения ВМ и реальную возможность recovery после failed. Не
создавать Report AI jobs и не добавлять интеграционный тест.
