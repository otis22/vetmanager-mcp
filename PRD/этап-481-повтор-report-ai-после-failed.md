# Этап 481. Повтор #170 после terminal failed

## Цель и граница

Проверить на тестовом devtr6 переход `create → terminal failed → create` для одного безопасного intent и отдельно точный повтор, пока job активен. Разрешение владельца от 19.11.2026 покрывает новые тестовые jobs только для этой проверки. Production и другие worktree не меняются. Не создавать серию jobs для подбора исхода; при rate limit ждать окно и не начинать новый job на retry poll.

## Исходные факты

- Диагностика 471 видела три разных terminal `failed/PREVIEW_FAILED/OTHER` jobs #170, но не проверила текущий повтор того же intent.
- Диагностика 483 показала ошибочный upstream semantic match: старый отчёт имел 0 строк, новый seed — 12 строк с zero-fill. Это отдельное наблюдение, не доказательство поведения create после failed.
- `create_report_ai_job` передаёт intent в `POST /rest/api/report-ai-job`; MCP не выбирает job или matched report. Контракт HTTP и формы ответа сверять по живому ответу и существующему исследованию Report AI.

## Подзадачи

1. **481.1a** (≤2 ч): подготовить безопасный сценарий и сторож обезличенного evidence с красными мутациями.
2. **481.1b** (≤2 ч): выполнить один ограниченный create→dedup сценарий на devtr6, продолжить только тот же job до конечного состояния, сохранить counts и ответы.
3. **481.1c** (≤2 ч): классифицировать фактический исход, провести применимые проверки, передать куратору evidence и обновить Roadmap/AssumptionLog.

## Сценарий и лимиты

1. Зафиксировать базовый SHA, контур, время и безопасный снимок известного evidence. Подготовить сторожа, которые падают при подмене terminal статуса, флага дедупликации, ID или числа вызовов.
2. Отправить один безопасный агрегированный intent через штатный MCP `create_report_ai_job` с `wait_seconds=0`. Пока job активен, сразу повторить **точно тот же intent** один раз; сравнить HTTP, `is_deduplicated`, job ID и статус. Если флаг не `true` или ID различается, остановить дальнейшие create, классифицировать провал положительного контроля отдельно и исследовать его без новых jobs.
3. Поллить только полученный job до terminal или ограниченного времени. Если статус `failed`, повторить точно тот же intent **один раз**. Для локализации использовать только прямой GET существующего job; прямой сравнительный POST запрещён. Если job завершится другим статусом, зафиксировать, что ветка после `failed` не измерена, без создания новой серии jobs.
4. Для каждого ответа сохранять вне репозитория только время, код, флаг, ID тестовых jobs, статус, безопасный error code и counts. Не сохранять строки, preview значения, токены или сырые тела с данными клиники. При HTTP 429/RUN_RATE_LIMITED записать retry window и ждать его; без повторного StartReport.

## Приёмка и классификация

- Положительный контроль: active exact repeat возвращает `is_deduplicated=true` и тот же ID; отклонение требует парного прямого API и MCP доказательства.
- После подтверждённого terminal `failed` фиксируется фактический флаг и ID повторного create. Новый ID с `is_deduplicated=false` допустим для recovery; возврат старого failed ID или иной исход оценивается по живому контракту, без заранее выбранной классификации.
- MCP-дефект объявляется только при доказанном расхождении его ответа или действия с прямым ВМ на одинаковом intent и контуре; тогда минимальная правка с red→green и всеми гейтами. Совпадающие ответы с дефектом dedup или semantic match — upstream, эскалация куратору для ВМ.
- Если terminal `failed` не получен в одном сценарии, результат `NOT_MEASURABLE` для этой ветки. Не выдавать active dedup за проверку recovery после failed.
- Обновить Roadmap, AssumptionLog и внешний work log с counts, классом, evidence и SHA; docs-only вывод проходит соответствующие структурные и review checks.

## Простота

Один intent, максимум три create POST во всём сценарии (включая любые диагностические вызовы), третий только после terminal `failed`; GET poll не создаёт job. Новые runtime абстракции не нужны. Сторож проверяет обезличенную проекцию, а не приватный ответ.
