# Этап 236 — Полезный контекст в событиях трекинга

## Цель

Сделать отказ MCP-инструмента одним пригодным для расследования Sentry-событием:
с именем инструмента, account ID, HTTP-статусом upstream (когда он известен) и
release, равным SHA собранного образа. Штатный отказ локальной валидации фильтра
должен оставлять низкокардинальный operational signal, но не создавать Sentry
error/alert.

## Контекст и scope

PYTHON-5 нельзя привязать к вызову или деплою: transaction содержит внутренний
URL контейнера, release равен `vetmanager-mcp@unknown`, а один отказ создаёт
доменное исключение и оборачивающий `ToolError`. PYTHON-7 показывает, что
`Unknown filter property` ошибочно становится incident error.

В scope входят все пункты Roadmap 236.1–236.5:

1. На event отказа инструмента добавить безопасные tags `tool`, `account_id` и
   `upstream_status` (последний только если exception несёт HTTP status).
2. Передавать SHA git-коммита сборки как `ERROR_TRACKING_RELEASE` через Docker
   build arg, запечённый в image ENV; без build arg сохранить явный fallback
   `vetmanager-mcp@unknown` для локальной разработки.
3. Оставить ровно один captured event на один отказ tool call, не меняя ответ,
   MCP transport, auth flow или формат ToolError.
4. Установить Sentry transaction в имя MCP-инструмента, а не URL ASGI
   контейнера.
5. Для `Unknown filter property` записывать бизнес-метрику с фиксированным
   event name и structured warning с именем поля; не вызывать Sentry capture
   и не использовать field name как Prometheus label.

## Ограничения и приватность

- Подключения Claude и ChatGPT через существующий HTTP MCP transport должны
  остаться совместимыми; middleware только обогащает наблюдаемость.
- Не изменяются ручные настройки Sentry, DSN, production host и transport
  contract.
- Допустимы clinic domain и `account_id`; здесь передаётся только `account_id`.
  IP-адреса и секреты не добавляются. Existing `before_send` sanitiser остаётся
  последней линией очистки.
- `tool` — зарегистрированное имя, `upstream_status` — bounded decimal HTTP
  status либо отсутствует; они не несут clinic/user input.

## Архитектурное решение

### Проблема

Framework-level Sentry/Starlette capture видит URL HTTP request и цепочку
исключений, но не semantic MCP call context. Отдельная отправка domain error и
его `ToolError` создаёт дубликаты и шум.

### Варианты

1. Оставить автоматическую Starlette capture и пытаться переписать event в
   `before_send`. Плюс — мало кода; минус — middleware не получает надёжного
   tool/account context для каждого внутреннего exception и нельзя гарантировать
   exact-once.
2. Добавить capture в каждый tool/helper. Минус — широкая дубликация и легко
   пропустить non-CRUD tool либо отправить несколько events в одном вызове.
3. Один FastMCP middleware на границе `on_call_tool`: он получает tool name,
   запускается внутри уже установленного runtime credentials context, ловит
   terminal exception один раз, задаёт Sentry tags/transaction и делегирует
   capture централизованному helper. Выбрано.

### Выбранное решение

Добавить узкий error-tracking middleware **после регистрации** OAuth preflight
(значит, как inner middleware FastMCP) так, чтобы
исполнение tool проходило с `RuntimeCredentials` в ContextVar. Middleware
оборачивает поддерживаемый FastMCP `on_call_tool(context, call_next)`. При
terminal `ToolError` он извлекает `status_code` из exception/cause-chain;
central helper безопасно отправляет один event в isolation scope с tags,
transaction и static tag `mcp_tool_failure_capture=manual`. Перед повторным
raise middleware маркирует этот exact `ToolError` object как already handled.
`before_send` отбрасывает automatic event только если одновременно видит этот
marker и не видит manual tag. Поэтому FastMCP automatic Starlette capture не
создаёт второй event, но unrelated `ToolError` не становится globally ignored;
manual helper остаётся единственным sender для marked tool failure. Обычные
web-route incidents сохраняют существующее tracking поведение.

`validate_filter_properties` перед raise записывает `filter_property_rejected`
через существующий allowlisted business-events counter и safe warning logger.
Field name остаётся structured log attribute (без metric label) для этапа
235.5. Это не вызывает capture API. Для этого rejection вводится явный
`FilterPropertyValidationError`; middleware распознаёт его в cause-chain и
не вызывает manual capture. FastMCP всё ещё возвращает прежний ToolError
контракт; middleware маркирует этот object как expected, а `before_send`
подавляет только его automatic capture.

Marker lookup reads `hint["exc_info"]` and walks `__cause__`/`__context__`
with identity-based cycle protection; no `exc_info` means no suppression.
For a manual tool event sanitiser removes inherited request, user, contexts,
breadcrumbs and extra, redacts exception value and frame locals, and retains
only safe tags. This applies equally to MCP arguments and request headers/body.
FastMCP core wraps normal tool exceptions into `ToolError` before this inner
boundary; OAuth challenge returns an MCP error result and is not captured.

Docker image получает `ARG ERROR_TRACKING_RELEASE` (bare SHA либо `unknown`)
и запекает его в image `ENV ERROR_TRACKING_RELEASE`. Compose передаёт только
build arg из `GIT_SHA` (default `unknown`) и **не** переопределяет runtime ENV:
образ остаётся источником release даже при prebuilt/pulled image. Repository
deployment entrypoint `scripts/deploy_server.sh` computes `git rev-parse
--verify HEAD` after source sync and passes it as the production Docker build
arg; a build without a verified SHA fails rather than silently using unknown.
Resolver
canonicalises bare value to `vetmanager-mcp@<sha>`, но уже-prefixed explicit
runtime override `vetmanager-mcp@...` сохраняет без двойного prefix.

### Инварианты

- Без DSN tracking helpers остаются no-op и не меняют tool result/exception.
- Один terminal tool failure даёт ровно один manual Sentry event; event
  имеет `transaction == tool name` и tags `tool`, `account_id` when available,
  `upstream_status` when available.
- `FilterPropertyValidationError` не вызывает ни manual, ни automatic Sentry
  error для `Unknown filter property`.
- Metric cardinality не зависит от unknown property name.
- `ERROR_TRACKING_RELEASE` не содержит secret и release Sentry не меняет
  Docker image runtime command или MCP transport.

### Rollback/fallback

`ERROR_TRACKING_RELEASE` необязателен, поэтому старый/ручной image стартует с
`unknown` fallback. Если middleware окажется несовместим с FastMCP runtime,
rollback application image возвращает прежнюю event semantics без migration.
Нулевой DSN и любые ошибки tracking capture остаются fail-open.

## Проверки и acceptance criteria

1. Unit tests с mocked Sentry доказывают tags, transaction, status, no-op и
   exactly-one capture for one authenticated tool failure; tests prove that
   `FilterPropertyValidationError` causes no capture and auto/manual
   deduplication does not suppress unrelated ToolError.
2. `Unknown filter property` increments only fixed business event and keeps
   field in safe log context without Sentry capture or dynamic metric label.
3. Dockerfile and compose contract tests prove build-only SHA propagation,
   no runtime compose override, and `_resolve_release()` for bare, prefixed
   and empty values.
4. Focused tests, exact documented Docker test command and PR CI pass.
5. Existing HTTP MCP success/failure contract keeps the same result and
   ToolError shape; captured event has canonical release and only allowed
   tags, with request headers/body, MCP arguments, breadcrumbs and mock
   sensitive values proving sanitisation.
6. `before_send` tests exercise marker lookup in direct/cause/context chains,
   cycles and missing `exc_info`; HTTP-MCP integration proves exactly one
   failure event and zero event for `FilterPropertyValidationError`.

## Out of scope

- Changing error text, tool schemas, OAuth scopes, MCP transport or retry
  policy.
- Expanding stage 235.5 field validation coverage.
