# Этап 331. Контракт `create_pet` и `create_medical_card`

## Цель

Привести схемы и описания MCP-инструментов создания питомца и медкарты в
соответствие с наблюдаемым контрактом Vetmanager, чтобы агент не предлагал
значения, которые апстрим гарантированно отвергает или молча преобразует.

## Контекст и проверенные факты

- Сверка с внешними исходниками согласуется с наблюдаемым REST-контрактом:
  для создания питомца нужны положительные идентификаторы вида и породы, для
  медкарты — `patient_id`, `date_create`, `clinic_id`; `admission_type`
  передаётся как числовое значение.
- Текущий MCP-код не отправляет нулевые `breed_id`/`clinic_id`, но описывает
  их как допустимые значения. `create_pet` поэтому получает отказ апстрима,
  а `create_medical_card` — отказ о клинике.
- Наблюдаемые ответы стенда (включая чтение созданной медкарты) дополнят этот
  PRD до реализации. Внешние исходники используются только для сверки
  наблюдаемого контракта, без переноса реализации.

### Живой контур 18.09.2026

Тела ниже сокращены до контрактных полей и не содержат идентификаторов
пациентов/владельцев или данных доступа.

- `POST /rest/api/pet` без `breed_id` → HTTP 422,
  `Поле breed_id обязательное для заполнения.`; тот же POST с `breed_id=0`
  → тот же HTTP 422 и тело. Справочник пород зависит от вида, но служебная
  универсальная «неизвестная» порода контрактом не объявлена;
  автоподстановка исключена.
- `POST /rest/api/MedicalCards` без `clinic_id` → HTTP 500,
  `No Clinic selected`.
- Справочник `ComboManualName` содержит `admission_type`; у его items
  `title="Первичный"` соответствует строковый `value="3"`. POST с названием
  вернул HTTP 201, а GET созданной карты — `admission_type: 0`; POST с
  кодом-строкой `"3"` вернул HTTP 201 и GET — `admission_type: 3`.
  Следовательно, название не является валидным входом, хотя API не сообщает
  об ошибке.
- PUT созданной карты с тем же обязательным контекстом и
  `admission_type="4"` → HTTP 200; GET → `admission_type: 4`. Поле можно
  безопасно добавить в `update_medical_card`.
- POST с JSON-числом `admission_type=3` → HTTP 201, GET →
  `admission_type: 3`; PUT с JSON-числом `admission_type=4` и только
  `patient_id`, `doctor_id`, `clinic_id` из прочитанной карты → HTTP 200,
  GET → `admission_type: 4`. MCP должен отправлять целое число, а его
  существующий update уже сохраняет этот минимальный обязательный контекст.

## Scope и декомпозиция

1. **331.1 (≤150 LOC):** живыми безопасными пробами и чтением справочника
   установить контракт `breed_id`; сделать `breed_id` и связанный `type_id`
   обязательными у `create_pet`, с локальной ошибкой до I/O.
2. **331.2 (≤150 LOC):** принимать `admission_type` только как положительный
   целочисленный код справочника; строковое название отвергать до I/O. Не
   делать отдельный сетевой lookup и не создавать локальный кэш: наличие
   конкретного кода — ответственность Vetmanager, а проверяемая проблема —
   молчаливое преобразование названия в `0`. Добавить подтверждённое PUT-поле
   в `update_medical_card`.
3. **331.3 (≤100 LOC):** сделать `clinic_id` обязательным у
   `create_medical_card` и отклонять неположительное значение до I/O.
4. **331.4 (≤100 LOC):** регрессионные mock-тесты, документация контракта,
   evidence и тексты закрытия репортов #71/#73. Новые real-suite сценарии
   создания не добавлять, если аналогичных безопасных сценариев в нём нет.

## Решение

Предпочтителен минимальный вариант: не создавать локальный кэш справочников и
не подставлять «метиса» автоматически. `breed_id`, `type_id` и `clinic_id`
становятся обязательными положительными аргументами. Для `admission_type`
инструменты честно принимают только положительный целочисленный код из
`combo_manual_items`; строковое название отклоняется до I/O. Существование
кода не дублируется сетевым lookup: это исключает скрытый выбор справочника и
сохраняет один прямой вызов API.

## Acceptance criteria

- Схемы `create_pet` и `create_medical_card` отмечают обязательные поля;
  отсутствующее/нулевое обязательное значение не посылает HTTP-запрос.
- Описания не обещают `0 = unknown/default` и называют `admission_type` кодом
  справочника.
- `update_medical_card` передаёт подтверждённый код `admission_type`; прочие
  обязательные связи сохраняются существующим кодом.
- Guard-тесты сломаны намеренно, затем возвращены в зелёное состояние.
- После реализации живые вызовы именно MCP-инструментов подтверждают: локальный
  отказ отсутствующих/нулевых обязательных полей без I/O; успешный
  `create_pet` с действующими видом/породой; `create_medical_card` с кодом
  `admission_type`; и `update_medical_card` с новым кодом, с кодом и
  сокращённым телом ответа в evidence. Тестовые создания отмечены маркером
  этапа и не затрагивают существующие записи.
- Mock suite и opt-in real suite пройдены; результат real suite зафиксирован.

## Out of scope

- Автоматический подбор «неизвестной» породы, изменение справочников и новые
  real-suite сценарии создания: в существующем real suite уже есть сценарий
  создания медкарты, поэтому отдельный не добавляется.
- Изменение `update_pet`, прав доступа или исходников Vetmanager.

## Риски и rollback

Изменение обязательности сигнатур ломает некорректные прежние вызовы, но они
уже не создавали запись в Vetmanager. Откат — возврат предыдущей сигнатуры;
он не рекомендован, пока апстрим сохраняет подтверждённую валидацию.

## Architecture Critique

Не требуется: этап меняет локальные параметры и payload одного MCP-слоя,
не затрагивая auth, storage, public transport или новую архитектуру.

## Оценка простоты

Проверены triggers: нет новой абстракции, factory, кэша, второго API или
indirection. Разрешение названий через сетевой справочник увеличило бы число
вызовов и добавило бы неоднозначность, поэтому выбран прямой контракт с кодом.
