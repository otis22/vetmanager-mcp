# Этап 427 — маршруты трёх MCP-промптов

Дата: 23.10.2026. Источник: `Roadmap.md`, этап 427, и `artifacts/review/2026-10-20-full-stage-420.md`, R6. Решения владельца 427.1 утверждены.

## Цель и проверенные факты

Исправить три зарегистрированных промпта без изменения поведения инструментов. `get_clients` принимает `phone`, `name`, `status` и `filter`, но не отдельный `id`; фильтр `id` разрешён, `status=""` включает неактивных, ответ содержит серверное поле `balance`. Телефонный фильтр требует ≥4 цифр и сам нормализует ввод. `get_invoices` (`tools/invoice.py`) и `get_client_payment_applications` (`tools/finance.py`) принимают `client_id`, `limit` и `sort`; для обеих списковых выборок поддержано поле сортировки `create_date`. Applications не включают неприменённые авансы. `create_medical_card` требует `patient_id`, `doctor_id`, `date_create` в формате YYYY-MM-DD либо YYYY-MM-DD HH:MM:SS и `clinic_id`. Его `diagnosis` снят, а непустой `diagnosis_text` при создании отклоняется: текст сохраняется через `update_medical_card(card_id, diagnosis_text=...)`. `get_medical_card_by_id` читает карту по ID; поле в записи называется `diagnos_text`, что закреплено `tests/test_stage225_diagnosis_contract.py`. Эти факты проверены по текущему коду указанных инструментов; API поведения не домысливаем.

## Три acceptance

1. `find_client`: цифровой query рендерится с `get_clients(phone=query, limit=20)`, прочий — с `get_clients(name=query, limit=20)`; текст описывает обе ветки. Слишком короткий телефон (<4 цифр) должен быть запрошен заново до вызова инструмента. Красный сторож ловит подмену phone на name.
2. `client_balance`: рендер запрашивает клиентскую запись по `id` через поддерживаемый `filter` с `status=""` (включая неактивных), использует её `balance` как серверный баланс; при пустом результате не выдумывает баланс. Счета и применения платежей ограничены `limit=100`, явно отсортированы по `create_date DESC` и названы детализацией «последние 100»; это последние записи по дате создания, не обязательно последние события оплаты. Нельзя объявлять их сумму полным долгом. Красный сторож ловит подмену источника баланса на сумму документов.
3. `add_medical_note`: `clinic_id` обязательный аргумент промпта; рендер вызывает `create_medical_card(patient_id=pet_id, doctor_id=doctor_id, clinic_id=clinic_id, date_create=today, description=note)` с датой YYYY-MM-DD по локальному календарю клиники; если дата клиники неизвестна, агент выясняет её до записи. После успешного создания при непустом тексте диагноза — `update_medical_card(card_id=created_card_id, diagnosis_text=diagnosis)`; пустой текст не порождает update. Старый `diagnosis=diagnosis` не вызывается. ID извлекается из фактического успешного ответа, без предположения о ключе; если не найден, остановиться и сообщить неопределённость, не повторять create. При ошибке update сообщить ID созданной карты и частичный результат, проверить поле `diagnos_text` через `get_medical_card_by_id` перед повтором только update. Красный сторож ловит отсутствие `clinic_id`, устаревшее поле и потерю инструкции против дублирования.

## Архитектурное решение

Проблема: инструкции агенту расходятся с сигнатурами tools и семантикой upstream. Ограничение: публичный MCP prompt contract меняется; инструменты, доступ, безопасность и API payload остаются неизменными. Вариант буквально вызвать `get_clients(id=...)` и передать `diagnosis_text` на create невозможен по текущим сигнатуре и валидации. Выбран минимальный рабочий маршрут: ID-фильтр существующего list tool и двухшаговая запись свободного диагноза. Установка обязательного `clinic_id` ломает вызовы промпта старого клиента без него; это утверждённое владельцем изменение, описание промпта сообщает о новом аргументе, клиент должен запросить ветку до рендера. Сохраняется серверный источник баланса и утверждённое поле `diagnosis_text`. Инварианты: нет ложного total debt, нет retired `diagnosis`, обязательный `clinic_id`, не обещается сохранение текста до успешного update, не дублируется карта при частичной ошибке. Форма ID create-ответа не подтверждена живым вызовом в этом этапе; поэтому промпт не предполагает конкретный ключ и останавливается при отсутствии ID. Rollback — вернуть промпты и сторожа одним коммитом; при изменении upstream пересмотреть маршрут по живому контракту.

Architecture Critique: required — публичный MCP prompt contract и write-flow. PRD, Architecture Critique и diff-review проходят Spark → Astra+Opus по действующему workflow. Простота: три прямых промпта и три теста, без новых абстракций.
