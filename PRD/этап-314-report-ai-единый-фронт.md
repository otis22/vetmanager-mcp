# Этап 314. Report AI: единый фронт известных ограничений

## Цель

У активных известных проблем Report AI должен быть один честный и исполнимый
ответ: для каждого из трёх повторяющихся сюжетов зафиксировать, что исправляет
MCP, а что остаётся ограничением Vetmanager, и дать агенту безопасный следующий
шаг.

## Контекст и факты

- Live-кластер: #11, #19, #20, #28, #29, #35, #42. Все записи активны и имеют
  playbook, но решения исторически разнесены по отдельным инцидентам.
- `tools/report_ai.py` уже проводит вызовы Report AI через `_call_vm` и
  `instrument_call`; export-download также инструментирован. Нулевой счётчик
  из старой реализации через голый `VetmanagerClient` не воспроизводится.
- У upstream есть два разных предела: renderer физически отдаёт максимум 1000
  строк, а поле `limited` сравнивает с 10000. Этап 296 уже называет ровно 1000
  строк вероятной обрезкой и направляет в CSV/XLSX export; этап 303 зафиксировал
  первопричину как upstream и остановлен решением владельца.
- `intent_text` уже принимает до 20000 символов; старое ограничение 1000 не
  является текущим живым инцидентом. Новые агрегирующие инструменты не заводим
  (решение этапа 259).

## Решение по сюжетам

1. **Зависание / незавершение (#19, #28, #29, #35).** Ограничение upstream.
   MCP уже наблюдает очередь и ограничивает автоматический polling: не создавать
   дубликат, повторно проверить тот же ID позднее, после 15 минут для `job_id`
   или 30 минут для `report_file_id` остановить автоматические повторы. После
   остановки сообщить, что нужен повторный вызов того же ID позднее. Playbook
   обязан назвать именно этот путь.
2. **Обрезка строк (#11, #20).** Исправление уже находится в MCP: этап 296
   добавил явную диагностику при 1000 строках и штатный export через
   `get_report_ai_job_export` / `get_report_export_download`. Корень лимита
   остаётся upstream, отдельная новая правка кода не нужна.
3. **Идентификатор вместо ФИО (#42).** Ограничение данных upstream. Не выдавать
   identifier за имя и не строить N+1-цепочку пользователей. Пространство
   Report AI identifier не доказано равным `admission.user_id`, поэтому
   автоматически сопоставлять его с расписанием нельзя. В отдельном расписании
   `doctor_name` — конечный плейсхолдер приложения, не ФИО для текста модели;
   при отсутствии такого отдельного контекста честно оставить `doctor_id` с
   обозначением, что это идентификатор, а не имя.

## Scope

1. Сверить live-список и валидность playbook всех семи записей через штатный
   triage CLI; заменить playbook там, где он не выражает выбранное решение.
   Source of truth — production `known_issues`; playbook записывается только
   `set-playbook`, который валидирует JSON и имена инструментов. До замены
   сохраняется только маскированный штатный вывод; rollback — та же команда с
   предыдущим валидным JSON, без SQL и без файлов production-сервера.
2. Зафиксировать три решения и отсутствие метрик-дыры в AssumptionLog.
3. Обновить Roadmap и PRD. Если аудит обнаружит реальное отсутствие
   `instrument_call` на внешнем вызове Report AI, владелец этапа добавляет
   инструментирование в этом же этапе: сначала сторож-тест красным, затем
   зелёный тест и живой вызов изменённого инструмента с кодом и телом в
   AssumptionLog. Если граница уже инструментирована, код не меняется.

## Не входит

- Исправление renderer/queue Vetmanager и повторное решение владельца о крупном
  отчёте.
- Новый агрегирующий инструмент, расширение реестра полей или канал жалобы
  человека.

## Приёмка

- Ни одна из семи активных Report AI записей не остаётся без валидного playbook:
  #19/#28/#29/#35 запрещают дубликат job/export и называют повторную проверку
  того же ID с остановкой автоповторов после 15/30 минут; #11/#20 называют
  ровно 1000 строк признаком вероятной обрезки и путь CSV/XLSX export; #42
  запрещает выдавать `doctor_id` за ФИО и задаёт fallback при отсутствии
  `doctor_name`; playbook #42 не сопоставляет Report AI identifier с расписанием
  автоматически и направляет к `doctor_name` только для уже однозначно данной
  строки расписания.
- Операционный чек-лист в штатном `set-playbook`/`unreachable-issues` подтверждает
  каждый ID: #11 и #20 — export при 1000 строках; #19/#28/#35 — тот же `job_id`,
  остановка polling после 15 минут; #29 — тот же `report_file_id`, остановка
  polling после 30 минут; #42 — `doctor_id` не объявляется ФИО. До/после
  фиксируются только как ID, status и `playbook=yes`, без текста репортов.
- AssumptionLog содержит решение с обоснованием для всех трёх сюжетов.
- Аудит подтверждает метрики на границе каждого проверяемого Report AI
  инструмента. При найденной дыре применяются тест-first и живой вызов из
  Scope; при отсутствии дыры изменённых инструментов нет. Операционная
  проверка использует только triage CLI.
