# Этап 490. Безопасная диагностика отказов `get_invoices`

## Цель

Расследование 489 нашло два tool-level отказа с разными request ID, одним
worker и одной учётной записью. Runtime, nginx и audit не содержат безопасного
класса отказа, upstream status и формы аргументов. Цель — при следующем
естественном отказе отличить входную валидацию, локальную обработку,
transport и ответ Vetmanager без раскрытия данных клиники.

## Объём

1. До реализации проверить текущие точки обработки `get_invoices`,
   `crud_list`, клиента Vetmanager и обёртки ошибок. Определить одну точку
   адресного диагностического события; не расширять logging всех tools.
2. Записывать для отказавшего вызова только allowlisted поля: имя инструмента,
   `request_id`/`correlation_id`, идентификатор worker, фиксированный
   `failure_source` (`input`, `local`, `transport`, `upstream`, `unknown`),
   `error_class` из фиксированного набора (`input_validation`,
   `local_processing`, `connect`, `timeout`, `http_status`,
   `response_shape`, `unknown`), числовой HTTP/upstream status при наличии и
   форму параметров. Форма — имена разрешённых аргументов, признаки их
   присутствия, типы, число элементов `sort`/`filter` и allowlisted имена
   свойств; никакие значения, даже хеши свободного текста, не записывать.
   Не читать тело ответа и не сериализовать исключение для этого события.
3. Неизвестное исключение обозначать только `unknown`; traceback, `str(exc)`,
   URL, headers, токены, ID клиентов/счетов, даты, суммы, filter values,
   ответ API и raw args запрещены. Ограничить длину/кардинальность полей;
   неподдерживаемая форма должна быть `unknown`, а не строковым представлением.
4. Red privacy guard должен падать при добавлении значения, текста исключения
   или нового неразрешённого поля. После green выполнить focused, fast и
   применимые полные контуры по workflow. Изменённый инструмент вызвать
   вживую на выбранном до запуска тестовом стенде; приложить код и безопасное
   тело ответа. Продовый вызов ради диагностики не создавать.

## Приёмка и решение по результату

- Событие связывает runtime с audit по request ID и указывает worker,
  источник и класс ошибки; shape не содержит значений.
- При upstream отказе отдельно сохранён безопасный status/code. При локальном
  дефекте создать отдельный red→green fix PRD/этап; не чинить его в 490.
- При VM-side отказе зафиксировать наблюдаемое поведение и владельца, закрыть
  результат статусом `stop` без активного ожидания; возобновлять по новому
  фидбеку или подтверждённому исправлению upstream.

## Вне объёма

Retry, timeout, финансовая семантика, pagination, права и общий формат
логирования. Не добавлять traceback или захват request/response body.
