# Этап 386. Потерянная MCP-сессия: наблюдаемость и восстановление

## Цель и проверенные факты

Сделать видимой долю отказов `/mcp` из-за неизвестной сессии и дать клиентам
явный порядок восстановления. Наблюдение 14.10: один клиент часами повторял
`POST /mcp` с HTTP 404 без `initialize`. Другой источник давал 400 и
`missing_authorization`; Docker health-check обращается к `GET /healthz`.

FastMCP/mcp runtime возвращает 404 JSON-RPC `Session not found` при неизвестном
`Mcp-Session-Id`; тем же ответом скрывается несовпадение владельца сессии.
При неверном `Accept` transport возвращает 406; при отсутствующем обязательном
session ID — 400. `record_http_request` охватывает только custom routes.
Текущий `/metrics` собирает Redis shared counters; три slot должны видеть один
снимок. Главный PRD требует MCP-совместимый клиент, технические требования
закрепляют streamable HTTP `/mcp`; OpenAPI Vetmanager к transport не относится.

## Архитектурное решение

**Проблема:** FastMCP обслуживает `/mcp` вне custom route observation, поэтому
транспортный отказ не измеряется, а клиент не знает, когда сбросить session ID.

**Варианты:** (1) менять FastMCP handler — хрупкая привязка к upstream;
(2) ASGI middleware на входе сервера — наблюдает фактический статус и не
буферизует поток; (3) разбор access log — дублирует метрики и может затянуть
чувствительные данные. Выбран (2). Считать только завершённые `/mcp` отказы
400/404/406 в новом Redis counter с закрытыми метками `status_code`, `reason`.
Для 404 `session_not_found` только при точном JSON-RPC сообщении, иначе
`other`; для 400 различать фиксированный `missing_authorization` как `missing_auth` и
`missing_session`, иначе `other`; для 406 `invalid_accept`, иначе `other`.
Тело ограничивается несколькими КБ в памяти одного запроса, не логируется.
Никакие session ID, IP, токены или текст ошибки не экспортируются.
При успешной отправке `http.response.start` любого `/mcp` ответа в существующую
shared `http_requests_total{route=MCP_PATH,method,status_code}` добавляется
знаменатель; методы ограничены GET/POST/DELETE/OTHER. В том числе считаются
открытые SSE-ответы. Доля = прирост `session_not_found` / прирост всех
ответов настроенного MCP route за одно окно; во время rolling deploy наблюдаются
только новые slot, поэтому интерпретировать долю после завершения rollout.
Этот путь пишет непосредственно в shared Redis, не создавая process-local
счётчик.

Ответ 404 остаётся по MCP протоколу. Уточнять его текст опасно: 404 также
скрывает несовпадение владельца. В клиентской документации: на 404
`Session not found` отбросить прежний ID, выполнить новый `initialize` без
него и продолжить с новым ID; перед повтором записи проверить её результат.
Метрика показывает класс, но не причину потери и не факт доставки клиенту.

Новый counter хранится в отдельном Redis hash: старый slot читает прежний
`COUNTERS_KEY` и не встречает неизвестную семью при rolling deploy/rollback.
Новая версия объединяет оба hash при scrape. Это проверяется сторожем на
отсутствие новой семьи в старом hash.

**Инварианты:** обычные MCP ответы и SSE не меняются; middleware не читает
request body и не буферизует response stream; счётчик только shared Redis;
отказ Redis не меняет ответ; метки имеют фиксированный конечный словарь.
**Rollback:** старая версия игнорирует отдельный hash; его можно оставить
до плановой очистки. Клиентский совет остаётся совместимым с MCP. При
изменении текста FastMCP неизвестный ответ
попадает в `other`, а не ошибочно в `session_not_found`.

## Приёмка и декомпозиция

1. Сторожа transport: реальные 404/400/406, сохранение ответа, bounded метки,
   отсутствие дублей и Redis shared на трёх slot; показать красное состояние.
   ≤150 строк кода.
2. Middleware, счётчик, экспозиция HELP/TYPE, клиентская инструкция. ≤150 строк.
3. Изолированный живой тест: старый ID → 404 и прирост `session_not_found`
   на всех трёх `/metrics` в пределах 5 секунд (общая запись асинхронна);
   новый `initialize` → 200. Затем review,
   полный mock suite, commit, push, CI и production read-only smoke.

Architecture Critique требуется: transport contract, privacy и нагрузка.

## Оценка простоты

Один ASGI middleware считает уже сформированные ответы. Состояние сессии,
повторные попытки клиента и FastMCP handler не меняются. Новые причины
закрыты конечным словарём, новый Redis hash нужен только для безопасного
rolling deploy и отката старого reader.
