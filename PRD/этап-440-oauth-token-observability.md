# Этап 440. Наблюдаемость отказов `/oauth/token`

## Цель и проверенные факты

Инцидент 26.10.2026, account 44: 11 ответов 400 на refresh старого отозванного гранта при активном гранте того же клиента. Сейчас `web_routes_oauth.py` возвращает `OAuthRequestError` без события; `oauth_service.py` знает грант в refresh-ветке, но не передаёт его обработчику. `service_metrics.py` и `shared_metric_counters.py` предоставляют процессные и общие Prometheus-счётчики. `OAuthGrant` хранит account, client, status; `OAuthRefreshToken` — хеш и grant_id. Главный PRD требует структурированных логов и `/metrics`; технические требования описывают их контур. Vetmanager REST API не вызывается и его OpenAPI-контракт не меняется.

## Архитектурное решение

**Проблема:** код OAuth-отказа и идентификаторы связи не наблюдаемы, а повторный refresh отозванного гранта с живым наследником нельзя отличить от обычного invalid_grant.

**Варианты:** локальная память для дедупликации проста, но сбрасывается и не разделяется воркерами; Redis SET NX требует зависимости от работоспособности необязательного Redis; атомарная отметка в PostgreSQL на account держится между воркерами и перезапусками. Выбрана колонка `oauth_stale_refresh_marked_at` в `accounts` и условный `UPDATE` с интервалом 24 часа. Метрика повышается только при успешном захвате отметки. Отказ остаётся отказом, даже если наблюдаемость недоступна.

В обработчике `/oauth/token` один общий путь записи `oauth_token_rejected` для всех `OAuthRequestError`, включая `invalid_client`, обеих веток; ограниченные значения `error` и `grant_type` — метки счётчика, а `client_id` и `grant_id` — только поля лога. Значения `error` и `grant_type` вне фиксированных allowlist сводятся к `other`; `client_id` пишется только если совпадает с форматом выданного ID, иначе null. Токены, code, verifier, resource и description не логируются. Неверный Content-Type получает счётчик `invalid_request`, rate-limit — `temporarily_unavailable`; их лог ограничен одним событием на воркер в минуту для каждого кода без динамических ключей и памяти на IP. Для FormPayloadTooLarge сохраняется прежний 413, для UnicodeDecodeError сохраняется прежний 500; оба получают bounded `invalid_request` метрику/лог без сырого тела. Неизвестный grant_id — null. Сервис переносит `grant_id` и `account_id` в типизированные поля `OAuthRequestError` **только после успешного lookup хеша токена и проверки client/resource binding**; обработчик получает их после выхода из `async with` обменной сессии. Фактический порядок: hash lookup → client/resource binding → active-client check → grant status. Случай требует `grant.status=revoked`, а не только `refresh_token.status=revoked` при активном гранте. Затем в новой короткой сессии ищем active-грант того же account+client, отличный от старого, и атомарно захватываем суточную отметку. Увеличить stale-счётчик разрешено только после успешного commit. Ошибка этой транзакции логируется без секрета и не меняет исходный OAuth-отказ. Этот запрос не запускается для неизвестного токена, неверного binding, активного гранта или authorization code. Маркер не инициирует Telegram-алерт; только счётчик для сводки.

Обе новые семьи shared counters пишутся в **отдельные Redis-ключи**, как `mcp_transport_rejections_total`, а не в `COUNTERS_KEY`: старый воркер отвергает неизвестные семьи в общем хеше, что сломало бы `/metrics` в смешанном релизе. Новый snapshot читает отдельные ключи; отсутствующий ключ означает ноль. Старый snapshot их игнорирует. При недоступном Redis применяется текущий общий fail-closed контракт `/metrics`; отказ `/oauth/token` от этого не зависит.

**Инварианты:** OAuth HTTP-контракт и security-проверки не меняются; ошибку не превращаем в успех; в логах и метриках нет значений токенов; метки имеют фиксированный конечный набор; разные account дедуплицируются отдельно, один account не чаще раза за 24 часа; отозванный грант без наследника не отмечается. Дедупликация намеренно по account, даже если у него несколько client_id: таково решение владельца о частоте сигнала, ограничение подтверждается тестом. При сбое проверки маркера основной invalid_grant и обычное событие отказа сохраняются. Rollout: сначала расширить схему nullable-колонкой, потом новый код. Rollback: сначала старый код, затем удалить колонку; при временном несовпадении новый код сохраняет основной отказ, но тихий маркер может пропасть.

Ограничение двух хранилищ: между Postgres commit отметки и асинхронной доставкой в Redis возможна потеря только метрики при аварии процесса/Redis. После commit пишется отдельное `oauth_stale_grant_refresh` событие с account_id/client_id/grant_id без токена, по которому можно восстановить сводку. Общий контракт метрик уже допускает потерю доставки (`shared_metric_event_lost`); усложнение до outbox ради редкого случая не входит в этап.

Architecture Critique нужен: auth, storage и production-наблюдаемость. Совместить с сильным PRD-гейтом, если prompt покрывает архитектуру, полноту критериев и rollback.

## Приёмка

- Битый refresh через HTTP даёт 400 `invalid_grant`, структурированное событие с `error=invalid_grant`, `grant_type=refresh_token`, client_id и null grant_id, плюс `vetmanager_oauth_token_errors_total{error="invalid_grant",grant_type="refresh_token"}`.
- Ошибки authorization_code, invalid_client, malformed form, unsupported grant_type, неверного Content-Type (415), oversized form (413), invalid UTF-8 (текущий 500) и rate limit (429) наблюдаемы с ограниченными метками; повторные 415/429 не создают построчный лог при флуде; мусорные client_id и grant_type не дают log injection или новых меток; нет секретов в логе/метриках.
- Refresh известного отозванного гранта с active-грантом того же account+client даёт 400, старый grant_id в логе и один `vetmanager_oauth_stale_grant_refresh_total` на account за 24 часа. Без наследника, с иным client или с неверным binding маркер не растёт.
- Конкурентные вызовы в разных сессиях повышают суточный маркер один раз; отметка переживает переоткрытие сессии. Ошибка поиска/commit сохраняет HTTP 400 и основной лог, но не увеличивает маркер.
- После записи новых Redis-счётчиков старый reader общего `COUNTERS_KEY` продолжает отдавать `/metrics`; проверяется смешанная версия и пустые новые ключи. Миграция применяется штатным `alembic upgrade head` перед новым кодом, старый код проверяется с новой nullable-колонкой. Rollback: вернуть старый код, затем адресно откатить миграцию этапа 440 до её родительской ревизии только если нет более поздних миграций; при более поздних — отдельный согласованный schema rollback.
- Live-контроль на стенде: HTTP-код и тело битого refresh, фрагмент лога/метрики; сценарий отозванного гранта с наследником без затрагивания production.

## Декомпозиция

1. **440.1, ≤2 ч / ≤150 строк тестов:** красные HTTP-сторожа для кодов, отсутствия секретов, stale с наследником и без него, дедупликации и разных account. PRD и гейты до кода.
2. **440.2a, ≤2 ч / ≤150 строк кода:** контекст отказа, общий лог и bounded метрика, оба OAuth grant_type; red → green.
3. **440.2b, ≤2 ч / ≤150 строк кода:** атомарная суточная отметка, миграция, stale-маркер, фокусные тесты; затем аудит и committed-diff гейт.
4. **440.2c, ≤2 ч:** полный mock+real suite по финальному SHA с окном real suite ≥35 минут, живой стенд, Roadmap/AssumptionLog, push только dev-ветки и зелёный CI. Main/production — задача супервизора.

## Простота

Один обработчик событий отказа в web-роуте; дополнительный SQL выполняется лишь на известном отозванном refresh-гранте. Отдельная очередь и алертинг не нужны.
