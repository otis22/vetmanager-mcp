# Этап 323. Честная пагинация при ненадёжном `totalCount`

## Цель

Не выдавать неполную выборку Vetmanager за полную, если list-ответ не содержит
валидного `totalCount`, содержит заниженный счётчик либо возвращает прикладную
ошибку внутри HTTP 200. Для склеиваемых поисков обе ветки должны быть дочитаны,
дедуплицированы и отсортированы до применения пользовательских `offset` и
`limit`.

Finding F16–F19 из супер-ревью 16.09.2026 рассматриваются как указатели. Ниже
решение опирается на проверку исходников Ветменеджера и read-only пробы живого
тестового контура, выполненные до изменения MCP-кода.

## Проверенные факты API

### List и `totalCount`

- Обычный REST list выполняет получение страницы и подсчёт отдельными
  операциями с одинаковыми фильтрами/relations; лимит применяется только к
  странице, не к count. Поэтому при стабильных данных фильтр или join не дают
  отдельного механизма, который штатно занижает count относительно полной
  страницы.
- Страница получается раньше count. Конкурентное удаление между операциями
  способно дать наблюдаемый `totalCount` меньше уже полученной полной страницы.
  Поэтому полная страница — достаточное evidence продолжать чтение независимо
  от счётчика; остановка допустима только на короткой/пустой странице.
- 16.09.2026 read-only вызовы `invoice`, `invoiceDocument`, `user` и
  `closingOfInvoices` с `limit=1` вернули HTTP 200, `success=true`, объект
  `data`, целочисленный `totalCount` и одну строку. Штатный list всегда формирует
  счётчик, но MCP всё равно обязан fail-closed/дочитывать при нарушенном
  envelope, а не молча терять данные.
- Серверный предел `limit` фактически не зажимается. Это не отменяет локальные
  row/call caps и детектор отсутствия прогресса.

### OR и `IN`

- Фильтры верхнего уровня соединяются только через AND. Поддерживаются
  сравнения и `IN`/`NOT IN` значений одного поля; OR-групп и `IN` сразу по
  разным полям в REST filter contract нет.
- Живая проба вложенной OR-группы для `user` и `closingOfInvoices` вернула HTTP
  406 с `success=false`; `IN` нескольких значений одного `user.id` вернул HTTP
  200 с числовым `totalCount`.
- Следовательно, один запрос не выражает ни
  `last_name LIKE X OR first_name LIKE X`, ни
  `minus_document_id=I OR plus_document_id=I`. Остаются две ветки с полным
  bounded scan, дедупликацией и локальной глобальной сортировкой.

### Ошибки list

- Текущий exception path REST возвращает исходный HTTP-код: неверное имя
  фильтра на всех четырёх проверенных list endpoints дало HTTP 406,
  `success=false`, `error=true`. В штатном exception path HTTP 200-вариант не
  подтверждён ни исходниками, ни живой пробой.
- Тем не менее HTTP 200 с `success=false` остаётся допустимым нарушением
  transport/application boundary (proxy, иная версия или custom endpoint), а
  нынешняя period-ветка действительно превращает такой объект и malformed
  `data`/rows в пустую успешную страницу. F19 подтверждён как defensive bug в
  MCP, но не как воспроизведённый штатный ответ текущего стенда.

## Решение

### 323.1 Общий helper пагинации

`paginate_all`:

- принимает отсутствующий, bool, отрицательный, строковый или иной невалидный
  `totalCount` как unknown, но дочитывает страницы;
- не завершает scan по `totalCount`, если страница полная. Короткая страница
  завершает scan только при unknown счётчике или когда собрано не меньше
  валидного счётчика текущей страницы; при её `totalCount > collected` чтение
  продолжается. Пустая страница до валидного счётчика именно текущей страницы
  считается рассинхроном и даёт ошибку. Старый/максимальный снимок счётчика не
  удерживается: это исключает ложный отказ при конкурентном удалении;
- возвращает фактически собранное полное количество, а не неподтверждённое
  число envelope;
- требует `success is True`; отсутствующий/null/строковый флаг, malformed
  `data` и не-list entity rows отклоняются санитизированной reportable error;
- сохраняет `max_rows`, добавляет `max_calls=1000` и детектор повторной
  непустой страницы/отсутствия прогресса по нормализованным стабильным ID (с
  fallback на полный payload для нестандартной сущности без ID). Достижение
  guard означает ошибку, а не частичный успешный ответ. Каждый upstream scan
  использует полный порядок:
  к выбранному sort добавляется отсутствующий `id ASC`, а без sort идёт
  `id ASC`;

Расчёт свободных слотов и финансовый average используют тот же helper. Его
гарантии после изменения fail-closed: нарушение envelope, cap или повтор
страницы не превращаются в безопасный на вид результат. Локальный `_all_rows`
переоценки этапа 322 не переиспользуется и не ослабляется: он продолжает
требовать строгий стабильный `totalCount` до любой записи.

### 323.2 Склейка двух веток

Для invoice closings и поиска пользователей по имени:

- две невозможные через REST OR-ветки читаются параллельно через bounded
  `paginate_all`;
- превышение caps даёт явную ошибку и не возвращает partial page;
- строки дедуплицируются по `id`, затем весь merge локально сортируется по
  проверенному allowlist sort; к пользовательскому sort добавляется отсутствующий
  `id ASC` как уникальный tie-breaker, без sort используется `id ASC`;
- каждая merge-строка обязана иметь integer либо decimal-string `id`; значение
  нормализуется в int до дедупликации и tie-break. Missing, bool, null и иные
  значения дают санитизированную contract error вместо object-identity
  fallback и выдуманного `totalCount`;
- локальный ключ сортировки детерминирован для malformed/mixed данных: null
  всегда после значений, числа сравниваются численно, строки — по
  `casefold()` и исходной строке, прочие значения — по имени типа и строковому
  представлению; такая локальная семантика явно не обещает collation конкретной
  базы, но остаётся стабильной между страницами одного полного merge;
- только после этого применяются `offset` и `limit`;
- успешный ответ содержит `totalCount=len(full_merge)` и `limited=false`.
  Значение не выдумывается из размера одной страницы. Ошибка caps не маскируется
  как `limited=false`. Для обеих веток действуют `max_rows=10000` и
  `max_calls=1000`; отказ советует сузить name/filter либо проверить конкретный
  invoice, partial rows не отдаёт;

### 323.3 Period envelope

Обе фазы `get_invoice_documents_by_period` (`invoice` и `invoiceDocument`)
проверяют до извлечения строк:

- response — объект, `success is True` (missing/null/строка отклоняются);
- `data` — объект, entity rows — список;
- прикладная ошибка и malformed envelope дают санитизированную reportable
  upstream contract error;
- invoice `id`, а также invoiceDocument `id`/`document_id` должны быть
  integer-like; непригодная для связки строка отклоняет scan, а не исчезает из
  финансового результата. Финальная сортировка использует тот же
  null/type-aware helper и не вызывает сырой `int(...)` на неизвестном типе;
- повторная полная страница в любой из двух фаз считается отсутствием
  прогресса и отклоняется санитизированной ошибкой, чтобы дубликаты не стали
  успешным финансовым результатом;
- полная страница дочитывается независимо от `totalCount`; существующий общий
  лимит 20 upstream calls остаётся и при исчерпании возвращает честный
  `limited=true` без строк. Это намеренное отличие от общего helper: period tool
  с этапа 318 имеет публичный bounded-result контракт и возвращает отдельные
  `limited_reason`, `upstream_calls`, `next_offset=null` и совет сузить период;
  он не возвращает ни одной частичной финансовой строки и не заявляет
  `limited=false`/`totalCount=0`.

## Декомпозиция

- **323.1 (≤150 LOC):** красные guards отсутствующего/невалидного и заниженного
  `totalCount`, не-true `success`, malformed envelope, repeated full page и caps;
  затем укрепление `paginate_all` без изменения `_all_rows` склада.
- **323.2a (≤150 LOC):** красные guards invoice closings: обе ветки больше
  страницы, дедуп, одинаковые sort-значения с `id` tie-breaker, глобальная
  ASC/DESC сортировка, offset/limit и честные metadata; затем реализация.
- **323.2b (≤150 LOC):** те же guards и реализация для поиска пользователей с
  сохранением privacy projection.
- **323.3 (≤120 LOC):** красные guards HTTP-200 с любым не-true `success` и
  malformed envelope отдельно для invoice и invoiceDocument; затем fail-closed
  проверка period scan.
- **323.4:** focused/full tests, живые read-only вызовы изменённых tools,
  аудит, workflow/review gates, commit, push и CI/deploy.

## Acceptance criteria

1. Полная страница всегда вызывает чтение следующей; absent/invalid/low
   `totalCount` не обрывает scan. Короткая страница при валидном большем
   счётчике продолжает чтение, а преждевременно пустая даёт ошибку.
2. Scan конечен по короткой/пустой странице, `max_rows`, call budget и
   no-progress guard; guard failures не возвращают partial success.
3. `_all_rows` этапа 322 и real-test 245 не ослаблены.
4. Invoice closings и user name search дочитывают обе ветки, дедуплицируют,
   глобально сортируют с серверным и локальным `id` tie-breaker, затем режут
   page; успешные `totalCount` и `limited` соответствуют полному merge; null и
   смешанные типы не ломают сортировку.
5. Period scan различает пустую страницу, любой не-true `success` и malformed
   envelope для обеих сущностей.
6. Новые regression guards показаны красными намеренной поломкой охраняемого
   поведения и зелёными после реализации.
7. Изменённые инструменты вызваны на тестовом стенде; в AssumptionLog записаны
   только безопасные к публикации коды и формы ответов.

## Out of scope

- изменение REST API Ветменеджера или добавление OR-синтаксиса;
- ослабление fail-closed `_all_rows` массовой переоценки;
- cursor/keyset pagination и snapshot isolation, которых upstream не даёт;
- исправление отдельного flake real-теста этапа 245;
- возврат partial rows после достижения safety caps.

## Оценка простоты

Один усиленный `paginate_all` переиспользуется тремя существующими сценариями
и двумя merge-ветками. Отдельный paginator для каждого tool дублировал бы caps,
envelope checks и no-progress policy. Локальная сортировка нужна ровно двум
невозможным через REST OR-поискам и оформляется одной небольшой функцией без
классов/протоколов. Новые state machine, configurable factories и compatibility
shim не нужны; изменение укладывается в существующие helper/tool boundaries.
