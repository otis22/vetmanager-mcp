# Этап 422 — privacy Report AI reject и частичных ошибок

Дата: 20.10.2026. Источник: `artifacts/review/2026-10-20-full-stage-420.md`, R1 и R2.

## Цель и граница

При `is_depersonalized=True` результат `reject_report_ai_job_candidate` должен проходить ту же value-level очистку, что остальные job-результаты Report AI. Сейчас `REPORT_COLUMN_TOOLS` нормализует имена колонок, но не включает `report_mode` в `sanitize_tool_result`; policy reject отличается именно пропущенным слоем значений. Имена сгенерированных JSON-колонок произвольны: если в самом имени есть ФИО/email, его чистим согласованно в `rows`, `preview_example_row` и `columns` metadata (строки и объекты с `name`); коллизия очищенных имён fail-closed. Для имени нельзя применять исключение по маркеру улицы, которое есть у report-value: `Smith John Doe улица` и `Иванов И. И. улица` обязаны скрыть ФИО. Колонки `good` и `clinic` в report-mode не должны обходить очистку значения через исключение для неперсональной сущности. Для токена с ПД исходный результат сохраняется. CSV export имеет отдельный путь заголовков и не входит в R1/R2; его незакрытую границу фиксируем отдельно, не заявляя общую защиту всех заголовков.

Частичный `get_client_profile` и `get_pet_profile` несут `section_errors`. У pet-профиля ошибка документа счёта дублируется в `section_errors.invoice_documents[<id>]` и `last_invoices[*].invoice_documents_error`. `error_type` и `retryable` — безопасная структурная диагностика; свободный `message` исключения может содержать ПД и при токене без ПД заменяется точной строкой `Section request failed; see error_type and retryable.` во всех трёх местах на выходной границе MCP. При токене с ПД прежний `message` сохраняется. Существующая очистка успешных секций не меняется. Журнал `aggregator_partial` всегда получает только безопасные `error_type/retryable`, независимо от типа токена: он хранится вне границы MCP-ответа и не должен сохранять произвольный текст исключения.

## Архитектурное решение

Проблема: общая обёртка MCP включает report-mode по неполному набору имён; агрегатор формирует исключение до общей очистки и его `message` не является предсказуемым полем клиента.

Контекст: `tools/__init__.py` — единая граница по `credentials.is_depersonalized`; `resources/_aggregation.py` сохраняет структуру `error_type/retryable/message`. Требования проекта: не ослаблять слои stage 275–278, не превращать частичный ответ в полный отказ, не раскрывать текст апстрима токену без ПД.

Варианты: (1) чистить `str(exception)` словарём — останутся неизвестные формы ПД; (2) менять `gather_sections` для всех токенов — потеряется диагностика токена с ПД; (3) на выходе обёртки заменять `message` структурных секционных ошибок для профилей при деперсонализации, включая вложенные ошибки и дубликат в строке счёта, логировать лишь классификацию ошибки и включить reject в `REPORT_TOOLS`. Выбран (3): fail-closed для непредсказуемого текста, сохраняет machine-readable тип и retryability, действует на оба профиля и не меняет full-access ответ. Неожиданная форма `section_errors` у токена без ПД отклоняется безопасной ошибкой санитайзера вместо отдачи произвольного текста.

Инварианты: у токена без ПД произвольные имена и значения preview и текст ошибок не содержат ФИО/телефон/email; `error_type/retryable` не теряются; у токена с ПД диагностика без изменений; журнал не содержит произвольного текста секционной ошибки; обычные нерепортные поля продолжают прежнюю обработку. Rollback: вернуть изменение обёртки только после закрытия регрессии другим fail-closed способом; при неизвестном формате section_errors ответ санитайзера безопасен.

Architecture Critique и PRD-review: один сильный gate с prompt на архитектуру, scope, alternatives, risks, acceptance, tests и rollback; Spark перед ним, затем Astra и Sol xhigh параллельно. Указание владельца заменяет Opus на Sol.

## Декомпозиция и приёмка

1. **422.1, ≤2 ч**: PRD, исходниковая сверка, два красных MCP-сторожа до фикса, review gate. Красная мутация R1: произвольно названная `preview_example_row` с email/ФИО попадает в ответ reject, включая имена `good` и `clinic`. Красная мутация R2: частичная ошибка профиля с ПД в `message` попадает в ответ. Отдельный сторож чувствительного имени preview-колонки (также `Smith John Doe улица`) и коллизии после редактирования имени: в первом случае ключ очищен, во втором отдаётся безопасный отказ. Некорректная секционная ошибка с дополнительным текстовым полем не попадает в ответ токену без ПД; некорректный элемент `last_invoices` даёт безопасный отказ.
2. **422.2, ≤150 строк кода на подзадачу**: включить report-mode reject и добавить безопасную сериализацию `section_errors` на границе wrapper; фокусная матрица под токенами с ПД/без ПД для личных и неличных значений, включая оба профиля и вложенные invoice-document ошибки; отдельный тест реального `gather_sections` проверяет отсутствие текста исключения в логе. Live calls reject и агрегата, audit, committed review, полный mock+real suite, push в ветку и зелёный Tests. Выпуск = зелёный CI ветки, пост-релизные проверки после мержа.

Стенд: для live MCP выбрать `.env` TEST_DOMAIN/TEST_API_KEY, если полномочия и данные позволяют добиться нужных состояний; иначе bearer-стенд с разрешённым токеном. Решение записать до вызова. Не публиковать ответные ПД/секреты.
