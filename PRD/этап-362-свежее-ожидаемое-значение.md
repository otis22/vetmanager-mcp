# Этап 362 — свежее ожидаемое значение перед записью

## Цель и приёмка

При подтверждённой записи цены с `expected_price` значение сравнивается с текущим значением Vetmanager, даже если обычное чтение ранее прогрело кэш. При расхождении PUT не отправляется, сообщение `ToolInputError` содержит свежую цену как `str(_money(row['price']))`: для `2200.0000000000` агент видит `2200.0000000000`. Нечисловую цену проверка отклоняет до PUT. Проверка статуса из этапа 356 сохраняет ту же гарантию. Обычные чтения и записи цены без `expected_price` сохраняют прежнюю политику кэша. На devtr6 подтверждённое изменение цены и статуса проходит, исходные значения восстановлены.

## Проверенные факты и границы

- `goodSaleParam` имеет строковое десятичное поле `price`; OpenAPI v6 описывает `GET /rest/api/goodSaleParam/{ID}` и `PUT` той же строки. Запись цены использует только `price`, запись статуса только `status`.
- `VetmanagerClient.get(..., fresh=True)` и `crud_get_by_id(..., fresh=True)` обходят process-local кэш. В текущем `VetmanagerClient._request` флаг `not fresh` входит в `should_cache_get` и отключает также **запись** свежего ответа в кэш; это требуется изменить на уровне транспорта. Обычный GET кэшируется на 900 секунд. `PUT` инвалидирует тег сущности, но изменение в самом Vetmanager кэш MCP не инвалидирует.
- В `tools/warehouse.py` проверка `expected_price` этапа 322 сейчас читает без `fresh`; подтверждение статуса этапа 356 уже читает с `fresh=True` и сверяет подписанный снимок. Других сравнений ожидаемого значения с записью в инструментах не найдено. Групповая переоценка не принимает `expected_price` и не обещает optimistic guard для каждой строки.
- REST не предоставляет атомарный compare-and-swap. Между GET и PUT остаётся гонка; readback сообщает о расхождении результата. Процентные и массовые записи без `expected_price` могут строить план по кэшированному значению; это существующее ограничение инструмента, который не обещает сверку ожидания для этих режимов. Их безопасность и возможный отдельный guard требуют самостоятельного контракта и не расширяются этим этапом.

## Архитектурное решение

**Проблема.** Сверка с локальным кэшем подтверждает устаревшую цену и пропускает запись поверх новой цены Vetmanager.

**Варианты.** Глобально отключить кэш для `goodSaleParam` просто, но ухудшит обычные чтения и не нужно для цели. Инвалидировать кэш непосредственно перед сверкой сложнее и затрагивает другие запросы процесса. Выбран точечный `fresh=True` в GET при подтверждённой записи цены только с непустым `expected_price`, как уже сделано для проверки подписанного статуса. В транспорте отделяется право кэшировать endpoint от решения читать из кэша: успешный свежий GET обновляет запись **того же ключа** (домен, credentials, account, URL), но не кэшируемые endpoints сохраняют исключение. Ошибка свежего GET не меняет прежний кэш; запись блокируется, обычное чтение может оставаться устаревшим до TTL или следующего успешного свежего запроса. Записи цены без `expected_price`, в том числе процентные и массовые, сохраняют прежний путь; у них нет обещания сравнения с ожидаемым значением. Это сохраняет нагрузку остальных чтений и записей.

**Инварианты.** Сверка цены и статуса перед записью обходит кэш; при расхождении PUT не отправляется; ответ цены содержит фактическое текущее значение; обычное чтение попадает в обновлённый кэш. На сетевой ошибке проверочного GET запись не происходит и старое значение кэша не используется как fallback. Rollback при неожиданной нагрузке upstream: revert изменения с явной известной деградацией гарантии от устаревшего кэша; до исправления ограничить использование подтверждённой записи цены. При изменении контракта upstream — остановить запись и сверить OpenAPI/живой ответ.

## Проверки

Тест прогревает кэш старой ценой, затем меняет ответ upstream; подтверждённая запись с прежним `expected_price` обязана отказать без PUT, сохранить тип `ToolInputError` и показать новую цену в сообщении. Обычное чтение после отказа возвращает уже новую цену из обновлённого кэша без второго HTTP GET; обычные чтения до свежей проверки также остаются кэшированными. Тест сетевой ошибки свежего GET требует отсутствие PUT и отсутствие fallback к старому кэшу при записи; обычный GET может прочитать прежний кэш. Нечисловая цена свежего GET даёт существующий `reportable_error` до PUT. Транспортные тесты проверяют запись свежего ответа по обычному ключу, отсутствие записи при ошибке и для исключённых endpoints. Статусный тест прогревает кэш до изменения и проверяет отказ подтверждения без PUT. Оба guard-теста показываются красными при удалённом `fresh=True`. Живая devtr6 проверка включает прогретый MCP кэш, изменение цены прямым тестовым REST PUT, отказ MCP с текущей ценой без PUT и обязательное восстановление; затем успешные изменение цены и статуса с восстановлением. Фокусные тесты идут между review; полные mock и opt-in real suite — один раз на финальном коде перед push.
