# Этап 402. CI-гигиена сборки и теста параллельности

## Цель и проверенные факты

За 15–16.10.2026 пять запусков Tests падали до тестов при скачивании `public.ecr.aws/docker/library/python:3.12-slim`: ECR ответил 429 `toomanyrequests: Data limit exceeded`. `.github/workflows/test.yml` содержит три одинаковых шага Docker build (fast, default, postgres); ручной `.github/workflows/test-real.yml` содержит четвёртый. PostgreSQL service image `public.ecr.aws/docker/library/postgres:16-alpine` GitHub Actions загружает до checkout; этот отдельный отказ нельзя обернуть скриптом шага, он остаётся вне этапа. `Deploy Prod` запускается только после успешного `Tests` на main. Тест `test_get_users_name_search_runs_last_and_first_name_in_parallel` измеряет `perf_counter` вокруг вызова с двумя `sleep(0.05)` и порогом 0.09 с; это зависит от нагрузки runner. Реализация `get_users` применяет `asyncio.gather` к двум поискам. Технические требования и общий PRD проекта изучены; контракт Vetmanager API не меняется.

## Требования и приёмка

- В каждом из четырёх шагов Docker build использовать один скрипт ограниченного повтора. Не повторять тестовый шаг и не изменять `Deploy Prod`.
- Повторять только доказанный ECR 429 при загрузке базового образа: последняя итоговая строка ошибки Docker/BuildKit (`ERROR: failed to build/solve`) должна одновременно содержать `public.ecr.aws/docker/library/python:3.12-slim`, `toomanyrequests: Data limit exceeded` и маркер неудачного pull/resolve base image (`failed to resolve source metadata` или `failed to copy`). Это сверено с фактическим выводом упавшего CI run 38866717172; предыдущая ECR ошибка перед итоговой ошибкой Dockerfile не разрешает повтор. Иной exit, включая ошибки Dockerfile и тестов, завершать немедленно с исходным кодом. Лог каждой попытки, классификацию и паузу печатать в CI без секретов. Максимум три сборки, паузы 5 и 15 с; после третьей ошибки завершать с исходным кодом. Вывод не сохранять в артефакты.
- Контрактный тест скрипта: симулированный 429 → повтор/успех; непреходящая ошибка → одна попытка/исходный exit; серия 429 → ровно три попытки/отказ. Показать красный сторож удалением классификации/повтора.
- Тест `get_users` подтверждает оба фильтра и одновременный старт до завершения любого поиска без измерения стенового времени. Каждая фиктивная ветвь помечает старт и уступает event loop; до возврата любой ветви проверяется, что стартовали обе. Показать красный сторож заменой `gather` на последовательные вызовы. Повторить фокусный тест N=30 раз без падений.
- Выпуск: оба сильных verdict после Spark на PRD и committed diff; аудит; один полный mock и real suite на финальном кодовом SHA; push main; зелёный `Tests` и наблюдение последующего `Deploy Prod`. Текущий `deploy_scope_check.sh` считает workflow, script и test изменениями для деплоя, поэтому после успешного Tests ожидается production cutover. Проверить `deploy` job и post-deploy smoke. Сбой внутренней проверки cutover обрабатывается существующим автоматическим rollback; внешний public smoke имеет `continue-on-error: true` и при warning требует отдельной диагностики, а не автоматического rollback.

## Архитектурное решение

**Проблема:** внешний лимит ECR случайно ломает CI до тестов; стеновое время делает асинхронный тест чувствительным к нагрузке runner.

**Варианты:** повтор всего job может скрыть реальные падения тестов и дорог; переход на иной registry не решает сбой внешнего источника и меняет цепочку образа; общий shell wrapper четырёх шагов оставляет тесты вне повтора. Для теста увеличение порога сохраняет флаки; синхронизация корутин по шагам event loop проверяет именно порядок старта. Выбран wrapper и детерминированная синхронизация.

**Инварианты:** неуспех тестов никогда не повторяется; неклассифицированная сборка не повторяется; код и база образа не меняются; ручной real workflow остаётся ручным; Deploy Prod workflow не редактируется. При несовпадении формулировки ECR ошибка останется красной — после наблюдения можно расширить классификатор отдельным изменением. Откат CI-изменения — вернуть прямые команды build в workflow и прежний тест отдельным коммитом; он тоже проходит Tests и обычный production cutover. Production release сам собирает образ из ECR до входа в cutover: его 429 завершит deploy job без автоматического rollback, старый сервис остаётся активным; после диагностики возможен адресный rerun deploy job. Если сбой возник уже внутри cutover, действует существующий rollback. Пулл PostgreSQL service image до шагов Tests этим wrapper не охвачен; отдельное изменение registry/service потребуется лишь при наблюдаемой частоте таких отказов.

Architecture Critique: not required: меняются только CI-оркестрация и изолированный тест, без контракта сервиса, production-нагрузки, хранения и границ модулей. PRD review проверяет scope, классификатор, тесты и rollback.

## Декомпозиция

1. Оформить PRD, проверить исходные workflow/тест, пройти Spark и сильный PRD-гейт — до 2 ч, без кодовых изменений.
2. Добавить shell wrapper и его контрактный тест, показать красный/зелёный — до 150 строк кода.
3. Подключить четыре build шага, стабилизировать асинхронный тест, показать красный/зелёный и N прогонов — до 150 строк кода.
4. Аудит, committed diff-гейт, полный mock+real suite, выпуск и наблюдение CI — до 2 ч на подзадачу.

## Оценка простоты

Один wrapper и один тест без новых зависимостей. Скрипт ничего не знает о тестовых job кроме команды build; тестовая синхронизация не вводит искусственной задержки.
