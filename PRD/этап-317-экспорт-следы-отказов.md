# Этап 317. Экспорт не повторяет отказ и оставляет след

## Цель

После отказа запуска экспорта агент получает однозначную границу повторной
попытки и существующий playbook обхода. Каждый failure, который known-issue
lookup не сопоставил, оставляет ограниченный и санитизированный операционный
след, достаточный для создания точного match rule.

## Границы

- Не создаётся второй механизм подсказок: экспортная ошибка проходит обычный
  `augment_tool_error`, который уже добавляет playbook known issue.
- Для 403 с tenant-wide guard ответ буквально сообщает `retry after 1800
  seconds`; для REST-denied буквально сообщает, что повтор с теми же
  аргументами запрещён. Никакое nullable numeric поле не используется как
  флаг политики. Для retryable download-not-ready ответ называет короткую
  задержку и тот же `report_file_id`, не новый export.
- Только `kind=failure` с outcome `no_match` записывает один след: tool,
  status/code, результат `sanitize_text_with_metadata` plus a safe error
  normalizer that redacts URL/domain, numeric identifiers and secret/header
  shapes, time, account tag and `possible_pii` (true on any sanitizer privacy
  redaction or sanitizer uncertainty); matched/lookup_failed не пишутся.
- Хранилище чистится командой retention вместе с feedback reports при возрасте
  >180 дней и держит не более 1000 новых строк на инструмент: транзакция после
  вставки удаляет самые старые превышающие строки. CLI выводит только sanitized aggregate
  `tool × normalized_error_text × count` for `possible_pii=false`; potentially
  PII rows contribute only a separate count.

## Не делаем

- Не меняем правила деперсонализации, реестр фильтров и delete-инструменты.
- Не сохраняем domain, URL, identifiers, raw exception или bearer token.
- Не меняем метрику `vetmanager_known_issue_lookups_total{outcome=no_match}`.

## Архитектурное решение

### Контекст и варианты

Существующий `augment_tool_error` уже является единственной tool-boundary,
где сохраняются matched playbooks и метрика. Отдельный export hint или отдельная
таблица сырых ошибок обошли бы match semantics и privacy boundary. Возможные
варианты: (1) добавить текст лишь в `report_ai`; (2) расширить result ToolError;
(3) сохранить no-match в общем feedback service. Выбран (3): export создаёт
структурированное ToolError с retry metadata, а feedback service дополняет его
по обычной boundary и пишет только no-match trace.

### Инварианты, rollback и fallback

Trace не может блокировать ответ: все DB writes best-effort and bounded.
`matched` never writes a trace. Если миграция/хранилище unavailable, lookup and
existing error response remain available and runtime logs one safe event.
Rollback does not execute a destructive automatic downgrade on production;
development downgrade drops only the new trace table.

## Декомпозиция

1. Add model/migration and bounded no-match persistence from `augment_tool_error`.
   Test matched/no-match, sanitizer/PII and retention; ≤150 LOC per file.
2. Add triage aggregate command and tests; ≤150 LOC.
3. Adapt report export errors to structured retry metadata, preserving known-issue
   augmentation; regression tests are first made red by removing the retry field.
4. Run migration checks, real call, reviews, rollout and verification.

## Приёмка

- A mocked StartReport failure with a unique synthetic text, explicitly stubbed
  as no-match, returns an explicit do-not-repeat boundary and a no-match trace.
  A matched failure does not create one.
- `get_report_export_download` not-ready tells the caller exactly when to poll
  the same id again; it does not start another export.
- Triage aggregate exposes only sanitized fields and counts.
- Live stand calls of changed start and download tools return codes and safe
  response bodies; when a start failure cannot be safely induced, its exact
  failure branch is mock-covered and the successful start response is recorded.
  Full suite, Postgres migration and production rollout are green.

## Простота

The only new persistence object is an append-only bounded trace table because
it has a different lifecycle and semantic from a human/auto feedback report.
No generic event framework, cache or second advice dispatcher is added.

Architecture Critique: required — the stage changes persistent storage,
public MCP errors and production behavior.

## Review notes

Spark candidate findings accepted: do not overload nullable retry metadata;
name concrete retention and cap; do not prescribe destructive production
downgrade. Rejected: `account_id` and `possible_pii` are explicitly required by
the task and reuse existing feedback privacy semantics; `lookup_failed` must
not create a no-match trace because it is neither a no-match nor safe evidence
for a match rule.

External architecture review accepted: add URL/domain/identifier normalization,
hide possible-PII trace text in triage, and require a live call for both changed
tools. Rejected low finding about 1800 seconds: 30 minutes is the established
safe tenant-wide guard boundary in the existing export contract, not a claimed
upstream remaining-TTL value; it remains a named constant and is covered by a
regression test.

Second external review accepted: redact token/header-shaped values and make the
PII flag conservative on sanitizer uncertainty; pin the no-match test to a
synthetic absent incident rather than an operational registry state.
