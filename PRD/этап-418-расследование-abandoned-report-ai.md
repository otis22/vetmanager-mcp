# Этап 418. Расследование abandoned-воронки Report AI

## Цель и границы

Объяснить наблюдение дашборда от 19.10.2026 (114 терминальных исходов за 30 дней, из них 47 `abandoned_wait`) на уровне, доступном по production данным. Отделить наблюдаемые факты от гипотез. Никаких изменений production данных, MCP кода, инструментов или этапов 419–421. В публичный отчёт входят только агрегаты; идентификаторы аккаунта, подключения и job используются лишь во временных read-only вычислениях и не публикуются. Текст пользовательских интентов и комментариев не переносится.

## Проверенные источники и определение

Код `tools/report_ai.py` создаёт наблюдение при `create_report_ai_job`, обновляет его при ответах, которые явно наблюдают статус job (например, `get_report_ai_job` и save), и фиксирует `abandoned_wait` после 3600 секунд без **нового наблюдения статуса** или при вытеснении из переполненного реестра (`shared_metric_counters.py:cleanup_report_ai_lifecycle`, `force=True`). `get_report_ai_job_data` и `rate_report_ai_job` lifecycle observation не обновляют: `abandoned_wait` совместим с продолжением работы агента. Это исход MCP-наблюдения, не upstream статус job и не доказательство отказа пользователя. Код группирует рабочие статусы в стадии `queued`, `recognized`, `preview`, `ready_to_save`, `needs_confirmation`; `saved`, `failed`, `existing_report_matched`, `rejected` — терминальные наблюдаемые исходы. Стадия брошенного наблюдения может быть только последней видимой стадией. В `report_ai_job_ratings` production DB хранятся `account_id`, `connection_id`, `job_id`, `intent_text`, `score`, `created_at`, `rated_at`, `intent_from_create`; подтверждённая схема не содержит статуса job или времени его переходов. Таблицы jobs в локальной DB нет. Метрики Prometheus агрегированы и не несут `job_id`. Логи исследуются только если сохраняют пригодные безопасные признаки вызовов. Поэтому точная поимённая реконструкция событий abandoned невозможна по обнаруженным источникам; в этом случае указать границы и не подменять неизвестное причиной.

Окно: 30 суток до момента read-only снимка **по времени фиксации терминального события**, а не когорта jobs по времени создания; `abandoned_wait` обычно запаздывает из-за TTL и запуска очистки, но может возникнуть раньше при переполнении реестра. Для счётчиков Prometheus использовать `increase(...[30d])`, проверить присутствие исходных рядов у начала окна и интервалы без scrape, учитывать сбросы и отличие от дашборда, который был снят в другое время. Если ряд отсутствует на части окна, итоги — счёт доступного покрытия, а не полное 30-дневное число. Определение базы: все MCP-observed terminal outcomes, включая `existing_report_matched` и `rejected`, если появились; отдельно показывать каждый исход. Tombstone дедупликации живёт час: терминальные **события** за 30 дней нельзя автоматически назвать уникальными jobs. Проверить, что 114 и 47 воспроизводятся для доступного окна. Указание Roadmap 52+47+11=110, а не 114, требует отдельной сверки четырёх исходов.

## План анализа (подзадачи ≤ 2 ч)

1. **418.1 PRD и гейт:** сверить код и схему read-only запросами, оформить ограничения; Spark candidate review, пара Astra + Sol xhigh по прямому указанию владельца для 418 (исключение из постоянной схемы с Opus), исправить важные находки, оценить простоту.
2. **418.2a воронка:** read-only PromQL для 30-дневных исходов, переходов стадий, средней наблюдаемой длительности и попыток save; показать абсолютные числа и знаменатели. Метрика `*_max` хранит накопленный максимум с момента сброса и `max_over_time` не доказывает, что максимум возник именно в 30-дневном окне. Распределения длительностей по jobs в метриках нет. Не выводить причинность из корреляции метрик.
3. **418.2b срезы:** read-only SQL по рейтинговой таблице для аккаунтов/подключений, наличия оценки и времени; кластеризовать интенты исполнимым SQL `CASE WHEN intent_text ~* '(клиент|пациент|визит|прием|приём)' THEN 'clients_visits' ELSE 'other_combined' END` на стороне production DB. В публичных срезах по аккаунтам, датам, интентам и оценкам выводить только агрегаты с размером каждой ячейки ≥5, подавлять также дополнения/итоги, из которых можно восстановить ячейку <5. Глобальные обезличенные счётчики состояний без идентификаторов аккаунтов публиковать полностью для классификации воронки. По логам проверить видимость `get_report_ai_job_data` и prompt-helper до создания. Если связать событие с конкретным job нельзя, дать явное `unknown` и количественные границы, не приписывать отсутствие записи отсутствию вызова.
4. **418.2c выводы:** классифицировать наблюдаемые точки остановки с числом и долей событий, отделить возможные объяснения. Для гипотезы 420 различить чтение **реальных строк** (обычно уже после saved/matched, относится к оценке/экспорту) и чтение превью до сохранения; дать точное пересечение с abandoned, если оно измеряется, иначе границы `0..N`/«не измеряется». Предложения ранжировать по ожидаемому эффекту × охвату и цене проверки; каждое — только кандидат на отдельный этап.
5. **Выпуск:** аудит только документного diff, структура Roadmap и проверка состава diff до commit (полный mock+real suite по прямому указанию владельца для аналитического этапа без изменений кода/тестов не запускается), архивирование по окну, commit, Spark → Astra + Sol xhigh committed diff, запись evidence и self-attestation, push ветки и проверка Tests.

## Формат результата и критерии приёмки

В `AssumptionLog.md`: каждый production SQL/PromQL запрос дословно и краткий безопасный результат, время снимка, таблица причин/точек остановки с знаменателем и долей событий, охват и ограничения срезов, отдельный вердикт 420, ранжированные предложения, evidence ревью. До публикации проверить отсутствие адресов/логинов production, команд подключения, секретов, персональных данных, малых ячеек (<5) в срезах по аккаунтам/датам/интентам/оценкам и остатков, позволяющих восстановить такую ячейку. Результат запроса с такими ячейками фиксировать как «подавлено», без чисел; глобальные обезличенные счётчики стадий допустимы. Для причин, не устанавливаемых из данных, писать «не установлена», даже если стадия остановки известна. `Roadmap.md` закрывается после анализа; этапы 419–421 не меняются. Выпуск — push в `dev/roadmap-418-420` и зелёный Tests либо документированное отсутствие автозапуска с ручным запуском при наличии.

## Архитектурное решение

Проблема — наблюдаемость жизненного цикла распределена между in-memory/shared счётчиками и локальной таблицей интентов/оценок, а upstream job не хранится в MCP DB. Варианты: восстановление по агрегатам (быстро, но без job-level связи); чтение production логов с безопасной агрегацией (если содержат ключи); новый сбор событий (изменение кода, за рамками аналитического этапа). Выбран read-only анализ существующих источников с явными границами вывода. Инварианты: отсутствие записей в production, персональных текстов в публичных артефактах, вмешательства в этапы 419–421. Если источники не связываются, fallback — строгая оценка `unknown` и предложение отдельного этапа наблюдаемости. Architecture Critique: not required — не меняются API, storage, auth, production behavior или ownership; анализ описывает текущую архитектуру.

## Простота

Один PRD, один набор воспроизводимых read-only запросов и выводов в AssumptionLog; без нового кода или коллектора.
