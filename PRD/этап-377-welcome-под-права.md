# Этап 377. Welcome-маршруты под права токена

## Цель и границы

377.1 — только PRD. В 377.2 сделать первый сеанс полезным и для токена без
`report_ai.write`: показать реальные доступные данные, сверить их с человеком
и объяснить путь к отчёту, не вызывая запрещённый create. Для токена с полным
набором сохранить маршрут этапа 375 вплоть до подтверждённого сохранения и
чтения строк. 377.3 — аудит, committed diff review, полный прогон и выпуск.
Права, API, состав пресетов и событие сохранения не расширяются.

## Проверенные факты

- `server.py` создаёт `FastMCP(instructions=...)` единожды; в блоке первого
  сеанса всем подключениям предписаны чтение врачей, сверка с человеком,
  затем Report AI. Указатель говорит «full first-session route».
- `prompts.py` регистрирует `welcome_first_session` через `@mcp.prompt` без
  аргументов и auth-ограничения. Текст уже начинает с `tools/list`, но при
  отсутствии Report AI лишь велит сделать «permitted read and human check
  below»; далее весь детальный сценарий всё равно про отчёт.
- В установленном FastMCP 3.4.7 `list_prompts` фильтрует лишь компоненты с
  заданным `prompt.auth`; `get_prompt` проверяет тот же атрибут. У нашего
  `ToolVisibilityMiddleware` реализован только `on_list_tools`. Следовательно,
  **сегодня токен без `report_ai.write` видит** `welcome_first_session` в
  `prompts/list` и получает в `prompts/get` тот же один `user` Message с
  шагом 0 и полным сценарием 375. Это вывод по коду; 377.2 закрепит его
  HTTP-проверкой на devtr6.
- `tools/list` фильтруется по реальным scopes; отказ на вызов использует тот
  же `TOOL_REQUIRED_SCOPES`. `get_clinics` требует `reference.read`,
  `get_timesheets` — `analytics.read`; отсутствие одного из них возможно у
  произвольного набора прав. `create_report_ai_job` требует
  `report_ai.write`. Для полной цепочки проверить также наличие get/save/data
  и confirm там, где он нужен, а не один только create.
- `get_presets_allowing_tool` и `get_presets_granting_scope` считают названия
  из `TOKEN_PRESET_SCOPES` через `_presets_narrowest_first`: для
  `report_ai.write` сейчас `Analytics`, затем `Full access`. Формат отказа
  `tool_scope_security.py` уже даёт «Allowed presets» и действие для
  администратора. Другой список состава групп запрещён.
- `first_report_saved_at` отмечается только после успешного save в
  `tools/report_ai.py`. `report_saved_7d_accounts` считает фактически
  наблюдённые сохранения по всей eligible cohort; HELP пока не объясняет, что
  часть аккаунтов может иметь только read-доступ. OpenAPI v6 не описывает
  Report AI job; для этого маршрута источник — MCP-код и реальные ответы.

## Архитектурное решение

**Проблема и ограничения.** Статичные `initialize.instructions` не знают
текущих прав, а видимый всем prompt не может обещать write-маршрут каждому.
Нельзя поддерживать второй ручной состав групп. Текст не должен обходить
права, подставлять персональные данные, считать preview реальными строками
или увеличивать число запросов к API только ради выбора маршрута.

**Варианты.** (а) Один `welcome_first_session` с развилкой после `tools/list`:
сохраняет существующее имя и MCP-контракт, проверяет реальную видимость.
(б) Два prompt под наборы прав: сейчас оба доступны через `prompts/list`, а
правильная фильтрация потребовала бы отдельного prompt auth/middleware и
источника прав; выбор prompt всё равно зависит от клиента. (в) Подстановка
`instructions` на запрос: экземпляр `FastMCP` создан с одной строкой; в
текущем сервере нет per-request подстановки. Переписывание протокольного
initialize расширило бы границу auth и риск расхождения. Выбираем (а).

**Контракт выбора.** Короткий статичный `instructions` велит открыть prompt
для первого сеанса и до write-шагов свериться с `tools/list`; он не обещает
отчёт каждому. В `prompts/get` один общий рецепт. Вначале агент получает
фактический каталог. Для отчётного маршрута нужен разрешённый набор всей
цепочки 375 (create, get, save, data; confirm при предложенном кандидате),
а не предположение по названию пресета. Если необходимого инструмента нет,
агент сразу выбирает read-маршрут и не делает пробный запрещённый вызов.
Пустой/ошибочный/недостоверный каталог — не доказательство прав: сообщить
об ограничении и не начинать отчёт. Видимость каталога при внутреннем сбое
может быть полной (stage 271); если позже вызов всё же вернул scope denial,
остановиться и передать его честное объяснение без повторов.

**Read-маршрут.** Выбрать доступный read-инструмент из каталога и выполнить
хотя бы одно успешное чтение реальных данных выбранной клиники. Предпочесть
`get_clinics` + `get_timesheets` как в 375 при наличии обоих: уточнить филиал,
дату, применить фильтр `clinic_id`, проверить строки и пагинацию, назвать
смены расписанием, а не доказанной явкой. Если эта пара недоступна, выбрать
другой доступный безопасный read-инструмент по вопросу человека и объяснить
границы его ответа; нельзя угадывать несуществующий путь или использовать
write-tool вместо чтения. Если чтение отклонено, данные пусты или человек не
подтвердил контекст — честно завершить без заявления, что реальные данные
показаны. После чтения сверить результат с ожиданием человека. Назвать
`report_ai.write` и дающие пресеты из `get_presets_granting_scope` или
`get_presets_allowing_tool`, в порядке узкие → широкие, `Full access`
последним; попросить владельца аккаунта выдать подходящий токен, не просить
токен в чат и не гарантировать, что отчёт уже готов. Для нестандартных прав
перечень всё равно вычисляется реестром, а не угадывается по имени текущего
пресета. Если write есть, но нет другого инструмента цепочки, назвать именно
недостающую возможность, не приписывая отсутствие `report_ai.write`.

**Полный маршрут.** При наличии цепочки сохранить шаги 375: филиал и чтение,
сверка с человеком, согласие на один create, bounded poll того же job,
подтверждение кандидата только по выбору человека, оценка preview как
структуры, согласие на save, затем чтение настоящих строк. Пустой или
неоднозначный результат и отказ человека останавливают маршрут; success —
только подтверждённо сохранённый и проверенный отчёт, а существующий отчёт
так не называется. Если начальная пара read-инструментов отсутствует, не
начинать Report AI как первый шаг: применить read-маршрут к доступным данным
или объяснить, что безопасный первый сеанс сейчас невозможен.

**Метрика и откат.** `first_report_saved_at` остаётся событием успешного
save, не событием показа read-данных. Для read-only аккаунта отсутствие
события нормально; добавить это объяснение в HELP
`report_saved_7d_accounts` и сопровождающую витрину, если она интерпретирует
долю как качество маршрута для всех eligible. Знаменатель и прежнюю метрику
не менять; отдельную метрику/лейбл прав в этом этапе не вводить. Если текст
маршрута ухудшит работу клиентов, откатить текст prompt и краткий указатель
без миграции данных. При изменении FastMCP visibility повторно проверить
HTTP `prompts/list`/`prompts/get` и `tools/list`; источник истины остаётся
отфильтрованный каталог и отказ вызова. Architecture Critique требуется:
меняются публичный MCP prompt contract, поведение первого сеанса и граница
между статичным instructions и токеновыми правами; совместить critique с
сильным PRD review Astra.

запускается на сломанном охраняемом поведении и обязан стать красным;
self-attestation называет точную поломку. Тестировать отрендеренные
`initialize.instructions`, `prompts/get`, `prompts/list` и фактический
`tools/list`, а не наличие строк только в исходнике.

**Выдача тестовых токенов до реализации.** На devtr6 использовать именно
`TEST_DOMAIN`/`TEST_API_KEY` из `.env` для интеграции отдельного тестового
аккаунта в локальном MCP HTTP процессе (не bearer production-стенд). Через
действующий `POST /account/tokens` с CSRF выдать два краткоживущих токена,
задав в форме `access_preset=frontdesk` и `access_preset=report_ai`;
это имя поля проверено в `web_routes_account.py` и `web_html.py`.
`frontdesk` имеет чтение расписания без `report_ai.write`, `report_ai` имеет
полное чтение и отчётный write. `full_access` допустим дополнительно, но не
заменяет узкий отчётный preset. Не печатать токены, ключи, персональные
строки и raw bodies; сохранять только HTTP код и очищенную проекцию полей.
Проверка использует два разных bearer-токена и не подменяет ни один контур
другим при неудаче.
