# Этап 335. Реальный формат отпечатка в скрипте этапа 332

## Цель

Привести supervisor-only скрипт миграции 332 и его сторожа к
реальному контракту `error_fingerprint_hash`: принимать
`hmac-sha256:<64 hex>`, сохранить совместимость с голыми `64 hex` и
безопасно обрабатывать исходное состояние `KI-45=null`,
`report #80=<fingerprint>`, `#80→KI-45`.

## Проверенные факты и ограничения

- Read-only снимок супервизора от 19.09.2026 21:22:
  `stage-332/ki45-before-manual-2122.json` содержит KI-45 с
  `error_fingerprint_hash=null`, `related_tool=null`,
  `status=workaround_available`; `stage-332/report80-before-manual.json`
  содержит #80 с `hmac-sha256:<64 hex>` и `known_issue_id=45`.
- `agent_feedback_service.build_error_fingerprint_hash()` возвращает
  `f"hmac-sha256:{digest}"`. `scripts/seed_known_issues.py` вызывает эту
  функцию, а не формирует отдельный формат. Голые 64 hex остаются
  только как backward-compatible legacy/test form.
- `triage_agent_feedback._promote` в одной DB-транзакции создаёт
  `KnownIssue`, делает `flush`, присваивает `report.known_issue_id` и только
  затем вызывает один `commit`; поэтому после successful promote ссылка
  #80 атомарно содержит ID новой цели.
- Три supervisor apply завершились fail-closed до мутаций из-за
  regex голого `64 hex`. Миграция уже применена супервизором
  вручную; этот этап меняет только эталонный скрипт и тесты.
- Агент не обращается к production host/DB, не меняет `known_issues`
  и не перезаписывает файлы `stage-332/*-manual*.json` и
  `stage-332/ki45-before.json`.

## Scope и декомпозиция

### 335.1 — единый regex и реальные фикстуры (≤150 LOC)

1. Задать в shell один Python/Bash-compatible regex
   `^(hmac-sha256:)?[0-9A-Fa-f]{64}$` и передавать его в оба Python
   preflight parser; Bash-проверка before-state использует ту же
   переменную. Скрипт фиксирует `LC_ALL=C`; Python получает
   literal отдельным argv и вызывает `re.fullmatch`, Bash использует
   некавыченный RHS `[[ value =~ $fingerprint_regex ]]`. Статический
   сторож требует, что оба Python call-site и Bash call-site используют
   именно эту переменную.
2. Перевести happy-path фикстуры fake-SSH на
   `hmac-sha256:<64 hex>`; отдельно доказать приём legacy bare form
   и отказ от неверных prefix/length/hex. Parser команды
   `move-fingerprint` в fake-SSH должен принимать обе формы, чтобы
   present/present ветка проверяла скрипт, а не падала в harness.

### 335.2 — report-only state machine (≤150 LOC)

1. Допустить исходную пару `(None, report_fingerprint)`, если #80
   связан с KI-45; разные непустые отпечатки и source-only остаются
   fail-closed до write-команд.
2. `promote 80` создаёт target с отпечатком репорта;
   `move-fingerprint` вперёд и назад не вызывается, потому что source
   из snapshot был `null`.
3. Цель до любого KI-45 write проверяется по ID, exact title,
   `related_tool`, fixtures, допустимому status/link и
   `error_fingerprint_hash == report_fingerprint`. Существующий legacy marker
   `stage334-null-null-v1` не переименовывается, чтобы сохранить recovery
   контракт для будущих/прерванных запусков; текущая production-
   миграция уже применена вручную и не перезапускается. Ветка
   определяется не из имени marker, а из immutable source snapshot и
   текущего read-only report fingerprint. На каждом retry/rollback target
   сверяется с текущим report fingerprint; его дрейф отклоняется.
4. Fake-SSH проходит apply → retry → rollback → re-rollback → re-apply,
   а также crash-after-promote recovery без duplicate target. Перед
   `promote` marker=`prepared`; после атомарного promote сама ссылка
   #80 указывает candidate ID. Поэтому crash до записи ID
   восстанавлиает ID из read-only ссылки, но принимает его только
   после exact identity/fixtures/status/fingerprint preflight. `prepared` + #80→KI-45
   означает, что promote не commit-ился; `prepared` + чужая/неверная
   цель падает fail-closed без нового promote. После записи ID, link и
   KI-45 writes retry идёт по тому же ID и явной status/link-матрице.
   Rollback сохраняет marker и target-ID, ставит цель в `wontfix` и
   возвращает #80→KI-45; re-apply повторно проверяет эту деактивированную
   цель, перелинковывает #80 и реактивирует её без нового `promote`.

### 335.3 — сторож контракта и доставка (≤2 ч)

1. Тест строит инцидент через существующие
   `build_incident_from_exception` / `build_error_fingerprint_hash`, извлекает
   единственный regex из скрипта и требует полное совпадение.
   Тот же service-generated fingerprint передаётся в before-state и
   report fake-SSH happy path, то есть реально проходит Bash `[[ =~ ]]`
   и оба Python preflight. Статическая часть требует ровно один
   regex literal и его использование во всех трёх call-site без второго
   захардкоженного fingerprint-pattern.
2. Доказать сторожа красными: старая regex отклоняет
   service-generated fingerprint, а старая state machine отклоняет report-only.
3. Пройти focused, локальный live CLI в контейнере на SQLite,
   ShellCheck v0.9.0, `bash -n`, аудит, один полный mock + real suite,
   committed-diff reviews, push, Tests и Deploy Prod. После доставки
   записать completion без повторного применения migration.

## Архитектурное решение

Проблема локальна: storage уже хранит верный отпечаток, а
supervisor-скрипт дублирует его валидацию в трёх разных местах.
Выбран один shell literal, совместимый с Bash ERE и Python `re`, без
нового модуля или public API. Python parsers получают literal аргументом,
а тест извлекает его из исполняемого скрипта; поэтому копия regex в
тесте не может молча разойтись с runtime.

Три варианта отклонены: убрать валидацию (ослабит fail-closed),
вынести regex в отдельный файл (лишний runtime artifact ради одного
скрипта), переименовать legacy marker (сломает recovery у уже
подготовленного supervisor run). State machine расширяется только на
наблюдённую пару; ownership остаётся в supervisor-скрипте.

Инварианты: snapshot immutable; перед write проверены source/report/
target identity; target наследует точный fingerprint репорта; source-null
никогда не вызывает `move-fingerprint`; retry не создаёт дубль; rollback
возвращает KI-45 и #80 в snapshot/link и деактивирует target.
Backward compatibility означает, что bare/bare и prefixed/prefixed пары
валидны. Bare и prefixed значения не канонизируются и не
считаются равными только по одинаковому digest: общий CLI
`move-fingerprint` сравнивает хранимые строки точно, поэтому смешанная
пара остаётся fail-closed как несогласованное storage-состояние.

Rollback/fallback: существующий snapshot, target-ID и двухфазный marker
сохраняются. Неожиданный prefix, fingerprint, status, link или identity
останавливают запуск без угадывания. Architecture Critique совмещается
с первым strong PRD-review, потому что меняется production migration behavior.

## Acceptance criteria

- Service-generated `hmac-sha256:<64 hex>` и legacy bare `64 hex` проходят
  один regex; malformed values отклоняются.
- Report-only state красным ломает старый скрипт и зелёным проходит
  apply/retry/rollback/re-rollback/re-apply без `move-fingerprint`.
- Сторож формата строит fingerprint реальным service code и
  сопоставляет с regex, извлечённым из скрипта.
- Локальный SQLite CLI в контейнере показывает код и тело
  promote/link/rollback для report-only state.
- Focused, ShellCheck, `bash -n`, roadmap structure, один полный mock +
  real suite, committed-diff reviews, Tests, Deploy Prod и закрывающий CI
  зелёные; этап 335 в `done`.

## Out of scope

- Повторное применение миграции 332, production SSH/DB/`known_issues`.
- Изменение matcher, storage schema, public MCP/CLI contract или fixtures 332.
- Нормализация или перезапись legacy bare fingerprints в БД.

## Оценка простоты

Новых абстракций, CLI-команд или storage-полей нет. Меняются один
regex, одно условие матрицы и существующий harness. Отдельный
модуль regex и новая миграционная state machine были бы сложнее без
дополнительной гарантии.
