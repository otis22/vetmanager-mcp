# Этап 491.1. Production host security: PRD и read-only preflight

## Цель

Подготовить исполнимый план адресного обновления production host без неконтролируемого полного отказа сервиса. Владелец допускает RPO **не более 1 часа работы сервиса**: это верхний предел возможной потери пользовательских записей при вынужденном восстановлении, а не целевое значение. При обычном откате пакета сохраняется живая БД без потери записей. В этом ходе разрешены только чтение и проектирование. Свежий backup и **фактический успешный isolated restore** являются входными gates следующего вертикального шага; наличие файла backup или snapshot их не заменяет.

## Границы и декомпозиция

1. За ≤2 ч: сверить актуальные механизмы доступа, backup/restore, состав сервисов и release-state; снять только безопасные read-only результаты. Не читать `.env`, содержимое backup, БД, логи с данными клиник, приватные адреса и ключи.
2. За ≤2 ч: на production при подтверждённом доступе выполнить только `apt-cache policy` и `apt-get -s` для адресных пакетов; записать версии, транзакцию и exit codes без внутренних адресов. Если production недоступен, gate остаётся непроверенным.
3. За ≤2 ч: подготовить runbook, критерии остановки/восстановления и измерения простоя. Проверить PRD/Architecture Critique и механические gates. Пакеты, restart, backup и restore сейчас не выполнять.

## Проверенные локальные факты и открытые gates

- `docker-compose.yml` объявляет `postgres`, `redis`, `mcp`, `mcp2`, `mcp3`; `scripts/availability_probe.py` проверяет три slot и публичный `/healthz`.
- `scripts/backup_postgres.sh` и `scripts/backup_daily_cron.sh` делают `pg_dump` в gzip; скрипты не демонстрируют isolated restore. `scripts/rollback_db.sh` удаляет и пересоздаёт production БД — **запрещённый** путь восстановления после host update.
- `scripts/stage385_deploy.py` сохраняет `release-state`; `scripts/post_deploy_smoke_checks.sh` проверяет публичные маршруты. Они не доказывают восстановимость host backup.
- Production SSH BatchMode/StrictHostKeyChecking 21.11.2026 подтверждён на указанном куратором host. Read-only: `ssh`, `nginx`, `docker` активны; `nginx -t` exit 0; PostgreSQL 16.13, compose `postgres`, `redis`, `mcp` running. `mcp2`/`mcp3` не найдены через текущий compose selector; возможно, ими управляет иной release manifest, поэтому readiness трёх workers **не подтверждена** и требует точного приватного inventory. Независимая console не проверялась.
- Production `apt-get -s` по nginx/OpenSSH/OpenSSL/Python: 12 upgrades, 0 new, 0 remove; по Docker/containerd: 4 upgrades, 0 new, 0 remove. Среди точных транзакций есть зависимости (`libssl3t64`, компоненты Python, `nginx-common`, `openssh-client`, `docker-ce-rootless-extras`). Apt lists датированы этим днём, но их полнота и актуальность к окну не доказаны; симуляции предварительные, service triggers и обратная транзакция не проверены. Docker по-прежнему вынесен из 491.2 до доказательства непрерывности PostgreSQL/Redis/workers.
- Входной gate A — **unconfirmed**: независимый console доступ требуется доказать живым входом и возможностью управления машиной при потере SSH, с приватным evidence; одного SSH недостаточно.
- Входной gate B — **unconfirmed**: требуется свежий согласованный backup всех изменяемых данных, конфигурации, секретов и release-state, проверенный checksum и фактический restore в изолированном окружении с проверкой схемы, ограниченных контрольных счётчиков, тестового дешифрования и запуска приложения. Доступ к restored данным ограничен; данные клиник не попадают в публичные артефакты.
- Входной gate C — **unconfirmed**: при любом recovery доказать по UTC timestamp согласованной точки backup и моменту переключения, что возраст точки не превышает 1 час; оценить затронутые записи и остановить переключение при превышении. WAL replay/replication не обязательны, если этот предел доказан другим способом. Автоматический full snapshot/DB rollback запрещён. Совместимость приложения с восстановленной схемой проверяется до переключения.
- Входной gate D — **unconfirmed**: предварительная production `apt` simulation выполнена, но к окну требуется актуальная, точный список пакетов и сервисных эффектов, отсутствие удаления/неожиданных новых пакетов и kernel/reboot в транзакции. Симуляция по устаревшему локальному cache не засчитывается.
- Входной gate E — **unconfirmed**: требуется согласованное ночное окно с независимым наблюдением публичного сервиса, SSH, трёх workers и границей инцидента >30 минут. При деградации восстановление начинается сразу, не ожидая владельца.

## Runbook следующего вертикального шага (не исполнять в 491.1)

### Архитектурное решение

Сохранять живую PostgreSQL БД при пакетном recovery; при необходимости переноса применять только заранее проверенную согласованную точку возрастом ≤1 час. Разделить независимые обратимые группы SSH, nginx и остальных userspace пакетов; Docker/runtime допускать лишь после отдельного доказательства непрерывности общей БД, Redis, workers и сети. Обратная транзакция и локальные пакеты готовятся до окна. Такой порядок ограничивает blast radius и не требует автоматического отката всей машины.

Команды ниже — шаблон для console на production, не команда подключения и не разрешение на исполнение. Оператор сначала сверяет реальные service names, compose path, PostgreSQL major и имена пакетов в приватном preflight. Если они отличаются, исправляет runbook и повторяет review; подстановка догадок запрещена.

```bash
# Только read-only preflight на подтверждённом production host.
date -u +%FT%TZ
systemctl is-active ssh nginx docker
sudo nginx -t
docker compose --profile production ps --format json
apt-cache policy nginx openssh-server docker-ce docker-ce-cli containerd.io openssl python3.12
apt-get -s install --only-upgrade nginx openssh-server openssl python3.12
# Отдельно, лишь для решения о Docker: apt-get -s install --only-upgrade docker-ce docker-ce-cli containerd.io
```

Последнюю симуляцию запускать только для пакетов с установленной версией и доступным candidate. `apt-get -s` использует текущие apt indexes: если их свежесть неизвестна, результат `unconfirmed`, а `apt-get update` остаётся будущим разрешённым change step. Вывод симуляции и `policy` перед публикацией сокращать до имён/версий пакетов и кодов выхода, без repository URL.

### 0. До окна

Держать открытую независимую console и отдельную SSH-сессию. Записать UTC start и baseline: `date -u`, `systemctl is-active ssh nginx docker`, `sudo nginx -t`, `docker compose --profile production ps`, health каждого из `mcp`, `mcp2`, `mcp3`, публичные `/healthz` и `/readyz`, release-state manifest SHA и текущий package inventory. Вывод очищать от hostnames, IP, токенов, session IDs и данных клиник. Не запускать MCP tool с клинической выборкой.

Снять **новый** backup БД не более чем за 30 минут до начала **каждой** пакетной группы, без остановки записи через `pg_dump -Fc` в root-only временный каталог с `umask 077`; проверить exit code, ненулевой размер и SHA-256. В момент начала `pg_dump` записать UTC timestamp как консервативную границу согласованного MVCC snapshot; timestamp завершения и время старта пакета записать отдельно. Выполнять backup с `set -o pipefail`, чтобы ошибка `docker compose exec` не маскировалась перенаправлением; при любой ошибке удалить неполный файл и остановить изменение. Реальный каталог должен быть root-only и проверен до запуска. **До группы** перенести проверенную checksum копию в независимое закрытое off-host хранилище по шифрованному каналу с шифрованием при хранении, ограничением доступа и согласованным сроком хранения; проверить там SHA и доступность для isolated restore; ключ шифрования backup должен храниться и восстанавливаться независимо от исходного host, с назначенным хранителем и проверенной процедурой доступа. В isolated restore расшифровать именно эту off-host копию через независимый путь выдачи ключа и сверить SHA plaintext archive до `pg_restore`, не раскрывая ключ или данные; сохранить обезличенное restore evidence. После проверки независимой копии и isolated restore удалить временный plaintext archive с production host до начала пакетной группы; зафиксировать факт удаления и срок хранения off-host копии. Не считать обычное удаление гарантированным стиранием блоков: временный каталог должен размещаться на зашифрованном томе. Только этот свежий `-Fc` archive с проверенным SHA допускается для описанного ниже `pg_restore`. Действующие плановые `pg_dump | gzip` создают plain SQL, не подходят для `pg_restore`, не проверены isolated restore и с интервалом до 12 часов не доказывают RPO ≤1 часа; их нельзя подставлять в этот runbook или направлять в `rollback_db.sh`. Если к старту группы snapshot старше 30 минут, backup и isolated restore повторить. Не планировать группу, для которой точка может стать старше 1 часа до завершения безопасного recovery: перед следующей группой заново получить и проверить точку, а при затянувшейся деградации сохранять живую БД и устранять сбой сервиса без отката данных. Если сохранение доступности без восстановления БД невозможно, перед переключением отдельно доказать возраст точки ≤1 часа; иначе stop и incident, без заведомо просроченного restore.

Инвентаризировать и сохранить в закрытом off-host bundle host nginx/SSH конфигурацию, compose/release-state, pinned images, секреты и все изменяемые данные: PostgreSQL bind mount через согласованный dump, `mcp-data` (включая экспортные файлы), `mcp-logs` (аудит), `prometheus-data`, `grafana-data`. Проверить реальные цели symlink конфигурации: ссылка не сохраняет секрет. Секреты — только в независимом защищённом хранилище; isolated restore без доступа к исходному host должен проверить чтение тестового зашифрованного объекта восстановленным приложением без вывода ключа или plaintext в evidence. Согласованный off-host `pg_dump -Fc` остаётся восстановимой копией PostgreSQL при недоступном Docker исходного host; live копия файлов bind mount без согласования PostgreSQL не засчитывается. Для каждого volume определить владельца, способ согласованного копирования, timestamp, SHA, isolated проверку чтения и допустимость потери; если данные можно восстановить из другого проверенного источника, записать этот источник и решение. Не считать несогласованный снимок файлов live-БД её backup. Redis в compose настроен без RDB/AOF; проверить роль volatile state и эффект его потери до окна. Данные клиник и секреты не помещать в публичное evidence. Счётчики restored БД проверять внутри одного восстановленного snapshot; сравнение с живыми счётчиками во время непрерывной записи не является критерием точного совпадения. При любой ошибке backup или off-host проверки остановить изменение.

### 1. Изолированный restore и защита новых записей

Для входного gate B использовать **независимый host/VM** с отдельным Docker runtime и новым volume, без доступа к production volume и без публичного порта. Restore на том же host в отдельной Docker network годится только для узкой проверки формата и не засчитывается как доказательство восстановления после потери host. Запустить PostgreSQL той же major версии, создать пустую БД, выполнить `pg_restore --exit-on-error --single-transaction` из нового archive (`docker exec -i "$RESTORE_PG_CONTAINER" pg_restore -U "$RESTORE_DB_USER" -d "$RESTORE_DB_NAME" --exit-on-error --single-transaction < "$BACKUP_FILE"`), проверить exit, схему, отсутствие invalid constraints, агрегаты восстановленной БД и приватный старт приложения только на restored БД. `RESTORE_PG_CONTAINER` должен принадлежать изолированному окружению; command запрещён против production container. Уничтожение тестового окружения — отдельный контролируемый шаг после сохранения evidence. Записать checksum архива, restore exit, major versions, время, структурные/логические проверки и пригодность приложения без самих данных. Если restore не доказан, stop.

Для host package failure оставить production БД и volume на месте. До любого переключения image/config сверить совместимость с текущей схемой. Если потребуется перенос на иной host, сначала определить согласованную точку восстановления и доказать, что в момент переключения ей не более 1 часа; при задержке, способной нарушить предел, получить новую проверенную точку или сохранить живую БД и остановить recovery. Оценить возможную потерю записей и доступность переключаемого сервиса; при угрозе неконтролируемого полного отказа остановиться. WAL replay/replication допустимы, но для RPO ≤1 часа не обязательны. Snapshot может быть лишь дополнительной копией и никогда не применяется автоматически поверх живой БД.

### 2. Apt simulation и план пакетных шагов

После обновления apt indexes в отдельном разрешённом change step, повторить read-only `apt-cache policy nginx openssh-server docker-ce docker-ce-cli containerd.io openssl python3.12` и `apt-get -s install --only-upgrade <точные имена пакетов>`; получить точные installed/candidate версии, `Inst`/`Remv`/`Conf`, `needrestart` последствия, kernel и reboot requirement. Нельзя принимать список из старого аудита как актуальный. При `Remv`, неожиданном `Inst`, смене kernel, потребности reboot, замене Docker major или неоднозначном service restart — stop и новая оценка. **До первого пакета каждой группы**, включая OpenSSL/Python и их зависимости, сохранить в закрытом recovery bundle версии и локально доступные прежние `.deb` **всей точной транзакции**, проверить SHA и подготовить команды восстановления этой группы. Если хотя бы один прежний `.deb` недоступен локально или из заранее проверенного источника, группу не начинать. Обратную `apt-get -s install <каждый-пакет>=<прежняя-версия>` моделировать на копии фактического состояния **после** прямой транзакции либо в эквивалентном изолированном apt/dpkg окружении: до установки на текущем состоянии симуляция обратного шага недостаточна. Зафиксировать `Inst`/`Remv`/`Conf`, совместимость версий, service triggers и ожидаемый простой для полной группы; любое неожиданное удаление, новая зависимость или restart без контроля — stop. До окна проверить состояние APT periodic/unattended timers и активных jobs; согласованно исключить их запуск на время операции, зафиксировать прежнее состояние и восстановить его после окна. Не начинать при неуправляемой конкурирующей apt транзакции. Перед установкой разобрать maintainer scripts/triggers и настроить проверенное временное подавление автоматических restart/reload со снятием настройки через trap; если пакет или `needrestart` может обойти контроль, пакетный шаг остановить. Группы: сначала SSH с открытой console, затем контролируемая активация нового daemon и проверка версии **работающего** процесса и нового SSH входа; затем nginx с `nginx -t` до установки и после неё, после чего **контролируемый ночной restart**, проверка версии именно активного master и public smoke — простой reload не активирует новый бинарник; затем остальные адресные userspace security пакеты. Для OpenSSL/Python и других библиотек составить список затронутых работающих процессов, безопасно активировать каждый и проверить, что он загрузил новые версии; при риске остановки общих PostgreSQL/Redis или workers отложить активацию и не объявлять security fix завершённым. Docker/container runtime вынести из пакета 491.2 до отдельного доказательства, что точная транзакция и активация сохраняют PostgreSQL, Redis, все три workers и сеть; если доказательства нет, Docker не обновлять. После **каждой** группы проверить фактическую транзакцию и сервисы; `unattended-upgrades` и `full-upgrade` запрещены. Не обновлять kernel в 491.2.

### 3. Ночная операция и post-check

В окне начать независимые периодические пробы (UTC timestamp, 10–15 s cadence): внешние `/healthz`/`readyz`, nginx, отдельные readiness `mcp`/`mcp2`/`mcp3`, monitor health; missing sample не считать успехом. Записать последний успешный ответ перед шагом, первый отказ и первый устойчивый успех после него; `scripts/stage464_downtime.py` применить к очищенному CSV и указать предел неопределённости. Потеря доступности >30 минут — инцидент, но восстановление начать при первом признаке деградации.

После каждого шага проверить новый SSH login через независимое соединение, `systemctl is-active ssh nginx docker`, `sudo nginx -t`, `docker compose --profile production ps`, readiness PostgreSQL и Redis и всех трёх MCP workers, публичный smoke `scripts/post_deploy_smoke_checks.sh` и безопасный read-only MCP handshake/tools list, release-state SHA/active manifest, отсутствие новых ошибок в агрегированных метриках. При провале остановить следующие пакеты и немедленно восстановить конкретный затронутый сервис через console, проверенную сохранённую конфигурацию, подготовленный old-version package bundle или закреплённый совместимый image; сохранять текущую БД. Применять только заранее проверенную точную обратную транзакцию и затем проверять зависимые сервисы. Никогда автоматически не вызывать `rollback_db.sh`, не заменять volume и не откатывать full host snapshot.

### 4. Отдельное решение о kernel/reboot

491.3 — отдельный PRD/решение владельца и ночное окно после проверенного console, backup и isolated restore. Подтвердить путь загрузки и автозапуска, затем после reboot проверить SSH, nginx, Docker, все workers, публичный smoke, release-state и downtime. 491.1 не разрешает reboot.

## Приёмка 491.1

- PRD/runbook фиксирует gates A–E, точные безопасные шаги и немедленную реакцию на деградацию; явно отделяет будущие backup/restore и пакетную операцию.
- Read-only preflight сообщает для каждого gate `confirmed` или `unconfirmed` с причиной и безопасным следующим шагом; не подменяет отсутствие production доступа локальной симуляцией.
- PRD/Architecture Critique и применимые review gates имеют валидные verdict обоих ревьюеров и сведённые findings. Roadmap/AssumptionLog отражают только факты.

## Вне объёма

Любой production write, `apt update`/install/upgrade, backup/restore в этом ходе, restart/reload, kernel/reboot, deploy, upstream jobs, этапы 491.2/491.3/492/493. Секреты и внутренние адреса остаются вне публичного репозитория.

## Оценка простоты

Один runbook с пятью входными gates достаточен для текущего риска. Отдельный автоматический rollback orchestrator увеличил бы риск потери записей и не нужен для 491.1. Текст делится по фактической последовательности: baseline → backup/restore → apt → операция → отдельный reboot.
