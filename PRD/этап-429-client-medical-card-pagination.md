# Этап 429 — полнота медкарт клиента

## Цель

R9 в `artifacts/review/2026-10-20-full-stage-420.md`: `get_medical_cards_by_client_id` читает одну страницу `/rest/api/MedicalCards`, но скрывает `data.totalCount`. Пользователь может принять страницу за полную историю. Исправление ограничено этим ответом, без общего pagination envelope.

## Проверенные факты

- `tools/medical_card.py`: `limit` и `offset` публичны; фильтр `patient_id IN (...)` передаётся в upstream через `build_list_query_params`. После ответа строки не отбрасываются: цикл лишь добавляет `_pet_alias`/`_pet_id`. `medical_cards_count` считает все upstream строки. Уже возвращаются `medical_cards`, `pets_total`, `pets_truncated`.
- Соседний `get_medical_cards_by_date` уже обрабатывает отсутствующий `totalCount` как неизвестный total и вычисляет признак следующей страницы из `offset + len(cards) < total`.
- OpenAPI v6 описывает параметры `limit`/`offset` для `GET /rest/api/MedicalCards`, но оставляет `data` общим объектом без схемы `totalCount`. Форма `data.totalCount` подтверждена существующими тестами и наблюдением R9; отсутствие поля обрабатывается явно.

## Контракт

В ответ `get_medical_cards_by_client_id` добавляются только два поля:

- `medical_cards_total`: неотрицательное целое число `data.totalCount` для выборки медкарт по питомцам, которые были получены на шаге 1, до применения `limit`/`offset`. Принимаются JSON integer (кроме bool) и ASCII десятичная строка из цифр; отсутствие или непригодное значение даёт `null`.
- `medical_cards_has_more`: `true`, если `offset + medical_cards_count < medical_cards_total`; `false`, если условие ложно; `null`, если total неизвестен **или** upstream вернул пустую страницу до заявленного total (расхождение, при котором нельзя безопасно продолжать шагом по числу строк). Это признак записей **после текущей страницы**, а не наличия пропущенных страниц перед `offset`. `true` не обещает доступность всех следующих записей через этот инструмент: публичный `offset` ограничен 10000.

`medical_cards_count` по-прежнему число строк именно текущей страницы. Все существующие поля и их значения сохраняются. При отсутствии питомцев или пригодных ID total равен 0, has_more равен false. Если `pets_truncated=true`, total относится только к полученным питомцам и не удостоверяет полноту всех медкарт клиента; этот флаг остаётся независимым.

Новые поля аддитивны; потребитель, совместимый со старым ответом, может их игнорировать. Потребитель, которому нужна полнота истории, должен учитывать `medical_cards_has_more` и `pets_truncated`, а `null` не трактовать как `false`.

## Архитектурное решение

**Проблема.** Потеря upstream total в локальной проекции ответа.

**Контекст.** MCP contract публичен; менять существующие поля нельзя. Дополнительных HTTP запросов, персональных данных или общей абстракции не требуется. Параметры пагинации заданы OpenAPI; существующий инструмент по дате задаёт локальный образец обработки total.

**Варианты.** Общий pagination envelope повысил бы область изменений и уже отклонён владельцем как F8. Только `has_more` не объясняет полный объём. Точечная пара total/has_more сохраняет контекст и проста.

**Решение.** Прочитать `data.totalCount` в том же ответе, добавить два поля, вычислить признак из фактического числа полученных строк, не из запрошенного `limit`.

**Инварианты.** Существующие ключи не меняются; `has_more` не равен false при неизвестном total; `pets_truncated` не теряется; изменение только в одном инструменте.

**Откат.** При изменении upstream формата total оставлять `null` и не обещать полноту. Если локальный контракт окажется ошибочным, revert коммита удалит два аддитивных поля; до отката потребителей нового контракта надо уведомить, поскольку удаление полей для них несовместимо.

## Подзадачи и приёмка

1. **429.1, ≤150 строк:** PRD и тестовый guard. На странице меньше total тест падает на старом коде и требует `medical_cards_has_more=true`; покрыть offset, последнюю страницу, пустую страницу до total (`null`), строковый и непригодный total, отсутствие питомцев и независимость `pets_truncated`.
2. **429.2, ≤150 строк:** локальная реализация, фокусный прогон, живой read-only вызов на соответствующем стенде с кодом и обезличенным телом. Просмотреть соседние профили на похожие тихие страницы, результат перечислить в AssumptionLog без изменения их кода. Затем аудит, committed diff review, полный suite, push и зелёный CI ветки.

Architecture Critique совмещается с PRD-review: публичный MCP contract, prompt покрывает архитектуру, полноту PRD, тесты и откат.
