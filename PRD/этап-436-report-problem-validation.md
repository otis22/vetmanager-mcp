# Этап 436. report_problem: ответ при невалидном вызове

## Цель

Дать агенту безопасный способ исправить невалидный вызов и повторно отправить фидбек без изменения успешного пути сохранения.

## Проблема и факты

23.10.2026 на проде один вызов `report_problem` завершился общим `Error calling tool`; строка появилась до сохранения в `agent_feedback_reports`. Аргументы конкретного вызова и traceback отсутствуют: точный путь отказа не доказан. Локально FastMCP при пропущенном `details` отклоняет вызов до входа в инструмент: `ValidationError`, клиент получает `isError=true` с текстом Pydantic `Missing required argument` и отражением входных аргументов. При строковом `http_status="oops"` аналогично возвращается `int_parsing`. Это подтверждённый класс потери фидбека, но не доказанное воспроизведение конкретного production вызова. Значения входа могут быть личными, поэтому их нельзя отражать в подсказке.

`tools/feedback.py` регистрирует обязательные `category`, `severity`, `summary`, `details`. `agent_feedback_service.py` уже очищает поля перед записью. `rate_report_ai_job` (этап 400) использует `ToolInputError` с именем неверного поля и допустимой формой; у `report_problem` отказ возникает раньше такой проверки. Главный PRD требует понятных ошибок; технические требования фиксируют FastMCP и HTTP MCP. Vetmanager REST API здесь не вызывается, OpenAPI не определяет контракт обратной связи.

## Архитектурное решение

**Проблема:** валидация FastMCP происходит до функции и может отдать агенту сырой фрагмент аргументов, не объяснив способ исправления.

**Варианты:** (а) сохранять `invalid_partial` требует новой схемы и очистки каждого произвольного фрагмента, а неизвестно, какие обязательные поля отсутствуют и соответствует ли текст намерению пользователя; (б) превратить валидационный отказ только этого инструмента в конкретную безопасную ошибку и предложить повторный вызов; (в) оба наследует риски (а). Выбрано **(б)**. Сохранение происходит после успешной валидации, через существующие слои очистки. Перехват — middleware вокруг вызова `report_problem`, который ловит только Pydantic `ValidationError`. Из `errors()` берём лишь разрешённое имя поля и код ошибки, никогда `input`, `ctx` или строку исключения. Для обязательных полей даём короткий пример, для типов — пример корректного значения. Неизвестное поле даёт общую подсказку о схеме без отражения значения.

**Инварианты:** схема и поведение валидного вызова неизменны; ошибки других инструментов не затронуты; отказ не пишет в БД; текст ошибки не содержит переданные значения, даже если они персональные; auth и доступ не смягчаются. Middleware размещается в существующей цепочке после авторизации и до вызова инструмента. Откат — удалить middleware, не требуется миграция.

**Граница перехвата:** `FastMCP.call_tool` запускает middleware до `FunctionTool.run`; тот превращает ошибку аргументов Pydantic в `fastmcp.exceptions.ValidationError`, сохраняя Pydantic как `__cause__`. Middleware ставится после `ToolErrorTrackingMiddleware` в порядке регистрации (внутри его `call_next`) и превращает этот тип в `ToolInputError`, который внешний слой классифицирует как ошибку ввода без Sentry-события. Если cause или `errors()` отсутствуют/неожиданны, отдаётся только общая статическая подсказка. Приёмка обязана подтвердить перехват вызовом через реальный MCP клиент, а также неизменность ошибки другого инструмента. FastMCP пишет собственный warning с деталями входа до перехвата; для `report_problem` узкий фильтр заменяет только этот warning на статический текст без значений, не трогая диагностику других инструментов. Тест захватывает полные форматированные записи логов и проверяет отсутствие sentinel, а также отсутствие данных в трекинге ошибок. Метрика вызова должна продолжать учитывать отказ как ошибку ввода, без записи успешного фидбека.

**Сообщения:** закрытый список обязательных полей `category`, `severity`, `summary`, `details`. Для `missing_argument` у этих полей — имя и статический пример (`category="bug"`, `severity="medium"`, `summary="Short safe summary"`, `details="Safe description without personal data"`). Для `http_status` с ошибкой типа — `http_status=422 or omit it`; для `params_shape` — `params_shape=["date_from"] or omit it`; для остальных полей с ошибкой типа — статическая подсказка использовать схему `tools/list`. Неизвестный код, вложенная ошибка и ошибка без разрешённого поля получают общую безопасную подсказку `Check report_problem inputSchema in tools/list and retry`; входное значение и Pydantic `ctx` не включаются.

Architecture Critique обязателен: меняется публичное MCP-поведение. Совместить критику архитектуры с оценкой полноты PRD: scope, альтернативы, приватность, критерии и откат.

## Декомпозиция и критерии приёмки

1. **436.1 (≤150 строк теста):** вызвать через MCP неполный и типово неверный `report_problem`, зафиксировать прежний результат; написать сторож на `isError`, имя поля, пример, отсутствие входного текста и отсутствие записи. Проверить `params_shape` с вложенным секретом, все форматированные логи и отсутствие Sentry-события, неизменность ошибки другого инструмента, fallback без Pydantic cause и обязательные поля в схеме. Показать красный прогон; повторной мутацией warning подтвердить чувствительность log-сторожа.
2. **436.2 (≤150 строк кода):** middleware с безопасной ошибкой и узкое подавление небезопасного framework warning, фокусные тесты, живой вызов на devtr6 с битым и валидным аргументами, включая код и тело, проверка записи валидного фидбека. Тестовый аккаунт и временная sqlite БД из real suite; после теста БД удалить. Аудит, ревью и один полный mock+real suite по финальному SHA. Без изменения продакшена и без merge в main.

## Простота

Сохраняем обязательные параметры и существующий путь `create_feedback_report`; единственная новая логика — преобразование отказа валидации на границе FastMCP для одного инструмента.
