## Systemic observations from arbitration

Three reviewed findings—F2, F3, and F10—belong to a recurring boundary-contract failure class: payload keys and convenience-filter mappings are assumed from nearby entities or model memory while green mocks reproduce those assumptions. A focused sweep of every write payload key and convenience-filter mapping against authoritative backend entities, followed by targeted live read-backs, would address the class rather than only these instances.

F4 and F5 show that the warehouse module states “refuse rather than partially apply” as policy but does not enforce it structurally. Multi-row write tools should precompute targets from an immutable snapshot, bound and validate all pagination before the first mutation, and return an explicit partial-result envelope if an upstream failure occurs after writes begin.

F1 and F9 expose trust-boundary mistakes at different layers: upstream-provided network locators and process-local synchronization are both treated as authoritative beyond the boundary where they are reliable. These require explicit network-origin validation and database-owned invariants respectively.

The arbitration also corrected over-ranking of repository-script durability and capability-lifetime behavior. F7–F8 are real but lower-severity workflow risks, while original F6 reflects an intentional durable-grant capability model rather than a defect; only exact-token revocation behavior remains a potential product-policy question.
