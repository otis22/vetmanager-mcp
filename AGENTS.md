Краткий указатель правил и артефактов проекта. Агент обязан следовать workflow и обращаться к артефактам при планировании и реализации.

## Три гейта, которые нельзя пройти намерением

Полные формулировки и разбор случаев — в `CLAUDE.md` (4.0, 6.1, 6.2).
Здесь короткая версия, обязательная для любого агента в этом репозитории.

**Сторож принимается только красным.** Любой тест, существующий ради поимки
регресса — guard, сторож апстрима, линтер, проверка текста, — до приёмки
ломается вместе с тем, что он охраняет, и обязан упасть. Зелёный сторож
выглядит одинаково и когда защищает, и когда проверяет недостижимый код.
В self-attestation указывается, **чем именно его сломали**.

**Изменил инструмент — вызови его вживую на стенде и приложи ответ:** код и
тело. Мок не заменяет. Строка о живой проверке обязательна в `AssumptionLog.md`.
Причина: 23.08.2026 два пишущих инструмента уехали в main сломанными на 100%
вызовов при зелёных тестах — моки описывали форму ответа, которой у API нет.

**Стендов два, они разные, и путать их нельзя.** `TEST_DOMAIN`/`TEST_API_KEY`
из `.env` — один контур, стенд под bearer-токеном — другой. Какой именно нужен
проверке, решается до запуска, а не по факту непрошедшего теста.

## Что не уезжает в публичный репозиторий

Репозиторий **публичный с 27.02.2026**: `Roadmap.md`, `AssumptionLog.md` и
`PRD/` уезжают в открытый доступ тем же коммитом, что и код.

**Из чужих исходников переносится контракт, а не реализация.** Контракт — что
API требует и что отвечает: поля, коды, тексты ошибок, обязательность.
Реализация — код, имена классов и методов, порядок внутренних проверок.
Проверка одним вопросом: **это можно узнать, вызывая API снаружи?** Да — пиши;
нет — опиши наблюдаемое поведение, а разбор реализации оставь в задаче для
команды продукта.

Строже и отдельно — **всё, что помогает получить доступ**: ключи, токены,
внутренние адреса, описания обходов защиты. Не публикуется ни в каком виде,
включая примеры в документации и фикстуры тестов. Утёкший ключ чинится
ротацией, а не правкой файла: история git публична.

## Деперсонализация и выгрузки

Разобрано этапами 275–278. Условия для любого инструмента, который отдаёт
данные клиники наружу:

- **Отчётные данные проходят слои очистки.** Ключи колонок и значения чистятся
  на нашей стороне; право на отчёты не выдаётся группе без полного набора
  условий деперсонализации — связь закреплена сторожем.
- **Выгрузка идёт через нас, а не мимо.** Инструмент отдаёт ссылку, а не
  локатор апстрима; исходник живёт в памяти запроса и на диск не попадает.
  Инструмент получения локаторов снят намеренно — не заводить заново.
- **Чужой локатор не попадает в наш лог.** Журнал транспортной библиотеки
  приглушён, сторож ловит адрес выгрузки в записях логгера. Добавляешь
  логирование запросов — проверь, что адрес не поедет вместе с ним.
- **Правило регистра.** Правило деперсонализации, написанное общим флагом
  регистронезависимости, однажды съело `Анализ крови общий`. Формы
  перечисляются явно; после правки словаря прогоняется матрица личных и
  не-личных значений.

## Модель доступа — правила, которые нельзя переоткрыть

Разобрано этапами 268–274 по пользовательской ревизии прав. Это не история, а
условия, которым обязан удовлетворять любой новый или изменённый инструмент.
Каждое закреплено сторожем в `tests/`; правило меняется вместе со сторожем,
а сторож принимается только показанным красным.

1. **Инструмент без строки в реестре прав не существует.** Права живут в
   `tool_access_registry.py`, набор скоупов — в `token_scopes.py`. Пустой набор
   прав допустим только для инструмента, внесённого в поимённый список: иначе
   он рекламируется всем группам и отказывает на вызове.
2. **Удаление — отдельное право `records.delete`, никогда не `*.write`.**
   Создание и удаление разными правами не по вкусу, а потому что «Регистратура»
   должна заводить клиента и не должна его стирать. Право входит только в
   «Полный доступ». Второй слой требует его на любой `DELETE` под
   `/rest/api/`, включая пути, которых сегодня не касается ни один инструмент.
3. **Свободный текст, по которому строится выборка, — это запись.** Запуск
   отчётов требует `report_ai.write`, а не `analytics.read`: иначе группа,
   которой отказано в медкартах напрямую, получает их отчётом. Читающее по
   имени, но запускающее по сути — тоже запись.
4. **Состав группы не описывается вторым списком.** Он считается из прав тем же
   правилом, которое применяет проверка вызова. Отдельный «обещанный состав»
   расходится с реальным молча — так и вышло (77 против 28 у «Регистратуры»);
   список удалён и заводить его заново нельзя.
5. **Второй слой fail-closed на запись.** Неизвестный пишущий путь и метод вне
   разбора отклоняются до обращения к Ветменеджеру. Добавил вызов по новому
   REST-пути — внеси его в карту, иначе он не поедет. Полнота карты проверяется
   разбором `tools/` и `resources/` через AST, а не регуляркой по литералам.
6. **`tools/list` фильтруется теми же правами, что и отказ на вызов.** Каталог
   не рекламирует то, что не даст вызвать. Права для каталога читаются в обход
   журнала активаций — список инструментов не работа с данными. Сбой чтения
   прав оставляет каталог полным и пишет запись в лог, но не смягчает
   аутентификацию.
7. **Отказ называет все дающие группы, узкие раньше широких, полный доступ
   последним.** Подсказка не должна толкать к полному ключу.
8. **`delete_invoice` и `delete_invoice_document` сняты навсегда.** REST-удаление
   счёта идёт мимо предметной логики продукта: мягкое удаление, откат складских
   документов, пометка вакцинаций и журнал остаются несделанными. Инструменты
   с этими именами не регистрируются, вызов снятого имени читается как
   «инструмента нет», а не «не хватает прав». Возврат — решение владельца
   продукта после появления честного метода на стороне Ветменеджера, а не
   разработчика по ходу задачи.
9. **Интерфейс обязан говорить, что даёт уровень доступа.** Сводка по областям
   (чтение / изменение / удаление) считается из прав и показывается и в
   кабинете, и на экране согласия OAuth. Строка «Удаление: нет» показывается
   всегда — именно её отсутствие и породило исходный репорт.

Сторожа: `tests/test_stage268_invoice_delete_tools_removed.py`,
`test_stage269_report_launch_scope.py`, `test_stage270_delete_right.py`,
`test_stage271_tool_list_visibility.py`, `test_stage271_peek_scopes_matches_auth.py`,
`test_stage272_preset_composition.py`, `test_stage273_access_summary_ui.py`,
`test_stage274_rest_layer_fail_closed.py`, `test_stage264_scope_denial_is_explained.py`.

**Известный незакрытый край:** чтение по неизвестному REST-пути пока проходит и
считается метрикой `vetmanager_rest_unmapped_read_total`. Закрывается отдельным
этапом по её значению на проде — не «забыто», но и не сделано.

## Тесты и проверки

- ShellCheck и синтаксис Bash (обязательны перед commit при изменении `scripts/*.sh`): `find scripts/ -name '*.sh' -type f -print0 | xargs -0 docker run --rm -v "$PWD:/mnt" -w /mnt koalaman/shellcheck:v0.9.0 --severity=warning` и `find scripts/ -name '*.sh' -type f -print0 | while IFS= read -r -d '' f; do bash -n "$f"; done`. Первая команда сама скачивает официальный образ при чистой Docker-сессии и фиксирована на версии CI.
- Структура роадмапа: `scripts/check_roadmap_structure.py` (запускается и сам по себе, и из набора)
- Unit + mock e2e: `docker compose --profile test run --rm test`
- Real API e2e (только если в `.env` есть test `TEST_DOMAIN` и `TEST_API_KEY`; секреты не печатать): `docker compose --env-file .env --profile test run --rm test python scripts/run_opt_in_real_test_suite.py`
- CI: `.github/workflows/test.yml` (unit + mock); `test-real.yml` — ручной запуск с секретом.

Задача не считается завершённой без прохождения проверок и записи в AssumptionLog.

Дополнение к workflow:
- Перед `commit`/`push` агент обязан сделать аудит внесённых изменений.
- Если аудит потребовал рефакторинга, после него обязателен новый полный прогон тестов и проверок.
- Команда попадает в процессную документацию только после запуска в точно записанном виде: перед commit агент копирует её из документации и проверяет реальный exit code. Эквивалентная команда не заменяет эту проверку.
- Ревью сторонней моделью: Claude-агент проверяется Codex `gpt-5.5`, Codex-агент проверяется Claude Opus.
- Бюджет сторонней модели: 2 валидных запуска на PRD-review и 2 валидных запуска на code/diff review; валидным является только запуск с разбираемым вердиктом — findings или явный пустой список. `gpt-5.3-codex-spark` как обычный scout/subagent безлимитен и не расходует бюджет. Для Spark-review перед конкретным review gate действует отдельный лимит: максимум 3 запуска.
- Перед каждым PRD/code review агент делает Spark-review `gpt-5.3-codex-spark`, затем более сильное ревью. `gpt-5.3-spark` — неправильное/неполное имя модели; использовать только `gpt-5.3-codex-spark`.
- Spark findings являются candidate-only: агент обязан проверить адекватность и принимать только важные, проверяемые замечания; speculative/low-impact/неподтверждённые замечания отклоняются.
- Spark-review prompt должен быть узким: указать объект ревью (PRD, staged/uncommitted diff, committed diff), severity, формат ответа и запрет на правки.
- Правильный вызов Spark-review из Codex runtime: `timeout 1200 codex exec -m gpt-5.3-codex-spark -s read-only -C "$PWD" -`. Если read-only падает до чтения файлов из-за sandbox/runtime ошибки (`bwrap`, user namespace и т.п.), остановить зависший запуск и один раз повторить ту же модель с `-s danger-full-access` и review-only prompt: `Review only. Do not edit files. Do not run write commands.` Fallback на другую модель разрешён только при явной model/provider failure, не при sandbox/runtime failure. Итог Spark-review (`[]` или принятые/отклонённые findings) фиксируется в AssumptionLog.
- Claude Opus review из Codex runtime: real shell timeout должен быть минимум в 2 раза больше prompt deadline; default `timeout 1200`, в prompt писать `Finish this review within 600 seconds`, реальный timeout Claude не сообщать. Для inline diff/context отключать tools/MCP (`--strict-mcp-config --mcp-config '{"mcpServers":{}}' --tools ""`), запрещать правки/commands, требовать structured JSON findings через `--output-format json` + schema и писать `Think briefly, then return JSON matching the schema immediately`. Успех: JSON-конверт разобран, `is_error=false`, непустое поле `.result` разбирается по required schema. Валидатор вызывать напрямую как исполняемый `scripts/validate_review_result.py`, не через имя интерпретатора; CI проверяет этот вызов. Сбой: конверт не JSON, `is_error=true`, `.result` пусто/не разбирается/не соответствует schema либо provider/model error. `stop_reason` не участвует: при `--json-schema` structured result штатно доставляется tool call. Infrastructure failure не расходует слот и фиксируется отдельной строкой в `AssumptionLog` как `N/3`; максимум три таких попытки на strong review gate, затем `blocked` и push запрещён. Только запуск с разбираемым verdict расходует слот бюджета.

### Evidence Claude review

Каждую попытку Claude strong review запускать через
`scripts/run_claude_review.sh (--range <range> | --file <review-file>) --attempt <N/3>`.
Для committed/uncommitted diff использовать `--range`; для PRD, Architecture
Critique и другого file-object review — `--file`. Runner независимо
от exit сохраняет вне working copy raw envelope, stderr, prompt, schema и
metadata в `${XDG_DATA_HOME:-~/.local/share}/vetmanager-mcp-review-evidence`
(или `--evidence-dir`). В
`AssumptionLog` указывать путь к `*.envelope.json` и `subtype`, `stop_reason`,
`output_tokens`, `thinking_tokens`, `len(result)`; metadata содержит
`attempt`, тип/цель review, repo, evidence dir и все параметры запуска. Запись только «без output»
запрещена. Runner валидирует сохранённый envelope и возвращает non-zero при
invalid verdict.

## Feedback triage и `known_issues`

Production feedback triage — это операционная работа, а не изменение репозитория.

Не изменять и не коммитить файлы репозитория, если единственное действие:

- чтение `agent_feedback_reports`;
- обновление production `known_issues`;
- link/resolve feedback reports;
- правки `agent_playbook_json` или `match_rules_json`;
- исследование конкретного feedback report без кода/тестов/PRD.

Для такого triage source of truth — production DB (`agent_feedback_reports`,
`known_issues`) и внешний work log супервизора.

Запрещено по умолчанию добавлять в repo только из-за triage:

- `AssumptionLog.md`;
- `README.md`;
- `artifacts/report-ai-*`;
- любые ad-hoc research artifacts.

Repo changes допустимы только если feedback породил явное product/code intent:

- code fix;
- regression test;
- Roadmap/PRD задачу на будущий fix;
- документацию, которую пользователь явно попросил добавить в репозиторий.

Перед любым commit после feedback triage агент обязан проверить
`git status --short` и `git diff --stat`. Если diff содержит только разбор
feedback или результаты правок `known_issues`, commit запрещён.
